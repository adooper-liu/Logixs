# 外部协作

> 状态分类：外部任务、最小权限和回执分层为已确认原则；报关行门户、车队移动端和供应商门户为建议方案，具体合同责任与可见范围待确认。

## 一、参与方

- 报关行：清关任务、文件、申报、查验和结果回传。
- 车队：提柜、送仓、还箱任务及移动作业。
- 仓库和三方堆场：预约、接收、卸货、出场和异常。
- 供应商：未来接收备货单、确认交期和提交备货结果。

外部协作的目标不是给合作方开放内部系统，而是围绕一项被分配的任务提供刚好足够的信息和动作。每个外部参与方看到自己的责任范围，内部仍保留最终采信、状态推进和审计责任。

## 二、统一任务过程

```text
分配任务
→ 外部伙伴接受或拒绝
→ 执行
→ 回传结果和证据
→ Logix核验
→ 完成或要求补正
```

任务应明确对象、地点、时间窗、服务要求、所需能力、可见文件、责任人和截止时间。取消、转派和更正都保留记录。

任务分配后，外部伙伴可以接受、拒绝或提出调整。接受表示愿意承担任务，不表示任务已经完成；上传文件或照片表示已经回传材料，也不表示内部已经核验。内部核验不通过时，任务进入补正而不是覆盖原回传。

每次分配、接受、拒绝、转派、执行、补正和关闭都带操作人、时间、设备或来源及备注。相同请求因弱网重复到达时不能重复生成结果。

## 三、报关行门户

报关行只看到被分配的案件和必要文件，可以下载资料、提出补件、回传申报号和官方回执。其操作不直接修改货柜生命周期状态，系统根据回执和来源资格作出业务判断。

### 报关行实际操作过程

1. 报关行收到案件通知，登录门户查看国家、进口主体、货物范围、预计到港和截止时间。
2. 门户按该国资料参数展示已提供、待提供和待核验文件。
3. 报关行接受任务或说明拒绝原因，也可以针对具体文件提出补件。
4. 申报后填写申报号并上传官方回执；发生查验、Hold或补税时形成新的结果和任务。
5. 内部清关人员核验回执并采信相应事实。报关行自己的“完成”不直接推进海关放行。

文件更新后，报关行应看到新旧版本和变更说明，避免使用已经废止的发票或装箱单继续申报。

## 四、车队移动端

司机和调度需要：任务清单、地址和预约、箱号/封条/EIR扫码、车辆司机登记、到场/出场时间、拍照、签收、异常原因和弱网补传。

手机定位和设备时间可作为辅助证据，不自动替代码头EIR、仓库POD或还箱回执。

### 司机实际操作过程

司机不需要浏览复杂货柜档案，只需要按当天任务顺序看到提柜地点、预约、箱号、目的地、联系人和注意事项。到达码头后扫描或录入箱号，系统校验是否与任务一致；提柜后拍摄箱况和EIR，记录实际Gate Out。

送达仓库或堆场时，司机回传到场、排队、入场和交接结果；卸柜后接收空箱还箱任务，回传场站接收和EIR。临时改送、长时间等待、拒收、箱损或错误箱号通过明确异常动作处理，不能只上传一张照片后让后台猜测。

弱网时允许离线保存任务操作和附件，恢复网络后按稳定操作身份补传。系统同时保留设备记录时间和服务器接收时间，重复补传不重复推进业务。

## 五、权限和数据可见范围

- 外部伙伴只能访问分配给自己的对象。
- 文件按任务和用途开放，下载行为可追溯。
- 敏感数据不放入短信或邮件正文。
- 外部用户不能直接改变内部状态或已确认事实。
- 合同终止或任务结束后及时收回访问权限。

数据最小化不仅控制页面，也控制导出、通知和文件。司机通常不需要看到商业发票金额，报关行不需要看到车队报价，仓库不需要浏览其他仓库库存。敏感文件可以限制预览、下载、有效期和水印，并记录每次访问。

## 六、通知和回执

需要区分：通知已发送、对方已收到、对方已打开、任务已接受、业务已完成。任何一个阶段都不能替代另一个阶段。

通知渠道可以是站内、邮件、短信或企业消息，但敏感数据不直接放入消息正文。通知失败按照渠道规则重试，最终失败回到内部待办；业务任务本身不能因为通知失败而消失。

## 七、异常处理

支持拒单、超时、部分完成、离线重复、错误扫码、临时改送、任务取消、证据撤回和费用争议。更正保留原记录、原因和责任人。

## 八、仓库与三方堆场协作

仓库或堆场接收任务后确认预约、月台或场地能力。到场时核对柜号和任务，回传入场、等待、开始卸货、部分卸货、完成或出场。仓库拒收、预约取消、超时等待、短溢损和破损分别形成异常，不能用一个“未完成”概括。

三方堆场还需要确认可堆存柜型、危险品或特殊货物能力、容量、日租、免费期、进出时间和二次运输交接。堆场接收货柜不表示最终仓库已经收货。

## 九、供应商门户的未来衔接

供应商接收备货单后，可以确认数量、交期和工厂，反馈缺口、替代建议和实际备货结果，上传包装、检验和交接资料。供应商确认形成供应承诺；实际备货完成仍需数量和必要证据。

这一门户与当前导入不是两套业务。未来供应商提交的信息通过同一校验进入备货和可出运供给；文件导入继续作为历史和应急入口。

## 十、责任争议与证据

外部协作经常涉及等待费、爽约、货损和延误。系统应把任务版本、通知、接受、位置、时间、照片、EIR、POD、文件和双方更正串成证据链。系统记录事实，不自动替代合同责任判断；争议结果由授权人员确认并保留依据。

## 十一、验收标准

- 外部伙伴能完成分配给自己的实际任务，不需要回到线下重复录入。
- 内外部对“已通知、已接受、已执行、已核验”含义一致。
- 弱网、重复提交和更正不会制造重复事实或丢失原记录。
- 外部操作不能越权查看数据或直接改变内部权威结论。
- 内部岗位能够看到任务进度、缺口、证据和下一责任人。

### 报关行、车队、仓库与外部任务协作

> 追溯范围：原始对话第 4700-5210 行。建议仍为建议；已确认规则以本文前部、12号文档和业务ADR为准。

针对业务能力达到生产级，粗略需要：

- 第一阶段：2–3名工程师，约2–3个月；
- 生产级拖拽、版本、性能和并发：再增加3–5个月；
- 智能优化和持续校准：长期迭代。

这还需要调度业务负责人持续参与，不是纯前端任务。

如果目标是“完整复制Bryntum”，不建议做；如果目标是“覆盖提送卸还、车队、仓库、堆场和成本风险的专用调度器”，采用开源组件加自研领域能力是可行的，而且更贴合业务。关键是把自研投入放在业务约束、方案版本、解释性和稳定性上，而不是重写底层时间轴。

> 清关、提送卸还 四个节点后期需要与外部资源交互，比如与清关行，分配清关任务，清关行可以通过门户获取任务与返回结果，获取相关文件。 提柜、送仓需要与车队交互：车队需要通过手机扫描或录入日期等； 请分析

这实际上是“内部运营平台 + 外部协作门户”的模式。清关行、车队、仓库和还箱场站不能直接进入内部工作台，也不能直接修改货柜生命周期状态。

推荐链路：

```text
内部人员分配外部任务
  -> 外部合作方门户接收
  -> 外部人员执行并提交结果/证据
  -> 系统校验、必要时内部复核
  -> 形成规范业务事实
  -> 生命周期合法推进
  -> 内外双方获得结果反馈
```

“清关、提、送、卸、还”严格来说是五类作业场景，分别对应清关行、车队、仓库和还箱场站等外部资源。

### 一、统一外部协作模型

不要为清关行和车队分别开发两套完全不同的任务系统。建议建立统一的外部工作单：

```text
ExternalWorkOrder
- workOrderId
- workType
- tenantId
- subjectType / subjectId
- assignedPartyId
- assignedTeamId
- assignedUserId
- status
- priority
- plannedWindow
- deadline
- requirements
- allowedActions
- documentPackageId
- evidenceRequirements
- version
- idempotencyKey
```

`workType` 包括：

```text
customs_clearance
container_pickup
warehouse_delivery
container_unloading
empty_return
```

每类工作单共享分配、接收、拒绝、执行、提交、复核、关闭和审计机制，但有自己的业务表单与完成条件。

#### 工作单状态

```text
draft
-> assigned
-> accepted
-> in_progress
-> result_submitted
-> accepted_result
-> completed
```

正交结果：

```text
rejected
cancelled
blocked
failed
expired
revision_required
```

外部人员提交 `completed` 请求，不代表生命周期节点立即完成。系统必须根据证据、权限、状态机和内部复核政策决定是否接受结果。

### 二、外部主体与权限

建立正式合作方结构：

```text
BusinessParty
PartyOrganization
PartyTeam
ExternalUser
PartyCapability
PartyQualification
PartyServiceArea
PartyContract
```

主体类型：

- 清关行；
- 车队；
- 仓库；
- 三方堆场；
- 还箱场站；
- 文件服务商。

每个外部用户只应看到：

- 分配给其所属公司的任务；
- 任务所需的最小货柜信息；
- 当前步骤需要的文件；
- 被允许执行的动作；
- 自己提交的历史和反馈。

不能让车队看到采购价格、供应商合同、完整合规档案或其他车队任务。

权限至少要限定：

```text
tenant
合作方组织
任务
业务对象
允许动作
文件类型
有效时间
```

### 三、清关行门户

#### 内部分配流程

```text
清关人员打开案件
-> 选择具备目的国/口岸能力的清关行
-> 确认SLA和截止时间
-> 选择可共享文件包
-> 发送清关工作单
-> 等待接单
```

选择清关行时应显示：

- 服务国家和口岸；
- 清关业务能力；
- AEO或相关资质；
- 资质有效期；
- 当前任务量；
- 平均响应和放行周期；
- 退单率；
- 合同状态；
- 联系团队。

#### 清关行门户首页

```text
待接单
资料待核对
待申报
等待海关
补件/退单
查验或扣留
待提交放行结果
已完成
```

清关行进入案件后可以：

- 查看Shipment、柜号和提单；
- 下载被授权的发票、箱单、提单和证书；
- 查看申报行和已确认HS Code；
- 提出资料缺口；
- 接受或拒绝任务；
- 提交申报单号；
- 上传申报文件和回执；
- 记录查验、扣留、补件；
- 提交税费信息；
- 上传放行文件；
- 提交实际放行时间；
- 对错误资料发起更正请求。

清关行不能：

- 自行修改产品主数据；
- 覆盖已经确认的HS Code；
- 删除原文件；
- 修改内部生命周期；
- 查看无关SKU和商业数据；
- 把“已提交”直接改成“已放行”。

#### 文件交换

内部人员不是把文件永久复制给清关行，而是共享受控文件包：

```text
DocumentPackage
- packageVersion
- allowedDocumentTypes
- expiresAt
- recipientPartyId
- downloadPermission
- watermarkPolicy
- accessAudit
```

每次新增、替换或撤销文件都产生新版本。清关行应能明确看到“最新版本”和“已被替代”。

### 四、车队移动端

车队更适合移动端PWA或轻量门户，不应把桌面后台缩小到手机屏幕。

#### 车队调度端

车队调度人员看到：

```text
待接任务
待派车
今日提柜
今日送仓
三方堆场任务
还箱任务
异常任务
```

允许：

- 接受或拒绝任务；
- 指派司机和车辆；
- 填写计划时间；
- 调整任务顺序；
- 提交预约号；
- 查看港口、仓库、堆场地址和窗口；
- 反馈资源不足或预约失败。

#### 司机移动端

司机首页只显示当前和下一任务：

```text
当前步骤
地点
预约窗口
柜号
箱型
提单参考
联系人
允许动作
```

典型操作流程：

```text
到达港口
-> 扫描/录入柜号
-> 核对任务柜号
-> 拍摄柜体和封号
-> 录入或获取 Gate Out 时间
-> 上传 EIR
-> 开始运输
-> 到达仓库/堆场签到
-> 上传交接凭证
-> 完成送达
```

还箱：

```text
接收空箱任务
-> 核对柜号和还箱点
-> 到达场站
-> 扫描柜号
-> 拍摄柜况
-> 上传还箱EIR
-> 录入实际还箱时间
-> 提交完成
```

### 五、扫描与录入

扫描支持：

- ISO柜号文字识别；
- 二维码/条码；
- EIR二维码；
- 车牌；
- 封号OCR；
- 文件拍照上传。

扫描后必须显示识别结果供司机确认，不能自动提交。

柜号校验包括：

- 格式检查；
- 校验位；
- 是否属于当前任务；
- 是否已经被其他司机处理；
- 是否与提单和箱型一致。

日期时间优先由可信事件或服务器记录：

```text
设备采集时间
服务器接收时间
外部系统事件时间
业务确认时间
```

司机可以补录，但必须选择原因，保存原始录入值和设备时区。禁止用手机当前时间无提示地代填历史实际时间。

### 六、卸柜外部协作

仓库门户或移动工作区显示：

- 今日预计到仓；
- 已到仓待接收；
- 待分配卸柜门；
- 正在卸柜；
- 部分卸货；
- 差异待处理；
- 已卸空待取箱。

仓库人员可以：

- 确认实际到仓；
- 分配卸柜门；
- 核对柜号和封号；
- 记录开始卸柜；
- 按SKU或汇总记录实收；
- 保存部分卸货；
- 登记短少、多货、破损和错货；
- 上传照片和签收单；
- 确认卸柜完成；
- 单独确认空箱；
- 通知车队取空。

如果仓库已有WMS，应优先通过API/Webhook接收事实，门户作为补充和异常处理入口。

### 七、任务分配机制

内部人员可以手工分配，也可以由规则或排程方案推荐。

系统推荐依据：

- 服务能力；
- 国家、港口和仓库覆盖；
- 资质有效性；
- 合同价格；
- 当前容量；
- 历史时效；
- 历史异常；
- SLA；
- 智能排柜方案。

推荐不是正式分配。人工确认后才生成工作单。

批量分配必须先预览：

```text
将分配多少任务
分配给哪些合作方
各自截止时间
缺少哪些资质或联系人
预计费用
存在什么冲突
```

### 九、外部结果如何推进内部生命周期

正确链路：

```text
外部人员提交结果
-> 保存ExternalWorkResult
-> 注册证据
-> 校验任务范围和完成条件
-> 来源权威判断
-> 必要时内部复核
-> 形成LifecycleDateFact/CanonicalEvent
-> 状态机应用
-> 更新节点和后续任务
```

示例：

- 清关行上传放行单，不等于立即清关完成；
- 司机填写提柜日期，不等于立即推进到已提柜；
- 仓库点击卸柜完成，不等于自动确认空箱；
- EIR、可信Webhook或内部复核通过后，才成为权威事实。

### 十、异常与沟通

任务内需要结构化协作线程，不建议依赖微信或邮件作为唯一记录：

- 补件请求；
- 时间变更；
- 任务拒绝；
- 地址或预约问题；
- 柜号不匹配；
- 查验或扣留；
- 车辆故障；
- 仓库拒收；
- 柜损、货损和封号异常；
- 场站不接收还箱。

消息必须关联任务、对象和证据。重要业务结论仍通过正式动作提交，聊天消息不能直接改变状态。

### 十一、安全要求

- 外部用户采用独立身份域；
- 企业管理员管理本企业用户；
- MFA用于高风险操作；
- 临时邀请必须过期；
- 下载链接短时有效且不可猜测；
- 文件访问逐次鉴权；
- 病毒扫描；
- 敏感文件水印；
- 下载和查看审计；
- API凭据按合作方隔离；
- Webhook签名、重放保护和IP策略；
- 外部用户离职后立即禁用；
- 任务结束后按政策收回文件权限。

### 十二、实施顺序

建议依次交付：

1. 统一外部工作单、合作方、权限和证据模型。
2. 清关行门户：接单、文件、补件、申报结果和放行结果。
3. 车队调度门户：接单、派车和计划时间。
4. 司机移动端：扫描、拍照、提柜、送达和还箱。
5. 仓库门户：到仓、卸柜、差异和空箱确认。
6. API/Webhook直连，门户保留为异常与补充入口。
7. 接入智能排柜，发布方案时自动生成外部工作单。

最终应形成一个统一原则：

> 外部合作方操作“被分配的工作单”，提交结果和证据；Logix负责权限、校验、复核、状态机和后续流程。外部人员既不进入内部后台，也不直接修改货柜状态。

> 合规评审模块再深入分析与规划，尤其是合规项目与标准的引用与采信源

合规评审模块的核心不是“上传证书后打勾”，而是建立一条可解释、可复核的决策链：

```text
产品与市场事实
-> 识别适用法规
-> 确定合规项目
-> 引用法规与标准
-> 生成证据要求
-> 收集并核验证据
-> 人工作出评审决定
-> 在备货、装箱、出运和清关节点执行门禁
```

必须严格区分四类内容：

- **法规要求**：为什么需要合规；
- **标准与测试方法**：用什么技术方法证明；
- **证据**：实际拿到了什么报告、证书或声明；
- **评审决定**：这些证据是否足以支持该SKU进入特定市场。

任何一类都不能替代另外三类。
