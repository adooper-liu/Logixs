# 业务对象与信息关系

> 状态分类：Shipment定义、箱货多对多和物料不等于SKU为已确认业务决策；产品进化图谱及渠道Listing治理为建议方案；物理模型以技术契约为准。

## 一、Shipment业务身份

Shipment可以理解为“Logix正在管理的这一票出运业务”。它用于把计划、备货、订舱、单证、货柜和目的港执行连接起来。

更完整地说，Shipment是一次具有明确起运地、目的地、运输责任和货物范围的运输组织单元。它提供稳定的内部身份，让上游计划、订舱、提单、多个货柜以及到港后的执行可以围绕同一票业务协作。

它不等于：

- 箱号：说明使用哪个集装箱。
- 订舱号：说明向船司订了哪次舱位。
- 提单号：说明哪份运输单证。
- 备货单号：说明供应商准备哪批货。

这些号码变化、拆分或合并时，Shipment内部身份仍应保持稳定。

例如，一次出运先取得一个订舱号，随后船司拆分订舱；装船后又形成主提单和多个分提单。外部号码发生变化，并不表示内部要新建几票互不相关的Shipment。反过来，两个不同的运输责任和货物范围即使暂时共用某个参考号，也不应被误合并。

Shipment身份的建立和拆分、合并需要保留理由与历史关系。它不能仅依赖来源文件中的某一列，也不能把提单号当作永久主键。

## 二、备货单、产品行和货柜

```text
一张备货单有多条产品明细
一只货柜可以装多张备货单
一条产品明细可以拆入多只货柜
```

因此柜内货物关系是多对多的。系统以每次实际装载版本记录“哪条产品、装了多少、进入哪只柜”，而不是用主备货单号推断。

这种多对多关系解决供应商拼柜、一张备货单分批出运以及装箱现场调整。计划可以预先分配，但只有装箱确认后的版本才说明柜内实际货物。出现短装、超装、换柜或重装时形成新版本和差异原因，不能修改原计划后假装从未变化。

## 三、Product、Material、SKU和渠道商品

- Product：面向用户需求定义产品是什么、解决什么问题。
- Material：研发、采购、生产、包装和供应链实际处理的物料。
- SKU：可以独立销售、定价、上架、库存和履约的单元。
- 渠道商品：某个SKU在具体国家、渠道和店铺中的上架表达。

物料不等于SKU。同一基础物料可以形成多个国家或渠道SKU；一个套装SKU也可以由多个物料构成。

### 一个具体例子

同一基础电器产品因为美国和欧洲电压、插头、说明书语言、认证标志和包装标签不同，可能形成不同物料版本和不同SKU。某个欧洲SKU又可以在Amazon、独立站和线下渠道建立不同Listing。

如果只是Listing标题或图片变化，通常不需要复制SKU；如果库存不能混用、标签和合规要求不同，或消费者实际购买内容不同，就需要独立SKU。判断标准不是编码方便，而是能否在销售、库存、履约、售后和合规上安全互换。

## 四、两类变体

产品本身的变化包括颜色、尺寸、材质、功能、容量和配置。销售属性的变化包括国家、渠道、品牌、包装语言、法规版本、保修和套装方式。

二者需要分开管理，否则无法判断变化影响产品设计、采购、合规，还是只影响渠道上架。

## 五、产品进化

产品创新通常来自两类方向：

- 更多的“更”：更便宜、更好用、更可靠、更耐用、更高档、更易运输。
- 更多的“新”：新市场、新渠道、新场景、新用户和新组合。

系统应记录产品从哪个版本演化而来、为什么变化、依据是什么，以及变化带来的成本、销量、评价、退货和合规结果。产品进化关系不能通过覆盖旧产品资料表达。

产品进化图谱还应回答：新版本解决了哪类评价或退货问题，是否使用新物料或供应商，进入了哪些新市场，以及实际销量、毛利和质量是否达到预期。这样产品创新才能从一次性项目变成可复用的组织知识。

## 六、状态、任务、事件和日期

- 状态回答“现在处于哪一步”。
- 任务回答“谁接下来要做什么”。
- 事件回答“实际发生了什么”。
- 日期回答“计划、预计或实际何时发生”。

四者不能混用。例如完成“登记装船”任务，不等于货柜实际已经装船；收到预计到港时间，也不等于货柜实际到港。

### 计划、预计、承诺和实际日期

同一个节点可能同时存在内部计划、供应商或承运方承诺、根据最新情况预测的时间，以及最终实际发生时间。新的ETA可以替代当前预测，但不能删除旧预测；实际时间需要可靠来源和证据，不能由计划时间自动升级。

只有日期、没有时刻的历史数据使用业务地点当地日末 `23:59:59` 作为技术归一值，但必须保留“日期精度”和“时刻为系统补值”的信息。界面默认展示原始业务日期，不得把日末补值展示成真实发生时刻；该补值也不能单独用于小时级费用、事件先后裁决或不可逆过站。

## 七、文件和证据

文件不仅是一条下载链接，还需要知道版本、签发方、适用对象、有效期、来源和验证结果。任何清关、放行、可提和还箱结论，都应能回到对应证据。

## 八、核心关系总览

```text
出运计划
-> Shipment
-> Shipment与货柜关系
-> 货柜
-> 装载版本
-> 备货单产品行/SKU/物料

Shipment/货柜
-> 生命周期事件
-> 日期事实
-> 任务和工单
-> 文件与证据
-> 异常和费用
```

Shipment和货柜各有生命周期。一个Shipment中的多个柜可能在不同日期清关、提柜、送仓和还箱，因此不能用整票状态覆盖柜级事实。整票摘要只能按照明确聚合规则计算，例如“全部柜已还箱”或“仍有一柜清关受阻”。

## 九、综合页面与权威归属

“一柜一档”页面会同时展示装载、海运、清关、车队、仓库、还箱、费用和文件，但页面汇总不意味着这些信息都归货柜主表所有。每条信息仍由对应业务对象负责维护，并显示来源、更新时间、可信度和历史版本。

这样既方便用户查看全貌，也避免某个工作台为了显示方便复制另一模块的业务规则。

## 十、完整对象关系

### 订舱、提单和海运执行

Booking表示向承运人申请并取得的舱位安排，Bill of Lading表示运输单证，二者都不是Logix内部Shipment身份。一个Shipment可能因拆舱、改船或分单关联多个Booking或提单；一份提单也可能覆盖多只货柜。

海运执行按航段记录承运人、船舶、航次、起止港、码头、计划、预计和实际时间。转船不是把原航次字段覆盖成新船名，而是新增后续航段并保留变更原因。港口挂靠描述船舶层面的到离港及服务，不能直接推出某只货柜已经卸船或可提。

### 清关案件

清关案件关联Shipment、提单、货柜或货物范围，并拥有申报主体、报关行、法域、申报版本、HS归类、单证包、Hold、查验和放行事实。同一Shipment可以按国家、提单、货物或申报策略拆成多个案件。海关放行是外部权威结果，内部任务完成不能替代它。

### 提送卸还和仓库

内陆运输任务表达一次有起点、终点、承运资源和时间窗的移动。提柜、送仓、从堆场二次送仓和还箱可以是不同任务，但围绕同一货柜形成可追踪链路。

仓库预约表示承诺的接收窗口；仓库收货记录实际到达、月台、卸货、实收和差异。三方堆场停留是具有进场、堆位、箱况、费用和出场责任的业务对象，不是货柜上的一个地点备注。

### 文件、传输和外部任务

文件记录回答“这是什么版本的证据并适用于谁”；文件传输回答“何时通过什么方式发送给谁、对方是否接收或拒绝”；外部协作任务回答“哪个伙伴被授权完成什么结果”。三者相关但不能合并，否则无法区分文件存在、已经发送和业务已经接受。

### 免费期、费用、争议和结算

免费期规则说明从哪个权威事件起算、适用地点、天数、日历和版本；费用案件引用规则、计费期间、数量和币种形成估算、计提、账单和核定结果。争议或索赔独立保存责任、证据和处理结果。付款完成不等于业务生命周期完成，货柜已还箱也不等于财务已经关账。

## 十一、关系基数与聚合边界

    Shipment 1:N Container
    Shipment 1:N BookingReference
    Shipment 1:N BillOfLading
    Container N:M BillOfLading
    Shipment 1:N OceanLeg
    VesselJourney 1:N PortCall
    ReplenishmentOrder N:M Container
    ReplenishmentOrderLine N:M Container
    Shipment/Container 1:N CustomsCase
    Container 1:N InlandMove
    Container 1:N WarehouseAppointment/Receipt
    Container 1:N YardStay
    Container 1:N DocumentRecord/PartnerTask/ExceptionCase/CostCase

这些关系表达业务必须支持的最大现实复杂度，不要求每票业务都出现多个对象。技术模型可以通过关联对象实现，但不能为了当前20柜样本方便而收窄成一对一。

## 十二、对象完成条件

- Shipment完成：纳入范围内的货柜已达到运营终点，未关闭异常有明确处置；不代表费用已经结清。
- 清关案件完成：适用申报取得可采信结果，相关Hold解除或有明确终止结论，所需证据完整。
- 内陆运输任务完成：约定交付结果和POD/EIR已经形成，异常已经转入责任明确的案件。
- 仓库收货完成：实际到仓、卸货或交接结果及差异已经确认。
- 还箱完成：空箱被指定场站接收并取得可靠EIR；后续箱损或费用争议可以继续存在。
- 财务关账：应计、账单、分摊、争议和付款达到组织定义的关闭条件，不能仅由物流状态自动推导。

### Shipment业务身份及相关对象边界

> 追溯范围：原始对话第 12444-12722 行。建议仍为建议；已确认规则以本文前部、12号文档和业务ADR为准。

> - Shipment业务身份；→ 我不理解什么意思，请进一步明确

“Shipment业务身份”可以理解为：

> 系统中用于标识“一票运输业务”的身份信息，用来判断不同表、文件、接口和事件描述的是不是同一票货。

这里的 `Shipment` 不是货柜，也不等同于提单、订舱号或备货单。它代表从发货地到收货地、由一次运输委托组织起来的业务对象。

#### 为什么需要它

实际业务中，同一票货可能同时出现很多编号：

- 内部出运单号
- 客户订单号
- 采购单号
- 备货单号
- 订舱号
- Shipping Instruction编号
- 提单号
- 船司运单号
- 箱号
- 报关单号
- Arrival Notice编号

这些编号分别来自不同环节，不能任选一个作为整条生命周期的唯一身份。

例如：

```text
内部出运单 SHP-2026-001
  ├─ 2张备货单
  ├─ 1个订舱号
  ├─ 1份提单
  └─ 3个集装箱
```

这里的 `SHP-2026-001` 就是 Shipment 的内部业务身份；其他编号都是它在特定业务环节中的外部引用或关联对象。

#### 应该如何定义

建议把 Shipment 定义为：

> 一次具有明确起运地、目的地、运输责任和货物范围的运输组织单元，是 Logix 串联计划、订舱、单证、货柜和到港执行的核心业务对象。

最核心的内部标识是：

```text
shipment_id              数据库内部主键
shipment_reference       面向业务人员的稳定出运编号
```

例如：

```text
shipment_id: 8f92...
shipment_reference: SHP-CN-US-202609-00128
```

`shipment_id` 用于系统内部关联；`shipment_reference` 用于页面、导入、查询和沟通。

#### 它与其他对象的区别

| 对象            | 表示什么             | 与Shipment关系                      |
| --------------- | -------------------- | ----------------------------------- |
| 出运计划        | 计划运什么、运多少   | 一项计划可产生多票Shipment          |
| 备货单          | 通知供应商准备哪些货 | 多张备货单可进入一票Shipment        |
| 装箱任务        | 如何把货装入箱内     | 一票Shipment可有多个装箱任务        |
| Booking         | 向船司订舱的业务     | 一票Shipment可关联一个或多个Booking |
| 提单            | 承运和运输单证       | 一票Shipment可对应一份或多份提单    |
| Container       | 实际运输设备         | 一票Shipment可使用多个货柜          |
| Customs Entry   | 海关申报             | 一票Shipment可对应多次申报          |
| Transport Event | 运输过程中发生的事件 | 事件通过货柜、提单等关联到Shipment  |

特别要避免：

```text
Shipment = Container
Shipment = Bill of Lading
Shipment = Booking
Shipment = Stocking Order
```

它们都不是同一个概念。

#### 常见关系场景

##### 一票一柜

```text
Shipment A
  ├─ Booking B
  ├─ Bill of Lading C
  └─ Container D
```

最简单，但不能据此把Shipment和货柜合并成一张表。

##### 一票多柜

```text
Shipment A
  ├─ Container 1
  ├─ Container 2
  └─ Container 3
```

三个货柜共用一票运输业务，但每柜可能有不同的卸船、清关和提柜时间。

##### 一柜多张备货单

```text
Shipment A
  └─ Container 1
       ├─ Stocking Order A
       ├─ Stocking Order B
       └─ Stocking Order C
```

VGM属于这个货柜的装载实例，不属于其中任意一张备货单。

##### 一个订舱拆成多票Shipment

```text
Booking B
  ├─ Shipment A
  └─ Shipment B
```

例如共享一个船司订舱额度，但货主、目的仓或单证要求不同。

##### 一票货中途换柜

```text
Shipment A
  ├─ 原Container 1
  └─ 新Container 2
```

Shipment身份保持不变，设备关联发生变化。这正是不能使用箱号作为Shipment身份的原因。

#### “业务身份”包含哪些内容

业务身份不是把所有字段拼成一个主键，而是由“内部稳定ID＋外部引用集合”构成：

```text
Shipment
  ├─ 内部身份
  │    ├─ shipment_id
  │    └─ shipment_reference
  │
  ├─ 外部业务引用
  │    ├─ booking_reference
  │    ├─ shipping_instruction_reference
  │    ├─ bill_of_lading_number
  │    └─ carrier_shipment_reference
  │
  └─ 关联对象
       ├─ stocking_order
       ├─ container
       ├─ customs_declaration
       └─ transport_document
```

外部引用建议单独建表，而不是全部堆在 Shipment 主表：

```text
shipment_reference
- id
- shipment_id
- reference_type
- reference_value
- issuing_party
- carrier_code
- valid_from
- valid_to
- is_primary
- source
```

`reference_type` 可以包括：

```text
INTERNAL_SHIPMENT
BOOKING
SHIPPING_INSTRUCTION
BILL_OF_LADING
SEA_WAYBILL
CARRIER_SHIPMENT
FORWARDER_SHIPMENT
CUSTOMER_ORDER
```

#### 导入4张表时怎么识别Shipment

导入历史已出运数据时，不应简单以箱号一行生成一票Shipment。应先根据现有字段建立分组规则。

优先识别顺序可以是：

1. 内部出运单号或货运单号
2. 提单号
3. 船司订舱号
4. Shipping Instruction编号
5. 货主＋起运港＋目的港＋船名航次＋出运批次
6. 无法可靠判断时，创建“待确认Shipment”，不静默合并

例如：

```text
提单号相同 + 船名航次相同 + 起运港/目的港相同
→ 很可能属于同一Shipment
```

但这仍需考虑分提单、并单和换单场景，所以系统应保存：

- 分组依据
- 匹配规则版本
- 匹配置信度
- 是否人工确认

#### 与DCSA Shipment的关系

在DCSA语境中，Shipment通常是承运人接收的一项运输业务，贯穿：

```text
Booking
→ Shipping Instructions
→ Transport Document
→ Shipment Events
```

Logix内部Shipment范围可以比单个船司接口稍宽，因为还需要向前连接：

- 出运计划
- 备货单
- 装箱任务

向后连接：

- 清关
- 提柜
- 送仓
- 卸柜
- 还柜
- 费用和异常

因此建议：

```text
Logix Shipment
  ├─ 内部全流程业务身份
  └─ 关联一个或多个DCSA/船司Shipment引用
```

不要直接拿某家船司的 shipment reference 当作数据库主键。

#### 更直白的替代表述

如果“Shipment业务身份”容易产生歧义，可以在中文产品界面和文档中改为：

> 出运业务主单及其识别编号

或者：

> 一票出运业务的内部主档

数据库和接口中仍可使用：

```text
Shipment
shipmentId
shipmentReference
```

最终可以把它理解为：

> 箱号标识“用哪个箱子”，提单号标识“哪份运输单证”，订舱号标识“哪次向船司订舱”，而 Shipment 标识“Logix正在管理的到底是哪一票出运业务”。

只要这个内部身份稳定，后续换箱、拆单、并单、换船、转运或提单变更时，整条生命周期仍能持续关联，不会因为某个外部编号变化而断裂。
