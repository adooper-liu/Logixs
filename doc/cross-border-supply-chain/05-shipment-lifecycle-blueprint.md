# 端到端业务蓝图

> 状态分类：已出运后的主链和事实边界为已确认方向；采购、出运计划、供应商协同的详细聚合与权限为建议方案，待后续切片验证。

## 如何理解这条业务链

整条链路同时存在三种不同东西：计划说明准备怎么做，任务说明谁需要做什么，事实说明实际发生了什么。任何节点都不能因为计划日期到了、任务被点击完成或第三方接口返回成功，就自动认定业务结果已经发生。

Shipment负责串联一票出运的计划、订舱、单证和货物范围；货柜负责承载实际装载及箱级执行；清关案件、运输任务、仓库收货和费用则有各自的责任边界。用户可以从“一柜一档”查看全貌，但不能把所有业务压进货柜的一条状态。

## 一、出运计划

业务先按销售国家确定需要出运的SKU和总量，再按目的港、目的仓库拆分。随后综合供应商所在地、出运港、货量、交期和运输成本，确定整柜、同供应商拼柜或多供应商拼柜方案。

计划回答“准备怎么运”，不能提前表示货物已经备好、装箱或装船。

计划还需要说明分配理由，例如补缺货、维持安全库存、支持活动、新品铺货、仓间调平或降低长期仓储费。改变国家、渠道、仓库或目的港时形成新版本，并重新评估合规、标签、单证、费用和到仓时间。

## 二、备货

系统生成备货单并交给供应商。供应商确认数量、交期和缺口，提交备货完成信息和必要凭证。多张备货单可以进入同一个柜，一张备货单的产品也可以拆进多个柜。

备货完成表示货物具备装箱条件，不等于装箱完成。

供应商确认、预计完成和实际备货完成不是一个时间。口头答复只能作为计划信号；可追溯的书面确认形成承诺；实际完成还需要数量、包装和必要证据。短装、延期或替代料需要说明影响哪些出运计划。

## 三、装箱

```text
待装产品
→ 分配到装箱任务
→ 提取空箱
→ 实际装货
→ 绑定箱号和封条
→ 确认实际装载明细
→ 形成VGM及回执
→ 装箱完成
```

每次装载更正形成新版本，旧版本保留。柜内真实货物由实际装载明细说明，不能只看一张代表性备货单。

装箱前的分配是计划，装入柜内并确认的SKU和数量才是实际。一个柜可以包含多张备货单，一张备货单也可能拆到多个柜，因此必须保留“备货单产品行 -> 本次装载 -> 货柜”的数量关系。

提取空箱、开始装货、封箱、称重、VGM申报和VGM回执也是不同事实。箱号、封条号、箱况照片、称重方式和责任方共同构成装箱证据。

## 四、出运与海运

装箱后补齐订舱、船司、船名航次、起运港、目的港和运输路线。进港、装船和离港分别确认。海运期间持续接收船期和货柜动态，但商业船期、运营船期、港口作业和货柜实际事件必须分开理解。

ETA或ETD变化时保留每次变化，不能只留下最后一个时间。

需要特别区分：

- 进港不代表已经装船。
- 装船不代表船舶已经离港。
- 实际离港是当前“已出运”起点的重要事实。
- 船舶到港不代表货柜已经卸船，更不代表货柜已经可提。

船司、港口、码头和聚合平台可能给出不同时间。系统保留来源、接收时间和后续修订，经过映射和核验后再形成内部事实。

## 五、清关

清关工作从到港前开始，包括资料齐套、HS Code、预申报、报关行分工、正式申报、税费、查验、Hold和放行。船舶到港不代表货柜已经卸船，报关行“已处理”也不代表海关已经放行。

清关资料要求随国家、商品、贸易方式和监管安排变化。系统维护各国资料参数、接收方和传送方式，区分资料已准备、已发送、技术接收、业务接受、退回补正和海关放行。

AI可以抽取文件、比对字段、定位法规证据和解释风险，但最终申报、放行判断和风险接受必须由具备责任的人员完成。

## 六、提柜

提柜需要同时检查：海关放行、船司放货、码头卸船及可提、费用/Hold、预约和车队资源。满足条件后锁定计划并派车，司机通过移动端回传扫码、照片、EIR和实际时间。

“海关放行”只是可提条件之一。计划人员需要在同一处看到哪些条件已经满足、哪些仍在等待，以及最晚提柜日和潜在费用。

## 七、送仓、三方堆场和卸柜

正常情况下从码头直接送仓。当仓库容量不足、预约冲突或港口等待成本过高时，可先送三方堆场，再二次送仓。系统需要把新增运输和堆存成本与滞港风险放在一起比较。

到仓不等于卸柜完成。卸柜需要记录实际收货、短溢损、破损、部分卸货及差异处理。

三方堆场是正式可选节点。它通过增加一次提送和堆存成本，换取降低码头滞港费用或缓解仓库压力。系统比较直接送仓和经堆场中转的总成本、资源占用、时效和风险。

到仓、开始卸货、部分卸货、卸货完成和仓库确认收货分别记录。部分卸货时货柜仍可能占用月台和车队资源，不能因登记了一批收货数量就关闭卸柜任务。

## 八、还箱

卸柜后安排空箱回到指定场站，关注还箱截止时间、预约、箱况、EIR和损坏争议。完成还箱后仍需处理费用账单、争议和绩效复盘。

司机到达场站不等于场站已经接收空箱；只有形成可靠回场证据，才能停止相应滞箱风险计算。损坏争议和账单可能在还箱后继续处理，因此业务主链完成不等于财务事项全部关闭。

## 九、横向业务轨道

全流程同时存在三条横向轨道：

- 单证与合规：文件、证书、申报、资质和审核。
- 资源与费用：车队、仓库、堆场、预约、滞港和滞箱。
- 证据与异常：来源、冲突、补证、复核、纠偏和审计。

任何主流程节点完成，都不能只凭按钮点击、任务完成或接口返回成功来认定。

## 十、节点之间如何可靠交接

每次交接至少回答五个问题：

1. 上一岗位交付了什么业务结果，而不是只完成了什么操作。
2. 下一岗位开始工作所需的信息和证据是否齐全。
3. 哪些内容是计划、预计、外部申报或已确认实际。
4. 缺失或冲突时，是允许待补全、限制部分动作，还是必须阻断。
5. 失败、退回或重做后，原始信息和历史决定如何保留。

## 十一、完整闭环示例

某柜预计周一到港。船司更新ETA后，清关工作台发现一份目标国资质即将失效，AI定位适用规则并提示风险，清关人员确认需要补证。资料补齐并发送报关行后，系统分别记录技术接收、业务接受和海关放行。

与此同时，调度发现仓库周三无月台资源，而码头免费期即将结束。系统比较等待仓库、先提至三方堆场和调整其他柜次三种方案。计划人员选择先提至堆场并锁定车队。司机扫码提柜、上传EIR，堆场确认入场；仓库释放月台后再安排二次送仓。仓库记录到仓、部分卸货、短装差异和最终卸柜，车队最后完成空箱回场。

在这条链上，每个岗位看到自己的任务，但管理层可以回到同一柜档案，解释计划为什么变化、费用为何发生、谁作出决定以及实际结果如何。

**一、完整业务链路**

```text
采购计划
  -> 采购
  -> 按国别制定出运计划
  -> 确定 SKU 与计划总量
  -> 按目的港 + 仓库分仓
  -> 按供应商 + 起运港规划装柜
  -> 整柜 / 多供应商拼柜
  -> 生成并发送备货单
  -> 供应商备货
  -> 提空箱
  -> 装箱
  -> 关联集装箱与备货单
  -> 补充出运资料
  -> 实际出运
  -> 在途跟踪
  -> 到港、清关、提柜、还箱、入仓等后续生命周期
```

需要纠正一个容易固化错误模型的表述：“一柜一个备货单、一柜多个备货单”说明集装箱和备货单不是一对一，而是多对多关系：

- 一个集装箱可以装多个供应商的多个备货单。
- 一个备货单也可能因数量、体积或分批出运被拆到多个集装箱。
- 关联关系还必须记录本柜实际装载的 SKU、数量、体积、重量等。

因此不能在集装箱表中只放一个 `stockingOrderId`。

**二、当前项目的业务边界**

当前系统的流程起点建议定义为：

> 已实际出运，并且能够确认一次出运事实及其货物、航线和集装箱信息。

“已创建订舱”“预计开船”“已经装箱”都不等于已出运。当前导入起点应至少满足以下一种条件：

- 存在实际离港时间 `ATD`；
- 来源系统明确给出稳定的 `DEPARTED` 状态；
- 经有权限的业务人员确认已出运。

当前系统负责：

- 导入和校验已出运数据；
- 建立出运、集装箱、货物之间的权威关系；
- 跟踪船期、节点、异常和资料；
- 管理到港、清关、提柜、还箱、入仓等生命周期；
- 保留完整来源、变更和审计记录。

当前系统暂不负责：

- 计算国别需求和出运计划；
- 分仓优化；
- 供应商组合与整柜/拼柜优化；
- 生成或下发备货单；
- 提空箱和现场装箱作业。

这些上游对象现在可以被引用，但不应提前实现空壳状态机或虚构业务规则。

**三、不要只设计“一张大表”**

业务上可以称为“稳定的出运数据结构”，但数据库不宜是一张包含所有内容的宽表。出运、集装箱、SKU 明细和生命周期事件具有不同粒度：

| 对象                  | 粒度                   | 主要职责                                     |
| --------------------- | ---------------------- | -------------------------------------------- |
| `shipments`           | 一次业务出运           | 航线、船期、提单、起运地、目的地和总体状态   |
| `containers`          | 一个实际集装箱         | 箱号、箱型、封条号及箱级生命周期             |
| `shipment_containers` | 出运与集装箱关系       | 支持一次出运包含多个柜                       |
| `shipment_items`      | 出运货物明细           | SKU、数量、单位、目的仓及来源引用            |
| `container_items`     | 柜内实际装载明细       | 某柜实际装了哪些 SKU 和数量                  |
| `shipment_events`     | 一次生命周期事实       | 离港、到港、清关、提柜、还箱等不可丢失的事件 |
| `shipment_documents`  | 一份出运资料           | 提单、报关、装箱单等文件与版本               |
| `import_batches/rows` | 一次导入及一行原始数据 | 预检、幂等、错误定位和审计                   |

如果当前来源确实只有一柜一票，也仍应保留这些边界，不要把来源文件的偶然结构变成永久领域约束。

**四、`shipments` 应保存的稳定事实**

建议出运主表只保存出运级字段：

- 内部稳定 ID；
- 业务出运号；
- 来源系统、来源记录 ID、来源版本；
- 运输方式；
- 船公司、船名、航次；
- 主提单号、分提单号；
- 起运国、起运港；
- 目的国、目的港；
- 最终目的仓或交付地；
- 预计/实际离港时间 `ETD/ATD`；
- 预计/实际到港时间 `ETA/ATA`；
- 当前生命周期状态；
- 状态版本或并发版本；
- 导入批次、首次导入和最后更新时间；
- 创建人、修改人及审计信息。

时间应当是带语义的独立字段，不能只放一个模糊的“出运日期”。数据库保存 UTC；交换使用 ISO 8601；展示时转换到业务时区。

以下内容不应直接堆进主表：

- 多个集装箱号；
- 多个 SKU；
- 多个供应商；
- 多个备货单号；
- 事件历史；
- 文件列表；
- 用文本拼接的港口、仓库或状态说明。

**五、上游预留接口**

建议采用“引用而非复制规则”的方式预留：

- `sourceShippingPlanId`：上游出运计划引用；
- `sourceStockingOrderId`：备货单引用；
- `sourcePackingOrderId`：装箱任务引用；
- `sourcePurchaseOrderId`：采购订单引用；
- `sourceSystem` + `sourceRecordId`：通用外部身份；
- 可选 `upstream_references` 关系表：支持一个对象关联多个上游单据。

这些字段当前可以为空。将来接入备货平台时，由适配器把上游模型映射成当前系统的正式契约，不能让供应商平台的数据结构直接进入领域模型。

**六、导入已出运数据的必要能力**

导入不是简单地把 Excel 行写入数据库，至少需要：

1. 上传后先预检，不立即落入正式业务表。
2. 明确列级和行级错误，非法港口、时间、数量、箱号不得静默替换。
3. 以来源系统和来源记录 ID 做幂等；没有来源 ID 时使用经过定义的业务组合键。
4. 同一出运的多行 SKU、多个柜必须正确归组。
5. 整批正式导入使用事务，避免只落入一半关系。
6. 重复导入应区分完全重复、允许更新和业务冲突。
7. 保留原始文件、批次摘要、逐行结果和操作人。
8. 已进入生命周期后的关键事实更新要形成变更记录，不能覆盖历史。
9. 同一箱号出现在不兼容的活动出运中时必须报冲突。
10. 导入完成后给出新增、更新、重复、失败及需人工处理的明确结果。

**七、生命周期建议**

出运状态不应试图替代所有事件。建议：

```text
DEPARTED
  -> IN_TRANSIT
  -> ARRIVED
  -> CUSTOMS_CLEARANCE
  -> RELEASED
  -> PICKED_UP
  -> DELIVERED_TO_WAREHOUSE
  -> EMPTY_RETURNED
  -> CLOSED
```

异常如甩柜、延误、查验、滞箱、改单，应记录为事件或异常案件，不宜随意扩展成互斥主状态。系统的“当前状态”是事件投影出的便捷结果，事件记录才是可审计事实。

不同集装箱可能在不同时间提柜、还箱，所以出运级状态和箱级状态必须分开。只有定义了明确聚合规则，才能从多个箱状态计算整票出运状态。

**八、当前阶段的最小可交付闭环**

目标岗位需要能够：

- 导入已出运货物数据；
- 在提交前发现重复、缺字段和业务冲突；
- 查看一票出运下的柜、SKU、数量、目的仓和关键时间；
- 识别当前阶段、逾期节点和资料缺口；
- 录入或接收后续事件；
- 查看事件历史和修改来源；
- 确认最终到仓、还箱并关闭出运。

这才构成当前“出运后生命周期”的闭环。仅有一张出运表和一个导入接口，还不足以称为生命周期管理。

下一步应结合仓库现有 schema、导入模板和状态定义，形成一份“现状与目标模型差异清单”，再决定是扩展现有模型还是追加迁移。当前尚未对项目实际实现完成这一步核对。

```text
  -> 出运 Shipment（当前稳定起点）
  -> 多个货柜
  -> 柜内装载明细
  -> 出运后生命周期
```

最大缺口不是生命周期节点，而是缺少稳定的“出运/票级”聚合，且现有导入仍按“备货单号生成货柜”组织。

#### P0 缺口

##### 1. 缺少独立的出运主表/聚合

当前 schema 没有 `Shipment`。核心对象是 `ReplenishmentOrder` 和 `ContainerRecord`：schema.prisma、schema.prisma。

船公司、订舱号、船名航次和提单号被保存在每个柜的 `ContainerDispatchSnapshot` 中：schema.prisma。

这会造成：

- 一票多柜时，订舱、船名航次、提单等票级事实被每柜复制。
- 无法稳定表达“一次出运包含多个柜”。
- 同票多个柜的信息可能不一致。
- 无法在不依赖柜号的情况下管理出运级资料、时间和状态。
- 将来接入出运计划时，没有稳定对象可以承接计划与实际出运的关系。

建议增加：

```text
Shipment
ShipmentContainer
ShipmentItem（可选，或从装载明细投影）
ShipmentUpstreamReference
```

`ContainerRecord` 继续作为货柜生命周期聚合，不应被 Shipment 替代。

##### 2. 已出运导入仍按备货单号归组，不能可靠导入现实的一单多柜

导入执行逻辑使用 `orderNumber` 分组，并且每组只取第一个箱号：execute-import.service.ts。

写入时又按 `tenantId + orderNumber` 查找最多一个 `ContainerRecord`；发现两个就报冲突，已有箱号不同时也报冲突：prisma-replenishment-order-import-writer.ts。

因此当前虽然已经支持“一条产品明细拆入多柜”的后续装载分配，但初始导入仍不能自然表达：

- 一个备货单实际拆入多个柜；
- 一个柜包含多个备货单；
- 一次出运包含多个柜；
- 同一个备货单分批出运、分属不同航次。

这与目标流程中的实际基数直接冲突。

##### 3. “导入已出运数据”与实际落库状态不一致

新导入的货柜被明确创建为 `not_shipped`：prisma-replenishment-order-import-writer.ts。

领域文档也明确说明，导入只创建 `not_shipped`，之后必须由合格事件推进：IMPORT_DOMAIN_MODEL.md。

这套做法审计上严谨，但与当前目标存在语义差异：

> 当前输入本身就是“已经出运的货物数据”，导入成功后应该形成已出运起点，而不是产生一批待装箱、待装船的业务对象。

正确调整不是绕过事件，而是让导入事务形成：

```text
Shipment 建档
+ Container 建档
+ 装载关系
+ 已验证的出运事实
+ 生命周期从出运边界初始化
```

缺少有效出运证据的行应阻断或进入复核，不能退化为普通 `not_shipped` 记录。

#### P1 缺口

##### 4. 当前已经实现备货、装箱和装船工作台，并非“仅预留接口”

项目已经完成装箱岗位操作闭环，包括录入箱号、封号、重量、体积和 VGM：p6-container-stuffing-operational-flow.md。

装载分配、备货合规和出运交接也已有正式实现。换言之，当前项目实际边界已经向出运前延伸，而用户刚确认的范围是：

- 当前关注出运之后；
- 备货平台、装箱平台只预留接口；
- 后续再向采购、计划、备货和装箱延伸。

需要做产品范围决策：

- 保留已有代码，但将备货、装箱、装船工作台标记为后续模块，默认不进入当前岗位导航和验收范围；
- 当前主路径直接从“已出运数据导入”进入；
- 不要删除已有可靠事实模型，因为未来仍可复用；
- 不再继续扩展出运前 UI，直到上游领域重新定界。

##### 5. 出运级目的国、目的港、仓库和货物总量没有统一归属

现有路线是按柜版本化的 `OceanRoutePlan`，航段也挂在柜上：schema.prisma。

这适合记录柜级实际路线，但不能替代出运级事实：

- 本次出运服务哪个国家；
- 目的港与最终仓库；
- 本次出运总 SKU 和总量；
- 哪些柜共同属于同一次出运；
- 票级 ETD、ATD、ETA、ATA；
- 票级资料是否齐全。

目标模型需要明确：

- Shipment 保存出运级权威事实；
- Container 保存柜级事实；
- 柜发生甩柜、改船、分批到港时，以柜级路线覆盖或分化；
- 不能把同一套航次字段复制到所有柜并假定永远一致。

##### 6. 缺少稳定的上游引用模型

当前 `ReplenishmentOrder` 只有内部 ID、租户和备货单号：schema.prisma。

尚未形成统一引用：

- 出运计划；
- 采购订单；
- 供应商；
- 备货单；
- 装箱任务；
- 外部系统记录 ID；
- 来源系统及来源版本。

因为当前不实现上游业务，建议采用通用、受控的 `ShipmentUpstreamReference`，而不是现在就建立完整采购或备货状态机。

#### P2 缺口

##### 7. “已出运”的准入条件尚未收敛为一个明确导入门禁

现有文档提出必须证明货柜已到出运节点，但具体 blocker 和转人工规则仍待真实样本定稿：IMPORT_DOMAIN_MODEL.md。

需要明确最小准入组合，例如：

```text
业务出运标识
+ 实际出运时间 ATD 或权威 departed 状态
+ 起运港
+ 目的国/目的港
+ 至少一条 SKU 明细
+ 数量与单位
+ 箱号，或明确的散货/待补箱号策略
+ 来源系统与来源记录身份
```

`loaded` 和 `departed` 也需要业务确认哪个才是当前系统边界。两者不能混称“已出运”。

##### 8. 导入事务边界不是整批原子

单个备货单通过数据库事务写入，但批次按 `orderNumber` 循环执行；某组失败后其他组继续，最后批次仍转为 `completed`：execute-import.service.ts。

这并非一定错误，但需要在产品上区分：

- `completed_success`
- `completed_with_failures`
- `failed`
- 可重试失败行
- 已成功对象与失败对象的恢复策略

否则“批次完成”容易被误解为所有出运数据已经可靠建档。

当前项目已有不少目标能力，不需要重做：

- 导入批次、来源行、人工审核和逐行结果模型；
- 文件留存、幂等、替代批次和审计血缘；
- SKU 稳定身份；
- 一柜多单、一单拆多柜的版本化装载分配：schema.prisma、schema.prisma；

- 规范事件、来源权威、状态机和历史版本；
- 清关、提柜、送仓、卸柜等出运后工作台；
- 货柜级 14 节点生命周期与证据链。

#### 建议调整顺序

1. 确认 `Shipment` 的业务身份和唯一性规则。
2. 增加 `Shipment`、`ShipmentContainer` 和上游引用结构。

5. 让导入成功后从 `loaded` 或 `departed` 边界初始化生命周期。
6. 将现有备货、装箱、装船工作台从当前产品主路径隐藏或降为后续模块。
7. 保留现有装载分配和出运后生命周期实现，逐步改为挂接 Shipment。
