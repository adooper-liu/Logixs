# 管理层与业务评审总览

> 一句话：先用真实已出运货柜把后半程管起来，未来再把采购、计划、备货和装箱接到同一条业务链上。
> 状态分类：业务链、对象边界、工作台、交接、权限与实施顺序均已收敛为业务基线；真实合同、接口凭据、费率和法域参数作为实施输入维护。

## 一、要解决什么问题

目前一只货柜的信息分散在货柜、清关、物流、仓库和单柜状态表中，同一信息被多次维护，岗位之间依靠表格和人工沟通交接。Logix要形成“一柜一档”：任何时候都能说明这只柜在哪里、发生了什么、还缺什么、谁应处理、下一步能否执行。

真正的问题不是“缺一张汇总表”，而是同一事实在不同表中被反复复制、更新和写回。一个日期可能既表示原计划，也可能是第三方预计，后来又被人工改成实际；一个“已完成”可能表示报关行处理完了，也可能被误解为海关已经放行。没有来源、语义和证据，再完整的字段也无法支撑调度、费用和责任判断。

因此，“一柜一档”不是把所有字段塞进一张超级表，而是让货柜成为统一业务入口：页面可以综合展示，背后仍由Shipment、装载、海运、清关、提送卸还、费用和证据等各自负责的业务记录共同组成。

## 二、业务全景

```text
产品与SKU
→ 采购和出运计划
→ 按国别确定SKU与总量
→ 按港口和仓库分仓
→ 按供应商、出运港、距离、数量和成本组织整柜/拼柜
→ 备货
→ 装箱、箱号、封条、VGM
→ 出运与海运
→ 清关
→ 提柜
→ 送仓或三方堆场
→ 卸柜
→ 还箱
→ 费用、异常和持续改善
```

## 三、当前建设策略

| 主题     | 业务决定                           |
| -------- | ---------------------------------- |
| 当前入口 | 导入已经出运的真实货柜数据         |
| 最小信息 | 现有四类表的字段并集，保留原始来源 |
| 无SKU    | 允许建档，进入待补全，不让整柜失败 |
| 后续切换 | 正常流程和导入形成同一种业务记录   |
| 外部状态 | 先核验来源和证据，再改变业务结论   |
| 工作台   | 围绕岗位优先事项、动作和结果设计   |

### 为什么先从已出运开始

项目当前还没有采购、出运计划、备货和装箱的完整线上流程，但企业已经存在大量真实已出运货柜。选择“已出运”作为起点，可以先解决最迫切的海运跟踪、清关、提柜、送仓、卸柜、还箱和费用问题，同时用真实样本检验数据结构。

这个选择不表示上游不重要。恰恰相反，当前导入必须落入未来正常流程也会使用的同一批业务对象。将来备货和装箱上线后，只是数据入口从Excel变为上游流程自然交接，下游工作台和历史档案不需要重建。

### 为什么四张表不是四个系统模块

货柜、清关、物流和仓库四张表是现有工作的四个观察角度，而不是长期业务边界。同一个箱号、日期、提单或仓库可能在多表出现。系统需要保留每个来源的原始说法，再把经过核验的结果归到正确业务对象，不能继续让四张表相互写回和争夺“当前值”。

### 为什么允许缺SKU建档

历史货柜可能已经到港甚至完成送仓，但来源资料没有规范SKU。如果因为缺SKU拒绝整柜，就会丢失真实物流事实。正确做法是先建立Shipment和货柜档案，保留原品号、名称、数量和描述，把信息完整度标记为待补全；依赖SKU的合规、数量对账或仓库动作再受到针对性限制。

## 四、已经具备的基础

当前系统已经形成产品/SKU稳定身份、版本化装载关系、统一日期事实，以及装箱、出运、清关、提柜、送仓和卸柜等业务切片。后续工作应在这些基础上补齐业务，而不是重新建立另一套货柜链。

## 五、下一阶段重点

- 完善采购、出运计划、备货和装箱的上游协作。
- 建立物料、产品、SKU、渠道商品和产品进化关系。
- 深化清关合规、法规采信和AI辅助评审。
- 建立车队、仓库、三方堆场共同参与的智能排柜。
- 建立报关行门户、车队移动端和外部伙伴协作。
- 用统一方式接入船司、港口、码头及飞驼、云当等数据源。

## 六、管理价值

- 事实可信：知道信息来自谁、何时提供、是否核验、是否被更正。
- 运营可控：岗位看到优先级、缺口、下一动作和完成结果。
- 成本可算：把滞港、滞箱、运输、仓库和堆场成本共同考虑。
- 风险前置：船期、清关或资源变化时提前调整，而不是到期救火。
- 平滑演进：先导入、后直连、再向上游延伸，不反复推倒重来。
- 支持创新：把需求、产品、物料、SKU和市场反馈连成产品进化图谱。

## 七、管理层应看到什么

管理层不需要逐柜阅读全部明细，但需要从汇总指标进入具体事实：

- 哪些柜最可能产生滞港、滞箱、仓库等待或三方堆场费用。
- 哪些柜因清关资料、Hold、仓容或车队资源不能按计划推进。
- 计划时间与实际时间偏差来自船司、港口、报关行、车队、仓库还是内部决策。
- 哪些数据长期依靠人工补录，哪些外部来源稳定可靠。
- 哪些异常已经有人负责，最晚何时需要决定，不处理会造成什么损失。
- 同类问题是否反复发生，改善后成本、时效和风险是否真的下降。

管理指标必须能下钻到货柜、任务、事件和证据，不能只展示无法解释的红黄绿灯。

## 八、分阶段建设而不割裂业务

### 第一阶段：可信接入真实已出运数据

建立导入预检、原始数据保留、Shipment和货柜身份、装载关系、日期事实以及待补全机制。目标不是导入成功率本身，而是形成可以继续运营的真实档案。

### 第二阶段：打通出运后岗位闭环

让出运、清关、提柜、送仓、卸柜、还箱和异常岗位在各自工作台完成任务，并通过同一事件和证据链交接。

### 第三阶段：引入外部协作和智能调度

报关行、车队、仓库和堆场通过受控门户或移动端参与；船司、港口、码头和聚合平台通过统一接入能力提供外部事实。智能排柜在可靠输入上做方案比较和动态重排。

### 第四阶段：向采购和计划延伸

建立选品、产品开发、寻源、补货、采购、可出运供给池、出运计划和分仓，使数据由正常业务自然流入。历史导入仍保留为补录和应急入口。

## 九、已经收敛的治理决定

1. Shipment使用内部稳定身份；Booking、提单和柜号只是关联身份。起运地、目的地、运输责任或货物控制范围需要独立管理时拆分Shipment，合并或拆分均保留关系和原因。
2. 产品部门负责产品家族和变体，研发/供应链负责物料与BOM，商业运营负责SKU和渠道Listing，合规岗位负责法规属性和采用结论，数据治理岗位负责编码、去重和跨域变更。
3. AI只做抽取、匹配、建议、解释和风险预测；定点、下单、申报批准、放行、计划发布及突破冻结区必须由授权人员完成。
4. 排柜先满足安全、合规和物理硬约束，再保护法定期限、free time和已对外承诺，随后优化总成本、时效和资源利用。调度员生成候选，计划负责人发布和突破冻结区。
5. 外部伙伴只看到完成已分配任务所需的最小数据。伙伴回执形成证据候选，是否推进内部事实仍由来源资格和内部规则决定；法律责任以合同为准。
6. 外部接入顺序为聚合平台、一个主要船司官方来源、一个主要港口/码头来源，再按业务量、风险、覆盖率和数据质量扩展。

## 十、成功标准

- 历史导入和未来正常流程形成同一种业务事实。
- 一柜一档能够解释完整历史、当前缺口和下一动作。
- 岗位可以在工作台中完成实际业务，而不是回到线下表格闭环。
- 清关、可提、送仓、卸柜和还箱结论都能追溯到可靠证据。
- 管理层能够看到时效、成本、风险、资源瓶颈和改善结果。

成功不以“页面上线”“接口可调用”或“字段已落库”单独判断。目标岗位必须能识别优先事项、理解缺口、执行被授权动作、处理失败，并确认最终业务结果。
