# 核心对象关系

## 目的与范围

本文统一备货前业务域的业务对象、身份和关系。对象名称表达稳定业务概念，不直接等同于数据库表。

业务对象设计的目的不是把每个名词做成一张表，而是避免不同岗位用同一个词表达不同事实。例如运营所说的“产品”、采购所说的“物料”、仓库所说的“SKU”和平台所说的“Listing”可能指向同一件实物，但它们承担的业务责任并不相同。只有先把身份和关系说清楚，后续预测、采购、合规、库存和利润才能使用同一条事实链。

## 基础资料不是一个大字典

建议将基础资料按业务责任分成六个中心。这里的“中心”表示信息归属，不要求拆成六套独立系统。

### 商品中心

管理产品家族、型号和变体、物料及版本、BOM、SKU、组合装、渠道Listing，以及GTIN、UPC、EAN、ASIN等外部身份。商品中心回答“这是什么”和“它们之间是什么关系”。

### 市场与渠道中心

管理国家、销售区域、平台、店铺、履约模式、渠道类目、上架规则、销售币种以及佣金、仓储和履约费规则。它回答“在哪里、通过什么方式销售”。

### 供应商中心

管理供应商集团、法律实体、实际工厂、生产地点、能力、MOQ、箱规、交期、产能日历、付款条件、绩效、认证、审厂、风险和可服务起运港。它回答“谁能在什么条件下供应”。

### 物流网络中心

管理国内工厂、集货仓、装箱仓、起运港、目的港、海外仓、平台仓、三方堆场、标准路线、运输时效和设施能力。它回答“货物通过哪些节点流动”。

### 合规中心

管理销售国法规、产品认证、标签和语言、危险品或电池等属性、HS Code、EPR、VAT、平台禁限售、证书有效期和适用SKU。它回答“什么条件满足后才能销售和运输”。

### 计划参数中心

管理计划周期、采购和生产提前期、质检、集货、订舱、海运、清关、安全库存、目标覆盖天数、MOQ、包装倍数和装载参数。参数必须有版本和生效日期，不能用今天的参数重算并改写历史计划。

## 商品主线

```text
产品家族
-> 产品型号/变体
-> 物料
<-> BOM版本
-> SKU
-> 渠道Listing
```

- 产品家族表达共同需求、技术平台或产品定位。
- 型号/变体表达产品本身的功能、规格、材质或外观差异。
- 物料服务于研发、采购、生产和供应链，可以是成品、部件、包装或耗材。
- SKU是可以被销售、库存管理和履约的单元。
- Listing是SKU在特定国家、渠道和店铺的商业呈现。
- 物料与SKU允许版本化多对多关系，以支持包装、组合装和渠道差异。

工程BOM、采购BOM和包装/销售BOM分别管理并建立版本关联，避免工程结构、采购替代关系和销售包装互相覆盖。

### Material、SKU和Listing为什么要分开

Material产生于开发、采购和供应链阶段，可以是成品、零件、包材、说明书或耗材。SKU产生于销售与库存管理阶段，代表能够被独立销售、库存和履约的单元。Listing则是SKU在某个国家、渠道或店铺里的销售身份。

例如，同一个基础产品可能因为电压、插头、语言、包装、认证或品牌不同形成多个SKU；同一个SKU又可能在Amazon、Walmart和独立站形成不同Listing。反过来，一个套装SKU也可能由多个成品和包材组成，不能假装成单一物料。

### 如何判断是否需要新SKU

- 只修改内部工艺且成品可以完全互换，通常保留SKU，通过物料或BOM版本管理。
- 尺寸、颜色、功能、包装数量或客户可感知属性变化，通常形成新的产品变体或SKU。
- 条码、标签、语言、插头、法规标识或渠道包装导致库存不能混用时，应建立可独立库存和履约的SKU。
- 仅有标题、图片、关键词或店铺差异，通常建立新的Listing，而不是复制SKU。

最终判断不能只看外观是否变化，还要看旧货和新货能否在采购、仓储、销售、售后与合规上无差别替换。

### 三类BOM各自解决什么问题

- 工程BOM表达产品设计和组成，是研发判断功能与变更影响的依据。
- 采购BOM表达实际向供应商采购、委外或替代的组成，是采购和成本核算的依据。
- 包装/销售BOM表达某一市场SKU使用的包装、标签、说明书和套装组成，是销售、合规和履约的依据。

BOM必须版本化。已发布版本不能原地修改；替代料需要审批、适用范围和有效期；物料变化可能触发测试、认证或标签复核。不同供应商生产同一物料时，还应保留供应商料号及经批准的差异。

### 产品进化关系

新品可能源于旧产品降本、功能提升、材料替换、市场本地化、渠道包装或新的使用场景。通过产品家族、变体、物料和SKU版本关系，可以分析哪些创新真正改善了销量、毛利、质量或退货，而不是把每个新品当成彼此无关的孤立档案。

## 供应主线

```text
供应商集团
-> 法律实体
-> 实际生产工厂
-> 工艺/品类能力
-> 资格与认证
-> 可供物料/SKU
-> 价格、产能、交期和分配份额
```

供应商资格按照法律实体、生产工厂、品类或工艺、目标销售国和有效期确定。贸易、开票或收款主体不能替代实际生产工厂的能力和合规证明。

### 寻源对象

- 寻源项目及需求版本。
- 候选供应商及发现来源。
- RFI、RFQ、RFP及回复版本。
- 报价、阶梯价及结构化成本分解。
- 样品轮次、测试、验厂和整改。
- 供应商准入、定点和量产批准。
- 供应关系、主备关系、切换时间和分配份额。
- 合同、价格表、产能承诺及有效期。
- 供应商绩效、风险事件和退出记录。

样品通过、供应商准入、定点和量产批准是四个独立业务门，任一结论不得自动推导其他结论。

### 为什么供应商必须分层

合同可能与贸易公司签订，收款主体可能是集团内另一家公司，实际生产则位于不同城市的两家工厂。如果系统只记录一个“供应商”，就无法判断证书覆盖哪家工厂、产能属于哪里、质量问题应归责给谁，也无法准确评估集货距离和停产风险。

供应商准入不是永久的“合格/不合格”标签。某工厂可能能生产家具，但没有资格生产面向特定国家的儿童用品；同一认证也可能到期。资格必须带适用范围、证据和有效时间。

### 报价不是一个单价

可比较报价至少要说明币种、税制、贸易条款、MOQ、阶梯价、包装、模具或开发费、检测费、付款条件、有效期和产能假设。系统既要保留供应商原始报价，也要形成归一后的可比口径。

```text
基础单价
+ 包材和销售包装
+ 模具及开发费摊销
+ 检验和测试
+ 国内运输和出口操作
+ 海运及目的地费用
+ 关税、税费和清关
+ 仓储与资金占用
+ 退货、质保和质量损失
+ 汇率风险
= 可比较的总落地成本
```

原始条件和归一假设都必须保留，不能把不同贸易条款、付款周期或质量风险压成一个看似精确的数字。

## 需求与库存主线

```text
销售事实/市场信号
-> 预测版本
-> 批准需求
-> 库存策略
-> 库存位置与供给时间轴
-> 净需求
-> 补货建议
-> 补货决策
```

基础预测粒度为：

```text
SKU × 国家 × 渠道 × 履约网络 × 仓库 × 周
```

基础预测、运营调整、活动增量、新品预测和最终批准需求分别保存。活动结束后单独复盘，避免活动销量污染常态预测。

### 库存位置

库存至少区分国内原料、在制、待检成品、可出运库存、已分配、已装箱、海运在途、待清关、海外仓在途、海外仓可售、平台仓可售、已预留、不可售、退货和调拨在途。

在途供给同时保留原始数量、生命周期阶段、承诺时间、预测时间、风险和可纳入计划的数量。低可信度在途可以进入风险场景，但不得伪装成现货或确定可承诺库存。

### 补货所看到的库存不是一个数

同样是100件货，国内待检、已装箱未离港、海上运输、清关受阻和海外仓可售的业务价值不同。补货人员需要同时看到数量、位置、预计可售日期和兑现风险。

不建议简单使用“在途数量乘以概率”得到虚拟库存，因为这会制造无法解释的零碎可用量。更可靠的方式是保留完整数量事实，再形成基准、乐观和保守场景，由计划规则决定哪些数量可以抵扣需求。

### 预测版本必须彼此可解释

至少分别保存系统基准预测、运营调整、活动增量、新品预测、批准需求、实际销售和偏差原因。新品缺少稳定历史，应参考相似品、产品属性、价格带、竞品、上市国家、广告预算和首批铺货策略，并明确悲观、基准和乐观情景。

### 补货策略因SKU而异

- 稳定畅销品按目标覆盖天数持续补货，并保持较高服务水平。
- 高价值、低销量商品更强调现金和过量库存控制。
- 新品采用小批试销、快速复盘和逐级放量。
- 季节品围绕销售窗口倒排，窗口结束后不能机械补货。
- 清仓品停止自动补货，并优先调拨、促销和库存退出。

### 端到端提前期

补货不能只有一个静态“采购周期”。完整提前期至少包括订单确认、原料准备、生产排队、生产、检验整改、国内集货、等待舱位、海运、清关、提送卸和入库上架。每段都应区分标准值、供应商承诺、当前预测和实际结果。

## 执行与追溯主线

```text
补货决策
-> 采购计划行/调拨计划行/加急需求
-> 采购订单行
-> 供应商书面确认
-> 生产批次
-> 检验批次
-> 可出运供给批次
-> 出运需求行
-> 出运计划分配行
-> 备货单行
-> 装箱明细
```

采购允许合并多个补货需求，但必须保留每个需求的数量分摊。补货决策也可以拆分为采购、调拨和加急运输等多个执行方案。

## 状态、事件和日期

- 状态回答对象当前处于什么业务阶段。
- 事件记录发生了什么、由谁执行、何时发生以及依据是什么。
- 日期事实区分计划、承诺、预测和实际，不能只保留一个可覆盖日期。
- 业务身份、生命周期状态、时间事实和附件证据分别管理。
- 日期只有日期精度时，应保留原始精度和推定属性；技术上以业务地点当地日末 `23:59:59` 补齐，但不得将该补值展示为实际发生时刻。

## AI边界

AI可以用于候选供应商发现、报价归一、需求预测、异常解释、风险识别和方案比较。AI不能直接完成供应商定点、采购下单、质量放行、备货释放或突破冻结区。

## 验收标准

1. 物料、SKU和Listing可以清楚区分并建立版本化关系。
2. 供应商法律实体、实际工厂及适用资格可以独立识别。
3. 需求、补货、采购、供给、出运和备货之间保持数量追溯。
4. 同一业务对象的状态、事件、日期和证据不会混为一个字段或结论。
