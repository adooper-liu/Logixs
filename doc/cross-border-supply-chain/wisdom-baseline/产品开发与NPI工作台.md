核心判断：当前 NPI 已有正确的业务骨架和较完整的设计 brief，但实现仍是“阶段展示 + 自由文本记录 + 推进/发布按钮”，还不是能够证明产品经过验证后才发布的 NPI 闭环。

仓库事实依据包括 [岗位工作台规格 (line 149)](D:/Logixs/doc/cross-border-supply-chain/08-role-workbenches.md:149)、[NPI blocked brief](D:/Logixs/docs/planning/tasks/product-npi-visual-flow-return-v1.md)、[产品定义契约 (line 8)](D:/Logixs/packages/contracts/schemas/v1/product-definition.schema.json:8)和[数据库模型 (line 2229)](D:/Logixs/database/schema.prisma:2229)。

**行业实践与项目差距**

| 关键能力   | 较成熟做法                                             | 当前项目事实                     | 判断                     |
| ---------- | ------------------------------------------------------ | -------------------------------- | ------------------------ |
| 阶段结构   | Concept → 工程验证 → 设计验证 → 生产验证 → 量产/发布   | 已有 Concept、EVT、DVT、PVT、MP  | 名称和主路径基本正确     |
| 阶段计划   | 进入阶段前明确目标、交付物、验证项、责任和门槛         | 主要保存当前阶段和文本结论       | 严重缺口                 |
| 验证执行   | 关联样机/批次、测试项、结果、偏差和证据                | 主要是结论文本与证据 UUID        | 无法证明真正做过验证     |
| 阶段决策   | Go/Kill/Hold/Recycle，由相应权限人员作决定             | 非空结论即可向后推进             | 推进规则失真             |
| 问题闭环   | 严重度、阻断性、责任人、期限、处置、复核、重开         | 没有结构化问题闭环               | 严重缺口                 |
| 冻结与变更 | DVT 后形成基线；后续变更必须评估影响并触发再验证       | 没有正式冻结基线和变更控制       | 严重缺口                 |
| 发布门禁   | MP正式通过、阻断问题关闭、适用验证完成后才可发布       | 当前主要检查规格和合规假设       | 存在越级发布风险         |
| 外部结果   | 实验室、工厂、认证结果经过对象匹配、来源核验和人员采信 | 只有证据标识，缺少完整性与采信链 | 证据可信度不足           |
| 工作队列   | 按风险、阻断、逾期、等待原因和下一责任组织             | 主要按时间和领取状态             | 岗位优先级不清           |
| 权限       | 执行、评审、变更批准、发布相互分离                     | 仍需核实是否依赖粗粒度能力       | 不能用一个“编辑权限”覆盖 |

最危险的事实是：当前发布逻辑没有充分证明“已经到 MP 且 MP 正式通过”。因此即使页面显示完整阶段轴，也可能只是视觉上的流程完整。

行业依据目前只确认了 Stage-Gate International 的官方说明：阶段承担跨职能工作，Gate 承担 Go/Kill/Hold/Recycle 和资源决策，后期投入越大、所需证据越强。ISO、APQP、PPAP、FDA 等尚不能泛化为本项目全部品类的统一规则；不同产品的样机数、良率、认证项目必须按品类、目标市场和风险批准，不能由 AI 编造固定数字。

**定位选择**

- `A 阶段记录台`：保留现有模型，加强字段与发布校验。投入较低，但仍难证明测试、问题和返工真正闭环。
- `B 阶段验证与发布控制台（推荐）`：管理阶段计划、适用交付物、样机/批次、测试、问题、阶段决定、冻结、变更、返工和发布。
- `C 完整 PLM/QMS/MES 平台`：覆盖工程文件、质量体系和制造执行。范围过大，会吞掉主数据、寻源、质量及工厂系统边界。

我建议选 `B`：NPI 对“概念如何被验证成可发布产品定义”负责，但不替代实验室、工厂 MES、完整 PLM/QMS；外部结果以证据和采信事实接入，供应商定点归寻源，发布后的稳定产品身份归主数据。

请先选择 `A、B 或 C`。选择后下一轮确定“统一阶段骨架 + 按品类启用的验证模块”。



确定选择 **B：阶段验证与发布控制台**。

它的责任边界是：证明产品定义经过适用验证、问题处置和正式决策后，才允许发布；不替代 PLM、QMS、实验室系统或工厂 MES。

下一项需要定案的是阶段模板结构：

- `T1 统一骨架 + 品类适用模块（推荐）`
  每阶段统一执行“计划、验证、证据、问题、决定、交接”；再按品类、市场和风险启用电气、结构、包装、合规、生产等模块。既能统一治理，也不会虚构所有产品都适用的检查项。
- `T2 各品类独立模板`
  灵活，但模板容易分叉，跨品类统计和权限控制会逐渐失真。
- `T3 全产品统一固定模板`
  实施最简单，但会产生大量“不适用”项目，也可能让团队机械打勾。

建议选择 `T1`。模块是否适用必须说明产品类别、目标市场、风险依据和批准人，不能由系统或 AI 根据名称自行猜测。请选择 `T1、T2 或 T3`。



确定 `T1：统一阶段骨架 + 品类适用模块`。

每个阶段都必须遵循：

```
定计划 → 做验证 → 收证据 → 处问题 → 作决定 → 做交接
```

品类模块只决定“需要验证什么”，不能改变上述闭环，也不能绕过发布门禁。

下一项是门槛如何确定：

- `G1 产品级预批准门槛（推荐）`：可继承品类模板，但必须在阶段执行前形成该产品的门槛版本；执行中修改门槛需要留痕、说明原因并重新批准。
- `G2 品类统一硬门槛`：管理简单，但不同价位、市场和风险等级可能不适用。
- `G3 评审时临场判断`：灵活，却容易出现先看结果、再改变标准的问题，审计价值很低。

建议 `G1`。它不是为每个产品重新发明规则，而是“品类默认值 + 产品适用性裁剪 + 执行前冻结”。请选择 `G1、G2 或 G3`。



确定 `G1：产品级预批准门槛`。

门槛版本必须在阶段执行前冻结，并记录来源、适用范围和批准人。执行中调整门槛要生成新版本，不能覆盖旧标准，也不能为了让已有结果通过而静默降标。

项目已经确定阶段决定为“通过、返工、暂停、终止”，因此不再重新讨论“有条件通过”。下一项是问题闭环：

- `I1 统一问题台账（推荐）`：记录严重度、是否阻断、责任人、期限、处置、复核、再验证、关闭与重开。阶段通过只要求阻断问题关闭；非阻断问题可以带责任和期限进入下一阶段。
- `I2 只结构化阻断问题`：较轻，但普通问题仍会散落在结论和附件中，后续难以升级或追责。
- `I3 仅关联外部 Jira/工单`：避免重复录入，但 NPI 无法自行证明问题与产品版本、测试结果和阶段决定的关系。

建议 `I1`。NPI 保存权威的问题闭环和外部工单引用，不要求替代完整缺陷管理系统。请选择 `I1、I2 或 I3`。



确定 `I1：统一问题台账`。

这意味着“问题没有消失”与“阶段可以继续”要分开判断：阻断问题未关闭，不能通过；非阻断问题可带着明确责任、期限和复核要求进入下一阶段。问题关闭后仍可因新证据重开。

下一项是冻结与变更控制：

- `C1 DVT 形成冻结基线，后续变更走正式变更单（推荐）`
  冻结的是已批准的产品定义，不是禁止改动。变更单记录原因、影响范围、受影响验证、批准人和是否需要回开阶段/再验证。
- `C2 只在 MP 前冻结`
  开发更灵活，但 PVT 很容易在未受控变更下失去验证意义。
- `C3 不设冻结，依靠版本号记录`
  有历史但没有变更决策和影响分析，无法判断旧证据还是否有效。

建议 `C1`。它只建立 NPI 所需的基线与变更事实，不把项目扩展成完整 PLM。请选择 `C1、C2 或 C3`。



确定 `C1：DVT 形成冻结基线，后续变更走正式变更单`。

变更不是简单改字段，而是：

```
提出变更 → 分析影响 → 批准/拒绝 → 回开必要阶段 → 重新验证 → 更新基线
```

旧基线、旧证据和原决定必须保留，不能覆盖。

下一项是外部检测、工厂试产和认证结果如何进入 NPI：

- `E1 外部结果采信链（推荐）`：区分“已接收、已匹配产品/版本、来源已核验、已采信、被拒绝、已过期”。只有已采信且仍有效的结果才能满足阶段门槛。
- `E2 上传附件即视为有效证据`：实现简单，但附件存在不等于内容可信，也无法防止错产品、错版本或过期报告。
- `E3 人工把结果重新录入 NPI`：结构化较容易，但会丢失来源真实性，并产生抄录错误。

建议 `E1`。NPI 保存来源、适用对象、关键结果、有效期和采信决定；原始报告可继续保存在外部实验室、认证或文档系统中。请选择 `E1、E2 或 E3`。



确定 `E1：外部结果采信链`。

外部结果进入系统后只是“收到的事实”，不自动等于“可用于通过阶段的证据”。系统要保存来源、产品与版本、样机/批次、测试项、签发时间、有效期和采信决定；错配、拒绝或过期的结果仍保留历史，但不能满足门槛。

下一项是 NPI 权限分工：

- `P1 能力分离、角色可配置（推荐）`：至少区分阶段执行、阶段评审、变更批准和产品发布；对象范围由产品、经营主体和责任关系限定。
- `P2 一个 NPI 管理权限`：配置简单，但同一权限可以填结果、批准自己、修改基线并发布，缺少制衡。
- `P3 按固定角色写死权限`：表面清晰，但未来新增岗位、跨国团队或代理审批时需要改代码。

建议 `P1`。能力分离不等于必须由四个人完成；小团队可以给同一人配置多项能力，但系统必须保留“执行者、评审者、批准者、发布者”分别是谁，并允许高风险品类要求职责分离。请选择 `P1、P2 或 P3`。

确定 `P1：能力分离、角色可配置`。

权限机制控制“谁可以做什么”；阶段门槛和产品状态规则仍属于 NPI 业务模块，不能搬进通用权限模块。租户隔离不可配置，经营主体、产品责任和分派关系属于对象范围。

下一项是发布与主数据交接：

- `H1 不可变发布包 + 下游接收回执（推荐）`：NPI 发布一个带版本的产品定义包，主数据模块明确接收或退回；接收后形成稳定产品身份，后续修改必须产生新版本。
- `H2 NPI 直接写入主数据表`：步骤少，但两个模块会争夺产品事实的所有权，失败恢复和审计困难。
- `H3 只把 NPI 状态改为已发布，下游实时读取当前记录`：最省事，但 NPI 后续变化可能悄悄改变已发布产品，无法证明下游当时接收了什么。

建议 `H1`。发布成功与主数据接收成功是两个事实：前者说明 NPI 已批准，后者说明稳定产品身份已经建立。退回时保留原发布包和理由，修正后生成新版本，不能覆盖旧包。请选择 `H1、H2 或 H3`。



确定 `H1：不可变发布包 + 下游接收回执`。

这样可以明确三件事：NPI 当时批准了什么、主数据实际接收了什么、失败后由谁继续处理。发布包和接收回执都不可覆盖。

下一项是 NPI 如何衡量结果并改进门槛：

- `M1 过程指标 + 上市结果反馈（推荐）`：同时观察阶段周期、返工、阻断问题、变更次数，以及上市后的质量、退货、合规、交期和经营偏差；用于校准模板与门槛。
- `M2 只看 NPI 过程指标`：容易把“按时过门”误认为产品成功。
- `M3 只看上市经营结果`：结果重要，但反馈太晚，也难区分是产品定义、供应、营销还是运营造成。

建议 `M1`。指标用于发现决策质量问题，不能反向篡改历史评审，也不应把所有上市结果都归因给 NPI。每项反馈必须标明数据来源、观察窗口和可能责任环节。请选择 `M1、M2 或 M3`。



确定 `M1：过程指标 + 上市结果反馈`。

这使 NPI 不只追求“走完阶段”，而是持续检验：当初的门槛、证据和决定，是否真的减少了上市后的质量、合规、交付和经营偏差。

下一项是工作台界面组织方式：

- `W1 异常驱动的验证工作台（推荐）`：队列优先显示阻断、逾期、待评审、待采信、变更影响和退回事项；详情区围绕当前阶段展示计划、交付物、验证、证据、问题和决定。
- `W2 阶段看板`：适合观察 Concept/EVT/DVT/PVT/MP 分布，但难以告诉岗位“今天先处理哪件事”。
- `W3 产品表单页`：录入直接，但容易再次退化为填写字段和点击推进。

建议 `W1`，并保留阶段看板作为辅助视图。服务端返回缺口、允许动作和拒绝原因，前端只负责呈现，不能自行判断“是否可以过阶段或发布”。请选择 `W1、W2 或 W3`。



确定 `W1：异常驱动的验证工作台`，阶段看板作为辅助视图。

主队列不按“最近修改”排序，而按阻断、逾期、待决策、待采信、变更影响和退回优先；详情页按同一业务步骤展示数据、任务、权限动作和结果回执。

下一项是责任归属：

- `O1 单一立项负责人 + 专业任务责任人（推荐）`：每个产品始终有一名 NPI 结果负责人；测试、合规、工程、包装等任务分别指派专业责任人，并明确下一责任方。
- `O2 完全共享队列`：调度灵活，但容易出现人人可见、无人负责。
- `O3 每阶段固定一个部门负责`：边界清楚，但跨职能问题容易在部门之间反复移交。

建议 `O1`。结果负责人不替代专业判断，也不能越权批准自己的高风险决定；其职责是确保缺口有人处理、决策按时发生、交接真正完成。请选择 `O1、O2 或 O3`。



确定 `O1：单一立项负责人 + 专业任务责任人`。

每条待办都必须回答：谁负责结果、谁正在处理、等待谁、何时到期、下一步交给谁。共享队列只用于发现和调度，不能替代责任归属。

下一项是验证结果绑定到什么对象：

- `V1 显式验证对象（推荐）`：测试结果必须关联具体产品版本，以及适用的样机、样品批次、试产批次或软件/固件版本。
- `V2 只关联产品定义`：简单，但产品发生变更后无法判断旧测试是否仍有效。
- `V3 只保存外部样品号或报告号`：保留来源，却无法稳定关联内部产品版本和阶段。

建议 `V1`。并非所有产品都强制有实体批次；验证对象类型按产品适用，但“到底验证了哪个版本、哪批对象”不能缺失。请选择 `V1、V2 或 V3`。



核心判断：推荐 `V1`，并将其明确为“双层显式绑定”。

**已证实事实**

- 业务权威已经要求验证基于“受控版本”，并登记对应样机、批次、测试结果和版本。[岗位工作台规格 (line 165)](D:/Logixs/doc/cross-border-supply-chain/08-role-workbenches.md:165)
- DVT 后变更必须分析影响并重新验证，旧结果不能无条件沿用。[岗位工作台规格 (line 240)](D:/Logixs/doc/cross-border-supply-chain/08-role-workbenches.md:240)
- PVT、MP 明确依赖试产或量产批次，单纯关联产品定义无法证明验证对象。[岗位工作台规格 (line 215)](D:/Logixs/doc/cross-border-supply-chain/08-role-workbenches.md:215)
- 当前契约只保存阶段、自由文本结论和证据 UUID，没有验证对象。[产品定义契约 (line 15)](D:/Logixs/packages/contracts/schemas/v1/product-definition.schema.json:15)
- 当前 `ProductDefinition.version` 每次写入都会递增，主要承担乐观锁语义，不是工程、设计或量产基线版本，不能直接拿来代表“验证了哪个产品版本”。[领域实现 (line 102)](D:/Logixs/apps/api/src/modules/product-selection/domain/product-definition.ts:102)
- 当前 NPI Schema、契约和模块中没有显式的样机、试产批次或软件构建身份模型。

**关键未知**

- 发布前的样机、试产批次和构建版本由 NPI 自身登记身份，还是引用工厂、实验室等外部系统身份。
- 一份结果是否可能覆盖多个样机、序列号范围或软硬件版本组合。
- 外部编号发生重号、改名或系统迁移时，内部如何保持稳定追溯。

这些未知影响后续对象所有权和基数，但不阻塞 `V1` 的原则定案。

**互斥方案**

- `V1 双层显式绑定（推荐）`：每条结果必须绑定一个不可变的受控产品基线，再绑定适用的具体对象，如样机、样品批次、试产批次、量产批次、软件或固件构建。外部报告号只是来源引用，不能代替内部对象身份。
  收益：支持变更影响分析、证据失效、再验证和审计。成本：需要建立对象匹配与版本关系。风险：若把对象类型做成固定全集，会错误限制不同品类。可逆性：高，可逐步增加新对象类型。
- `V2 只绑定产品定义`：成本最低，但产品变化后无法判断旧结果验证的是哪个状态，也无法可靠支持 DVT 冻结和回开。风险是旧证据错误放行新版本。后续迁移到 V1 时通常需要人工补链，可逆性较差。
- `V3 只保存外部编号`：接入快，但内部无法稳定识别对象；供应商编号重用、报告覆盖多个批次或外部系统变化都会破坏追溯。可逆性最低，因为历史编号未必能重新匹配。

**推荐结论**

选择 `V1`。其业务口径应是：

```
验证结果
  → 必须绑定受控产品基线
  → 再绑定该验证实际作用的样机、批次或构建版本
  → 外部编号和报告作为来源及匹配证据
```

实体产品不强制拥有软件版本，软件产品也不强制虚构实体批次；但任何结果都必须回答“验证了哪一个受控版本、哪些具体对象”。

外部编号不能代替内部稳定身份；不适用的对象类型无需虚构。该结论仍需由 Claude 写回业务权威和当前 task brief 后，才能成为实施依据。

- `S1 NPI 建立轻量稳定身份，保留外部引用（推荐）`

下一项是受控基线发生变更后，旧验证结果如何处理：

- `X1 影响评估后决定有效性（推荐）`

- `X2 任意变更使全部旧结果失效`
  最保守、规则简单，但文案、包装或无关局部变化也会触发全面重测，周期和成本很高，容易诱发绕过变更流程。
- `X3 旧结果默认继续有效，人工发现问题后再撤销`
  执行成本最低，但变更可能悄悄继承不再适用的证据，无法可靠支撑 DVT 冻结、阶段回开和发布门禁。

下一项是“受控产品基线”如何表达：

- `B2 单一产品版本号`
  所有变化统一递增一个版本。实现和沟通简单，但无法说明到底是设计、固件、工艺还是包装发生变化，影响评估容易扩大或遗漏。
- `B3 只引用各专业系统版本`
  NPI 不形成自己的基线包，只保存 PLM、MES、代码仓库等外部版本。避免重复，但缺少阶段评审和发布时的统一冻结对象；外部版本组合变化后，难以证明旧决定针对哪组内容。

确认选择 `B1：版本化基线包`。

NPI 冻结的是一组受控版本的组合及其关系，不复制设计、BOM、固件、工艺等专业内容。每个新基线包追加保存，并明确替代关系；验证结果绑定当时的基线包和实际验证对象。

- `Q2 一份报告就是一条结果`

**结果指标与最低保障**

业务结果指标：

- 晚发现损失：本可在较早阶段发现、却在模具/认证/试产后才暴露的问题所造成的实际报废、返工金额和延期。
- 发布后逃逸：发布后观察窗口内，可归因于NPI漏验或错误接受的质量、退货、合规和量产稳定性问题。
- 上市窗口达成：通过项目在批准窗口内完成发布的比例，同时排除经批准的暂停，不得靠降低验证标准换取。
- 错误投入避免：因有效验证而在投入扩大前终止或调整的项目，记录避免的下一阶段承诺资源；不能用“终止数量越多越好”。

阶段周期、等待时间、首次通过率和回开次数只是领先指标。跨租户事件、未授权发布、不可追溯发布、重复写入等应保持为最低保障指标，不能冒充经营结果。

**反事实检验**

没有统一控制面时，岗位仍必须完成：接住立项、判断是否继续投入、对失败方案返工或停止、确认可量产版本并完成发布交接。因此控制面不是产品目的。

即使权限、状态、证据和控制面全部完美，只要错误投入、发布后损失或上市延误没有改善，这台工作台仍不算成功。答案明确为“否”。
