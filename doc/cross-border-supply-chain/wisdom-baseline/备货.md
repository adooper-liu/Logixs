**核心业务目的**

现行业务权威给出的方向是：在出运计划已经释放备货后，让供应商按时、按量、满足适用要求地备齐货物，形成“可交给装箱岗位的产品行”，但不表示已经装箱或出运。[08-role-workbenches.md (line 315)](/D:/Logixs/doc/cross-border-supply-chain/08-role-workbenches.md:315)

按本轮损失优先原则，建议把唯一核心结果收窄为：

> 在约定装箱窗口前，把已释放备货单转化为按量、按版本真实可装的产品行；未就绪部分必须在造成装箱中断前形成明确差额、承诺和处置决定。

**目标岗位与关键决定**

项目权威只确认了“备货人员”这一职能，现有界面把 `cargo_ready_operator` 显示为“备货专员”，但没有真实岗位材料证明其实际组织归属。[cargoReadyWorkbench.ts (line 172)](/D:/Logixs/apps/web/src/data/cargoReadyWorkbench.ts:172)

推荐候选岗位是内部“备货履约专员/跟单岗位”：

- 业务时点：出运计划生成并释放备货单后，实际装箱开始前。
- 处理对象：已关联计划版本、供给来源和计划数量的备货单及产品行。
- 关键决定：哪些产品行已经可按计划交给装箱；哪些存在短装、错货、延期或条件不满足，需要补货、换货、改期或退回上游。
- 不负责：需求补货、采购下单、质量放行、目的地分配、实际装箱和已出运确认。

是否由内部岗位、供应商本人，还是出运协调岗承担，是当前第一个真实未知项。

**优先减少的 1～3 类经营损失**

建议当前只锁定两类，合规暂列最低保障：

1. **备货未按时足量完成，导致装箱计划中断或错过出运窗口。**
   可能进一步产生改配、重新订舱、加急运输和目标库存晚到，但项目尚无损失金额或发生率证据。
2. **产品、数量、版本或目的地不一致，直到装箱时才暴露。**
   造成现场停工、返工、短装、错装或重新分配。
3. **适用资料、包装或质量条件不满足。**
   权威要求它能够阻断不可信交接，但当前没有证据证明它是本台最主要的经营损失，因此建议作为 C 类底线，不列首要产品目标。

**结果指标与最低保障指标的区分**

业务结果指标候选：

- 按批准承诺日足量备妥率，建议按备货产品行计算。
- 装箱首次接收率，即无需因备货原因退回、改配或等待的比例。
- 因备货原因导致的装箱中断、错过窗口、延期天数及可归因增量费用。
- 短装、错货或版本错误在装箱前被发现的比例。

最低保障指标只证明系统可信，不证明工作台成功：

- 租户越权、未授权写入和未知授权值均被拒绝。
- 备货确认有来源、版本、操作者和证据。
- 幂等、并发冲突、审计和失败恢复成立。
- 未通过质量或适用要求时不能伪造备货完成。

ASCM SCOR 的 [Perfect Supplier Order Fulfillment](https://scor.ascm.org/performance/reliability/RL.1.2) 将供应商履约拆成足量、原承诺日期、单证准确和货况合格，可作为指标候选；它是供应商订单级框架，不等于 Logix 已接受口径。GS1 的 [Despatch Advice](https://www.gs1.org/despatch-advice) 表示货物已经发出，支持把“已出运”留给下游，而不拿来定义备货完成。

1. 没有统一控制面时，岗位仍必须把已释放备货范围按时足量交给装箱，并在窗口前解决差额。

**行业候选与项目边界**

供应商自助确认承诺和上传资料属于常见协作方式，但“门户”只是渠道。项目必须保持：

```

→ 来源与版本校验
→ 专业岗位核验

→ 形成备货结果
```

不能缩成“供应商点击完成 → 备货完成”。

**最低保障**

- 供应商采用独立外部身份，只能访问分配给本企业和本任务的对象。
- 确认、拒绝、修改、短装、替代和实际备妥均保留操作者、时间、对象版本和原始内容。
- 供应商“接受任务”不等于备货完成；上传资料不等于资料有效。
- 供应商可以提供证书和检验材料，但不能自行批准法规适用性、商检/植检结论或例外放行。
- 更正追加新版本，不覆盖已被内部采信或下游使用的历史。
- 外部提交不能直接改变内部生命周期状态。

**优先减少的损失**

1. 延期或不足导致装箱中断、错过窗口和加急。

**当前损失形成机制**

若整单只有一个“完成/未完成”：

- 一行延期会遮住其他已可装货物；
- 为赶窗口可能在线下删减范围，却不留下批准依据；
- 供应商短装、替代和分批交付无法准确归因；
- 指标只能看到整单晚了，不能看到哪一批、多少数量、由什么原因造成。

若每次部分提交都直接标成“备货完成”，又会让下游误认为整单已经齐备。

**行业候选与项目边界**

SCOR 的供应商履约指标允许从产品行判断产品、数量、日期、单证和货况，但这只支持行级衡量候选；Logix 仍需自己决定什么时候汇总成整单完成。

**决定一：备妥结果粒度**

| 方案                                       | 收益                                                         | 成本、风险与边界                                             |
| ------------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **A. 行/批次事实，整单一次最终确认，推荐** | 支持分批、短装和部分可装；同时保持当前“一单一次有效完成确认” | 需要明确计划范围变更和短装批准；整单完成只能在全部范围已备妥或剩余差额已有正式处置后形成 |
| B. 整单全有或全无                          | 最简单，完成语义清楚                                         | 一行延期阻塞全部，无法准确衡量分批履约，容易逼业务回到线下   |
| C. 一张备货单允许多次部分完成              | 最灵活，可逐批交接                                           | “完成”含义不稳定，下游难判断剩余范围；需修改已批准生命周期契约，历史兼容成本最高 |

**最低保障**

- 供应商每次提交必须对应具体备货行、批次、数量、单位和订单版本。

## 代码核实：Codex 说得偏重了

Codex 说现有服务"在物料档案齐全且装柜分配完成后显示'完成备货确认'"。实际代码（`list-replenishment-orders.service.ts` 第 339～350 行）是：

- `workReason.label` 为"完成备货确认"，说明为"物料事实齐全，已完成装柜分配"。
- `nextAction` 为"继续备货确认"，指向 `work_execution.continue_cargo_ready`。

也就是说，这是一个**待办提示**（"请去完成备货确认"），而不是"已经备妥"的结论，Codex 的表述偏重了。但问题依然存在：它进入这一步的前提只有档案齐全和已分配装柜，两者都不是实际备妥的证据。而且"完成备货确认"这个文案容易让人误读成已完成，至少应改成"待确认实际备妥"一类的说法。

其余几处核实结果成立：
- `CargoReadinessFact` 只存在于契约 `lifecycle-state-machine.schema.json`，数据库里没有对应模型。
- `CargoReadyWorkbench.vue` 第 134～139 行显示"Shipment 交接"，并链接到出运工作台，跳过了直接接收方装箱。

## 需要 Claude 解决的问题

1. **供应商承诺现在有三台都在管。**

   | 工作台           | 管的承诺                                           |
   | ---------------- | -------------------------------------------------- |
   | 采购履约（已定） | 供应商书面承诺，以及数量、交期、条款的商业重新协商 |
   | 生产验货（已定） | 生产兑现、验货和整改，形成可出运供给               |
   | 备货（本次）     | 供应商"确认数量、交期和工厂"，提交短装、替代、改期 |

2. **"独立门户"和寻源已定的"渠道中立"冲突。**
