# 集团租户

这个要求成立，但不能简单在“用户”或“用户组”上增加一个 `country` 字段。你真正需要的是：

> **集团租户下增加“账套主体/经营主体”，国别是该主体的属性，也是用户授权范围之一。**

**概念必须分开**

| 概念 | 回答的问题 | 示例 |
|---|---|---|
| `Tenant` 租户 | 哪个集团的数据安全边界 | Aosom 集团 |
| 账套主体 `AccountOwner` | 当前以哪个公司身份经营、核算和承担责任 | Aosom US LLC |
| 注册国 | 该公司依法注册在哪里 | US |
| 组织单元 | 属于哪个区域、部门、事业部 | 北美区、物流部 |
| 用户组 | 哪些用户共享一组授权 | 美国运营组 |
| 货主 | 这票货属于哪个业务主体 | Aosom US LLC |
| 销售国 | 商品在哪个市场销售 | CA |
| 目的国 | 货物运往哪里 | US |
| 原产国 | 商品原产资格属于哪里 | CN |

因此，货主、销售国、目的国、注册国可以有关联，但绝不能互相推导。

例如，一票货可以是：

```text
集团租户：Aosom Group
当前账套主体：Aosom US LLC
主体注册国：US
货主：Aosom US LLC
销售市场国：CA
运输目的国：US
商品原产国：CN
```

这四个国家值同时存在并不冲突。

**推荐模型**

```text
Tenant 集团租户
└─ OrganizationNode 组织树
   ├─ LegalEntity / AccountOwner 账套主体
   │  ├─ registeredCountry 注册国
   │  ├─ baseCurrency 本位币
   │  ├─ defaultTimeZone 默认时区
   │  ├─ fiscalCalendar 财务日历
   │  └─ status
   ├─ Region 区域
   ├─ Department 部门
   └─ Team 班组

User
├─ TenantMembership
├─ UserGroupMembership
└─ RoleAssignment
   ├─ capability：能做什么
   ├─ accountOwnerScope：能操作哪些账套主体
   ├─ organizationScope：能操作哪些组织
   └─ locationScope：能操作哪些仓库、港口或地点
```

“当前国别”在界面上应表现为“当前账套主体”，例如：

```text
当前主体：美国公司（US）
```

不能只显示“美国”，因为同一国家可能有多个公司、分公司或账套。切换账套主体会改变数据范围、币种、时区、合规主体和授权范围；切换销售国或目的国则不应改变登录权限。

**权限规则**

以后权限判断应固定拆成四层：

```text
租户：是不是这个集团的人
能力：能不能执行这个动作
账套/组织范围：能操作集团里的哪个公司
业务守卫：当前对象和状态是否允许操作
```

用户可以同时属于多个账套主体，角色也不必为每个国家复制。例如，同一个 `operations_dispatcher` 角色可以：

- 张三：只允许美国主体；
- 李四：允许美国和加拿大主体；
- 集团经理：跨主体只读；
- 财务人员：只能访问指定主体的费用和核算数据。

这正好符合“机制一次建立，未来角色持续配置”的原则。

**当前仓库事实**

目前仓库只有：

- `tenantId + roles + capabilities` 的运行时身份，见 [authenticated-user-identity.ts](D:/Logixs/apps/api/src/modules/identity/domain/authenticated-user-identity.ts:3)；
- 契约中预留了 `organizationScope[]` 和 `locationScope[]`，见 [IDENTITY_ACCESS_MODEL_V1.md](D:/Logixs/docs/product/domain/IDENTITY_ACCESS_MODEL_V1.md:16)；
- ISO 国家参考数据 `CountryCodeReference`，见 [schema.prisma](D:/Logixs/database/schema.prisma:252)；
- 货主与销售国映射 `CargoOwnerReference`，见 [schema.prisma](D:/Logixs/database/schema.prisma:274)。

但数据库里还没有正式的用户、用户组、组织树、账套主体、成员关系和角色授权表。所以这不是“给现有用户表补一列”，而是身份与组织主数据尚未落地的真实缺口。

现有领域设计也已经明确：公司注册国、销售国、目的国、原产国必须分轨，见 [MASTER_DATA_DICTIONARY.md](D:/Logixs/docs/product/domain/MASTER_DATA_DICTIONARY.md:51)。

**方案选择**

推荐方案 A：

> 一个集团一个 Tenant，集团下有多个账套主体；用户、用户组和角色授权到具体账套主体。

收益是集团视角统一、跨国人员可复用账号、授权边界清晰，也支持未来合并报表。代价是需要正式组织主数据、主体切换器和范围授权。

不建议：

- 每个国家建一个 Tenant：隔离简单，但集团汇总、跨国用户和共享主数据会非常困难。
- 给用户或用户组直接加国家字段：实现便宜，但无法处理一国多公司、跨国岗位和公司重组。
- 把货主当账套主体：短期看相似，后续第三方货主、代理关系和多角色公司会混乱。

这项应写进现有两套体系，不新增第三套：`doc/` 定义集团、账套主体和业务含义；技术侧更新身份访问模型、主数据契约和实现 brief。首版只建立主体与权限范围，不顺带建设总账、科目、凭证等完整财务模块。


规则本身的定位已经稳定：它要求“机制先行、角色渐进”，但不把业务状态机塞进授权模块。



# 角色

你的判断大约对了七成：**不应现在穷举所有未来角色，但权限也不只是“角色勾选几个菜单”。**

**求真结论**

当前任务确实开始出现“追求完整授权体系，把业务无限推迟”的倾向。原目标是“路由默认拒绝”，现在 brief 已扩展出 `AUTH-B2-01` 到 `AUTH-B2-12`，其中混入组织范围、地点范围、职责分离、费用规则、导入归属、动作策略等多个业务域。如果要求这些全部完成才能合并，确实会陷入完美坑。

但 B2F1R 不能因此取消。它修的是确定的跨租户读取和写入漏洞：A 租户用户可能读取或操作 B 租户任务。这不是未来角色设计，而是多租户系统必须立即守住的隔离底线。

**“角色配置权限”为什么还不够**

角色和权限只回答：

> 这个人有没有“完成工单”的钥匙？

还必须回答：

> 他能完成哪一个租户、组织、仓库、班组或被分配给他的工单？

否则拥有 `task.execute` 的用户可能操作全系统任意工单。正式契约也明确规定“角色只是能力包”，租户和对象范围是另一层：[IDENTITY_ACCESS_MODEL_V1.md](D:/Logixs/.worktrees/feat-authz-default-deny-v1-c2b2/docs/product/domain/IDENTITY_ACCESS_MODEL_V1.md:9)。

正确模型应是：

```text
用户/用户组
→ 角色
→ 能力
→ 数据范围
→ 具体动作的业务前置条件
```

新增角色通常只组合既有能力和范围，不需要改 Controller。

**现在不应一步到位的内容**

不需要现在定义全部未来角色，也不需要一次实现：

- 所有工作台的组织、地点和岗位范围
- 所有动作的四眼复核
- 所有字段级权限
- 完整权限管理后台
- 通用规则引擎
- 独立权限微服务

这些规则应随每台工作台推进，只实现真实岗位已经确认的部分。

**当前真实实现**

目前还不是完整的可配置权限机制：

- 已有 8 个最小角色，但硬编码在 [role-capabilities.ts](D:/Logixs/.worktrees/feat-authz-default-deny-v1-c2b2/apps/api/src/modules/identity/domain/role-capabilities.ts:9)。
- `CapabilityCode` 还是普通 `string`。
- OIDC Token 可以携带角色或 capability，但仓库不能证明生产 IdP 如何配置、审批和审计。
- 身份上下文只有租户、角色和能力，没有组织、地点、assigned、owned 和策略版本。
- 数据库没有角色、权限、授权范围等正式模型。
- `ActionDefinitionV1` 契约已存在，但目前只有一个真实动作进入目录。

所以不能声称“权限配置机制已经完成”。

**要不要专门权限模块**

建议采用中间方案：

> 在现有模块化单体中建立小型 `access-control`/授权策略模块，但不建设独立服务，也不阻塞当前安全 PR。

职责边界：

- `IdentityModule`：确认“你是谁”、Token 是否可信。
- 授权策略模块：计算“你能做什么、能操作哪些对象”。
- 各业务模块：判断“当前业务状态是否允许做”。
- 前端：只展示服务端返回的允许动作，不自行算权限。

权限模块第一版只需要：

1. 单一 capability 目录。
2. 角色到 capability 的版本化配置。
3. 用户/用户组到角色及范围的授权关系。
4. 有效权限解析接口。
5. 变更审批、审计、生效时间和失败关闭。

不要把物流状态、费用规则、证据资格等业务判断塞进权限模块，否则它会变成新的巨型模块。

**建议收缩当前任务**

1. 完成 B2F1R 的确定性跨租户漏洞。
2. 确认所有路由默认拒绝、能力声明和静态门禁有效。
3. 将 `AUTH-B2-03`～`12` 中非租户隔离事项拆回对应身份基础或业务工作台切片。
4. 合并当前安全 PR，不再要求它完成全部未来角色和对象策略。
5. 下一任务建立最小授权配置机制；之后每台工作台按真实岗位逐步增加角色、范围和动作。

最终原则是：

> **一次做好机制和租户隔离，不一次猜完所有角色；角色可配置，能力码受控，范围随岗位落地，业务规则留在业务模块。**

结论先说清：**当前仓库已经定义了 20 个业务工作台的岗位、目标和交接链，但还没有为每个工作台完整固化“行业最佳实践操作规范”。**

现状是：

- 20 个工作台都有岗位结果和上下游交接定义：[workbenchNetwork.ts](/D:/Logixs/apps/web/src/data/workbenchNetwork.ts:192)
- 12 个标记为 `live`
- 只有 11 个具备详细的 `allowedActions / systemDoes / missingHandling / discipline` 操作规格：[workbenchNetwork.ts](/D:/Logixs/apps/web/src/data/workbenchNetwork.ts:471)
- **寻源已经标记 live，却还没有岗位操作规格**
- 需求补货、采购履约、生产验货、出运计划、海运运营、还箱、费用、异常中心仍主要是框架级定义

所以不能声称“每个工作台的最佳实践已经定完”。下面才是我基于项目目标和行业规范整理出的应有基线。

**行业底座**

行业实践不应直接变成菜单或页面，而应成为业务控制规则：

- [ASCM SCOR DS](https://www.ascm.org/corporate-solutions/standards-tools/scor-ds/)：以 Orchestrate、Plan、Order、Source、Transform、Fulfill、Return 组织端到端供应链。
- [GS1 Traceability](https://www.gs1.org/standards/traceability)：以稳定对象标识、关键追踪事件 CTE、关键数据 KDE 建立跨伙伴追溯。
- [GS1 GTIN](https://www.gs1.org/standards/id-keys/gtin)：产品、贸易项和地点使用稳定可交换身份。
- [DCSA Track & Trace](https://dcsa.org/standards/track-and-trace)：海运计划、预计、实际事件采用统一语义，保留来源和更新时间。
- [WCO 跨境电商标准框架](https://www.wcoomd.org/en/topics/facilitation/instrument-and-tools/frameworks-of-standards/ecommerce.aspx)：提前电子数据、风险管理、税费、清关和跨境参与方协同。
- [ICC Incoterms](https://iccwbo.org/business-solutions/incoterms-rules/)：明确买卖双方任务、成本和风险转移边界。
- [Stage-Gate](https://www.stage-gate.com/about/stage-gate-innovation-performance-framework/)：产品创新采用分阶段证据和门禁，不把活动完成冒充立项或发布。
- [OMG BPMN](https://www.omg.org/spec/BPMN/2.0.2/About-BPMN)：角色、事件、等待、分支、补偿和结束条件必须能被业务和系统共同理解。
- [ISO 9000](https://www.iso.org/standards/popular/iso-9000-family)：客户结果、过程方法、证据决策、持续改进和责任闭环。

这些来源支持方法，不替代 Logix 自己的业务定案。

| 异常中心 | 跨域协调，但把结果归还权威业务域 | 异常不是万能状态；必须关联对象、来源事实、影响、等级、责任人、SLA、临时控制、根因和恢复条件；关闭需证据；异常中心协调，最终业务事实仍由原领域写入 |

**所有工作台共同必须具备**

1. 一个岗位结果、一个主选择源、一个当前主动作。
2. 上游交接、本岗新建、批量导入三类入口按实际适用。
3. 回退/重开、作废/归档、受限删除三层退出能力。
4. 当前责任人、下一责任人、截止时间和等待原因。
5. 事实、缺口、异常、外部观测和同步状态分轨。
6. 正常对象批量处理，异常对象逐条恢复。
7. 每次交接使用不可变快照，明确版本、来源、发送方、接收队列和待补事项。
8. 指标衡量业务结果与流动效率，不统计按钮点击和页面访问冒充绩效。
9. AI 只能做匹配、摘要、建议和风险排序；业务判断、责任确认和状态推进必须由规则或人员完成。
10. 验收必须让真实岗位拿真实样本走完正常、等待、拒绝、冲突、返工和恢复路径。

最需要补齐的不是再画一轮页面，而是把上表逐台变成与现有 11 台相同格式的正式岗位操作规格。优先顺序应为：**寻源规格缺口 → 当前 NPI/选品闭环 → 需求与补货 → 采购履约 → 生产验货 → 出运计划 → 海运运营 → 还箱 → 费用 → 异常中心**。这能确保后续 UI 不再依赖开发者临场理解行业流程。


这两个门槛分别解决两个最基本的问题：

1. **谁可以做**
2. **页面应该依据什么让他做**

它们不是要把系统做到完美，而是先把地基固定，避免继续改一台坏一台。

**门槛一：授权默认拒绝**

现在系统存在一种风险：用户只要已经登录，部分接口没有写明需要什么权限，就可能被放行。

用人话说，相当于：

- 公司大门有门禁，证明进来的人是员工。
- 但里面部分财务室、证据室、费用修改室没有单独上锁。
- 当前工作就是给每扇门登记用途和钥匙，未登记的门一律锁住。

其中几个技术词实际是：

- **路由清单**：列出系统所有可以调用的接口，也就是所有“门”。
- **逐路由 capability**：明确每扇门需要哪把“钥匙”，例如只能看、可以操作货柜、可以修改费用。
- **Guard 默认拒绝**：没有明确登记钥匙的接口，系统必须拒绝，而不是因为用户已登录就放行。
- **错误契约**：被拒绝时统一告诉前端“权限不足”，带追踪编号，不能有的页面报 403、有的白屏、有的泄露内部错误。
- **CI 门禁**：以后开发者新增接口但忘记写权限，代码不能合并。

完成后的实际收益是：Cursor 后续增加工作台动作时，不会意外制造一个“登录即可调用”的高风险接口。

这里不追求一次完成最精细的岗位权限。最低完成线只是：**所有接口有明确分类、未声明就拒绝、错误一致、新增接口不能漏标。**

---

**门槛二：共享控制面契约**

现在各工作台容易各自发明一套表达方式：

- A 台叫 `currentOwner`
- B 台叫 `assignee`
- C 台由前端自己判断按钮能不能点
- D 台提交后只返回“成功”，不知道下一步给谁

这就是过去“改 A 坏 B”和页面出现假动作的原因。

共享控制面就是规定所有工作台共用的五种“包装格式”：

| 内容 | 用人话解释 |
|---|---|
| 队列 | 这件事为什么现在轮到我、谁负责、何时到期、卡在哪里 |
| 详情 | 当前事实是什么、来自哪里、哪个版本、是否过期或冲突 |
| 缺口 | 缺什么、是否真的阻断、谁补、从哪里处理 |
| 动作 | 现在允许做什么、为什么不能做、提交时需要什么 |
| 回执 | 是否真正完成、新版本是什么、下一步给谁、如何追踪 |

领域内容仍然各不相同。例如验货有缺陷与抽检数据，海运有船期与提单，费用有账单与币种；共享的只是外围控制信息，不会做成一个包罗万象的大 DTO。

`GC-012` 与“升级 `GC-010`”只是决定这套规则放在哪里：

- **升级 GC-010**：如果 GC-010 原本就负责工作台查询和动作投影，直接扩充最简单，少一份契约。
- **新增 GC-012**：如果 GC-010 的职责不同，硬塞进去会越来越乱，就单独建立工作台控制面契约。

我的取舍标准是：**能在 GC-010 中自然表达且不破坏原语义，就升级 GC-010；否则才建 GC-012。** 不为了编号整洁新增文档，也不为了少一个编号把旧契约塞成杂物箱。

完成门槛也不应扩大为“20 台全部接入”。最低线是：

- 五类信封字段定案；
- JSON Schema 和 TypeScript 类型有一个权威来源；
- 前端不得自行计算权限和允许动作；
- 选一台做参考接入，证明契约可用；
- 其余工作台按顺序迁移。

一句话总结：

- **授权门槛**防止“不该做的人做了”。
- **控制面门槛**防止“每个页面各自猜该做什么”。

两项合入后，就可以正式恢复逐台业务流代码打磨，不需要等到安全体系或 20 台工作台全部达到理想状态。

对。你指出的是核心：**数据、任务、底层技术不是三个先后项目，而是同一件业务事情的三个表达面。**

我前面把它讲成“先完成两个技术门槛，再恢复业务”，容易演变成技术先行的串行工程，这不符合项目本身，也容易继续原地打转。需要修正。

例如“NPI 退回选品”这一件事：

| 面 | 必须回答 |
|---|---|
| 数据 | 退回原因、原结论快照、版本、发送方、接收方、待补事项如何保存 |
| 任务 | 谁发起退回、选品侧谁接收、何时处理、如何重开、完成后交给谁 |
| 技术 | 谁有权退回、状态机是否允许、怎样防重复提交、并发冲突如何处理、如何审计和回执 |

缺任何一面都不算完成：

- 只有数据，是档案库。
- 只有任务页面，是假工作台。
- 只有技术架构，是没有业务落点的平台工程。

因此两个门槛要重新解释。

**授权默认拒绝不是独立安全工程。**  
逐路由登记时必须同时说明：这个接口代表哪个岗位动作、影响哪项权威数据、需要什么能力、还有哪些对象范围和业务条件。不能只机械地给 39 条路由贴 capability。

**共享控制面也不能脱离真实工作台先设计一套完美 Schema。**  
它应该和第一台真实工作台一起长出来。建议用“寻源”作为参考台，因为它是机器权威复审顺序第一位，也是当前最大的运行时规格缺口：

1. 用寻源真实任务验证队列、详情、缺口、动作和回执。
2. 同时明确事实来源、版本、责任和写入结果。
3. 把其中确实跨台共用的部分提炼进 GC-010 或 GC-012。
4. 只做一台参考实现证明契约可用，不提前猜完 20 台差异。
5. 再按统一最低线逐台迁移。

调整后的执行方式是：

- 当前继续完成授权 P0，但路由定权必须绑定业务动作和数据影响。
- 同时可以进行寻源的业务规格、样本和三面映射，不必停等。
- 授权完成后，**共享控制面契约与寻源参考实现同步推进**，不再“先抽象契约、再等业务开工”。
- 寻源跑通后，按既定顺序推进其余工作台。

以后每个 brief 都必须用同一张三面表收口：

```text
岗位任务与结果
→ 所需事实、证据、版本和写入
→ 权限、状态机、事务、接口和回执
```

所以，更准确的恢复条件不是“两项纯技术工程全部做完”，而是：

> 授权底线关闭真实安全漏洞；共享控制面在一台真实工作台中被验证。随后立即恢复逐台业务打磨。

这才符合“数据 + 任务 + 底层技术架构，同一事情三体一面推进”。


正式恢复工作台代码打磨，需要通过两个门槛：
authz-default-deny-v1 完成并合入
路由清单、逐路由 capability、Guard 默认拒绝、错误契约和 CI 门禁全部完成。当前 Cursor 即将执行的切片 A 只是清点，不是完成。
共享控制面契约定案并合入
明确采用 GC-012 还是升级 GC-010，完成队列、详情、缺口、动作、回执信封及 Schema 基线。此时前端才有稳定依据，不再自行猜动作和责任。  这二项是不是要按三体一面 重新定义

是，必须按“三体一面”重新定义。否则原来的两个门槛仍然是“先做技术底座、再做业务”，会再次陷入技术闭环了、工作台仍不能用的局面。

而且原定义有一个逻辑矛盾：**如果共享控制面完全禁止工作台代码参与，就无法证明它适合真实工作台。** 因此应允许一台参考工作台作为门槛二的一部分，禁止的是全面铺开，不是禁止验证。

建议把两个门槛正式改成下面这样。

## 门槛一：业务动作授权闭环 V1

不再只叫“授权默认拒绝”，而是同时完成：

| 一面 | 最低要求 |
|---|---|
| 任务 | 每条路由说明它代表哪个岗位动作；读、写、审批、推进不能混为一类 |
| 数据 | 说明动作影响什么业务对象和权威事实，至少覆盖租户与对象边界 |
| 技术 | 路由显式 capability、Guard 默认拒绝、稳定错误、CI 防漏标 |

最低验收：

- 所有 HTTP 路由完成清点和显式分类。
- capability 与实际岗位动作相符，不是为了通过检查随便贴码。
- 高风险写动作明确数据影响、对象范围和现有业务守卫。
- 未声明权限默认拒绝。
- 错误响应稳定，前端能区分权限拒绝和业务条件不满足。
- CI 阻止新增未分类路由。

这里不要求一次设计出完美 RBAC，也不要求立即拆细所有宽能力码。目标是关闭默认放行，并让“岗位动作、数据影响、技术权限”能够对上。

## 门槛二：工作台任务控制面闭环 V1

不再只是“共享 Schema 定案”，而是：

| 一面 | 最低要求 |
|---|---|
| 任务 | 队列、详情、缺口、动作、回执能支撑一个岗位完成真实结果 |
| 数据 | 事实包含来源、版本、新鲜度、冲突；交接与写回有可靠记录 |
| 技术 | GC-010/GC-012、Schema、类型和 API 投影保持单一权威 |

最低验收：

- 先判断升级 GC-010 还是建立 GC-012，不重复定义。
- 五类信封只规定真正跨工作台共用的字段。
- `allowedActions`、责任人和阻断原因由服务端给出，前端不猜。
- 选择“寻源”作为参考工作台，走通正常、等待、拒绝、冲突、返工、恢复六类路径中的代表样本。
- 证明契约可用后才冻结 V1，并允许其余工作台逐台接入。
- 不要求门槛二完成时迁完 20 台。

## 恢复边界

新的执行边界应是：

1. 门槛一完成前：可以做业务澄清、数据映射和测试设计，不合入新的高风险业务动作。
2. 门槛一完成后：启动“共享控制面 + 寻源参考实现”，两者作为同一个三体一面切片推进。
3. 门槛二通过后：正式恢复其余工作台的连续代码打磨。

代价是每条路由和控制面字段都要多回答一个业务问题；收益是不会得到“安全检查全绿但业务不能做”或“Schema 很漂亮但页面无法使用”的假完成。

因此不是增加第三道门槛，而是把原来两个偏技术的门槛改造成两个真实业务闭环。
