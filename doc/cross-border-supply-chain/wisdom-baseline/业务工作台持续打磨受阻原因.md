# 业务工作台持续打磨受阻原因

> 记录日期：2026-10-04  
> 地位：跨工作台诊断基线，不是业务权威，不直接构成实施依据  
> 适用范围：解释项目为何已有大量技术切片和部分工作台能力，却尚未形成逐台持续打磨及正式验收节奏

## 一、结论

项目不是没有推进业务工作台，也不是开发速度不足。

真正的问题是：

**项目持续把“保证未来所有工作台可治理、可授权、可证明、不可漂移”放在“让下一台工作台今天真正可用”之前。**

项目已经交付过市场信号、选品、NPI、主数据、寻源以及多个物流工作台的业务和界面薄片，但始终没有保护其中一台连续完成：

1. 岗位业务目的；
2. 优先损失；
3. 责任与时限；
4. 所需事实和缺口；
5. 服务端允许动作；
6. 拒绝、失败与恢复；
7. 跨工作台接收和责任转移；
8. 界面信息层级与交互打磨；
9. 真实岗位六类路径验证；
10. `operational` 和 `validated` 成熟度确认。

因此出现了明显的剪刀差：

- 技术底座和治理能力不断增强；
- 仓库中有大量已完成技术切片；
- 多台工作台已有页面和生产 API；
- 但正式完成的工作台仍为 0 台。

更准确的描述不是“从未进入工作台打磨”，而是：

> **项目曾短暂进入业务工作台打磨，但没有形成选定一台、持续迭代、直至岗位结果验收的稳定节奏。**

---

## 二、当前工作台成熟度事实

截至本次调查，23 台工作台大致分为：

| 成熟度事实 | 数量 |
| --- | ---: |
| 已进入正式工作台目录 | 23/23 |
| 有独立岗位页面和生产 API 或写路径 | 12/23 |
| 使用通用框架页 | 8/23 |
| 仅为无业务动作的目录占位 | 3/23 |
| 正式达到 `operational` | 0/23 |
| 通过真实岗位验证达到 `validated` | 0/23 |

业务权威明确说明：

- 页面存在不等于工作台通过；
- API 可调用不等于业务闭环；
- 数据已经落库不等于责任已经交接；
- 技术操作规格不等于真实岗位验收；
- 当前没有任何工作台被标记为通过本轮复审。

依据：

- [`../08-role-workbenches.md`](../08-role-workbenches.md) 第 15～23 行；
- [`../08-role-workbenches.md`](../08-role-workbenches.md) 第 44～88 行；
- [`../08-role-workbenches.md`](../08-role-workbenches.md) 第 137～176 行。

所以，当前核心问题不是缺少页面，而是已有能力没有被连续收口成岗位业务结果。

## 三、主要原因

### 1. 实施路线反复切换

2026-09-24 的当前实施路线要求：

> 先完成已出运 Shipment 从接管到还箱关闭。

当时的近期主线是：

- 装箱；
- 出运；
- 海运；
- 清关；
- 提柜；
- 送仓；
- 卸柜；
- 还箱；
- Shipment 关闭。

该路线还明确规定：前端岗位交互是主交付面；数据库、API 和事件只有真正被岗位用于判断和行动时才算交付。

依据：

- [`../../../docs/planning/DOMAIN_VERTICAL_DELIVERY_PLAN.md`](../../../docs/planning/DOMAIN_VERTICAL_DELIVERY_PLAN.md) 第 1～22 行；
- [`../14-roadmap-decisions.md`](../14-roadmap-decisions.md) 第 19～32 行。

但到 2026-10-03，路线切换为：

1. 建立 23 台工作台目录；
2. 建立 GC-012 provisional 公共契约；
3. 完成市场信号到选品交接；
4. 完成选品到 NPI 交接；
5. 完成 stable-V1 资格评审；
6. 再向其他工作台推广。

依据：

- [`../../../docs/superpowers/plans/2026-10-03-gc012-rollout.md`](../../../docs/superpowers/plans/2026-10-03-gc012-rollout.md) 第 37～49 行；
- [`../../../docs/superpowers/specs/2026-10-03-gc12.md`](../../../docs/superpowers/specs/2026-10-03-gc12.md) 第 435～479 行。

这相当于把原本正在推进的下游岗位闭环，重新排到了：

`全局目录 → 公共契约 → 两段上游交接 → 稳定性评审`

之后。

每次接近一段局部闭环，项目就重新回到全局范围、共同口径或统一控制面的定义，导致同一工作台无法连续收口。

---

### 2. 完成标准整体抬高，但没有立即选一台做到新标准

项目后来正确认识到：

- 有页面不等于岗位能完成工作；
- 有正常路径不等于异常可以恢复；
- 有状态字段不等于事实可信；
- 发起交接不等于下游已经接收；
- 按钮可见不等于服务端授权；
- 技术测试通过不等于经营损失已经减少。

因此建立了 `WB-B01`～`WB-B10` 和五面协同最低线。

这项纠偏是必要的，能够防止“页面上线即闭环”的虚假完成。

问题在于：标准抬高之后，没有强制选定一台工作台立即按新标准走到终点，而是先为全部 23 台建立统一目录、公共契约、成熟度规则、检查器和治理流程。

结果是：

- 原有 20 台工作台全部重新进入待评估状态；
- 新的治理规则和证明体系不断增加；
- 正式完成台数仍然是 0。

于是，“防止虚假完成”在执行中演变成了“长期没有真实完成”。

---

### 3. 把“不能宣布完成”误当成“不能继续开发”

当前 `blocked` 混合了至少四种不同状态：

#### 3.1 真正不能编码

例如：

- 岗位业务目的未确定；
- 责任主体未确定；
- 状态语义未确定；
- 退出和退回政策未确定；
- 权限政策未确定。

这些事项只应阻塞依赖相应决定的具体动作。

#### 3.2 可以编码，但不能部署

例如：

- 真实 IdP 尚未完成部署环境冒烟；
- 外部 Temporal 环境尚未完成迁移；
- 生产配置和外部系统证据尚未就绪。

这些事项应阻塞部署或 task `done`，而不是阻塞本地业务实现。

#### 3.3 可以继续实现，但不能宣布 `validated`

例如：

- 尚无真实或脱敏岗位样本；
- 尚未完成六类真实岗位路径；
- 尚无经营 KPI 结果；
- 尚未确认业务损失确实下降。

这些事项应阻塞 `WB-B10`、KPI、上线验收和 `validated`，但不应阻塞边界清楚、可回滚的机制与界面薄片。

#### 3.4 已完成当前薄片，但没有下一片获得预授权

市场信号工作台就是典型实例：

- 当前验证承诺薄片已经合入；
- 数据库、API、Web 和测试均已交付；
- 但 brief 随即回到 `blocked`；
- 没有下一项已批准的 coding slice；
- 后续等待真实验收或新的业务政策定案。

依据：

- [`../../../docs/planning/tasks/market-signals-opportunity-radar-v1.md`](../../../docs/planning/tasks/market-signals-opportunity-radar-v1.md) 第 522～560 行。

这说明当前调度体系经常把：

> “现在还不能宣布完成”

错误地解释成：

> “现在不能继续推进任何下一片”。

---

### 4. 横向治理和基础设施占据了主产品流

近期主要投入包括：

- API 授权默认拒绝；
- 租户隔离和 capability；
- Web OIDC/PKCE；
- 全库数据字典；
- 代理角色映射；
- 独立复审和交接协议；
- 23 台工作台目录；
- GC-012 目录漂移检查器；
- 合并后的状态记录 PR。

这些工作需要分为两类。

#### 4.1 真实安全或业务前置

以下内容是必要的：

- 写接口默认拒绝；
- 租户隔离；
- 服务端 capability；
- 生产身份认证链；
- 接收、拒绝和退回；
- 不可变交接；
- 唯一责任主体；
- 幂等、并发和事务保障。

缺少这些能力，会造成越权、跨租户访问、重复写入或责任悬空。

#### 4.2 有治理价值，但不是首台工作台打磨前置

以下内容不是第一台岗位闭环的共同前置：

- 完成全部 112 张表、1,589 个字段的数据字典；
- 先把 23 台工作台全部纳入统一目录；
- 为目录表达建立复杂的 AST 防绕过门禁；
- 先完成全部成熟度登记；
- 反复调整代理角色、模型家族和交接格式；
- 每次功能 PR 合并后再建立独立状态 PR。

这些事项并非毫无价值，但它们使用了与业务工作台相同的设计、复审、集成和决策带宽。

名义上的并行无法消除主代理仍是共享瓶颈这一事实。

---

### 5. GC-012 的最小真实依赖被扩大成平台级串行前置

市场信号到选品、选品到 NPI 的确需要：

- 不可变交接；
- 接收、拒绝和退回；
- 唯一责任主体；
- 交接后的退出能力；
- 双方都能看到的结果回执。

这是跨工作台闭环的真实依赖。

但这不等于必须先完成：

- 全部 23 台目录；
- 全局统一成熟度体系；
- 全部公共契约；
- 两个消费者的完整迁移；
- stable-V1 资格评审；
- 再开始其他工作台的业务打磨。

仓库规则明确要求：

> 跨工作台抽象必须由至少一个真实业务动作验真；参考实现通过后即可逐台推广，不以先覆盖全部工作台为前置，也不得脱离消费者建设完美平台。

依据：

- [`../../../AGENTS.md`](../../../AGENTS.md) 第 27～29 行。

GC-012 的正确定位应当是：

> 跟随“市场信号 → 选品”真实交接逐步生长的最小公共能力。

而不是：

> 所有工作台继续推进之前必须完成的平台。

---

### 6. UI 被安排在技术链末端，而不是与业务步骤共同交付

GC-012 的实施计划把 UI 排在长串前置之后。

典型顺序是：

1. 业务政策定案；
2. Schema；
3. 数据库迁移；
4. 持久化；
5. Adapter/API；
6. 事务语义；
7. Web UI；
8. 测试和评审。

依据：

- [`../../../docs/superpowers/plans/2026-10-03-gc012-g2-market-selection.md`](../../../docs/superpowers/plans/2026-10-03-gc012-g2-market-selection.md)；
- [`../../../docs/superpowers/plans/2026-10-03-gc012-g3-selection-npi.md`](../../../docs/superpowers/plans/2026-10-03-gc012-g3-selection-npi.md)。

这会造成：

- 前置政策未定时，UI 完全不启动；
- 岗位动线无法提前暴露业务理解错误；
- 服务端投影和界面信息层级不能同步校正；
- UI 只能以大批次进入；
- 视觉打磨长期被视为“最后统一处理”。

但工作台五面协同要求，UI 不应是技术链末端，而应与同一业务步骤中的岗位任务、数据事实、技术保障和权限边界同步推进。

---

### 7. 治理和复审流程本身成为了主要交付对象

GC-012 G0 是最明显的案例。

该切片：

- 约 26 个提交；
- 涉及 37 个文件；
- 约 5,000 余行变更；
- 主要投入在计划、spec、brief、检查器和测试；
- 产品运行时代码主要是目录拓扑和无业务动作的占位页。

G0 自己明确声明：

- 不新增 GC-012 Schema；
- 不修改数据库和生产 API；
- 不新增生产交接动作；
- 不构成任何工作台的 `WB-B` 最低线；
- 不构成业务闭环或上线验收。

依据：

- [`../../../docs/planning/tasks/gc012-g0-catalog-v1.md`](../../../docs/planning/tasks/gc012-g0-catalog-v1.md) 第 4～10 行；
- [`../../../docs/planning/tasks/gc012-g0-catalog-v1.md`](../../../docs/planning/tasks/gc012-g0-catalog-v1.md) 第 69～81 行。

但 G0 经历了：

- 多轮 finding；
- 多轮返工；
- 正则检查器改为 AST；
- AST 绕过修复；
- 运行时路由覆盖；
- 占位页控件计数；
- 多次 brief 状态回写；
- 合并后再次建立状态 PR。

依据：

- [`../../../docs/planning/tasks/gc012-g0-catalog-v1.md`](../../../docs/planning/tasks/gc012-g0-catalog-v1.md) 第 146～209 行；
- [`../../../docs/planning/tasks/gc012-g0-catalog-v1.md`](../../../docs/planning/tasks/gc012-g0-catalog-v1.md) 第 215～227 行。

这些工作提高了目录可靠性，但没有增加岗位可以完成的业务动作。

问题不在于评审没有价值，而在于治理对象被不断强化，逐渐占据了原本应留给业务工作台的主调度。

---

### 8. 真实样本和负责人决策确实不足，但阻塞范围过宽

当前真正缺少的业务输入包括：

- 真实或脱敏的正反案例；
- 岗位责任人；
- 业务时限；
- 交接后谁退出、谁接收；
- 拒绝和退回后的恢复路径；
- 可信事实门槛；
- 结果 KPI；
- 六类真实岗位路径。

这些内容确实是 `validated` 和生产上线的真实依赖。

但它们不应阻止：

- 已确定口径的服务端岗位投影；
- 缺口和拒绝原因展示；
- 结果回执；
- 恢复入口；
- 不依赖待定政策的可回滚动作；
- 使用 synthetic 数据验证机制和 UI。

因此，当前问题不是“缺少样本，所以什么也做不了”，而是：

1. 负责人决策和真实样本吞吐不足；
2. 任务没有把待定事项拆成只阻塞受影响动作；
3. 当前薄片完成前，没有准备不依赖这些决定的下一片。

## 五、需要保留的边界

### 5.1 不能把所有基础设施认定为浪费

以下事项是受保护写动作上线的真实前提：

- 默认拒绝；
- 租户隔离；
- 服务端授权；
- OIDC 身份链；
- 幂等；
- 并发控制；
- 事务；
- 数据迁移验证。

纠偏目标不是取消这些能力，而是只让它们阻塞实际依赖它们的业务动作。

### 5.2 GC-012 G0 不是零价值

G0 建立了：

- 23 台正式目录；
- fan-in/fan-out 拓扑；
- 三台 planned 页；
- 成熟度防误标；
- 目录和运行时路由防漂移。

问题主要在于它的投入比例和串行位置，而不是该工作完全无价值。

### 5.3 业务工作台并非完全没有推进

市场信号的“单一当前验证承诺”是最明显的正向实例，它同时交付了：

- 数据库迁移；
- 领域和应用逻辑；
- API；
- Web UI；
- 跨刷新和跨班次恢复；
- 冲突处理；
- 窄屏和键盘路径；
- E2E 与集成测试。

此前市场关闭态、市场到选品投影、选品页面 Mode、NPI 阶段轨和退回、寻源准入与事实修正也都属于真实业务/UI 推进。

因此不能得出“团队只写文档”的结论。

准确判断是：

> 真正的业务薄片存在，但数量较少，被很重的治理和验证成本包围，而且合入后没有连续安排下一片。

### 5.4 Git 次数不等于精确工时

上述统计基于：

- commit subject；
- 分支和 PR 主题；
- 文件路径；
- task brief 状态；
- 本地 Git 历史。

它们能够说明投入方向，但不能直接换算为人时或开发效率。

## 六、根因排序

按影响程度排序：

1. **实施路线反复切换，优先级权威并存。**
2. **完成标准抬高后，没有立即选定一台做到新标准。**
3. **把最小跨台依赖扩大成平台级串行前置。**
4. **把上线和验收阻塞错误传播成编码阻塞。**
5. **治理、复审和状态维护占用了过多主调度。**
6. **UI 被安排在技术链末端，而不是五面同步交付。**
7. **真实业务决策和样本吞吐不足。**
8. **完成当前薄片之前，没有预授权下一业务薄片。**

一句话归因：

> **项目一直在完善所有工作台的开工条件、治理规则和证明体系，却没有保护一台工作台从岗位目的连续走到真实验收。**

---

## 七、纠偏原则

### 7.1 不再新增新的总治理层

当前最缺的不是另一份全局规范、统一目录或检查器，而是第一台正式达到 `operational` 的工作台。

新的横向能力必须由当前真实业务动作证明其必要性。

### 7.2 固定一条业务路线

建议选择当前已经最接近闭环的：

> `市场信号 → 选品`

在该路线达到 `operational` 之前，不再因新的全局治理主题切换主线。

### 7.3 GC-012 只实现真实消费者所需的最小能力

当前只实现市场信号到选品真正需要的：

- 交接事实；
- 版本；
- 接收；
- 拒绝；
- 退回；
- 唯一责任主体；
- 结果回执；
- 退出和恢复。

不得把全部 23 台未来可能需要的能力提前装入当前切片。

### 7.4 五面在同一业务步骤中同步推进

每一片必须同时回答：

- 哪个岗位；
- 完成什么业务结果；
- 减少什么损失；
- 需要哪些事实；
- 服务端允许什么动作；
- 权限边界是什么；
- 界面如何呈现优先事项、缺口、动作、回执和恢复。

UI 不再作为 Schema、API 和所有政策完成后的最后阶段。

### 7.5 将任务状态分轨

建议至少区分：

- `code-ready`：可以继续编码；
- `owner-decision`：只阻塞依赖负责人决定的动作；
- `validation-blocked`：实现完成，等待真实样本或岗位验收；
- `deploy-blocked`：代码可合并，部署条件未满足；
- `review`：正在技术复审；
- `operational`：目标岗位可完成业务结果；
- `validated`：真实岗位六类路径和结果证据通过。

不得继续用单一 `blocked` 表达所有状态。

### 7.6 每个薄片必须有预授权的下一片

当前薄片进入 review 前，应明确：

- 下一片是什么；
- 是否依赖负责人决定；
- 如果依赖，哪些不相关部分仍可继续；
- 哪些真实样本只阻塞验收；
- 哪个任务将保持在途。

不得出现一个业务薄片合并后，所有工作台任务同时回到 `blocked`。

### 7.7 视觉打磨必须绑定业务切片

界面品质不再作为以后统一处理的独立项目。

每个业务薄片同时完成与该业务步骤直接相关的：

- 信息层级；
- 优先队列；
- 缺口呈现；
- 主动作；
- 拒绝原因；
- 结果回执；
- 恢复入口；
- 桌面和窄屏；
- 键盘操作；
- 加载、空状态、冲突和失败状态。

视觉调整必须服务岗位决定和动作，不以装饰制造完成感。

---

## 八、纠偏后的结果指标

后续不再用以下指标判断项目是否推进：

- 新增多少规则；
- 新增多少目录项；
- 新增多少 Schema；
- 新增多少检查器；
- 新增多少测试；
- 合并多少 PR；
- 完成多少技术 task brief。

改用以下指标：

1. 是否始终至少有一台工作台处于连续业务实现队列；
2. 是否出现第一台正式 `operational`；
3. 是否能由目标岗位完成正常、等待、拒绝、冲突、失败和恢复路径；
4. 是否完成跨工作台接收和唯一责任转移；
5. 是否有真实或脱敏样本完成岗位验收；
6. 是否出现第一台正式 `validated`；
7. 每个横向能力是否由真实业务消费者证明必要性。

---

## 九、建议的近期执行顺序

建议近期只推进以下顺序：

1. 固定“市场信号 → 选品”为当前主线；
2. 核对两台工作台已有业务目的和优先损失；
3. 只列出影响下一动作的负责人决定；
4. 实现最小交接、接收、拒绝、退回和责任转移；
5. 同片补齐服务端岗位投影；
6. 同片完成页面信息层级和交互打磨；
7. 使用 synthetic 数据验证机制和 UI；
8. 使用真实或脱敏样本完成岗位验收；
9. 将市场信号或选品中的第一台提升为 `operational`；
10. 真实验证通过后提升为 `validated`；
11. 再把已验证的最小模式推广到下一段交接。

在该链条形成第一台 `operational` 之前，不再把以下事项放到主线前面：

- 全量 23 台统一扩写；
- 新的全库治理项目；
- 不绑定真实消费者的公共平台；
- 独立视觉翻新工程；
- 仅记录状态的独立 PR；
- 对未变化风险面重复执行完整门禁或 fresh review。

## 十、事实与推断边界

### 已证实事实

- 项目已经交付过多台工作台的业务和 UI 薄片；
- 当前没有工作台通过本轮正式成熟度复审；
- 当前没有工作台达到正式 `operational` 或 `validated`；
- GC-012 G0 不交付生产交接动作，也不构成工作台闭环；
- GC-012 G1～G3 被安排为串行后续步骤；
- 当前 task brief 中没有持续在途的 `coding/review/fix` 业务队列；
- 最近交付中治理、授权、测试和目录投入占比较高；
- 市场信号真实业务薄片合并后没有连续批准下一 coding slice。

### 基于证据的判断

- 最大瓶颈不是底层技术能力，而是路线和调度顺序；
- 项目多次把“不能验收”解释成“不能继续开发”；
- 公共能力被过早扩大成平台级前置；
- 治理和复审流程已经部分成为主产品流；
- 只有保护一台工作台连续走到 `operational/validated`，才能真正改变当前状态。

---

## 十一、最终判断

项目当前最需要的不是继续证明“系统未来不会漂移”，而是证明：

> **一个真实岗位今天可以依靠这套系统完成业务结果，并且在等待、拒绝、冲突和失败后仍然能够恢复。**

只要仍然没有一台工作台连续走到这个结果，即使目录、Schema、权限、测试和治理继续增长，也不能认为项目已经进入业务工作台成品化阶段。
