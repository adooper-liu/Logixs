**核心业务目的**

现行业务权威已确定：异常中心不是“统一工单控制面”，而是让跨工作台、无法在正常路径内解决的异常获得明确承接和专业处置，并把可继续执行的结果归还原业务域。

唯一核心结果建议表述为：

> 在最早业务期限造成实际损失前，使跨域异常得到有效处置或经批准的风险接受，并让原工作台能够继续、重算或明确停止。

这比“异常已分派”“案件已关闭”更严格。分派和关闭只是过程，不是业务成功。

**优先减少的损失**

目前权威能够支持、但尚无真实样本量化的三类候选损失是：

1. **期限穿透损失**：异常迟迟无人承接，错过清关、提柜、送仓、还箱、免费期或客户承诺时间，形成滞箱、堆存、延期交付等损失。
2. **主流程持续阻断损失**：异常已有处理动作，但结果未归还原工作台，导致货柜、Shipment、库存或履约继续等待。
3. **错误纠偏损失**：协同人员越过专业域，用备注或非权威结论修改清关、费用、生命周期事实，造成错误放行、错误核费或错误推进。

第 1、2 类有直接项目权威依据；第 3 类有明确禁止性依据，但实际发生频率与金额未知。

**已证实事实**

- **负责人已定政策**：异常中心是 20 台工作台之一，属于支撑工作台；岗位结果是“集中分派跨域异常并把处理结果归还权威业务域”。见 [08-role-workbenches.md (line 104)](D:/Logixs/doc/cross-border-supply-chain/08-role-workbenches.md:104)。
- **负责人已定政策**：优先关注阻断主流程、临近法定或费用期限、高影响、长期未处理异常；异常中心不拥有清关、费用、生命周期等专业结论。见 [08-role-workbenches.md (line 441)](D:/Logixs/doc/cross-border-supply-chain/08-role-workbenches.md:441)。
- **负责人已定政策**：处理完成必须是原因解决，或形成获批准且可追溯的风险接受；解除后由原工作台继续、重算或升级。
- **已接受 ADR**：`exception-management` 是支撑模块，不拥有专业业务结论。见 [ADR-010 (line 30)](D:/Logixs/docs/architecture/decisions/ADR-010-bounded-context-modules.md:30)。
- **当前物理事实**：已有独立异常案件表，只覆盖货柜/Shipment、来源、严重度、四种技术状态、摘要、证据引用和解决时间；数据库字典把大多数业务用途标为“待业务确认”。见 [schema.prisma (line 1263)](D:/Logixs/database/schema.prisma:1263)。
- **当前实现差距**：`exception-management` 模块为空壳，没有专用应用服务、API 或业务测试；现有异常数据只被货柜详情和 Shipment 风险队列读取。
- **当前界面差距**：`/workspaces/exceptions` 是明确标注“业务能力待接通”的框架页；实时工作台的异常集合固定为空。
- **样本事实**：仓库明确记录“无真实脱敏异常样本”；前端两条异常记录是演示种子，不能证明真实损失、岗位或时限。见 [NODE_PDCA_VALIDATION.md (line 18)](D:/Logixs/docs/product/domain/NODE_PDCA_VALIDATION.md:18)。

**当前损失形成机制**

当前可证明的是“形成损失的可能链条”，不是已经量化的损失事实：

```
专业域发现跨域问题
→ 原岗位无法单独消除
→ 承接岗位不明确、补证或决定等待
→ 最早法定/费用/履约期限继续逼近
→ 主流程、到仓或库存可用性延后
→ 产生额外费用、客户延期或错误业务决定
```

另一个已被权威明确防范的链条是：

```
异常协同人员直接修改专业事实
→ 原专业域未确认
→ 生命周期、费用或清关判断使用错误结果
→ 错误推进、错误核费或重复返工
```

目前没有可引用样本证明每条链的发生次数、等待时长、损失金额或主要责任断点。

**行业候选与项目边界**

行业候选通常有三种责任形态：中央异常协调、专业域自行负责、运营值班经理统筹。它们只能作为组织方案候选，不能冒充项目事实。

项目边界已经比较清楚：

- 上游原工作台负责报告对象、来源事实、影响和专业缺口。
- 异常中心负责跨域承接、协调、升级以及结果归还。
- 原专业域负责确认专业结论。
- 原工作台负责根据返回结果继续、重算或停止。
- 费用结算负责金额核定；生命周期域负责流程事实；绩效改善负责长期供应商或规则改善。
- 异常中心不能把“案件关闭”直接等同于上述结果已经发生。

**2～3 个业务方案**

**R1：中央异常协调岗，推荐**

目标岗位是专职或轮值的异常协调员；对跨域异常的承接、催办、升级和结果归还负责，但不替专业域下结论。

- 证据：最符合“集中分派、升级、归还”的现有权威。
- 收益：跨域事项有唯一协调责任，期限和悬空问题最容易暴露。
- 成本：必须存在真实可排班、可问责的岗位。
- 风险：容易膨胀成万能客服或工单管理员。
- 边界：只对恢复协调结果负责，不对清关、费用等专业正确性负责。
- 可逆性：高；若业务量不足，可改为运营岗位轮值。

**R2：原业务域负责人主责**

不设中央岗位；异常中心只是各专业负责人共同使用的跨域视图，发现异常的业务域持续负责到结果返回。

- 证据：专业事实本来就归原业务域，能减少责任转手。
- 收益：专业责任最直接，不需要新增组织岗位。
- 成本：跨多个业务域时需要自行协调，管理负担分散。
- 风险：最容易出现“每个域都只完成自己部分，但无人对恢复负责”。
- 边界：异常中心不拥有独立业务责任。
- 可逆性：高；出现大量悬空案件后可升级为 R1。

**R3：运营值班经理主责**

由运营经理或值班经理负责高影响异常的优先级、资源协调和风险接受，普通异常仍归专业域。

- 证据：权威要求优先处理高影响、临期和长期未处理事项。
- 收益：重大异常升级迅速，适合异常量较少但影响较大的阶段。
- 成本：占用管理人员时间，日常案件可能得不到持续跟进。
- 风险：异常中心变成升级会议入口，基层恢复动作仍悬空。
- 边界：只承接重大或升级案件。
- 可逆性：中；后续需要重新划分普通案件责任。

**最低保障**

无论选择哪种岗位形态，以下要求不可关闭，但不作为产品目标：

- 专业事实只能由权威业务域确认，异常中心不得越权改写。
- 租户隔离、服务端授权和未知值拒绝。
- 来源事实、处理决定、纠偏结果、风险接受和关闭证据可追溯。
- 无法判断时保持开放并升级，不以默认值或自由文本伪造结论。
- “已分派、已回复、案件关闭、原流程已恢复”必须保持不同事实。
- 失败后能够重新打开、重新交接或回到原业务域处理。

**推荐及结果指标**

推荐 **R1**，但成立条件是确有一个可以承担日常跨域协调的岗位或轮值机制。若现实组织中不存在该岗位，应选 R2，而不能在系统里虚构“异常协调员”。

在负责人选定岗位和优先损失前，结果指标只能作为候选：

- 在最早法定、费用或履约期限前完成“有效归还”的异常比例。
- 从异常发现到原工作台确认可继续、重算或停止的中位数及 P90 时长。
- 因异常处理延迟实际发生的滞箱、堆存、延期交付或错失库存可用金额/次数。
- 归还后再次因同一缺口被退回的比例。
- “案件已关闭但原业务仍阻断”的数量，目标应为零。

真实样本至少需要覆盖：临近费用期限、跨两个以上专业域、结论被驳回或补证、无法恢复而接受风险、关闭后成功回到原工作台五类案例。

- 可逆性：高，但早期责任选择数据可能不可靠。

**RS3：按异常类别固定主责**

- 每类异常预先绑定 R1、R2 或 R3，例如专业资料问题归 R2、跨域恢复归 R1、重大风险接受归 R3。
- 收益：分派稳定、培训成本低。
- 成本：必须先取得足够真实样本并建立可信分类。
- 风险：当前没有异常样本，立即采用会把假设固化成错误政策。
- 边界：类别不明时仍需兜底责任。
- 可逆性：中，调整会影响历史统计和组织习惯。

**最低保障**

- 任一时点只能有一个明确的协调责任岗位。
- 专业事实仍由原业务域确认。
- 升级不等于转移专业责任。
- R3 的风险接受必须可追溯，并说明影响对象和恢复条件。
- 转交失败、拒绝或无人接收时不得清空原责任。
- 案件关闭不能代替原工作台确认已恢复。
