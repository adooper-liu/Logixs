## 总体结论

项目目前处于：

> **技术底座已较完整，但业务工作台仍处于逐台复审和闭环验收初期。**

现在已经具备数据库、公共契约、生命周期、任务工单、可靠消息、导入、授权默认拒绝、数据字典和多个纵向工作台实现；但按最新业务权威口径，**20 个正式工作台目前没有任何一个被认定为“通过本轮复审”**。已有页面、API 或正常路径可运行，都不能单独算业务闭环完成，见 [岗位工作台:14-22](doc/cross-border-supply-chain/08-role-workbenches.md#L14-L22)。

所以当前不能用一个“项目完成百分比”准确描述。更合理的判断是：

- **工程底座：中后期**
- **生产认证与安全收口：接近完成，但仍有阻断**
- **上游产品链工作台：已有若干薄片，完整业务闭环尚早**
- **出运后工作台：纵向实现较多，但需要按新标准重新验收**
- **完整产品可生产使用：尚未达到**

### 1. Web OIDC/PKCE 会话：当前第一技术关键路径

Web OIDC 工作树正在 `fix`，尚无 PR，且有大量未提交实现：

- 68 个 tracked 修改；
- 19 个未跟踪实现文件；
- 当前 HEAD 仍是旧基线；
- 相对最新 main 已落后约 33 个提交，最终集成前必须同步 main。

A/B/C 的主要能力已经实现：

- OIDC Authorization Code + PKCE；
- 统一 API Client；
- Bearer Token 注入；
- development 身份与生产 OIDC 分离；
- 旧固定开发身份和各 API 直接 fetch 迁移；
- 登录、callback、401/403、注销及 focused OIDC E2E；
- focused OIDC E2E 5/5；
- Web 单测 613 项通过。

但 C3 独立安全复审确认一项高危阻断：

> `vite build` 在继承 `NODE_ENV=development` 且配置 development auth 时仍可成功生成带固定开发身份的部署制品。

证据位于：

- [config.ts:67-86](../feat-web-oidc-session-v1/apps/web/src/auth/config.ts#L67-L86)
- [vite.config.ts:8-22](../feat-web-oidc-session-v1/apps/web/vite.config.ts#L8-L22)

必须在 Vite `command === "build"` 边界强制：

- 所有 build 只允许完整 OIDC 配置；
- development auth 在生成任何资产前失败；
- 不依赖 `NODE_ENV` 判断是否为部署制品。

第二个阻断是依赖审计。但该结果来自旧基线；数据库字典 PR #115 已把相关 `brace-expansion` 和 `@grpc/grpc-js` high 修复合入 main。因此正确顺序是：

1. 修复生产构建边界；
2. 同步最新 `origin/main`；
3. 重新运行 `pnpm security:audit`；
4. 再判断审计门禁是否关闭。

真实 Keycloak/等价 IdP 冒烟仍是 deployment/done gate，不应伪造完成。

## 当前主要风险

### 1. 文档状态存在漂移

例如 [docs/INDEX.md:62](docs/INDEX.md#L62) 仍把数据库字典写成 `review`，但权威 brief 已是 `done` 且 PR #115 已合并。

此外 INDEX 中一些“待合入”“coding”“设计中”条目已经落后于代码或 brief。今后判断状态应优先：

```text
origin/main 上 task brief frontmatter
→ 已合并 PR 与 CI
→ 代码/测试
→ INDEX 或路线图摘要
```

### 2. 两套路线不要混淆

目前存在两个不同顺序：

- **UI/共享控制面参考顺序**：市场信号先行，选品第二；
- **20 台业务详细复审顺序**：寻源、选品、NPI、需求补货……之后才到市场信号。

两者用途不同，但文档表达容易让执行者误以为冲突。后续 brief 必须明确自己是在做：

- UI 参考验真；
- 还是岗位业务复审。

### 3. 历史路线图已部分过时

[DOMAIN_VERTICAL_DELIVERY_PLAN.md](docs/planning/DOMAIN_VERTICAL_DELIVERY_PLAN.md) 仍写 UI-02A 是当前活动任务，并保留旧的“一次一个 brief”规则；最新仓库已经采用有界并行和五面协同交付。

该路线图可以作为出运后产品主线历史基线，但不应继续单独作为当前调度权威。

### 4. Worktree 数量很多，但多数不是活动任务

当前登记了十多个 worktree，其中很多属于已合并或历史治理分支。它们不代表十多个任务并行推进。

实际生产写主线目前主要是：

1. Web OIDC `C3-FIX`
2. API authz `review` 外部/政策收口

共享控制面及多数业务工作台仍是 blocked。

### P0：关闭 Web OIDC 生产构建漏洞

- 确认生产 Temporal Schedule 迁移；
- 将仍未定的对象范围/职责分离政策分别保留或定案；
- 不要把未来所有细粒度权限继续无限塞进默认拒绝任务；
- 具备证据后把 authz brief 从 `review` 收口。

### P2：启动市场信号参考台 + 共享控制面验真

同步完成：

```text
岗位任务
+ 相关数据事实子集
+ 技术保障
+ 权限边界
+ 界面实现
```

只在市场信号真实读写动作上验证共享信封，不先建设面向20台的完美平台。

### P3：选品作为第二台，验证跨域复用

- 本岗手工新建；
- 回退/重开；
- 作废/归档/受限删除；
- NPI 退回理由可见；
- 重判后只生成并使用最新 handoff；
- 新旧版本和审计不被覆盖。

### P4：按业务复审顺序继续推进

选品/NPI回程闭合后，再推进需求补货、采购、生产验货、出运计划等，避免继续只增加页面或字段而没有岗位结果。
