收益：批量审批效率高，运行结果容易整体对账。

边界：可以作为批量容器和运行审计，不宜成为首页主任务。

**批判性风险**

- 如果三种模式分别创建任务，同一缺货风险可能被批准三次，产生重复采购或重复调拨。

- 批次求出的“全局最优”可能牺牲某个国家或渠道的最低服务要求；数学最优不自动等于业务可接受。
- 缺少批准的目标权重时，把成本、利润、现金、缺货损失和成功概率压成一个总分属于伪精确。

- 硬约束：合规、库存所有权、标签适用性、供应商产能、冻结区、资金上限、数据新鲜度。
- 优化目标：服务水平、缺货损失、贡献利润、增量成本、现金占用、原节点风险。
- 人工政策：哪些目标优先、允许牺牲多少、谁能批准例外。

硬约束不能通过加权被抵消；目标权重也不能由 AI 静默补齐。

项目证据：同时满足运行批次、计算粒度、风险优先队列和多方案拆分规则。
收益：兼顾批量效率、计算追溯和逐项责任，不会重复落账。
成本：需要维护 `运行 -> 单元 -> 风险 -> 方案 -> 执行需求` 的完整版本关系。
风险：聚合规则设计错误会隐藏不可互换库存，必须逐项预检。
边界：视角可切换；身份、权限、状态和审计不能随视角变化。
可逆性：高，可以调整界面和聚合算法，不改变已经批准的决定。

**方案 2：三种独立业务模式，由用户自由选择**

每种模式拥有自己的任务、状态和批准动作。

风险：重复承诺、状态漂移和通过切换模式绕过控制的概率很高。
边界：只有三类流程确实拥有不同业务结果时才成立；当前证据不支持。
可逆性：低，产生执行事实后很难重新合并。

**方案 3：由优化器自动选择粒度和处理模式**

系统根据风险规模自动决定逐格、逐事件还是整批处理。

收益：正常项可以高度自动化，理论效率最高。
成本：需要成熟样本、稳定参数、可信目标函数和可解释聚合算法。
风险：当前项目没有足够事实证明自动选择可靠，容易形成不可解释的黑箱。
边界：更适合作为后续建议能力，不能直接批准或释放执行需求。
可逆性：中等，但错误自动决策的业务影响可能不可逆。

**推荐及理由**

推荐方案 1，并将你的“可选择”精确定义为：

- 可选择查看和分析层级；
- 可选择批量还是逐项处理；
- 可组合多个执行方案；
- 不可选择另一套事实、权限或落账语义。

求优过程建议采用“硬约束先过滤，再展示多个非支配方案及影响差异”，而不是立即压成一个神秘总分。负责人批准目标优先级后，才能进一步形成稳定排序。

**对岗位与界面的影响**

首页默认风险事件视角；用户可切到计划批次处理正常项，也可下钻预测单元检查来源。批量提交必须先逐项预检，异常自动退出批量并进入风险任务。无论从哪个视角发起，最终回执都指向同一个补货决定及其执行需求。

建议把你的意见收敛为方案 `1`。请确认 `1`，或选择 `2/3`。确认后，下一轮讨论多目标求优采用“单一加权分、政策场景组合，还是 Pareto 方案集”。

**核心判断**

已收敛的新决定是：

- 批次、预测单元和风险事件作为三个可切换视角共存；
- 三者共用同一套事实、权限、状态和审计；
- 批量处理正常项，异常退出批次后逐项处理；
- 最终批准只落到风险事件及其方案组合。

该结论仍需 Claude 写回业务权威和 task brief。下一项决定是“多目标求优如何产生推荐”。

**已证实事实**

补货岗位目标同时考虑服务水平、库存风险、贡献利润和现金占用，不是单目标最小成本。[专题规格 (line 111)](D:/Logixs/doc/cross-border-supply-chain/03-sourcing-and-replenishment-workbenches.md:111)

方案必须比较时间、成本、缺货损失、现金占用、平台与合规限制，以及对其他库存节点的影响。[专题规格 (line 180)](D:/Logixs/doc/cross-border-supply-chain/03-sourcing-and-replenishment-workbenches.md:180)

AI只能建议、解释和排序风险，不能替人员批准、下单或突破冻结区。[业务基线 (line 79)](D:/Logixs/doc/cross-border-supply-chain/17-confirmed-upstream-business-baseline.md:79)

**行业对照与项目差距**

Oracle 提供库存政策比较、模拟、库存再平衡、例外和采购建议，说明成熟计划系统通常保留多个方案及其政策依据，而不是只返回一个数字答案。

项目还需要处理跨国标签、税务、库存所有权、平台规则和冻结区。这些属于可行性约束，不能因为某方案总分较高就被抵消。

**批判性风险**

- “全局最优值”并不存在，除非负责人先批准目标权重和约束优先级。
- 把缺货损失、利润、现金和风险全部折算成一个分数，会隐藏单位、时间范围和假设。
- 不同权重可能让结果从空运加急瞬间变成延后采购，推荐稳定性可能很差。
- 没有历史样本时不能编造“成功概率”；只能显示未知、依据不足或情景范围。
- 单个动作未必最优，真正可行的结果可能是“调拨一部分、采购一部分、少量空运”的组合。
- 算法推荐若未保存输入、政策版本和候选集合，事后无法解释为什么当时这样决定。

**关键未知**

系统应返回一个最高分方案，还是返回多个非支配方案供人员权衡；同时还要确定政策偏好是否允许每次自由调整。

**方案 1：硬约束过滤 + 政策化 Pareto 候选集，推荐**

处理顺序固定为：

```
校验硬约束
-> 生成单一及组合方案
-> 删除全面劣于其他方案的方案
-> 按已批准政策档案排序
-> 展示少量候选及“不处理”基线
-> 人员选择、调整或拒绝
```

项目证据：同时满足多方案比较、人工决定、冻结区和审计要求。
收益：既能求优，又不会用单一总分掩盖真实取舍；可以保留服务优先、现金优先等不同政策。
成本：需要版本化政策档案、约束解释、组合方案生成和非支配比较。
风险：政策档案本身若未经真实样本校准，排序仍可能误导。
边界：政策只能排序可行方案，不能覆盖合规、所有权、冻结区或授权约束。
可逆性：高，调整政策版本后可以重算，但不会改写历史决定。

**方案 2：单一加权总分，直接推荐最高分**

例如把服务、利润、现金、成本和风险标准化后计算一个综合分。

收益：实现和解释界面最简单，适合高频自动排序。
成本：必须确定权重、标准化方法、时间范围和缺失值处理。
风险：伪精确最严重；相同总分可能隐藏完全不同的业务后果。
边界：只适合目标稳定、样本充分且权重已经正式批准的窄场景。
可逆性：中等，权重变化会导致历史推荐难以比较。

**方案 3：纯 Pareto 候选集，不做政策排序**

系统只排除明显劣势方案，剩余方案全部交给人员比较。

收益：不替负责人隐含价值判断，透明度最高。
成本：候选可能很多，日常决策负担较重，批量处理效率低。
风险：人员可能按个人偏好反复选择，导致组织政策不一致。
边界：适合高风险例外、战略新品或政策尚未校准的阶段。
可逆性：高，后续可以增加政策排序。

**推荐及理由**

推荐方案 1。它不是寻找抽象的唯一最优，而是：

1. 先排除不可执行方案；
2. 找出合理的组合方案；
3. 用负责人批准且版本化的政策缩小候选范围；
4. 明确展示各方案相对“不处理”的增量影响；
5. 由有权限人员形成最终决定。

系统只能说“在政策版本 P3 和当前输入下推荐方案 A”，不能说“A 是绝对最优”。

**对岗位与界面的影响**

方案区应展示政策版本、阻断约束和三到五个候选组合。每个候选并排显示预计到达、缺货影响、增量成本、现金占用、利润影响、原节点风险和不确定项。人工调整后必须重新计算影响；覆盖推荐需要原因，但不能通过覆盖解除硬约束。

**核心判断**

已继承决定：采用“硬约束过滤 + 政策化 Pareto 候选集”。系统提供多个非支配组合方案，按已批准政策排序，由人员最终决定，不宣称存在绝对最优解。

下一项需要确定的是：政策如何适配不同 SKU、市场和业务情景。这里同样不能把“弹性”理解为人员随意切换到对自己最有利的政策。

**已证实事实**

- 安全库存需要按 SKU 分层，并结合需求波动、服务水平和端到端提前期。[业务基线 (line 95)](D:/Logixs/doc/cross-border-supply-chain/17-confirmed-upstream-business-baseline.md:95)
- 不同品类的冻结周期可以不同。[业务基线 (line 43)](D:/Logixs/doc/cross-border-supply-chain/17-confirmed-upstream-business-baseline.md:43)

- 平台仓和海外仓具有不同所有权、调拨资格、费用和销售可用性，不能合并处理。[业务基线 (line 61)](D:/Logixs/doc/cross-border-supply-chain/17-confirmed-upstream-business-baseline.md:61)

**行业对照与项目差距**

Oracle 使用动态需求分层、`item-location` 分组和 Policy Assignment Sets，把库存政策分配到适用对象，而不是让操作人员每次临时选择一个“模式”。

这支持按业务范围解析政策，但项目仍需自行确定 SKU 生命周期、国家渠道、库存池、活动和冻结区之间的优先关系。

**批判性风险**

- 允许人员在看到结果后自由选择“服务优先”或“现金优先”，会形成政策挑选，审计失去意义。
- 给每种场景建立完整独立档案，会快速产生大量重复参数和相互矛盾的政策。
- 只设一个全局政策，则新品、成熟品、清仓品和战略活动会被错误地同等处理。
- 多层政策若没有确定的优先顺序，同一风险可能匹配多个结果。
- 政策版本变化不能覆盖历史决定；否则无法复现当时推荐。
- “现金不足”有时是硬预算约束，有时只是优化目标，不能固定归入同一种性质。

**关键未知**

当前不是决定具体权重，而是决定政策组织方式：统一政策、人工选档，还是由业务范围确定性解析。

**方案 1：分层、版本化、确定性解析政策，推荐**

建立一份基础政策，再按明确范围叠加受控差异，例如：

```
基础政策
-> SKU 生命周期/分层
-> 国家与渠道
-> 库存池与履约网络
-> 活动或战略例外
-> 冻结区约束
```

每个风险事件只能解析出一个有效政策版本。人员可以模拟其他政策，但不能直接用模拟结果批准；如需改变有效政策，必须走授权例外并记录原因、期限和退出条件。

项目证据：符合 SKU 分层、新品、活动、库存池和冻结区的既有差异规则。
收益：具有适应性，同时保持结果可复现、可审计。
成本：必须定义作用域、优先顺序、冲突检测、生效期和版本替代。
风险：叠加层过多会变成难以理解的规则网络，因此 V1 必须限制维度。
边界：只调整优化目标和合法参数，不能覆盖合规、权限、所有权等安全不变量。
可逆性：高，新版本只影响后续计算，历史继续引用旧版本。

**方案 2：命名政策档案，由人员逐次选择**

预设“服务优先、均衡、现金优先、利润优先”等档案，处理任务时人工选择。

收益：直观、灵活，适合快速情景比较。
成本：需要维护多套完整参数并培训选择规则。
风险：人员可能根据希望得到的结果选择档案，造成相似业务处理不一致。
边界：更适合模拟视角，不适合作为正式批准政策的唯一来源。
可逆性：中等，历史可保留档案版本，但政策一致性较难恢复。

**方案 3：单一全局政策，加少量人工参数**

所有业务使用同一目标优先级，只允许调整服务水平、预算或提前期等少数参数。

收益：实现简单、结果一致、容易解释。
成本：难以表达新品、活动、不同库存池和生命周期差异。
风险：表面一致但业务失真，最终会依赖大量人工覆盖。
边界：仅适合业务结构单一或用于早期验证。
可逆性：高，但升级为分层政策时需要补充适用范围。

**推荐及理由**

推荐方案 1，但 V1 只启用有权威依据的最小维度：

1. SKU 生命周期或已批准分层；
2. 国家、渠道和履约网络；
3. 目标库存池；
4. 常态、活动、新品或清仓需求类型；
5. 灵活、半冻结或冻结区。

不得预先穷举行业模板。没有负责人批准的权重和阈值保持未知，不能写入 Schema、界面默认值或优化逻辑。

**对岗位与界面的影响**

风险详情显示“当前采用的政策、为什么适用、版本和生效时间”。用户可切换政策进行只读模拟，比较候选变化；正式提交始终使用当前有效政策。需要偏离时，界面显示例外原因、批准人、有效期和恢复入口，而不是提供无审计的模式开关。

- 人工采信若没有期限，临时判断会永久污染后续计划。
- 数据缺失不能按零处理；“没有数据”和“数量为零”是不同事实。

各类输入最低要求：

- 预测：已发布版本、业务粒度、周期、数据时点；基础预测与活动增量分离。

- 在途：来源供给、当前阶段、数量、目标节点、预计可售时间、更新时间和冲突状态。
- 采购承诺：书面确认、供应商、SKU、数量、承诺日期、当前版本和有效状态。
- 调拨库存：来源节点影响、目标适用性、所有权、标签、税务和平台资格。

收益：事实完整、计算保守且可解释；支持后续重新采信和重算。
成本：需要资格规则、来源裁决、冲突队列、快照版本和人工采信动作。
风险：规则过严时可能高估缺口，因此必须同时展示“未采信数量可能造成的影响”。
边界：采信改变计算资格，不改变原始观测；不得覆盖来源记录。
可逆性：高，后续资格变化通过新快照重算，历史仍可复现。

**方案 2：按置信度折算数量**

例如 1000 件在途、可信度 70%，按 700 件参与净算。

收益：结果平滑，便于数学优化和情景模拟。
成本：必须建立可靠概率模型并持续校准。
风险：700 件并不真实存在，容易导致少补货；同时直接冲突于现行业务基线。
边界：可以用于风险情景或敏感性分析，不能作为权威可用数量。
可逆性：低，一旦折算量进入采购决定，很难解释实际承诺。

**方案 3：只采信最终确认事实**

只有当前可售库存、已入仓调拨和完全确认的采购供应参与计算，所有预计在途都排除。

收益：最保守、规则简单，不会把不确定供给当成库存。
成本：会系统性高估缺口和重复采购，跨境长提前期下尤其严重。
风险：现金占用和库存过量可能显著增加。
边界：适合数据质量极差时的临时保护模式，不适合作为正常规划方式。
可逆性：高，但形成的过量采购无法撤回。

**推荐及理由**

推荐方案 1。核心原则是：

- 保存所有观测，但只让合格事实参与净算；
- 不确定性通过状态、情景和影响范围表达，不通过概率乘法伪造库存；
- 每次运行冻结输入快照；

下一项是库存池边界。库存池不能等同于国家、仓库或渠道中的任何单一维度，否则容易产生跨货主、跨平台或跨合规范围的错误调拨。

**已证实事实**

- 分仓顺序已经确定为“国家 → 渠道/履约模式 → 仓库 → 目的港”。[业务基线 (line 57)](D:/Logixs/doc/cross-border-supply-chain/17-confirmed-upstream-business-baseline.md:57)
- 平台仓、自营海外仓和三方海外仓在所有权、可调拨性、预约、费用和销售可用性上不同。[业务基线 (line 61)](D:/Logixs/doc/cross-border-supply-chain/17-confirmed-upstream-business-baseline.md:61)
- 跨国、跨渠道或跨仓调拨必须检查商品和包装、Listing、条码、税务海关、库存所有权、平台规则及原节点影响。[专题规格 (line 202)](D:/Logixs/doc/cross-border-supply-chain/03-sourcing-and-replenishment-workbenches.md:202)
- 账套主体、货主、销售市场国、运输目的国和库存位置属于不同事实，不能互相推导。[业务基线 (line 105)](D:/Logixs/doc/cross-border-supply-chain/17-confirmed-upstream-business-baseline.md:105)

**行业对照与项目差距**

Oracle 以供应链节点和 `item-location` 组合规划，并允许把过量库存再平衡到短缺节点。项目需要在此基础上增加跨境适用性、账套主体、货主、渠道和平台限制。

因此，“来源节点有货”只能触发候选评估，不能直接证明这批货可以转到目标节点销售。

**批判性风险**

- 同一个物理仓库可能同时保管不同货主、渠道和销售资格的库存，不能视为一个自由共享池。
- 同一个 SKU 的包装、标签、Listing 或法规版本不同，也可能不能跨市场使用。
- 调拨资格具有方向性：A 可以调到 B，不代表 B 可以调回 A。
- 调拨资格还具有时间性；证书、平台预约、税务安排或活动窗口变化后，旧结论可能失效。
- 把所有来源和目标组合预先配置成矩阵，会形成难以维护的组合爆炸。
- 只保存一个 `transferable=true` 会丢失适用 SKU、数量、时间、方向和依据。

**关键未知**

需要确定库存池是按物理地点、业务汇总范围，还是按能够共同承诺和消耗库存的责任边界建立。

**方案 1：稳定库存池 + 有方向的逐次互换资格评估，推荐**

库存池是稳定业务身份，至少区分：

```
账套主体/库存所有权
+ 实际或逻辑库存节点
+ 渠道与履约网络
+ 保管及可售责任边界
```

国家、仓库和平台是池的属性或关联事实，不能单独充当身份。

调拨时针对 `来源池 -> 目标池 + SKU版本 + 数量 + 需求窗口` 生成资格评估，逐项检查商品、包装、Listing、条码、合规、税务、所有权、平台、运力、成本及来源池服务影响。评估版本随补货运行快照冻结。

项目证据：完整承接现有分仓顺序、平台仓差异和跨节点检查要求。
收益：既能表达真实物理库存，也能支持跨仓、跨渠道和跨国优化。
成本：需要库存池主数据、资格规则、来源证据和评估版本。
风险：规则缺失时会产生大量待核验项，必须允许人工补证但不能静默放行。
边界：评估只说明特定方案是否可执行，不改变原库存身份和所有权。
可逆性：高，可以增加资格规则或拆分库存池，历史评估仍可复现。

**方案 2：按物理仓库建立库存池**

同一仓库中的库存归为一个池，通过 SKU 或库存状态字段补充限制。

收益：模型直观，容易和 WMS、库存盘点及仓库操作对接。
成本：需要在每次计算时重新处理货主、平台和渠道差异。
风险：容易把同仓但不可互换的库存合并，导致虚假可用量。
边界：仅适合同一仓内所有权和销售资格高度一致的业务。
可逆性：中等，后续拆池需要重建历史余额归属。

**方案 3：按国家、渠道和履约网络建立汇总池**

库存首先按预测粒度对应的市场网络汇总，物理仓库作为明细。

收益：预测、风险和库存覆盖容易对齐，管理视图简洁。
成本：物理位置、预约、保管责任和实际调拨路径被弱化。
风险：汇总层看似有货，但可能没有任何一个真实节点能够兑现。
边界：适合作为分析投影，不适合作为权威库存身份或执行来源。
可逆性：高，但不能用汇总余额直接落执行需求。

**推荐及理由**

推荐方案 1，并明确两层结构：

- 权威库存池回答“这批库存由谁在什么节点、以什么履约责任持有”；
- 互换资格评估回答“这批货在当前时间和证据下能否用于另一个目标”。

国家、渠道和计划批次可以自由聚合展示，但不能合并底层库存身份。系统不维护永久的全量调拨矩阵，而是在产生候选方案时按当前事实评估并冻结结果。

**对岗位与界面的影响**

风险详情先显示目标库存池及责任边界，再列出候选来源池。每个来源明确标记可调拨、待核验、阻断或数据过期，并逐项给出原因。汇总视图允许按国家、渠道和仓库切换，但提交调拨方案前必须展开到实际来源池和数量。

**方案 2：批准即完成**

成本：需要额外机制发现交接失败。
风险：最容易形成“批准了但没人收到”的虚假闭环。
边界：只有交接具备同步、事务性保证时才可能成立；当前项目不满足。
可逆性：中等，后补交接状态会改变既有完成语义。

收益：可以直接观察决定是否真正实现。
成本：任务持续数周或数月，跨越多个岗位和状态机。
风险：责任混淆、队列积压，并诱导需求计划岗直接操作下游事实。
边界：适合作为复盘跟踪视图，不适合作为当前岗位退出条件。
可逆性：中等，需要重新拆分历史责任区间。

- “交接已接收”表示岗位责任已转移，不表示执行成功；

持有补货批准能力且对象在授权范围内，即可调整输入、选择方案并批准。

收益：速度最快，责任集中，适合小团队。
成本：需要更强的事后审计和异常检测。
风险：自我修改输入、自我选择政策并自我批准，难以证明决定独立可靠。
边界：不应覆盖冻结区、政策例外、争议事实采信或跨所有权边界。
可逆性：中等，后续增加职责分离会改变岗位流程。

**推荐及理由**

推荐方案 1。权限判断顺序应固定为：

```
身份与能力
-> 租户/账套主体/库存池对象范围
-> 职责分离
-> 当前风险、证据和冻结区业务前置
-> 写入决定与授权审计
```

角色只是这些能力和范围的组合。已有 `planning.read`、`planning.draft` 不足以自动授权补货批准、争议采信或冻结区例外；是否新增更窄能力码必须等真实动作和消费者正式写回后评审。

**对岗位与界面的影响**

服务端返回当前允许动作、拒绝原因和待审批责任队列。页面可以隐藏明显无权动作，但仍应在需要交接时说明“由谁批准、等待什么”。高风险提交先显示影响，再进入独立复核；审批人看到原始输入、准备人调整、候选方案和覆盖理由，不能只看到一个“同意”按钮。

**核心判断**

已继承决定：采用按风险分级的能力、对象范围和职责分离。普通政策内事项保持效率，高风险动作由不同人员复核。

下一项不是简单列出“哪些按钮要审批”，而是区分三类控制：

```
永远不可越过
需要双人复核
授权范围内可单人完成
```

双人复核不能把法律、安全或所有权不成立的动作变成合法。

**已证实事实**

- 租户隔离、成员关系、未知值拒绝和服务端执行属于不可关闭的安全不变量。[AGENTS.md (line 207)](D:/Logixs/AGENTS.md:207)
- 冻结区变化必须审批并产生新版本，保留对订单、供应商、库存和运输的影响。[业务基线 (line 99)](D:/Logixs/doc/cross-border-supply-chain/17-confirmed-upstream-business-baseline.md:99)
- 金额只是风险维度之一，低金额也可能涉及高合规风险或关键单一来源。[业务基线 (line 49)](D:/Logixs/doc/cross-border-supply-chain/17-confirmed-upstream-business-baseline.md:49)

**行业对照与项目差距**

成熟计划产品通常把政策管理、模拟、例外和建议释放作为不同动作面。项目需要进一步处理冻结承诺、跨货主库存、争议输入和“不处理”风险接受，因此不能只用金额审批表。

**批判性风险**

- 把所有约束都称为“可审批例外”，会让双人审批变成绕过安全与合规的通道。
- 只按金额触发复核，会漏掉低金额但高缺货、合规或单一来源风险。
- 采信争议数据的人再批准依赖该数据的方案，职责分离仍然失效。
- 政策发布者若能立即用新政策批准自己的方案，可能通过修改权重影响结果。
- 第二审批人如果看不到输入版本、差异和影响，只是在机械点击。
- 找不到第二审批人时必须保持等待或升级，不能静默降级为单人批准。

**关键未知**

需要确定强制双人复核是依据动作性质、指标阈值，还是覆盖所有正式决定。

**方案 1：固定高风险动作 + 受治理阈值触发双人复核，推荐**

三层边界如下。

不可通过审批越过：

- 租户、账套主体或对象范围不匹配；
- 操作者缺少必要 capability；
- 库存所有权或来源身份不成立；
- 法律、制裁或明确合规禁止；
- 必需事实未知、载荷非法或证据被撤销；
- 幂等、版本或并发冲突。

V1 强制双人复核：

- 发布或替换正式补货政策；
- 改变冻结区内已经承诺的计划；
- 限时采信冲突、过期或来源不足的输入，并用于可执行决定；
- 批准政策覆盖或其他可例外业务约束；
- 接受重大残余缺货、库存、利润或现金风险而决定不处理；
- 跨账套主体、货主或受控所有权边界的库存转移；
- 达到已批准的服务、金额、现金、利润或风险影响阈值。

授权范围内可单人完成：

- 查看、模拟和比较方案；
- 在灵活区内准备、调整并批准政策内方案；
- 拒绝某个候选并要求重算；
- 刷新数据、请求补证或延期到明确日期；
- 批量批准全部通过预检的正常项。

收益：风险边界明确，同时保留正常补货效率。
成本：需要动作分类、阈值政策、双人身份校验和待审批队列。
风险：阈值未定前，相关动作只能保持待决，不能静默默认。
边界：双人复核只能批准业务例外，不能突破安全、所有权和法律不变量。
可逆性：高，可按审计结果调整触发条件和阈值版本。

**方案 2：只按量化阈值触发双人复核**

金额、数量、预计损失或现金占用超过阈值时双审，其余单审。

收益：规则容易自动执行，岗位容易理解。
成本：需要统一计量、币种换算和阈值维护。
风险：遗漏冻结区、争议事实、政策发布和低金额高合规风险。
边界：可以作为方案 1 的补充条件，不能独立承担全部控制。
可逆性：高，但历史漏审决定无法补救。

**方案 3：所有正式批准均强制双人复核**

任何补货、调拨、加急或不处理决定都要求不同人员批准。

收益：规则统一，独立复核覆盖最广。
成本：正常项吞吐量下降，批量处理也形成审批瓶颈。
风险：审批人面对大量低风险任务时容易流于形式。
边界：适合低频、高价值或受强监管范围。
可逆性：中等，后续放宽会改变组织控制口径。

**推荐及理由**

推荐方案 1。还需增加两项不可省略的技术保障：

- 准备人、事实采信人和第二审批人按触发原因检查是否必须不同，不能只检查角色名称；
- 审批绑定输入快照、政策版本和方案版本。相关事实发生实质变化后，旧审批不能继续释放执行需求。

具体金额、缺货损失和现金阈值目前没有项目证据，必须保持待负责人后续定案，不能先填行业默认值。

**对岗位与界面的影响**

普通任务直接显示“批准并交接”。触发双审时，主动作变为“提交复核”，并说明触发原因、当前影响和审批队列。审批人看到准备前后差异、输入资格、政策版本、候选方案及不处理基线。不可越过的动作只显示阻断与补正路径，不显示“申请例外”。

**行业对照与项目差距**

AWS Forecast Lock 会把已定值带入下一周期，但当预测粒度改变时，旧覆盖和旧锁不再有效。这说明批准有效性需要识别语义变化，而不只是检查更新时间。[AWS 官方资料](https://docs.aws.amazon.com/connect-decisions/legacy/userguide/forecast_lock.html)

**批判性风险**

- 任意字段变化都作废审批，会造成持续重算和审批疲劳。
- 只按固定有效期判断，会允许库存、合规或供应承诺已经失效的方案继续执行。
- 容差若逐次比较，多个小变化可能累计成重大偏差；必须始终与批准基线比较。
- 只检查最终数量不够：交付日期、来源库存池、成本、原节点风险或冻结状态变化也可能改变决定性质。
- 已经被下游接收的决定不能撤回改写；此时只能发起变更或继任决定。
- 政策版本变化不能自动套用到历史批准，但执行前发现旧政策已经被强制撤销时必须阻断。

**关键未知**

需要确定批准依赖哪些事实，以及什么变化属于“实质变化”。具体容差值尚无真实样本依据，本轮只能确定机制。

**方案 1：依赖指纹 + 语义实质性判断，推荐**

每个候选方案、批准和交接绑定：

```
输入快照版本
+ 政策版本
+ 目标与来源库存池
+ 资格评估版本
+ 方案版本
+ 成本/汇率口径
+ 风险分类与审批条件
```

执行或交接前由服务端重新校验。

始终失效并阻断：

- SKU、货主、账套主体、来源池或目标池身份变化；
- 库存所有权、合规、Listing、标签或调拨资格失效；
- 采用的证据被撤销，或输入从合格变为冲突、过期、未知；
- 冻结区、能力、对象范围或必需审批条件变化；
- 人工修改已批准方案；
- 当前版本或幂等前提冲突。

重新计算，并按影响决定是否重新审批：

- 预测、库存、在途、供应承诺或需求窗口变化；
- 数量、到达时间、成本、现金、利润或原节点风险相对批准基线超出政策容差；
- 候选方案排序、可行集合或风险等级发生实质变化；
- 累计小变化超过批准基线容差。

不使批准失效：

- 不影响业务语义的展示文字或补充说明；
- 在政策容差内且不改变可行性、执行数量、来源、日期和审批等级的更新；
- 下游已经接收后的执行进度更新。

收益：安全性和岗位效率平衡，能够解释为什么需要重新审批。
成本：需要依赖清单、差异分类、批准基线和重校验服务。
风险：容差配置不严谨会产生漏审或频繁重审。
边界：容差只能处理业务波动，不能放宽安全、法律、所有权和身份约束。
可逆性：高，可通过新政策版本调整容差，历史仍引用旧规则。

**方案 2：任何依赖事实变化都重新审批**

只要输入快照版本不同，原批准立即失效。

收益：规则最简单，安全侧保守。
成本：跨境运输和库存数据频繁变化，会产生大量无实质意义的重审。
风险：审批疲劳使真正的重要变化反而不受关注。
边界：适合极低频、高价值决定。
可逆性：高，但运营成本较大。

**方案 3：批准在固定时间内有效**

例如批准后若干小时或天内有效，到期才重新计算。

收益：实现简单，岗位容易理解。
成本：需要为不同场景设定有效期。
风险：重大事实可能在有效期内变化，仍错误释放执行需求。
边界：TTL 可以作为新鲜度辅助条件，不能替代依赖校验。
可逆性：高，但无法补救有效期内的错误执行。

**推荐及理由**

推荐方案 1。需要明确两个时间边界：

- 下游接收前：实质变化可以使批准失效，阻止交接；
- 下游接收后：旧决定和交接保持不可变，变化形成受控变更、撤销请求或继任决定。

系统不得自动把重新计算的新方案视为已经批准。

**对岗位与界面的影响**

任务出现变化时展示“哪些事实变化、相对批准基线的差异、是否仍可执行、为什么需要重审”。非实质变化只写入核验记录；实质变化把主动作改为“重新计算并提交复核”。已经交接的对象显示变更入口，不把历史状态退回。

**批判性风险**

- 只优化缺货率，会倾向多买、多备，最终把服务水平问题变成滞销和现金问题。

- 预测准确率不是最终结果；即使预测误差较小，错误的补货政策仍可能制造库存。
- 一开始建设复杂算法、全量策略平台和全部接口，会延迟真实岗位验证，并可能精确地计算错误问题。

**方案 1：双向库存风险工作台，推荐**

同一任务池处理两类事件，但使用不同方案组合：

| 风险         | 主要候选动作                                                 |
| ------------ | ------------------------------------------------------------ |
| 缺货         | 调拨进入、在途改配、供应商加急、新增采购、运输加急           |
| 过量/滞销    | 暂停或减少新供给、延期采购或生产、调拨转出、在途改配、交给商业岗位处理促销/降价/清仓 |
| 混合网络失衡 | 从过量节点转向短缺节点，并计算两端影响                       |

每个风险都展示“不处理”的预计结果，再与候选组合比较。商业促销、采购取消和运输改配由对应岗位接收，不由需求计划岗越权执行。

收益：直接服务缺货损失、库存健康、现金和利润四个核心结果。
成本：需要定义过量和滞销事实、供给减少动作以及商业交接。
风险：范围容易扩大，因此 V1 只选择少量真实场景验真。
边界：一个工作台统一判断库存风险，但专业执行仍属于采购、商业和运输岗位。
可逆性：高，后续可深化不同风险类型，不需要拆掉共同事实链。

**方案 2：首版只做缺货补货，滞销只提示**

工作台完成采购、调拨和加急决定；过量库存只显示风险，不提供处置闭环。

收益：范围较窄，较快形成第一条执行路径。
成本：库存降低能力不足，不能完整回答当前核心问题。
风险：系统可能持续提高供给，却没有对称的减供给机制。
边界：只能称为缺货补货首片，不能称为完整需求与补货工作台。
可逆性：高，但后续需要扩展业务对象和交接。

**方案 3：拆成补货与库存健康两个工作台**

补货岗处理缺货，库存健康岗处理过量和滞销。

收益：职责专注，适合组织中确实存在两个独立岗位的情况。
成本：同一 SKU 的缺货与过量可能分散在两个队列，需要额外协调。
风险：一个工作台补货，另一个工作台去库存，可能产生相互冲突的决定。
边界：只有真实组织责任已经分离时才成立；当前项目没有这项证据。
可逆性：中等，后续合并任务和历史责任较困难。

**推荐及理由**

推荐方案 1，但首版只验证三个真实业务路径：

1. 未来缺货：比较调拨、采购和加急。
2. 未来过量：比较减单、延期、转出和商业去库存交接。
3. 网络失衡：一个节点过量、另一个节点缺货，判断能否转移。

首版不需要原生机器学习、通用优化平台或穷举全部策略。必须保留的技术最低线只有：事实可追溯、决定可解释、服务端授权、版本冲突保护、交接可确认、结果可复盘。

**对岗位与界面的影响**
