## 核心业务目的

现行业务权威已经给出送仓台的存在理由：**把已可靠提柜的货柜按已发布计划送到正确目的仓，并取得可信到仓回执。**

受控临时堆场只是异常或计划路径中的中间交接点，不等于目的仓送达，也不得完成 `warehouse_delivery`。

两个反事实结论：

1. 没有统一控制面时，调度仍必须保证货柜送对仓、赶上预约、处理途中异常并取得仓方接收。
2. 即使权限、状态和证据体系全部完美，只要错送、拒收、失约和额外运输损失没有下降，本台就不算成功。

## 目标岗位与关键决定

现有权威只确定为“内陆运输岗位”，尚未明确最终结果责任人。

推荐目标岗位：**送仓运营调度员**。其关键决定发生在可靠 Gate Out 后：确认本次运输能否按冻结计划执行；出现堵车、拒收、仓库变更或司机异常时，决定继续、改约、申请改送或升级；最终确认目的仓是否真实接收。

外部司机是执行协作者：

- 扫码、接单、发车、到场、异常上报等动作发生即保存原始观察；
- 返回提柜、发车、到仓等观察时间；
- 司机扫码、点击或 GPS 不自动成为权威到仓事实；
- 仓库、WMS、门岗或合格 POD 完成采信后，才确认到仓。

## 优先减少的 1～3 类经营损失

推荐当前聚焦三类：

1. **错仓、拒收及首次送达失败**：产生返程、二次运输、改约和下游卸柜空等。
2. **错过预约或承诺窗口**：产生司机等待、仓库等待、重新派送，并压缩卸柜和还箱期限。
3. **途中异常发现或处置过晚**：堵车、事故、司机失联、仓库临时拒收未及时处理，导致损失继续扩大。

智能计划直接取得并发布预约，送仓只执行。适合预约与资源优化完全一体化的场景；成本是计划控制面承担外部协作和持续变更。风险是控制面再次成为产品中心，且执行期改约责任容易悬空。

**B3 卸柜或仓库岗位负责预约**

仓库侧确认月台并把结果交给送仓。适合自营仓且仓库拥有完整排期权；收益是贴近仓库容量。风险是外部仓、车队和途中异常无法由仓库岗位统一处理，也容易把送仓责任推给下游。

## 推荐方案及不成立条件

推荐 **B1**：计划提出窗口，送仓取得并维护有效预约，仓库确认，司机执行。

若所有仓库预约都由内部仓储团队集中办理且送仓调度无权联系仓库，B1不成立，应采用B3；若智能计划已经能直接获得仓方确认且持续负责执行期改约，才适用B2。

## 已核实的事实

- **现行权威把预约归给提柜。** 08 第 388 行写的是提柜工作台"向送仓工作台交付在途任务、目的地和预约"；送仓的允许动作只有确认接单、登记到场、申请改送和上传 POD，没有办理预约。所以这一轮推荐的"送仓调度负责预约（B1）"是对现行权威的修订，不是对原文的解释。写回时要同步修改提柜一节的下游交接。上一轮提柜摘要里"送仓接收在途任务、目的地和预约"的说法也要随之调整。
- **到仓守卫读取了证据权威。** `node-specialized-guard.ts` 第 174～183 行的 `warehouse_delivery` 守卫会读取送达指令、地点和 `evidenceAuthorityContexts`，和"司机观察不能单方面完成到仓"的说法一致。我没有逐行展开 `decideWarehouseDelivery`，司机来源具体怎样被拒，还需要单独确认。

## 需要 Claude 处理的问题

1. **冻结后更换预约责任方，和提柜台的 E1 规则冲突。** 送仓摘要写的是"冻结计划发布后，改变 S 模式或 B 责任方必须走客观异常"。但提柜台刚定的 E1 明确规定，切换策略本身不算客观异常；能突破冻结的只有"新出现的可验证事实"。如果严格按 E1 执行，冻结期内就永远换不了责任方。

   建议写成：触发条件必须是一个满足 E1 的事实，比如仓库取消预约，或原责任方确实无法处理；更换责任方只是处置这个事实的结果。单纯"想换一种预约策略"不能突破冻结。

2. **预约叠了三层选项，首片只能启用一个组合。**
   - B1、B2、B3：预约由谁负责；
   - S1、S2、S3：怎样选出负责方；
   - G1：S 模式由运营负责人治理。

   其中 B2 由计划层负责预约，而计划层在 22 台里的位置还没定；B3 由仓库或卸柜岗位负责预约，又会把预约责任放到另一台。我建议首片只启用"S1 + B1"，也就是按运营单元和仓库固定由送仓负责预约。B2 和 B3 等计划层位置、卸柜台定案之后再启用；S3 自动判定继续作为候选。

3. **需要一个所有台共用的权威预约对象。** 预约可能由送仓、计划层或仓库侧三个地方的人负责，但仓方确认、变更历史、当前有效版本必须只有一份。否则就会出现摘要里列出的风险："计划、仓库和送仓各持一个预约结果"。这一点影响 Schema 和契约，要和计划层的位置一起定。

4. **治理角色越来越多，需要统一对应。** 目前各台已经出现：

   | 角色           | 出自哪一轮             |
   | -------------- | ---------------------- |
   | 场景负责人     | 排柜                   |
   | 运营治理管理员 | 排柜，负责权限模板     |
   | 计划负责人     | 提柜，负责处理 E1 异常 |
   | 运营负责人     | 送仓，负责治理 S 模式  |
   | 资源负责人     | 提柜，负责共同确认     |

   它们很可能是同一批人的不同说法。需要并入跨台角色清单统一对应，否则各台的授权规则对不上。
   - 好的一面是，送仓用的"运营单元"和提柜的 S1 一致；但和排柜那一轮的"运营场景"仍然需要统一。

5. **外部司机端依赖外部身份认证。** "司机动作即记录"需要司机账号、承运商级别的对象范围和账户恢复，和供应商门户、报关行、外部车队是同一个前置条件，而授权相关任务目前处于阻塞状态。首片里，司机的回传只能由调度代为录入，或通过外部 TMS 或文件导入进来。

## 可以直接写回的部分

- F1 是唯一核心结果；途中异常干预（F2）和司机回传（F3）只是支撑能力，不能并列为产品目的。
- 司机扫码、点击、GPS 都只是原始观察；仓库、WMS、门岗或合格 POD 才是接收的权威确认。
- 临时堆场接收不算目的仓送达，也不能完成 `warehouse_delivery`。
- 准时的判定口径：有预约的以预约窗口为准，没有预约的以冻结计划的承诺时间为准，两者都没有的不计入准时率（对应 T1）。
- 首次接收的判定口径：仓方接受，且不需要返程或再次派送，不要求已经卸柜（对应 A1）。
- 首版损失只计算可以直接归因的部分（对应 L1 和 M1）。
- 每个任务只能有一个预约责任方；预约责任方持续负责预约本身，送仓调度始终负责运输执行（对应 H1）。
