# 岗位工作台

> 定位：全部岗位工作台的业务范围、共同操作规则、复审顺序和岗位规格权威。
> 技术实现、当前完成度、DTO、状态码、数据库和测试证据由 `docs/` 承接。
> 状态：23 个工作台及其岗位结果是业务范围基线；任何“已有页面”“已接真实 API”
> 或“已有技术操作规格”都不自动等于通过本轮业务复审。成熟度与评估状态分开记录，
> 现有运行表面不因目录迁移被提升或降级。

## 一、业务规格如何使用

工作台必须围绕六个问题组织：今天先处理什么、为什么、还缺什么、可以做什么、
失败怎么办、完成后交给谁。页面共同组成是优先事项、对象上下文、缺口与风险、
允许动作、证据和活动时间线、结果反馈。

本文件使用三种状态，禁止混用：

| 状态         | 含义                                                                   |
| ------------ | ---------------------------------------------------------------------- |
| 范围基线     | 已确认项目需要该工作台及其岗位结果，不代表详细规格或实现完成           |
| 已有业务规格 | 已记录岗位目标、所需信息、动作、失败和交接，仍须按当前十项共同要求复审 |
| 通过本轮复审 | 已完成行业对照、事实审查、方案取舍、实现和真实岗位六类路径验收         |

当前没有任何工作台仅凭页面、接口或历史任务被标记为“通过本轮复审”。

## 二、共同业务规则

### 2.1 岗位操作原则

每台工作台开始详细规格前，必须先锁定本台的目标岗位、唯一核心业务结果、优先减少的
1～3 类业务或经营损失、与上下游的责任边界和结果指标。业务目的决定为什么做、优先做什么；
共同规则、控制面、安全、合规和数据真实性只是最低可信保障，可以否决不可信或越界方案，
但不得反向主导产品、改变本台偏重，或用规则与技术完整度冒充岗位结果。

工作台不是把同一张详情复制给每个岗位。每个岗位看到的是同一组权威事实在本岗
目标下的投影，排序、上下文和允许动作由岗位结果及其优先减少的损失决定。

用户从“今天必须处理”的任务进入，而不是先记住内部编号再搜索。页面先说明为什么
现在需要处理、不处理的影响和最晚决定时间，再集中展示判断所需的事实、来源和
缺口。动作完成后，系统必须说明形成了什么结果、哪些对象受影响以及下一责任人是谁。

动作暂时不能执行时，页面说明缺少什么、由谁补齐和怎样恢复，不能只把按钮置灰。
批量处理先预检，提交后逐项反馈成功、待补、冲突和失败。

### 2.2 所有工作台共同必须具备

1. **`WB-B01` 单一作业焦点**：每台只有一个岗位结果、一个主要选择来源和一个随当前阶段变化的主动作。
2. **`WB-B02` 入口三源**：按实际业务需要提供接收上游交接、本岗新建和批量导入；不适用的入口必须说明原因，不能机械铺满。
3. **`WB-B03` 退出三层**：对本岗拥有的对象提供回退或重开、作废或归档、受限删除；已经交接、被引用或有保留义务的对象不能物理删除。
4. **`WB-B04` 责任和时限**：始终显示当前责任人、下一责任人、截止时间和等待原因，让跨班次、跨岗位工作能够继续。
5. **`WB-B05` 状态分轨**：已确认事实、待补缺口、异常阻断、外部观测和同步状态分开表达，不压成含义不清的总状态。
6. **`WB-B06` 正常批量、异常逐条**：正常对象默认支持批量处理；冲突、例外和高风险确认逐条恢复。
7. **`WB-B07` 不可变交接**：每次跨岗交接使用不可变快照，说明版本、来源、发送方、接收队列和待补事项；更正追加新版本，不反写历史。
8. **`WB-B08` 结果指标**：指标衡量业务结果、首次通过、周期、等待和返工，不用按钮点击、页面访问或机械录入量冒充绩效。
9. **`WB-B09` AI 边界**：AI 只能做匹配、摘要、建议和风险排序；业务判断、责任确认、允许动作和状态推进由规则或有权限人员完成。
10. **`WB-B10` 六类路径验收**：真实岗位必须使用真实或脱敏的真实样本走完正常、等待、拒绝、冲突、返工和恢复路径。

### 2.3 逐台同步推进与完成声明

每台工作台都按同一个交付单元推进，不能先孤立地画页面、补字段或建设技术底座，再等待其他部分以后对齐：

| 组成               | 必须回答的问题                                                                   |
| ------------------ | -------------------------------------------------------------------------------- |
| 岗位规格           | 谁在什么条件下接手，要完成什么结果，按什么步骤判断和操作，失败、退出与交接怎么办 |
| 相关数据事实子集   | 本次步骤使用哪些事实，来源和版本是什么，当前能否可靠保存，仍缺什么               |
| 技术保障与界面实现 | 系统允许什么动作，如何保证权限、状态、落账、审计和恢复，界面如何让岗位完成操作   |

三者必须以同一业务步骤逐项对应。一个步骤只有规格没有数据承载，只能说业务规格已定；只有数据和接口没有岗位可用流程，只能说技术能力已实现；只有页面能点击但没有服务端规则和可靠落账，只能说界面已出现。以上任何一种都不等于工作台闭环完成。

相关数据事实子集只覆盖本台当前业务步骤真正消费的事实，不要求先把全库字段全部人工确认完。子集必须分开说明：

1. **当前物理事实**：数据库、Schema、迁移、契约和实现已经存在且可以核验的内容，不根据字段英文名猜业务含义。
2. **已定业务缺口**：本文件、其他负责人确认的 `doc/` 或 `doc/adr/` 已经要求，但当前数据承载仍缺失的内容。
3. **行业候选建议**：行业标准或最佳实践提出、但尚未成为 Logix 规则的内容。每项必须说明来源、为什么适用、收益、成本、不采用风险和可逆性。

行业候选经负责人定案并写回 `doc/` 或 `doc/adr/` 后，才能成为 Logix 业务要求。定案后还要判断它应由字段、关系、历史记录、不可变快照、事件、约束、派生投影还是操作规则承载；涉及架构取舍时写入 `docs/architecture/decisions/`。技术 ADR 只能承接实现选择，不能替代业务适用性定案，也不能看到行业常见项就默认新增数据库列。承载方式仍未决定时，只阻塞依赖该事实的实现，不拖停无关步骤。

一台工作台可以拆成多个实现切片，但所有切片必须回到同一份岗位规格、同一份相关数据事实子集和同一张业务步骤映射中收口。任何一面缺失时，只能声明该面完成；三面全部形成证据并通过真实岗位约定路径验收后，才能声明工作台闭环完成。

### 2.4 23 台共同最低可用线

`WB-B01`～`WB-B10` 合起来才是工作台的共同最低可用线，不是十个可以任选的功能点。每台进入“本轮复审通过”前，必须逐项留下当前事实、适用性、剩余缺口、实现承接和验收证据；不适用项也要说明业务理由并由负责人确认。

单个实施切片可以只完成其中一部分，但必须明确仍缺什么，不能用以下任一结果替代整台通过：

- 网络图标记为 `live`；
- 已有页面、接口、数据库表或运行时操作规格；
- 正常路径能走通，但等待、拒绝、冲突、返工或恢复尚未验证；
- 点击成功或数据已落库，但岗位无法确认业务结果和下一责任人。

### 2.5 批判求真的决策互动

每台工作台按重审顺序推进时，主代理不能只向负责人索要答案，也不能自行补造业务政策。每轮澄清聚焦 1～3 个会改变岗位结果的决定，并按以下固定顺序互动：

1. **先给事实**：区分已实现、文档已定、真实样本已证实、合理假设和仍未知，不把设计意图说成上线能力。
2. **再给选项**：提供 2～3 个互斥且可执行的方案；推荐项放在第一位，同时说明为什么推荐。
3. **讲清取舍**：每个选项都说明业务收益、实施和运营成本、主要风险、可逆性以及对上下游岗位的影响。
4. **负责人定案**：负责人选择、否决或要求补证；主代理应指出证据冲突和弱假设，不作无依据迎合。
5. **写回权威**：业务结论进入本文件或对应 `doc/` 业务章节；架构决定进入 ADR；当前 brief 只记录映射、状态和来源，不另建第三套规则。
6. **未定不造假**：尚未定案的内容保持候选，只阻塞真正依赖它的动作；其他事实审查、样本准备和无关切片继续推进。

以下事项必须与负责人互动定案：岗位最终结果、关键状态和完成语义、责任与交接、回退/作废/删除政策、业务权限和复核、风险接受、指标口径及不可逆投入。符合既有权威的局部代码结构、测试设计、命名和可逆实现细节由主代理自主负责（角色映射见 `AGENTS.md` §1.2 第 4 条），不把工程判断转嫁给业务负责人。

每台 task brief 必须保存“事实与未知、候选选项、推荐与理由、负责人结论、权威落点”五项记录。聊天中形成但尚未写回权威的结论，不得进入实现。

## 三、当前项目定义的全部 23 个工作台

目录按业务阅读顺序排列，不强制运行拓扑为线性：主链允许 fan-in/fan-out；支撑/横向工作台按真实消费者接入。

| -------- | ----------------------- | -------------------- | --------- | ------------------------------------------------------------------------------------------------ |
| 1        | `market_signals`        | 市场与经营信号       | 主链      | 把经过最低验证的真实市场信号形成不可变新品候选交接，并披露证据、反证和未决不确定性               |
| 2        | `product_selection`     | 选品立项             | 主链      | 完成商业论证和资源取舍，决定是否形成有责任人的产品立项                                           |
| 3        | `product_npi`           | 产品开发与 NPI       | 主链      | 在重大投入扩大前作继续、返工、暂停或终止决定，并发布经过验证的产品定义                           |

`booking`、`export_customs`、`compliance_operations` 是批准后的目录项，只新增无业务动作的 `planned` 目录占位 route 与页面，不因此新增 API 或生产写动作。`customs` 保留 stable code，正式名称为“进口清关”。

### 3.1 成熟度与评估状态

成熟度只允许以下四级，且页面、route、API、HTTP 成功、运行时操作规格或旧 `live/framework` 标记均不能单独证明任一成熟度：

- `planned`：身份、目标岗位、唯一结果和边界已定；可展示目标和现有事实入口，不允许生产写动作或虚假队列。
- `facts_only`：可读取、导入或受控更正事实，并提供来源、版本、新鲜度和冲突；没有原生岗位任务、责任/时限闭环和真实岗位验收。
- `operational`：具备服务端动作、授权与对象范围、责任、时限、事务/幂等/并发、交接回执和六类自动化路径；只证明岗位机制可用，不证明经营损失下降。
- `validated`：在 `operational` 之上完成真实/脱敏样本、真实岗位、六类路径、下游使用和指标口径验收；只有该级可计入 `WB-B10` 或宣称真实业务验收。

评估状态与成熟度分开：`pending_assessment` 表示尚未按本权威完成证据审查；`assessed` 表示已有证据清单、缺失门禁和负责人结论，可写入正式成熟度。`pending_assessment` 不是第五个成熟度，不产生任何运行时 promotion/demotion 语义。

### 4.1 市场与经营信号工作台（`market_signals`）业务目的

- **目标岗位**：负责市场与经营信号发现、初步分类和验证的经营人员。
- **主目标**：减少真实机会遗漏或响应过晚，让值得验证的信号在市场窗口内进入经营判断。
- **制衡目标**：减少弱信号、短期峰值和无依据假设被误判为机会后，对选品及后续产品、供应链资源造成的浪费。
- **首个岗位闭环**：发现优先信号 → 完成一次有效验证 → 决定是否形成可信机会。首版产品机制和自动化测试允许使用永久标注为 `synthetic_rehearsal` 的一正一反演练样本，分别覆盖容易遗漏的窗口机会与表面高热但不应进入选品的弱信号；合成演练不得用于阈值或 KPI 校准，也不得冒充真实岗位验收。真实或脱敏样本只作为 WB-B10、上线业务验收、指标发布及经营损失改善声明的门禁，不阻止边界清楚、可回滚的产品机制开发。不以建设完整机会治理平台为目标。
- **上下游边界**：本台负责发现、分类、验证和形成可评审机会；选品负责完整商业论证、盈利判断、产品组合取舍和是否立项。成本、供应可行性和完整合规结论不得提前压回本台。
- **首批运营结果指标**：从信号进入到完成分类的时间、到期验证按时完成率、可信机会被选品首次接收的比例、因证据不足或方向错误被退回的比例。它们只观察流程响应和下游质量，不能单独证明机会漏失或资源浪费已经下降；每项正式启用前必须再定义分母、起止点、暂停和排除口径，并另行定案可回溯的机会窗口与下游无效投入结果观测。登记量、证据量、点击量和页面访问量不得冒充业务结果。
- **最低可信保障**：来源与证据可追溯，责任和期限明确，可信机会资格由服务端校验，跨岗交接使用不可变版本，权限、幂等、并发、审计和失败恢复成立。最低保障可以否决不可信或越界操作，但不得代替业务目的、优先级和经营判断。

共享契约、细粒度 capability、三阶段回执和统一 UI 壳只在上述首个岗位闭环证明需要时作为支撑切片进入；其完成度不得成为市场信号产品主线或本台业务验收结果。现有页面、接口和状态只作当前物理事实，不反向定义本节业务目的。

首个生产薄片只建立“单一当前验证承诺”：经营人员选择继续观察时，必须明确本次验证重点和下一检查日期，由服务端将当前认证用户登记为负责人，可选记录正在等待的内容。负责人可以重新安排自己的承诺并保留历史；同租户其他用户不得静默覆盖或接管，接管/转派政策另行定案。当前验证承诺在交选品、不采纳、作废、归档或选品退回生效后清空当前投影，历史判断不删除。该薄片不新增可信机会、评分、验证通过或逾期状态，不改变现有交接与退出政策。

## 五、产品开发与 NPI 工作台（`product_npi`）

### 5.1 岗位结果与边界

- 岗位目标：把选品立项交来的概念，经过工程、设计、制造和量产验证，形成可发布、可追溯的产品定义。
- 主要选择源：按风险、门槛阻断、截止时间和等待时长排序的 NPI 项目队列。
- 当前主动作：领取或接受概念；补齐当前阶段最优先的门槛缺口；提交阶段评审；MP 通过后发布。任一时刻只突出其中一个。
- 必须看到：立项快照、当前责任人和下一责任人、阶段基线、交付物、证据、未关闭问题、冻结级别、变更影响、截止时间和外部同步状态。
- 完成结果：MP 阶段评审通过后，由产品负责人执行“发布并交主数据建档”，形成不可变交接快照。
- 权威边界：选品立项拥有概念判断；NPI 拥有工程到量产验证；主数据拥有发布后的产品、物料、BOM、SKU 和 Listing 身份。三个岗位不得相互改写对方事实。

“概念 → EVT → DVT → PVT → MP”是本项目的标准主路径。不同品类可以增加专项验证，
也可以申请不适用，但必须记录适用性、理由、批准人和影响；不得由页面、AI 或执行人员
静默跳段。样机数量、良率、可靠性和认证项目是产品级门槛，必须在对应阶段开始前确定，
不能把行业常见数字硬编码成所有产品的统一标准。

### 5.2 每一阶段共同的工作闭环

每一阶段都必须走完以下闭环，缺任一步都只能显示“进行中、等待或返工”，不能显示通过：

1. **定计划**：明确本阶段交付物、适用测试、通过门槛、负责人、计划完成时间和证据要求。
2. **做验证**：按受控版本制作样机或生产批次，执行测试、评审或产线验证。
3. **收证据**：登记样机或批次、测试结果、外部报告、来源、版本、执行人与发生时间。
4. **处问题**：问题分级，明确责任人、截止时间、处置和再验证；阻断问题未关闭不能过门。
5. **作决定**：有权限的人选择通过、返工、暂停或终止，并写明结论；AI 不得代替决定。
6. **做交接**：通过时冻结本阶段快照，写清下一阶段接收队列、待办事项和当前冻结级别。

阶段通过不是“填过一段结论”，也不是系统根据材料数量自动判断测试成功。系统只验证
门槛是否完整、证据是否有效、阻断问题是否关闭和决定人是否有权限；业务人员对结果负责。

### 5.3 概念阶段（Concept）闭环

- 岗位结果：确认要解决的用户问题、目标市场和商业假设值得进入工程验证。
- 权威输入：选品立项的不可变交接快照，包括目标用户与市场、竞争与供应、价格带与利润、合规风险四类评审结果。
- 当前主动作：NPI 负责人接受交接；交接不完整或立项假设发生实质变化时，填写原因退回选品。
- 必须看到：立项目标、依据与来源、主要假设、已知风险、待补事项、发起人、接收队列和交接版本。
- 必需交付：产品目标和范围、目标市场与用户、价值和利润假设、主要合规与供应风险、NPI 负责人和阶段计划。
- 通过门槛：选品立项已经通过；交接必填项齐全；NPI 责任已被接受；没有使立项结论失效的未处置阻断问题。
- 失败与恢复：信息待补时保持原交接并进入等待；实质性问题退回选品重判；选品重新通过后产生新版本交接，不能覆盖旧版。
- 完成证据：概念阶段展示选品通过快照和 NPI 接收记录，不在 NPI 内复制第二套概念结论。

### 5.4 EVT 阶段闭环

- 岗位结果：证明核心功能、工程架构和关键技术方案能够实现。
- 权威输入：已接受的概念快照、工程需求基线、EVT 计划和预先确定的通过标准。
- 当前主动作：关闭当前最高优先级的工程验证缺口，全部就绪后提交 EVT 阶段评审。
- 必须看到：需求与验证项的对应关系、样机或构建版本、功能测试结果、工程风险、失败现象、责任人和再验证状态。
- 必需交付：工程需求基线；架构和关键器件或材料方案；工程样机或构建记录；功能测试报告；关键工程风险处置；下一阶段验证计划。
- 通过门槛：必测核心功能达到预设标准；工程方案可行；没有未关闭阻断问题；未关闭非阻断问题都有责任人、期限和 DVT 承接计划。
- 失败与恢复：测试失败进入返工并保留原结果；方案变化形成新工程版本和影响记录；概念假设失效时退回选品，不得在 EVT 内偷偷改立项依据。
- 完成证据：EVT 通过决定、受控版本、测试结果、问题处置和交给 DVT 的不可变快照。

### 5.5 DVT 阶段闭环

- 岗位结果：证明设计在目标使用、可靠性和适用法规下稳定，并形成设计冻结基线。
- 权威输入：EVT 通过快照、DVT 设计基线、可靠性计划、目标市场法规和认证要求。
- 当前主动作：关闭当前最高优先级的设计、可靠性或合规缺口，全部就绪后提交 DVT 阶段评审。
- 必须看到：设计版本、模具或样件版本、可靠性和滥用测试、认证状态、问题严重度、设计变更及其影响和再验证范围。
- 必需交付：设计基线；适用的模具或样件记录；可靠性与寿命验证；适用法规和认证结果；设计风险与变更处置；PVT 生产验证计划。
- 通过门槛：设计满足预设的功能、可靠性和市场准入要求；设计相关阻断问题已关闭；设计冻结范围和例外明确；PVT 所需资料和验收标准就绪。
- 失败与恢复：失败项必须关联设计更改或接受决定并再验证；外部认证未完成或被拒绝时按其市场适用性阻断，不得写“预计能过”冒充通过。
- 完成证据：DVT 通过决定、设计冻结版本、测试与认证证据、遗留事项和交给 PVT 的不可变快照。

合规工作不能等到 DVT 才开始。概念阶段识别目标市场风险，EVT 做方案和预测试，DVT
完成适用的正式验证；界面必须保留这条连续证据链。

### 5.6 PVT 阶段闭环

- 岗位结果：证明正式产线、工装、物料、人员和作业方法能够按目标质量与节拍稳定复制产品。
- 权威输入：DVT 通过和设计冻结快照、正式生产资料、PVT 批次计划以及预先批准的良率、质量、节拍和产能门槛。
- 当前主动作：关闭当前最高优先级的生产验证缺口，全部就绪后提交 PVT 阶段评审。
- 必须看到：批次和序列范围、正式产线与工装、物料批次、作业指导书、检验计划、良率和缺陷分布、返工、节拍、产能和供应准备情况。
- 必需交付：正式产线试产记录；受控 BOM、工艺和作业指导书；检验与过程控制方案；良率及缺陷分析；产能和供应链准备结果；量产爬坡计划。
- 通过门槛：预先批准的良率、质量和节拍门槛达到；主要缺陷有闭环证据；生产资料受控；供应和产能满足批准计划；没有未关闭阻断问题。
- 失败与恢复：工艺问题留在 PVT 调整并再跑；涉及冻结设计的变化必须进入变更评审，通常回到 DVT 做受影响验证后再进入 PVT。
- 完成证据：PVT 通过决定、批次和产线证据、质量和产能结果、遗留事项和交给 MP 的不可变快照。

PVT 批次不因“做出来了”就自动成为可售库存。只有同时满足质量放行、法规、标识、
追溯和库存接收条件的单位，才能按单独的放行决定转为首批库存。

### 5.7 MP 阶段闭环

- 岗位结果：证明产品已经在受控量产和爬坡中保持质量、交付和供应稳定，达到对外发布条件。
- 权威输入：PVT 通过快照、批准的量产版本、量产授权、爬坡计划、质量控制计划和供应保障计划。
- 当前主动作：关闭当前最高优先级的量产放行缺口，全部就绪后提交 MP 阶段评审。
- 必须看到：量产版本、批次和产量、良率与缺陷趋势、停线或偏差、供应风险、交付准备、质量放行和受控变更。
- 必需交付：量产放行决定；爬坡批次质量结果；交付与售后准备；供应连续性确认；量产变更控制和早期质量监测安排。
- 通过门槛：批准版本已投入受控量产；质量和交付门槛达到；适用市场准入完成；供应、追溯、售后和召回所需信息就绪；没有未关闭阻断问题。
- 失败与恢复：量产异常可在 MP 内受控纠正；涉及产品设计、法规或关键工艺的变化必须按影响回开 DVT 或 PVT 验证，历史 MP 记录不被覆盖。
- 完成证据：MP 通过决定、量产与质量证据、开放但不阻断事项及责任、可发布产品定义版本。

### 5.8 冻结、变更与返工规则

| 阶段 | 冻结要求                     | 允许变化                     | 变化后的最低处理                            |
| ---- | ---------------------------- | ---------------------------- | ------------------------------------------- |
| 概念 | 冻结立项目标和关键假设快照   | 选品可重判并形成新交接版本   | NPI 重新接受，不改写旧交接                  |
| EVT  | 版本化工程需求和方案         | 允许工程迭代                 | 记录原因、影响和受影响项再验证              |
| DVT  | 形成设计冻结基线             | 只允许受控设计变更           | 变更评审、影响分析和适用的 DVT 再验证       |
| PVT  | 设计原则上冻结，生产资料受控 | 正常调整工艺；设计变化为例外 | 工艺再验证；设计变化通常回开 DVT 后重做 PVT |
| MP   | 发布版本、工艺和质量基线受控 | 仅经批准的工程或生产变更     | 按影响回开 DVT/PVT/MP，并产生新发布版本     |

“阶段不可逆”只表示已通过的快照和审计历史不可删除、不可改写，不表示发现问题后禁止
返工。当前工作阶段可以受控回开；系统必须记录发起人、原因、影响范围、批准人、回开到
哪一阶段和重新通过的版本。

阶段决定只有通过、返工、暂停和终止。非阻断遗留项可以在有责任人和期限时随交接带入，
但不得用含糊的“有条件通过”掩盖阻断问题。

### 5.9 发布并交主数据

“发布并交主数据建档”是 MP 闭环完成后的终止动作，不是与 MP 并列的第六阶段，也不能
在 EVT、DVT、PVT 或未通过的 MP 阶段出现为可执行主动作。

发布必须同时满足：当前阶段为 MP；MP 决定为通过；必需交付物和证据完整；没有未关闭
阻断问题；发布人有权限；将要交出的产品定义版本明确。发布在同一业务事务中形成不可变
交接快照，至少包含来源立项与历次阶段快照、发布版本、规格与适用市场、合规依据、关键
物料或 BOM 引用、变更状态、发送方、主数据接收队列、待补事项、发布时间和幂等标识。

主数据岗发现建档资料缺口时，只能退回待补或请求新版本，不能反写 NPI 历史。新版本发布
后保留旧版本及两者关系。

### 5.10 界面与人性化操作规则

- 首屏先显示“为什么现在要处理、卡在哪里、由谁处理、最晚何时”，阶段轨只做导航和状态摘要。
- 当前阶段工作区固定展示交付物清单、证据、问题与责任、门槛判断四块；每一项都能追到来源和版本。
- 只编辑当前阶段；已通过阶段可查看不可变快照，未来阶段只显示计划和前置缺口。
- 阶段卡住时逐项列出缺什么、为什么阻断、谁补、何时到期和补完后怎样恢复，不用百分比、齐半缺或颜色替代具体缺口。
- 页面底部只保留一个当前主动作；退回、暂停和终止是次要但可达动作，均需展示影响并按规则要求原因。
- 正常样机、测试或问题可批量登记并先预检；阶段通过、返工、暂停、终止、设计变更和异常恢复必须逐项目确认。
- 外部实验室、工厂或认证结果属于外部观测，只有完成匹配、来源核验和人员采信后才成为门槛事实；同步失败单独显示。
- AI 可以匹配需求与测试、摘要报告、提示遗漏和排序风险；不得生成不存在的测试结果、关闭问题、确认责任、判定阶段通过或执行发布。

入口按本工作台实际适用：正常项目只从选品交接进入，不能在 NPI 本岗新建项目绕过立项；
批量导入只用于样机、测试、问题和生产结果，并必须预检、幂等、逐行反馈和可恢复。退出分为
退回选品或回开阶段、暂停或终止后归档、仅对从未交接且没有证据引用的误建草稿受限删除。

### 5.11 结果指标与真实验收

岗位指标至少包括阶段首次通过率、从阶段开始到决定的周期、等待时间、阻断问题关闭周期、
设计变更与回开次数、PVT 良率相对门槛、量产爬坡稳定性和发布后早期质量问题。样本数、
按钮点击、页面访问和录入条数不能冒充绩效。

真实岗位验收必须使用真实或脱敏项目，逐段验证正常通过、等待外部结果、评审拒绝、版本
冲突、测试失败返工和问题关闭后恢复。还必须覆盖 DVT 后设计变更回开、PVT 批次不合格、
MP 未通过禁止发布、主数据退回待补和新版本再发布。没有这些证据前，不得声称 NPI 闭环
已经符合行业最佳实践。

## 六、备货工作台（`cargo_ready`）

- 岗位目标：让供应商按时、按量并满足适用要求地备齐货物。
- 每日优先事项：临近承诺日期、缺货、合规阻断和装箱计划已锁定的备货单。
- 必须看到：备货单、SKU/物料、数量、供应商承诺、缺口、合规整改和装箱要求。
- 允许动作：确认接单、反馈缺口、调整承诺、上传凭证和申请备货完成。
- 前置条件：备货单身份明确，产品行可识别；缺 SKU 时显示待补全及受限动作。
- 失败处理：数量、身份或合规冲突进入补正，不用默认值替代。
- 完成结果：形成可装箱的备货结果，不表示已经装箱。
- 权威事实：供应商承诺、备货数量、有效证据及经核验的备货完成事实。
- 下游交接：向装箱工作台交付可装产品行、限制条件和所需凭证。

## 七、装箱工作台（`stuffing`）

- 岗位目标：准确记录一只柜实际装了什么，并完成箱号、封条和 VGM 交接。
- 每日优先事项：临近截港、装载冲突、超量分配、缺箱号或封条和 VGM 未接受的任务。
- 必须看到：待装产品、剩余数量、来源备货单、箱型、重量、冲突和凭证。
- 允许动作：分配和调整货物、绑定箱号、登记封条、记录称重和提交 VGM。
- 前置条件：备货结果可用、装载对象可识别、数量单位一致并满足专业约束。
- 失败处理：超分配、重复箱号、重量异常或 VGM 拒绝进入补正，保留原版本。
- 完成结果：形成版本化实际装载；更正不能抹掉上一版。
- 权威事实：当前有效装载版本、箱号、封条、称重/VGM 回执和装箱实际日期。
- 下游交接：向出运工作台交付柜内货物、运输设备身份和装船前限制。

## 八、出运工作台（`dispatch`）

- 岗位目标：确保满足条件的货柜完成进港、装船和离港交接。
- 每日优先事项：临近截点、VGM/单证缺失、进港异常、甩柜和船期变化。
- 必须看到：订舱、船名航次、港口、截点、VGM、单证、Hold 和外部同步结果。
- 允许动作：补全运输资料、处理拒绝、确认运输路线和登记专业事实。
- 前置条件：货柜身份、装载、订舱和必要装船条件明确。
- 失败处理：身份、航次、港口或回执冲突进入复核，不用任务完成冒充事实。
- 完成结果：由可靠装船或离港事实证明货柜已经出运。
- 权威事实：进港、装船、离港的实际日期及对应来源证据。
- 下游交接：向海运运营工作台交付路线、航次、单证和时间基线；清关通过海运运营的到港准备交接接收所需事实。

出运工作台不继续办理海运、清关、提柜、送仓、卸柜或还箱。它可以显示下游去向
和交接结果，但不得拥有下游专业动作或改写下游事实。

## 九、海运运营工作台（`ocean_operations`）

- 岗位目标：从实际离港开始持续掌握航段和货柜执行变化，使下游基于最新且可解释的海运事实工作。
- 每日优先事项：ETA 显著变化、中转风险、甩柜或改港、长时间无更新、多来源冲突和即将到港但下游未准备。
- 必须看到：Shipment、货柜、当前航段、船名航次、港序、中转关系、ETA 历史、最新实际事件、来源和新鲜度。
- 允许动作：确认或驳回来源候选、关联换船或新航段、登记异常、锁定人工核验值和通知受影响岗位。
- 前置条件：外部身份能够匹配本次运输实例，来源语义和地点明确，实际事件具备来源资格。
- 失败处理：无法匹配、来源冲突、状态倒退或接口陈旧进入复核；甩柜、改港和中转失败形成异常案件。
- 完成结果：清关、提柜和仓库等下游获得最新裁决事实和变化通知，而不是一条被覆盖的 ETA。
- 权威事实：航段和换船版本、外部观测、采用的计划/预计/实际时间、来源裁决、异常和通知回执。
- 下游交接：向清关提供到港窗口，向提柜和仓库提供执行影响，向费用提供可采信的计费起点。

## 十、清关工作台（`customs`）

- 岗位目标：在时限内完成资料、申报、查验、缴税和放行。
- 每日优先事项：申报或 ISF 临期、资料缺失、回执拒绝、查验、Hold 和临近到港货柜。
- 必须看到：国家规则、HS Code、文件齐套、接收方、传送回执、案件状态和截止时间。
- 允许动作：分派报关行、补件、复核、发送资料、登记回执和处理查验或放行。
- 前置条件：适用国家资料参数、清关接收方、必要附件和责任主体明确。
- 失败处理：发送失败、资料拒绝、规则冲突和来源不足分别进入重试、补正或复核。
- 完成结果：以海关或认可渠道的放行证据为依据。
- 权威事实：申报、查验、Hold、放行事实及相应文件和回执。
- 下游交接：向提柜工作台提供清关放行、未解除限制和可用证据。

## 十一、提柜工作台（`pickup`）

- 岗位目标：在码头、海关、船司和资源条件同时满足后完成提柜。
- 每日优先事项：临近最晚提柜日、已可提未预约、Hold、车队冲突和高费用风险。
- 必须看到：可提条件、Hold、预约、车队、仓库或堆场容量和成本风险。
- 允许动作：预排、锁定计划、派车、扫码、上传 EIR 和登记重柜出场。
- 前置条件：清关放行、船司放货、码头可提和预约资格满足。
- 失败处理：预约失败、司机或车辆变更和码头拒绝触发重排或升级异常。
- 完成结果：以可靠 Gate Out 证据确认。
- 权威事实：码头重柜出场实际时间、EIR 及执行资源。
- 下游交接：向送仓工作台交付在途任务、目的地和预约；改送堆场时形成受控分段交接。

## 十二、送仓工作台（`delivery`）

- 岗位目标：按预约把货柜送到正确仓库或受控临时堆场。
- 每日优先事项：在途超时、预约临近、仓库拒收、改送和司机异常。
- 必须看到：路线、车辆、目的地、预约、等待、改送方案和 POD 要求。
- 允许动作：确认接单、登记到场、申请改送和上传 POD。
- 前置条件：有效提柜事实、目的地指令、预约和承运资源存在。
- 失败处理：堵车、拒收、错送和证据缺失分别进入改约、改送或补证。
- 完成结果：确认货柜到达指定地点，但不等于卸柜完成。
- 权威事实：实际到达、POD、承运资源和异常记录。
- 下游交接：直送仓交卸柜；临时改送形成保管和二次运输交接，不把原任务伪装成完整送仓。

## 十三、卸柜工作台（`unloading`）

- 岗位目标：完成实物接收、处理差异并确认货柜卸空。
- 每日优先事项：已到仓待卸、月台等待、部分卸货、短溢损和破损。
- 必须看到：预计和实际 SKU/物料、数量、批次、破损、部分卸货和剩余量。
- 允许动作：扫码收货、登记差异、拍照、暂停或继续卸货和完成核对。
- 前置条件：货柜实际到场、卸货资源可用且收货对象可识别。
- 失败处理：未知 SKU、数量冲突、破损或部分卸货形成差异和后续任务。
- 完成结果：货物实际卸出并完成规定核对；只有确认卸空后才能交还箱。
- 权威事实：卸货进度、实收数量、差异、证据和卸柜实际完成时间。
- 下游交接：向 WMS 交实收结果，向还箱工作台交空箱状态。

## 十四、还箱工作台（`empty_return`）

- 岗位目标：在截止时间前将符合要求的空箱还到指定场站。
- 每日优先事项：临近最晚还箱日、预约缺失、场站变更、箱损和费用风险。
- 必须看到：还箱场、截止时间、预约、箱况、EIR 和费用风险。
- 允许动作：派车、登记到场、上传空箱回场凭证和发起损坏争议。
- 前置条件：卸空确认、可接受场站和有效预约或指令存在。
- 失败处理：场站拒收、预约失效或箱损争议进入改派、补证和费用处理。
- 完成结果：有可靠还箱接收证据；物流责任关闭与费用关账分别可见。
- 权威事实：空箱场站接收时间、EIR、箱况和争议记录。
- 下游交接：向费用结算和绩效复盘交还箱结果。

## 十五、费用结算工作台（`charges`）

- 岗位目标：把生命周期费用从估算、计提、账单核验、分摊和争议推进到支付或关账。
- 每日优先事项：即将跨过免费期、账单超过估算、缺计费证据、重复收费、争议临期和物流完成但财务未关闭。
- 必须看到：费用类型、计费对象、服务期间、费率版本、数量和阶梯、币种税费、各金额阶段、凭证和责任方。
- 允许动作：刷新估算、建立计提、匹配账单、确认差异、发起争议或索赔、按规则分摊、提交审批和登记支付结果。
- 前置条件：计费起止事实、费率和币种明确，账单身份唯一，分摊基础可解释。
- 失败处理：缺计费事件进入补证，费率不适用进入合同复核，重复账单阻断，争议期间保留未决金额。
- 完成结果：每项费用有核定结果、分摊去向和支付或争议结论；物流完成与财务关账分别可见。
- 权威事实：费率版本、计费期间、估算、计提、账单、核定、分摊、争议、审批和支付证据。
- 下游交接：向财务付款和经营分析交核定金额，向相关岗位反馈成本和索赔结果。

金额使用定点数并携带币种。跨币种分析保存汇率来源和日期；分摊必须保留原始费用
和分摊规则，不能只剩摊后结果。

## 十六、异常中心（`exceptions`）

- 岗位目标：集中分派跨工作台无法在正常路径内解决的问题，并把处理结果归还权威业务域。
- 每日优先事项：阻断主流程、临近法定或费用期限、高影响和长期未处理异常。
- 必须看到：对象、影响、来源证据、责任岗位、截止时间和关联任务。
- 允许动作：认领、分派、补证、升级、纠偏、解除和关闭。
- 前置条件：异常类型、来源事实和影响对象明确。
- 失败处理：无法判断时保持开放并升级，不用自由文本直接改变专业事实。
- 完成结果：异常原因得到解决，或形成经批准且可追溯的风险接受。
- 权威事实：异常、处理决定、补偿或纠偏结果和关闭证据。
- 下游交接：解除阻断后重放原业务事实或通知原工作台继续执行。

异常中心不拥有清关、费用、生命周期或其他专业结论。它只管理跨域分派、升级和
恢复；专业事实仍由原业务域确认。

## 十七、跨工作台交接与反馈

下游发现问题时不得直接改上游字段。例如仓库发现短货，应登记实收差异并请求
装箱或供应链核对；清关发现品名或 HS 资料不一致，应建立缺口和补件任务；费用
岗位发现还箱时间缺证，应请求还箱岗位补证。原岗位处理后返回新版本或明确驳回，
下游再决定重算、继续或升级异常。

每次交接必须显示：

1. 交接对象和不可变版本；
2. 发送岗位、发送人和发送时间；
3. 接收岗位、接收队列和当前责任人；
4. 已确认事实、限制条件和待补事项；
5. 接收、拒绝、冲突或同步失败的结果；
6. 返工后替代了哪个旧版本。

## 十八、任务池、详情页和导入

每个工作台首页是可行动的任务池，不是字段总表。默认按业务原因、期限和影响排序，
支持岗位实际需要的国家、港口、仓库、伙伴、责任人、时间窗和风险筛选。

详情页保持稳定阅读顺序：

1. 为什么现在需要处理以及最晚决定时间；
2. 完成判断所需的业务上下文；
3. 已确认事实、真实缺口、异常、外部观测和同步结果；
4. 服务端当前允许的唯一主动作及必要恢复动作；
5. 操作形成的业务结果、证据、下一责任人和交接状态。

导入、本岗新建和上游交接必须进入同一权威对象、同一校验和同一后续流程。历史
导入可以恢复已经发生的事实，但不得要求岗位重演已经结束的业务动作。具体导入
过渡规则见[导入与正常流程衔接](./07-import-transition.md)。

## 十九、验收

每台工作台必须依次完成：

1. 行业实践对照，只把有一手证据且适用于本项目的内容作为候选；
2. 当前代码、契约、数据库、迁移、测试和真实样本的事实审查；
3. 对误导操作、错误推进、历史丢失、责任混淆和重复劳动的批判评审；
4. 推荐方案、替代方案、成本、收益和风险比较；
5. 当前获准工作台的独立 task brief；
6. 实现后由真实岗位完成 `WB-B10` 六类路径验收。

只证明 API 可调用、数据已落库、页面能打开或按钮能点击，均不算岗位业务完成。
