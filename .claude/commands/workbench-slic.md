# 工作台业务薄片接管

工作台参数：`$ARGUMENTS`

你正在接管 Logixs 的一台业务工作台。本命令只负责业务核对、数据流梳理和薄片定义；除非负责人明确要求实施，否则不得修改产品代码、测试、迁移、运行配置或生成物。

## 1. 先恢复现场

开始前必须：

1. 读取仓库根目录 `AGENTS.md` 和目标目录适用的嵌套 `AGENTS.md`；
2. 核对当前分支、HEAD、`git status` 和相关 worktree；
3. 找到该工作台的正式 `doc/` 业务权威、对应 `wisdom-baseline`、`README`、已接受 ADR 和当前 task brief；
4. 按顺序核对 Schema/迁移、服务端、前端、测试和现有样本；
5. 只加载当前工作台和当前业务步骤需要的材料，不扫描无关工作台，不触碰其他任务的未跟踪或未提交内容。

智慧基线是决策输入，不自动替代正式业务权威；聊天内容不是项目权威。

## 2. 数据真实性与演示数据

负责人确认的真实业务数据直接作为项目业务数据使用，不再反复要求外部来源、历史实绩或第三方材料证明其真实性。

开发演示数据只验证是否符合真实业务规则，不验证是否真实发生。可以在明确标记 `development_demo` 的范围内补充计划、演示 actual、金额和其他场景值，以支持工作台开发；必须检查对象关系、事件类型、时间先后、时区/精度、数量/单位/币种、职责权限和上下游流转。演示 actual/金额不得伪称生产事实或原始来源证明，不得关闭服务端安全控制。

现有演示数据不因某项验证未通过而整体阻塞进度。应在现有数据基础上：

- 确认业务需要什么；
- 确认当前已经有什么；
- 找出缺什么；
- 找出字段、关系、版本、语义或显示错误；
- 修正错误；
- 增加当前业务步骤真正需要的承载。

只有错误会导致当前动作不安全、越权、无法解释、无法落账或无法交接时，才阻塞该动作。其他缺项标记为“未知/待补/不适用”，继续推进不依赖它的步骤。

不得把未知显示为 0，不得把候选当承诺，不得把计划/预计当实际，不得编造负责人、阈值、金额、权限、来源或验证结果。

## 3. 固定推导顺序

严格按以下顺序分析：

```text
业务目的
→ 优先减少的损失
→ 目标岗位的唯一业务结果
→ 当前最小办理步骤
→ 岗位要看的事实
→ 允许动作和前置条件
→ 本台产生的事实/决定/回执
→ 下游消费与责任交接
→ 关键字段和业务记录/表结构
→ 权限、技术和 UI 承接
→ actual 回流与结果验证
```

不能从已有数据库字段、API 或页面倒推业务目的。

## 4. 每次只推进一台、一个步骤

先用业务人员能理解的话说明：

- 谁在什么情况下接手；
- 为什么现在要处理；
- 要回答什么问题；
- 需要看哪些事实；
- 可以做什么；
- 操作后产生什么结果；
- 交给谁；
- 失败、拒绝、冲突和恢复怎么办。

不要一次设计整台工作台，不要先建设通用平台，不要把“当前经营决定卡”做成新的工作台。

当前经营决定卡只作为跨工作台追溯和验真入口，连接：

```text
上游依据
→ 本台事实与判断
→ 本台决定/执行回执
→ 下游接收
→ actual 与差异解释
```

它不复制各领域权威事实，也不赋予跨领域写权限。

## 5. 必须说明数据流

对当前步骤分别列出：

### 上一个工作台输出

上游产生的业务事实、决定、承诺、版本和交接回执。

### 本台读取

本台办理必须消费的字段、来源、版本、新鲜度和缺口。

### 本台产生

本台形成的事实、判断、决定、异常、执行请求、交接快照或回执。

### 下游消费

下游岗位消费的字段，以及接受、拒绝、补充或退回方式。

### actual 回流

执行后从哪里取得实际结果、何时观察、如何与原决定/计划比较，以及差异如何解释。

## 6. 固定增加双面财务投影

每个业务步骤同时输出两层：

### 岗位执行层

- 当前任务、责任人、等待对象和截止时间；
- 允许动作与前置条件；
- 成功结果、拒绝原因、冲突处理和失败恢复；
- 下一责任人与下游接收。

### 双面财务投影层

分别表达：

- 收入/贡献；
- 成本/费用；
- 现金；
- 库存；
- 风险/机会。

每项标明属于：`actual`、`plan`、`commitment`、`projected`、`forecast`、`assumption` 或 `unknown`。

不要把库存本金当成本，不要把现金回收当利润，不要把预计避免支出当已实现收益，不要重复计算落地成本及其组成项。对象、期间、币种、数量基础或包含关系不可比时保留分项并说明原因，不强行合成净额。没有直接财务影响时写“本动作无直接金额确认”，不要补 0。

## 7. 从业务问题推导关键字段和表结构

先用业务语言说明每条业务记录代表什么：

- 一行代表什么业务对象；
- 谁产生；
- 谁拥有；
- 谁读取；
- 哪些字段来自上游；
- 哪些字段由本台产生；
- 哪些字段本台不能修改；
- 如何保留版本和更正；
- 下游如何引用。

然后列出当前步骤真正需要的关键字段：

1. 对象身份与业务范围；
2. 当前问题、触发和优先级；
3. 事实值、事实类型、来源、版本和新鲜度；
4. 缺口、冲突和错误；
5. 允许动作及前置条件；
6. 决定人、执行人、责任和交接；
7. 双面财务投影；
8. 结果回执；
9. actual 与差异解释；
10. 审计、幂等、并发和恢复所需信息。

现有字段如果不支撑当前业务结果，不要因为已经存在就纳入本片；没有当前消费者的未来字段不要预建。

## 8. 固定区分事实类型

每个结论标记为以下之一：

- 已证实项目事实；
- 负责人已定业务政策；
- 当前实现事实；
- 当前实现差距；
- 行业候选；
- 未知/待补；
- 本轮建议。

行业候选未经负责人定案，不得进入 Schema、契约、权限或生产界面。

## 9. 交互规则

每轮先说结论，再说依据、影响、代价和下一步。

只有以下事项需要负责人决定：业务目的和优先损失、岗位唯一结果、状态和完成语义、责任交接、允许动作和权限政策、风险接受、金额/指标口径、不可逆业务成本。

需要负责人决定时，最多提出 1～3 个互斥选项，第一项给出推荐，并说明收益、成本、风险、边界和可逆性。普通工程选择由主代理直接负责，不把命名、目录、测试组织和可逆实现细节反问负责人。

## 10. 固定首轮输出

按以下顺序输出：

1. 核心业务目的；
2. 优先减少的损失；
3. 目标岗位和唯一业务结果；
4. 当前最小业务步骤；
5. 上游交来的数据；
6. 本台需要读取的数据；
7. 本台产生的数据；
8. 下游消费和责任交接；
9. 岗位执行层；
10. 双面财务投影；
11. 跨工作台追溯与验证链；
12. 关键字段和业务记录/表结构；
13. 已有、缺失和错误；
14. 当前页面/API/Schema 能承接什么；
15. 第一片业务薄片；
16. 验收路径和反证；
17. 真正需要负责人决定的事项；
18. 下一步。

用业务人员能理解的语言先讲清楚，再补充技术映射。不要在首轮直接写实现代码、建表、建 API、改页面或创建通用平台。

## 11. 完成声明限制

页面存在、API 可调用、数据已落库、Schema 已建立、测试通过、状态标记为 live、通知已发送或演示数据能显示，都不能单独证明工作台完成。

只有当目标岗位能够：

```text
识别优先事项
→ 理解事实与缺口
→ 执行允许动作
→ 确认正式结果
→ 看到下一责任人
→ 处理失败/冲突/恢复
→ 完成下游交接
→ 取得 actual 并解释差异
```

才可以称当前业务步骤完成。整台工作台仍需逐项核对共同最低线，不能用一片薄片冒充整台完成。
