# GC-012 G0: 23-Workbench Catalog Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the current normative 20-workbench linear catalog with the approved 23-workbench authority and a typed fan-in/fan-out graph, without adding GC-012 contracts or production actions.

**Architecture:** Business authority owns the 23 names, kinds and outcomes. A single typed Web catalog renders the directory and routes; relations are stored separately from stages, so reading order does not masquerade as business topology. Maturity and route surface are separate properties.

**Tech Stack:** Markdown authorities, TypeScript, Vue 3, Vue Router, Vitest, Playwright, Node repository checks, pnpm 10.

**Spec:** `docs/superpowers/specs/2026-10-03-gc12.md`

## Global Constraints

- Exactly 23 codes: 20 main-chain and 3 support/cross-cutting.
- Add `booking`, `export_customs`, `compliance_operations`.
- Keep technical code `customs`; formal display name becomes “进口清关”.
- G0 does not create GC-012 Schema, DB tables, APIs, receipts, responsibility transfer or production handoff actions.
- Reading order and graph edges are separate; do not restore an implied adjacent linear chain.
- New workbenches are `planned` and use catalog stubs with no production actions.
- Existing route/page behavior remains available; maturity is not inferred from `live`, route or API existence.
- Historical completed briefs, archives and historical sample counts are not rewritten.

## Review Focus

1. `/compliance` must remain distinct from `/workspaces/compliance-operations` and must not promote the new workbench.
2. A route or dedicated page must not imply `operational` or `validated` maturity.
3. Graph relations must support multiple incoming/outgoing edges without duplicating endpoints or inventing formal handoff types before G1.
4. Current historical documents containing “20” as sample/object counts or past execution evidence must remain untouched.
5. Planned stubs for booking/export customs/compliance operations must render no save/submit/complete controls at desktop, 375px and 320px.

- [ ] **Step 3: Implement the catalog types**

Use these exact public shapes:

```ts
export type WorkbenchMaturity =
  "planned" | "facts_only" | "operational" | "validated";
export type WorkbenchSurface = "dedicated" | "catalog_stub";
export type WorkbenchRelationKind = "handoff" | "fact_dependency";

export type WorkbenchAssessmentState = "pending_assessment" | "assessed";

export interface WorkbenchStage {
  code: WorkbenchCode;
  title: string;
  path: string;
  kind: "main" | "support";
  phase: WorkbenchPhase;
  sequence: number | null;
  assessmentState: WorkbenchAssessmentState;
  maturity: WorkbenchMaturity | null;
  surface: WorkbenchSurface;
  ownerRole: string;
  roleResult: string;
  requiredFacts: readonly string[];
}

export interface WorkbenchRelation {
  code: string;
  from: WorkbenchCode;
  to: WorkbenchCode;
  kind: WorkbenchRelationKind;
  handoffCode: string | null;
  label: string;
  facts: readonly string[];
}
```

Add:

```ts
export const workbenchBaseline = {
  version: "2026-10-03",
  total: 23,
  main: 20,
  support: 3,
} as const;

export function getInboundWorkbenchRelations(code: WorkbenchCode) {
  return workbenchRelations.filter(({ to }) => to === code);
}
export function getOutboundWorkbenchRelations(code: WorkbenchCode) {
  return workbenchRelations.filter(({ from }) => from === code);
}
export function getUpstreamWorkbenchStages(code: WorkbenchCode) {
  return getInboundWorkbenchRelations(code).map(({ from }) =>
    workbenchStage(from),
  );
}
export function getDownstreamWorkbenchStages(code: WorkbenchCode) {
  return getOutboundWorkbenchRelations(code).map(({ to }) =>
    workbenchStage(to),
  );
}
export function isProductionMaturity(maturity: WorkbenchMaturity | null) {
  return maturity === "operational" || maturity === "validated";
}
```

Keep route surface separate from maturity. Assign all three new workbenches `assessmentState: "assessed"`, `maturity: "planned"`, `surface: "catalog_stub"`. Assign every existing workbench `assessmentState: "pending_assessment"`, `maturity: null`, while preserving its current surface/runtime behavior. Do not assign any `validated` status in G0. `isProductionMaturity(null)` must return false; authorization and route behavior remain governed by existing runtime controls, not this catalog helper.

For relations whose formal GC-012 type does not yet exist, use `kind: "fact_dependency"` and `handoffCode: null`. G1 later upgrades only approved formal handoff relations.
