# GC-012 Cross-Workbench Rollout Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver the approved 23-workbench catalog and a provisional GC-012 handoff/responsibility contract, then validate it through market→selection and selection→NPI without building a universal workflow platform.

**Architecture:** Execute four independently reviewable stages. G0 establishes the 23-workbench authority and graph; G1 defines the provisional shared contract without persistence; G2 and G3 add domain-owned adapters, append-only receipts and responsibility projections to two existing handoff paths. Existing domain snapshots remain authoritative payloads.

**Tech Stack:** Markdown authorities, TypeScript, Vue 3, NestJS 11, Prisma ORM 7, PostgreSQL 16, JSON Schema, Vitest, Playwright, pnpm 10.

**Spec:** `docs/superpowers/specs/2026-10-03-gc12.md`

## Global Constraints

- The approved catalog is exactly 23 workbenches: 20 main-chain and 3 support/cross-cutting.
- New stable codes are `booking`, `export_customs`, and `compliance_operations`; technical code `customs` remains and its formal display name becomes “进口清关”.
- GC-012 is a minimal facade over domain payloads; it does not own domain state machines, business completion, fees, exceptions, evidence bodies or a universal persistence table.
- `received`, `claimed`, `accepted`, `rejected`, `return_requested`, `return_accepted`, and `superseded` are append-only facts; `closed` is not a shared disposition.
- Default responsibility transfers only on `accepted` and transfers back only on `return_accepted`.
- `planned`, `facts_only`, `operational`, and `validated` are maturity levels; routes, pages and APIs never promote maturity by themselves.
- Existing domain handoffs and V1 APIs remain available during explicit compatibility windows.
- The controlled off-repo sample package is mixed R/D/S/P evidence. It may guide G0/G1 and mechanism tests, but it does not satisfy G2/G3 real-role receipt, KPI, WB-B10 or stable-V1 gates.
- No task may copy the sensitive workbook, its exact local path, its fingerprint, or identifiable business data into the repository.
- Historical completed briefs and archives retain their historical 20-workbench wording; current authorities and live governance surfaces move to 23.
- Every behavior change follows RED → GREEN. High-risk integrated candidates run one final `pnpm validate` and fresh read-only review.

## Review Focus

1. A route or existing `live` marker must not silently promote a workbench to `operational` or `validated`; G0 tests pin maturity independently from surface routing.
2. A `claimed` handoff must leave cross-workbench result responsibility with the sender; G2/G3 domain and PostgreSQL tests pin this invariant.
3. A return request that is rejected, unaccepted or races another write must leave current responsibility intact; G2/G3 concurrency tests pin this invariant.
4. A superseding handoff must preserve the old snapshot and receipts while forcing explicit re-acceptance of the new version; G2/G3 migration and E2E tests pin this behavior.
5. Mixed R/D/S/P sample rows or legacy records with missing metadata must remain explicit unknown/legacy facts; adapters must not fabricate qualification, sender, deadline, acceptance or responsibility.

## Integration and PR Boundaries

- G0, G1, G2 and G3 are separate task briefs and separate PRs because they have independent authority, rollback and risk boundaries.
- Within a stage, task commits stay on one stage branch and one final PR.
- G2 does not start production coding until G0 and G1 are merged and G2 D0 is approved.
- G3 does not start production coding until G2 is merged and G3 D0 is approved.
- A green G2/G3 mechanism with synthetic tests does not promote GC-012 to stable V1 or either workbench to `validated`.

## Final Stable-V1 Review

After G3 merges, perform a separate read-only eligibility review. Stable V1 requires:

- controlled real/de-identified market→selection and selection→NPI cases;
- real-role received/claim/accept/reject-or-return receipts;
- two distinct domain payloads;
- accept/reject/return/supersede coverage;
- no R/D/S/P evidence inflation;
- compatibility evidence for old consumers;
- independent contract-owner review.

If any item is missing, GC-012 remains provisional D4 and rollout may continue only where the missing item is not required.
