# 23 台工作台与跨台共同接口设计

> 状态：五段设计已在对话批准，待负责人书面 spec 复审 · 2026-10-03
>
> 适用范围：23 台正式工作台目录、跨台交接与责任共同语义、GC-012 技术边界及首次落地顺序。
>
> 不构成：任一工作台的完整业务规格、统一业务状态机、全量 Schema 字段清单、23 台同时开工授权或真实业务验收结论。

## 1. 目的

项目正式目标已由 20 台扩为 23 台，新增：

- 订舱；
- 出口报关；
- 合规运营。

当前最大风险不是某一台缺字段，而是各台独立定义交接、接收、责任、时限、费用和恢复，形成同名不同义、责任悬空和下游无法可靠消费。本文先建立一套跨台共同接口与治理口径，再从市场与经营信号开始按业务顺序逐台落地，防止继续漂移。

## 2. 权威与输入边界

### 2.1 已批准结论

负责人在本轮确认：

1. 正式目标目录为 23 台；
2. 新增订舱、出口报关、合规运营；
3. 先建立全局跨台接口与共同口径，再从市场与经营信号逐台推进；
4. 目录采用 20 个主链工作台 + 3 个支撑/横向工作台；
5. 采用最小公共门面 + 领域 payload，不一次迁移全部领域；
6. 新增 `GC-012`，不把跨台写语义塞入 `GC-010` 查询投影；
7. 采用 `planned / facts_only / operational / validated` 四级启用状态；
8. 首次落地分为 G0～G3 四个可回滚薄片。

市场与经营信号另有以下已确认业务方向，供 G2 参考实现使用：

- 首版正式机会只代表新品候选；
- 可信机会由服务端资格校验后生成的不可变 handoff 承载；
- A 是统一、不可绕过的最低资格，B 是运营可选的结构化验证模板；
- 未完成 B 不阻止 handoff，但必须以尚存不确定性冻结；
- B 不评分、不自动判断、不改变资格等级；
- B 的固定目录及 A 的精确字段仍须在 G2 业务权威写回时收口，不能由本文静默补齐。

### 2.2 仓库现行事实

当前仓库仍只有：

- 20 个正式 `WorkbenchCode`；
- 18 个主链工作台和 `charges`、`exceptions` 两个支撑台；
- 12 个 `live`、8 个 `framework` 标记；
- 17 条前端相邻交接元数据；
- 多套相互独立的领域 handoff、领取、接收、退回和版本语义。

`booking`、`export_customs`、`compliance_operations` 尚不是正式 code/route。Booking 字段、出口方向枚举和 `/compliance` 页面存在，均不能冒充对应工作台已经成立或实现。

### 2.3 外部材料的效力

`D:\Logixs docs\` 下的 25 份材料是本设计的全局审视与逐台前置意见。除负责人在本轮明确确认的结论外，其中“推荐”“已定”“确认”等对话摘要不自动成为项目权威。逐台实施时必须重新区分：

- 负责人已确认政策；
- 仓库现行业务权威；
- 当前实现事实；
- 前置候选；
- 未知项。

正式业务目录与逐台唯一结果最终写回 `doc/cross-border-supply-chain/08-role-workbenches.md`；本文只规定技术架构与治理，不复制 23 台完整业务正文。

### 2.4 全链路样本包的证据边界

负责人提供的“受控仓外全链路样本包 v0.3”可作为本设计的结构对拍和样本缺口输入。只读盘点事实：

- 样本包包含 31 个工作表；
- 单元格按 `R / D / S / P` 分级：真实来源值、由真实来源推导、合成情景、待补；
- 样本包自称仓库外评审稿，不是项目权威；
- 当前按 22 台口径生成，缺少 `compliance_operations`；
- 交接链的接收时间和接收结论仍为待补，不能证明 GC-012 回执或责任转移已经成立。

工作簿最强的真实连续链段为出运计划、备货、订舱、装箱、出口报关和出运；中后段另有历史实绩、异常恢复和费率结构。市场、选品和 NPI 的核心业务结果主要为合成或推导；市场表没有真实市场观察、真实负向机会、真实岗位操作回执或独立后续结果。因此：

- 可用于 G0 的目录/对象关系核对；
- 可用于 G1 的字段、引用、时间、异常、正负 fixture 和领域 payload 候选设计；
- 可用于中后段 Adapter 的真实字段对拍，但必须逐值保留来源等级；
- 不得用于证明 G2/G3 真实业务路径、GC-012 稳定 V1、市场 KPI、WB-B10、生产验收或经营损失改善；
- `R` 只表示生成器声明从源表直取，本次未独立读取原始源文件，不能替代保管链、逐值来源或数据责任方采信；
- `D` 必须保留来源和算法，不得改名为真实事实；
- `S` 只用于机制、UI、异常路径和自动化演练；
- `P` 只能暴露缺口，不能补静默默认值。

原始样本包含人员、供应商、合同、运输与报关标识、价格、库存、销量、费率、路线和仓库等商业敏感信息。未经数据责任方确认敏感等级、最小化范围、脱敏方式、允许证明/不允许证明和发布授权，不得复制进仓库、生产 Seed、测试 fixture 或对外材料。仓内后续只保存经批准的脱敏摘要、来源别名、证明边界和受控引用；原始 manifest、文件指纹及保管位置继续留在仓外受控载体。

## 3. 23 台正式目录

### 3.1 主业务链：20 台

| 顺序 | stable code            | 正式名称             | 唯一核心业务结果                                                                   |
| ---: | ---------------------- | -------------------- | ---------------------------------------------------------------------------------- |
|    1 | `market_signals`       | 市场与经营信号       | 把经过最低验证的真实市场信号形成不可变新品候选交接，并披露证据、反证和未决不确定性 |
|    2 | `product_selection`    | 选品立项             | 完成商业论证和资源取舍，决定是否形成有责任人的产品立项                             |
|    3 | `product_npi`          | 产品开发与 NPI       | 在重大投入扩大前作继续、返工、暂停或终止决定，并发布经过验证的产品定义             |
|    4 | `master_data`          | 商品与物料主数据     | 建立无歧义、可追溯的产品、物料、BOM、SKU 和 Listing 身份，使寻源可直接引用         |
|    5 | `sourcing`             | 寻源与供应商定点     | 为指定产品、物料或供应范围形成并批准可执行的稳定供给方案                           |
|    6 | `demand_replenishment` | 需求与补货           | 在缺货与过量之间形成经批准的执行需求：哪里需要多少、何时要，以及不处理风险         |
|    7 | `procurement`          | 采购履约             | 对获批采购需求取得并维护可追溯的供应商书面商业承诺，处理数量、日期和条款偏差       |
|    8 | `supply_readiness`     | 生产验货与可出运供给 | 形成真实可出运数量、可信时间窗和当前限制，并及时反映生产、短装、验货和整改偏差     |
|    9 | `shipment_planning`    | 出运计划             | 把已批需求与可用供给形成版本化、可执行的分配、路线、港口和整拼柜方案               |
|   10 | `booking`              | 订舱                 | 在获批边界内取得并维持承运人确认、当前有效且可执行的订舱承诺                       |
|   11 | `cargo_ready`          | 备货                 | 在装箱窗口前形成按时、足量、按版本且满足本节点要求的可装产品行                     |
|   12 | `stuffing`             | 装箱                 | 形成可信的实际柜货关系、柜封、件重体及 VGM 生成版本                                |
|   13 | `export_customs`       | 出口报关             | 让全部必要出口案卷取得范围正确、来源可信的出口放行                                 |
|   14 | `dispatch`             | 出运                 | 汇合当前有效订舱、装箱/VGM、出口放行和码头条件，确认可信实际离港并交海运运营       |
|   15 | `ocean_operations`     | 海运运营             | 从可信离港开始裁决航段、港序、ETA 和重大变化，使下游及时获得可行动信息             |
|   16 | `customs`              | 进口清关             | 形成可信进口放行和未解除限制，交给提柜作联合可提判断                               |
|   17 | `pickup`               | 提柜                 | 汇合联合可提条件并取得正确货柜的可信重柜 Gate Out                                  |
|   18 | `delivery`             | 送仓                 | 把已提货柜送至正确目的仓，并取得仓库、WMS、门岗或合格 POD 的权威接收               |
|   19 | `unloading`            | 卸柜                 | 形成实收完成和独立卸空确认两个事实，并把可执行空箱交还箱                           |
|   20 | `empty_return`         | 还箱                 | 在期限内把空箱还到当前有效场站并取得 EIR/接收证据，关闭柜级设备物流责任            |

目录按业务阅读顺序排列，但运行关系允许 fan-in/fan-out。至少包括：

- 出运计划 → 订舱；
- 出运计划/生产供给 → 备货；
- 订舱 + 备货 → 装箱；
- 订舱 + 装箱事实 → 出口报关；
- 订舱 + 装箱/VGM + 出口放行 → 出运。

前端“每相邻两台恰好一条线”的旧模型只能作为兼容展示，不能继续作为业务契约。

### 3.2 正式支撑与横向工作台：3 台

| 顺序 | stable code             | 正式名称 | 唯一核心业务结果                                                                                 |
| ---: | ----------------------- | -------- | ------------------------------------------------------------------------------------------------ |
|   21 | `compliance_operations` | 合规运营 | 对产品版本、制造主体、目标国家、用途和业务日期形成有证据、可追溯、在有效期内的准入决定及变化影响 |
|   22 | `charges`               | 费用结算 | 以真实业务事件为依据，形成从费用暴露到核定、分摊、支付、贷项和争议的唯一金额账本                 |
|   23 | `exceptions`            | 异常中心 | 协调跨域异常在最早业务期限前取得专业处置或允许的风险决定，并把可执行结果归还原业务域接受         |

三台都是正式工作台，但不是主物流节点：

- 合规运营不替 NPI 发布、不建主数据、不选供应商、不确认生产/备货/装箱/出运完成，也不拥有进出口申报和海关放行；
- 费用台不改物流、采购、生产或清关事实；
- 异常中心不替原业务域作专业结论。

### 3.3 新增工作台边界

#### 订舱

拥有报价适用性、合同/运价适用结论、订舱申请、承运人确认、当前有效 Booking、变更链，以及 VGM 对外提交和承运人接受/拒绝回执。

不拥有出运计划经营意图、装箱实际、VGM 生成依据、出口放行、Gate In、Loaded、Departed 或最终账单核定。

#### 出口报关

拥有出口案卷集合、申报、退单、补件、查验、改单、外部海关放行真实性采信及“全部必要案卷已可信放行”的结果。

不拥有进口清关、装箱、订舱、装船、离港、产品市场准入或费用支付/分摊。

#### 合规运营

拥有法规来源与适用性、产品—市场准入案件、阶段性判断、最终准入、限制/不准入/条件准入/依法豁免、证据范围、生效/过渡/有效期和变化影响。

其他工作台消费带作用域、版本和有效时间的合规决定，不复制法规规则或直接改写合规结论。

### 3.4 兼容命名

- `customs` 技术 code 首阶段保留，正式中文名改为“进口清关”；是否迁移到 `import_customs` 另做消费者与兼容评审。
- `/compliance` 现有页面不能冒充 `compliance_operations` 工作台。
- Shipment 整票关闭暂不新增第 24 台；其责任岗位在逐跳交接设计中定案。
- 共享计划层首阶段作为横向能力，不计为第 24 台；只有证明存在独立岗位、队列、结果和验收后才提交增补决策。

## 4. 架构原则

1. 统一交接协议，不统一领域状态机。
2. 领域继续拥有业务对象、合法动作、完成条件、专业事实和恢复规则。
3. 公共层只拥有跨台身份、交接元数据、回执事实、责任投影、时间语义和权威引用。
4. `received`、`claimed`、`accepted`、本台完成和下游实际采用必须分轨。
5. 发送、接收、拒绝、退回、失效和恢复必须有稳定语义，不能用 HTTP 成功或页面状态代替。
6. 每条 handoff type 单独定义业务合法性和完成点；不得用一个万能状态机决定 23 台业务。
7. evidence、charge、exception 和领域 payload 只引用对应权威，不复制为第二套事实。
8. 首阶段不建通用业务表，不一次迁移全部 handoff。

## 5. GC-012 Workbench Handoff & Responsibility Contract V1

### 5.1 职责

新增 `GC-012`，而不是升级 `GC-010`。`GC-010` 继续拥有查询投影；`GC-012` 拥有跨台不可变交接、追加式回执、责任转移和统一时间引用。

`GC-012` 组合但不复制：

- `GC-005` 任务与工单；
- `GC-006` 证据与来源权威；
- `GC-007` 跨模块引用；
- `GC-008` 动作与权限；
- `GC-009` 同步可靠性；
- `GC-010` 查询投影；
- `GC-011` 公共错误。

### 5.2 工作台目录接口

每台稳定登记：

- `workbenchCode`；
- 正式名称和类型；
- 唯一核心结果；
- 目标岗位；
- route；
- 启用等级；
- 可生产/消费的 handoff type；
- 业务权威引用。

### 5.3 不可变交接快照

最小共同语义：

| 分类     | 必须表达                                         |
| -------- | ------------------------------------------------ |
| 身份     | handoff ID、type、contract version               |
| 业务对象 | subject type、ID 和可选范围引用                  |
| 发送方   | workbench、queue、actor/team reference           |
| 接收方   | workbench、queue reference                       |
| 来源     | 来源对象版本、决定版本、事实截至时间             |
| 内容     | 领域 payload 或 payload reference                |
| 证据     | evidence refs                                    |
| 未决项   | pending items、已知不确定性、适用限制            |
| 时限     | 接收截止或最晚处理时间引用；计算仍归专业域       |
| 版本     | handoff version、supersedes/lineage              |
| 可靠性   | created by/at、idempotency key、expected version |

不进入共同快照：领域状态、金额账本、异常状态、准入状态、采购承诺状态、物流节点和 KPI 分数。

### 5.4 追加式交接回执

共同回执动作语义：

- `received`：技术到达接收队列；不代表承担或可用；
- `claimed`：有人开始处理；默认不转移跨台结果责任；
- `accepted`：接收方确认快照足以开始专业工作；默认责任原子转移点；
- `rejected`：当前快照不可行动；责任留在发送方，必须返回原因、缺口和恢复动作；
- `return_requested`：接收后请求退回；请求本身不清空当前责任；
- `return_accepted`：目标方接受退回，责任才原子转回；
- `superseded`：新快照替代旧快照，历史不删除；
- `closed` 不作为公共 handoff 动作，领域自行定义完成。

动作是否合法由接收域判断。公共层记录事实，不替领域决定。

### 5.5 默认责任政策

1. handoff 创建前，发送方负责；
2. `received` 后，发送方仍负责；
3. `claimed` 后有人处理，默认发送方仍承担跨台结果责任；
4. `accepted` 后责任原子转给接收方；
5. `rejected` 后责任留在发送方；
6. `return_requested` 后责任仍在当前接收方；
7. `return_accepted` 后责任原子转回；
8. 同步失败、超时或无人接收时责任不清空；
9. 任一未关闭业务对象在同一责任维度上只有一个当前结果责任主体。

若某条 handoff type 需要偏离默认政策，必须在其登记中说明业务依据、风险和恢复，不得由 UI 或本地状态静默改写。

### 5.6 三类完成事实

必须分别记录：

1. **本台内部结果完成**：发送台形成自己的业务结果；
2. **跨台责任交接完成**：接收方 `accepted`，责任转移；
3. **下游实际采用/业务结果**：下游真正使用交接结果或形成后续结果。

不同工作台可以选择不同 KPI 完成点，但不能合并三者。例如主数据内部发布不等于寻源首次实际引用。

### 5.7 责任与时限投影

每台至少可投影：

- 当前/下一责任工作台、队列、actor/team；
- 等待谁及等待原因；
- 当前适用截止及类型；
- 当前唯一主动作；
- 拒绝原因和恢复入口；
- version/freshness。

统一时间类型：

- `external_hard_deadline`
- `latest_safe_action_at`
- `fee_deadline`
- `business_commitment_at`
- `planned_at`
- `estimated_at`
- `actual_at`
- `review_at`

每个时间携带 UTC、业务时区、来源、版本、occurred/recorded/as-of、派生/计算依据及 supersession。队列解释默认优先：硬截止 → 最晚安全动作 → 费用期限 → 业务承诺 → 计划 → 预计 → 复核；不得压成丢失语义的单一 `dueAt`。

### 5.8 权威引用

- evidence：引用 `GC-006` 记录；
- exception：引用异常中心权威 case；
- charge：引用费用权威事实/账本；
- domain payload：引用具体领域 Schema；
- 公共层不得复制正文、金额、专业状态或规则。

## 6. 跨台失败与恢复

统一错误类别，领域保留具体 reason code：

- `handoff_validation_failed`：快照无效，责任留在发送方；
- `handoff_delivery_failed`：可靠送达失败，使用 `GC-009` 重试，不重复业务写；
- `handoff_rejected`：业务不可行动，返回缺口和恢复；
- `handoff_conflict`：版本/范围冲突，不静默择一；
- `handoff_expired`：接收前快照被新事实取代；
- `accepted_handoff_invalidated`：接受后发生实质变化，生成变更交接，不回滚历史接受；
- `return_not_accepted`：退回未被接住，当前责任不清空。

异常中心只承接跨域、临近硬截止/损失、责任争议、经营风险取舍或多次恢复失败；普通校验、同步、补件、拒绝、版本刷新和原路退回应在原双方解决。异常中心拥有协调责任，专业结果仍归原领域。

## 7. 工作台启用等级

### `planned`

身份、目标岗位、唯一结果和边界已定；可展示目标和现有事实入口，不允许生产写动作或虚假队列。

### `facts_only`

可读取、导入或受控更正事实，并提供来源、版本、新鲜度和冲突；没有原生岗位任务、责任/时限闭环和真实岗位验收。

### `operational`

具备服务端动作、授权与对象范围、责任、时限、事务/幂等/并发、交接回执和六类自动化路径；只证明岗位机制可用，不证明经营损失下降。

### `validated`

在 operational 之上完成真实/脱敏样本、真实岗位、六类路径、下游使用和指标口径验收；只有该级可计入 WB-B10 或宣称真实业务验收。

正常升级：

```text
planned → facts_only → operational → validated
```

允许在事实来源已被其他权威系统稳定提供时跳过 `facts_only`。降级必须记录原因、影响和恢复条件；历史事实与交接不删除，服务端在不安全时失败关闭。

### 7.1 operational 门禁

进入 operational 前必须证明：

1. 唯一结果与优先损失已写回业务权威；
2. 至少一个真实消费者；
3. 入站/出站 handoff definition 完整；
4. 当前/下一责任和时间来源明确；
5. capability、租户、账套主体和对象范围明确；
6. 正常、等待、拒绝、冲突、返工、恢复有路径；
7. 事实来源、版本、新鲜度可追溯；
8. 不用页面、按钮、HTTP 200 或任务完成冒充业务完成；
9. 风险对应门禁和 fresh review 通过。

## 8. 现有实现兼容

现有领域 handoff 保留作为权威 payload：

- Market Opportunity；
- Product Initiative；
- Product Design Release；
- Sellable SKU Release；
- Supplier Nomination；
- Shipment handoff/work handoff。

首阶段由服务端 Adapter 映射 GC-012：

- 不重写历史表；
- 不伪造历史缺失的发送方、期限或责任人；
- 新 disposition 追加写，不覆盖旧 intake/claim/return；
- 旧 API 保持兼容窗；
- Adapter 可按 handoff type 单独关闭；
- GC-012 失败不反向删除领域结果。

机制参考可先使用永久标注的 synthetic rehearsal 与自动化反例实现。只有两个不同消费者各自补齐受控真实/脱敏案例和真实角色回执，并证明公共语义稳定后，GC-012 才从 provisional 进入稳定 V1；不得把局部真实字段、合成上游行和待补回执拼成真实闭环。

## 9. 首次实施切片

### G0：23 台治理基线

- 目录支持 fan-in/fan-out；
- 新增三台初始为 `planned` 或 `facts_only`；
- 不增加生产业务动作。

完成标准：仓库现行规范不再固定为 20 台；历史记录不追溯改写。

### G1：GC-012 契约

- 新增 GC-012 权威文档并登记全局契约表；
- 定义公共元数据、回执、责任、时间和引用；
- 提供正负 fixture；
- 不新增通用持久化表；
- 不定义万能业务状态；
- 契约可表达市场→选品和选品→NPI，但尚不强制生产采用。

### G2：市场 → 选品参考实现

- 复用 Market Opportunity 领域 payload；
- 固化新品候选、资格 handoff、A 最低资格、B 可选模板和不确定性冻结；
- 接入 GC-012 Adapter；
- 补 `received / claimed / accepted / rejected / return / superseded`；

- 保留现有 Product Opportunity API/intake 兼容窗。

完成标准：正常、等待、拒绝、并发冲突、退回、上游新版本失效和恢复通过 PostgreSQL/E2E。

### G3：选品 → NPI 第二消费者

- 分开选品投入决定与 NPI 接收；
- claim 不自动代表 accepted；
- NPI 退回先请求，选品接回后才转责；
- 新立项版本替代后，已接受方重新确认；
- 选品责任人、NPI 结果负责人、资源批准人和合规否决分轨；
- 原则上不再扩 GC-012 字段。

### 9.1 GC-012 稳定条件

1. G2、G3 的机制、自动化反例与受控真实/脱敏路径均通过，且每条路径包含真实角色的接收、拒绝或退回回执；
2. 两条路径使用不同领域 payload；
3. 均覆盖 accept/reject/return/supersede；
4. 工作簿或其他样本中的 `R/D/S/P` 证据等级保持可追溯，未把 D/S/P 冒充真实完成；
5. 公共字段未改变各台业务目的；
6. 无领域状态/完成条件泄漏；
7. 旧消费者可平滑迁移；
8. 全局契约 owner 完成独立复审。

## 10. 逐台推广顺序

GC-012 稳定后按业务顺序推进：

```text
市场与经营信号
→ 选品立项
→ 产品开发与 NPI
→ 商品与物料主数据
→ 寻源与供应商定点
→ 需求与补货
→ 采购履约
→ 生产验货与可出运供给
→ 出运计划
→ 订舱
→ 备货
→ 装箱
→ 出口报关
→ 出运
→ 海运运营
→ 进口清关
→ 提柜
→ 送仓
→ 卸柜
→ 还箱
```

横向/支撑台按真实消费者接入：

- 合规运营随 NPI、主数据、寻源、生产、备货逐步接入；
- 费用结算随订舱、出运、提柜、送仓、还箱等费用事实逐步接入；
- 异常中心在至少一条跨域异常归还路径验真后扩展。

每台固定完成：业务目的、优先损失、样本、入站/出站交接、唯一责任与时间、动作/拒绝/恢复、事实来源版本、界面主线、六类路径、下游反馈和启用等级。禁止提前把下一台专业状态塞入本台。

## 11. 防漂移门禁

1. 23 个 workbench code 与业务权威一一对应；
2. 每台只有一个唯一结果；
3. 每个生产 handoff type 登记生产者、消费者和 payload Schema；
4. 领域契约不得重新定义 GC-012 字段；
5. 每条交接声明责任转移点；
6. `received` 不得冒充 `accepted`；
7. `accepted` 不得冒充下游执行完成；
8. return 必须有接回方和责任转移事实；
9. deadline 必须有类型、来源、时区和版本；
10. evidence、exception、charge 只引用对应权威；
11. route/page/API 存在不能自动标 operational/validated；
12. 旧契约迁移必须有 Adapter、对拍测试和退役条件。
