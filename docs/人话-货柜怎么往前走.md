# 货柜怎么往前走（人话）

> 状态：**人话对照** · 2026-09-15  
> 挂在 [人话导读](./人话导读.md)。权威仍是 [PRINCIPLES](./product/PRINCIPLES.md) §1、[GC-002 状态机](./product/domain/CONTAINER_LIFECYCLE_STATE_MACHINE_CONTRACT_V1.md)、[GC-005 任务工单](./product/domain/TASK_WORK_ORDER_CONTRACT_V1.md)。本文只把正确顺序说成人话，不另立规则。  
> 「过站」释义见 [GLOSSARY](./product/GLOSSARY.md) 与填空表 [LIFECYCLE_NODE_IO_CATALOG](./product/domain/LIFECYCLE_NODE_IO_CATALOG.md) §1.1。

🗣️ 一句话：**建柜就把整条管道的活排进任务池；人工和外部事实决定哪些能做、哪些能收尾；只有核过的实际发生才让柜子过站。** 入口表决定柜子进不进系统，外部接口提供事实，不直接拥有流程状态。

## 1. 正确主链

```text
已出运货柜表（或其他入口）→ 系统里有了这一柜
  → 有真实箱号就自动启动主流程
  → 按整条管道生成任务和工单，进入全局任务池
  → 当前站、资料、资源及人工/外部事实持续计算哪些活能做、哪些能收尾
  → 人可以提前准备后续工作，外部权威事实也可以先到
  → 工单/任务可以先完成，但不自动过站
  → 只有「实际 + 合格证据 + 本站守卫」的规范事件
  → 状态机完成本站、进入下一站，并重新计算已有任务的条件
```

两件合法、不是错误的事：

- 外部事实可以比内部工单先到（先存着，轮到那一站再过检查）。
- 写进系统的顺序可以和真实发生顺序不同（先发生后补录，或乱序到达）。

不要用这条反着的链：表进系统 → 状态机看表现在在哪 → 事件派任务 → 人做完 → 事件过站 → 接口改字段当完工。**后半句里有三处因果是反的。**

## 2. 常见误解，按正确说法改

### 已出运货柜表是数据起点？

**半对。** 它是当前「哪些柜子能进系统」的入口，不是后面每个字段的最终权威。表上写了 ETA、港口、状态，不能拿来当已经发生。

业务主管道仍是备货到还箱。现在实施从已出运列表接手，只是把系统起点放在出运后，不是另做一套流程。进系统之后还要启动流程实例，Excel 自己不跑状态机。

### 状态机判断当前状态和节点位置？

**因果反了。** 状态机不读表、不猜现在在哪。它只回答：这条已经核验的实际发生记录，能不能完成本站、完了能不能打开下一站。

另外是两套投影，不要并成一句「当前状态」：

| 看什么      | 回答                                                                          |
| ----------- | ----------------------------------------------------------------------------- |
| 14 流程节点 | 现在停在哪一站                                                                |
| 8 个粗状态  | 货柜大阶段（未出运 / 已出运 / 在途 / 在港 / 已提柜 / 已卸柜 / 已还箱 / 取消） |

送仓过了，粗状态仍可能是「已提柜」。导入不能让客户端指定最终状态；已核验的事实按顺序重放。

### 对应事件触发任务和子任务？

**说反了。** 正常顺序是 **有真实箱号 → 展开全管道任务和工单 → 事实与节点位置持续计算任务条件**。事件用来证明实际发生和过站，不是创建后续任务的开关。

未来站的事实先到，可以让对应任务提前具备准备或完成条件，也可以支持人员先做后续工作；但不许跳过中间必做站推进货柜状态。

工序里按责任拆多张工单是正式允许的；把装箱拆成三件正式子任务还是候选。现网常常是一站一张必做工单。

### 人领取、处理、提交完工证据、完工？

**对人工作业对，不是唯一路径。** 工单可以是人做、系统做、外部做或混合。人这条链还要拆开：

- 领取、提交、页面成功 ≠ 业务完成
- 工单完成 ≠ 整道工序完成
- 工序完成 ≠ 过站（有的站完成工单根本不发过站记录）

现网只有装箱、出运、离港会在完成工单后申请过站。计划、ETA、最晚提柜日、点按钮，都不能单独过站。

### 对应事件推进流程节点？

**要加限制才对。** 能过站的只有：实际、仍有效、已核验证据、登记为本站完成资格、过了本站守卫。预计、AIS、同步成功、AI 推断都不行。同一条「到港」可以先完成海运、再完成到港，但是一步一守卫，不能一跳到底。

过站 = 完成本站；成功后通常打开下一站。还箱完成没有下一站。详见导读里的「过站」。

### 然后触发新任务？

**不再是。** 下一站的任务在建柜时已经存在。过站后只是把节点位置和新事实交给条件计算器，更新任务是否适用、能否领取、是否已经具备完成资格；中转港、海铁不适用时保留判定与审计，不制造假取消。

### 外部 API 更新字段，采信为完工证据？

**这句最需要改。** 供应商只提供证据，不拥有我们的流程状态。对接层不得直接完成工单、任务或节点。外部数据要经过：来源登记 → 留原始件 → 显式映射 → 对上这一柜 → 幂等和时序 → 生命周期守卫。过完这些，才可能成为规范事件。

改了某个字段，只是一条数据，默认不是完工证据。证据必须是已登记、已核验、仍有效、同一租户同一柜的引用。

AIS 不能当实际到港；司机点一下或 GPS 不能当送仓完成；ETA 更不能过站。外部放行先到、内部工单后补，是合法的：事实先待应用，轮到那一站再过守卫。

## 4. 当前实施边界

有真实箱号的柜子建档后自动展开14站任务；无箱号记录仍停在备货单层，显示“待绑定箱号”，不伪造货柜流程。当前已接入的导入实际/预计时间事实会参与清关、卸柜、还箱任务的条件计算；其他专业事实按各模块后续接入。装箱、出运、离港完成工单后会申请过站，海运及以后多数站仍需补齐规范事件输出。缺的槽位查 [14流程节点填空表](./product/domain/LIFECYCLE_NODE_IO_CATALOG.md)，不要从作业台反推规则。
