## 一句话

以到港参考日（选取策略可配；候选默认有实际用实际，否则 ETA）为锚，在卸柜能力、车队运力和合规约束下排出 `container_pickup` / `warehouse_delivery` / `container_unloading` / `empty_return`。**拒绝硬编码（封闭规则）**：凡能做成参数或策略的，必须做成参数或策略；登记表只是例子，不是穷尽清单。代码只跑机制和注册表。缺配置就标「要配」，禁止静默套源码默认。计划可**倒推清关最晚必须完成日**；清关与排程的前后关系本身也是策略。预约和计划不能完成节点。

## 为什么必须联立

四个时刻互相咬住：

```text
提柜 T_pickup  →  送仓 T_delivery  →  卸柜 T_unload  →  （卸空）  →  还箱 T_return
```

- 仓没有窗口却先提：场外用箱（Detention）开始走，拖车和车架被占住。
- 仓有窗口却提不出来：月台空转，别的柜子约不上。
- 卸不完就不能还：还箱窗口作废，Detention 继续。
- 先交给车队做场外缓冲：码头超期（Demurrage）可能停，但多一截拖车、车队堆存，并且一旦出场 Detention 仍可能起算。系统不给仓库预绑一个具体堆场名。

行业通行做法是把这段当成一条 **inland move**（码头/堆场 → 仓 → 还箱点），用预约 + 运力 + 场地能力一起算，而不是四张互不相认的日历。

目录里还有 `#13 container_unstuffing`（卸空）。还箱完成依赖卸净事实 `unstuffed`。调度屏是否显示卸空计划钟点是参数；引擎内部必须有「卸净之后才能还」这条硬耦合，不能跳过卸空去约还箱。

## 参考日：ETA 正排，清关倒推

参考日 `R` 和「清关未完成时是否仍排草稿」都读策略，禁止写死。当前登记的候选默认：参考日有到港实际用实际，否则用目的港 ETA（候选字段 `arrival_plan` / 航段 ETA）；清关未完成仍排内陆草稿并倒推必完日。没有目的仓或没有可用参考日，标「算不了、要补主数据」，不编造到港日。

**正排（能力约束下的合理计划；步骤随已选内陆顺序策略，下面是当前登记的 `warehouse_unload_first`）：**

```text
R（参考日策略选出的 ETA 或实际到港）
  → 从 R 起找仓库卸柜日历上第一个接得住本柜的日子（合规/能力先过，再按占用时机策略扣或不扣名额）
  → 车队先把运力排成「提柜 → 送仓 → 卸柜」
  → 还箱接在卸净之后
  → 进不了当天仓位、且车队有余力 → 才比滞港 vs 车队堆场
```

提柜计划不得早于 `R`。参考日、重排触发、占用时机都读配置。新 ETA 按重排策略处理草稿与未执行占用，不把旧 ETA 写成已到港。

**倒推（清关必须何时完成；是否启用读清关与排程策略）：**

```text
计划卸柜日 / 送仓日
  → 计划提柜日（减去可配置的港到仓拖车时间）
  → 清关最晚完成日 = 计划提柜日 − 清关缓冲参数
     （拖车时间、缓冲的数值和单位都是配置，禁止写死）
     （目录：货柜级 container_customs_completed 才完成清关；放行须先于提柜）
```

倒推出的是 `customs_must_complete_by`，写入计划，用来催清关任务和标逾期风险。清关已批准 N/A 则不做这条倒推。倒推**不能**：伪造 `container_customs_completed`、把清关计划日写成实际、在清关未完成时派提柜执行。

若清关预计完成日晚于倒推截止：计划标「清关来不及」，提示提前清关或延后进仓窗口（延后要重新过卸柜能力，可能触发滞港预计）。改占用走占用时机策略。

| 条件                                                       | 引擎可做什么（随策略）                           | 还不能做什么                     |
| ---------------------------------------------------------- | ------------------------------------------------ | -------------------------------- |
| 目的仓已知，且参考日策略选出了 ETA 或到港实际              | 起草四节点计划；策略允许则倒推清关必完日         | 把 ETA 写成已到港；完成清关节点  |
| 清关未完成                                                 | 按清关与排程策略决定是否排草稿、是否倒推必完日   | 派提柜执行（目录：放行先于提柜） |
| 清关已完成或已批准 N/A，且码头可提 `available`、适用放行齐 | 按占用时机策略占或不占执行名额；通过后可派拖送仓 | 把派单写成已提柜                 |
| 闸口 `gate_out` 等权威事件                                 | 无（执行事实）                                   | 用计划时间完成 `#10`             |

到港与清关谁先谁后以事实为准。没有箱型/重量/危品属性，能力约束无法判定，计划标「要补主数据」。

### 日期时间链从哪来

计划引擎只**读**时间线，不采集、不直连供应商。ETA、ATA、可提、提还箱等外部时刻走统一信封：`occurredAt` / `recordedAt`、`timeKind`（planned / estimated / actual）、`provider` 与 `authoritySystem` 分列。飞驼是传输方（provider），不是码头或船司权威。

接入顺序：

| 阶段         | 怎么进系统                                                            | 约束                                                                           |
| ------------ | --------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 目标         | 三方采集 API（飞驼为首个已整理适配器，其它供应商同一套 Port/Adapter） | 原始载荷留存 → 映射 → 规范事件候选 → 生命周期守卫。适配器不直写 `FlowInstance` |
| API 未接通前 | 文件/列表**导入**，或**手工更新**                                     | 必须带来源、操作者；手工还要原因。不得把导入/手填写成「飞驼实际」              |
| 任何阶段     | 新 ETA 用 `supersedes_estimate` 替换当前预计、保留历史                | 触发内陆计划重排。ETA/AIS 推算不完成到港节点                                   |

没有 ETA 也没有到港实际时，不编造参考日，标「要导入、手工补，或等采集」。手工/导入补上 ETA 后即可正排四节点并倒推清关必完日，行为与 API 写入相同，只是来源不同。

实际提柜、送仓、卸柜、还箱仍只认权威事件（`gate_out`、`delivered` / `warehouse_arrival`、`unloaded`、`returned_empty`）。飞驼或导入给出的预计、预警不得冒充这些实际。

## 引擎产出什么

一柜一份**版本化**的内陆计划（人提交后才生效）：

| 字段                 | 含义                                                                 | 对应候选时间字段       |
| -------------------- | -------------------------------------------------------------------- | ---------------------- |
| 计划提柜时刻与地点   | 码头或已出场后的堆场提离                                             | `pickup_plan`          |
| 计划送仓时刻与目的地 | 目的仓；路 B 时目的是已分配车队的缓冲能力，不是仓库主数据上的堆场 ID | `delivery_plan`        |
| 计划卸柜时刻与工位   | 通常与送仓同一座仓                                                   | `unload_plan`          |
| 计划还箱时刻与还箱点 | 船司指定或合同还箱场                                                 | `return_plan`          |
| 占用引用             | 扣了哪天、哪月台、哪班、哪辆车                                       | 预约/占用单 ID         |
| 方案标识             | 进仓 / 滞港等待 / 车队余力缓冲 等                                    | 策略码，不是事件码     |
| 清关最晚完成日       | 由计划提柜日倒推；给清关工序，不是清关实际                           | 对照 `customs_plan`    |
| 分项预计             | 见下一节                                                             | 费用计算版本，不是账单 |

计划变更追加新版本并引用旧版。取消必须退回占用。司机点击、GPS、预约回执、同步成功都不能完成节点（目录已批准）。

提交后的计划，作为作业上下文交给 `work-execution`：对应 [NODE_PDCA](../product/domain/NODE_PDCA.md) 里的 `dispatch_trucking_pickup`、`schedule_warehouse_delivery`、`schedule_unload`、`schedule_empty_return`。引擎不写工单状态，更不写流程状态。

## 费用：最优不是合成一个「滞港费」

[FEE_DEMURRAGE](../product/domain/FEE_DEMURRAGE.md) 与原则 P8：三类超期费分项；预计 ≠ 应计 ≠ 账单 ≠ 已审核 ≠ 已支付。缺合同就「算不了、要复核」，不准套系统默认免费天数。

比价时至少分列：

| 路                     | 常见分项（有合同才出金额）                                                            | 停的是哪座钟                      |
| ---------------------- | ------------------------------------------------------------------------------------- | --------------------------------- |
| A 继续等目的仓         | 码头 Demurrage；合同若有码头 Storage；一次港→仓拖车                                   | 箱子仍在码头，未出场              |
| B 先交给已分配车队缓冲 | 出场后 Detention（若合同从提柜起算）；车队堆存/操作；港→车队缓冲拖车；以后缓冲→仓拖车 | 码头 Demurrage 可能停；场外钟开始 |
| 当日直卸（仓接得住）   | 通常一次拖车；Demurrage/Detention 都短                                                | 能力/月台必须当天过关             |
| 还箱延误               | Detention 或还箱场 Storage（按合同），不是 Demurrage                                  | 卸完未还                          |

「最优」先服从已选的内陆顺序策略，再在该策略规定的步骤做费用比较。以当前登记的 `warehouse_unload_first` 为例：第 1、2 步进仓的柜子不做滞港/堆场比价。预计费用分项，不合成一个「滞港费」。引擎给排序和建议，不自动改期、不自动改目的地、不自动选最便宜的路。

进仓名额按卸柜能力切。多柜争同一天名额时，排序因子（临近免费期、已出场 Detention、危品必须当日卸等）是规则包权重，**不是代码里的固定名单**。占名额还要走争仓策略（含人工决策）。

## 约束引擎：开发期穷尽不了，规则必须可配置

卸柜能力、超长超宽库位、设备承重、月台高度对柜型、危品、证照与合规模板，都会随仓、随货、随法规变。底层只提供**机制**，现场用属性 + 规则包配置，不改代码加 `if`。

### 约束类型

| 类型            | 问的问题                           | 提送卸还上的例子                                                 | 过不去时                         |
| --------------- | ---------------------------------- | ---------------------------------------------------------------- | -------------------------------- |
| 能力 Capability | 这个场/设备/库位**能不能接这票货** | 月台高度 vs 柜型；叉车额定 vs 货重；OOG 是否有超限位；有无危品区 | 该场地对该柜不可行，不许占名额   |
| 资源 Resource   | 这个窗口**还有没有名额**           | 全仓日限额、月台时窗、班次、拖车、还箱闸口                       | 本窗口拒绝，给下一可约           |
| 时间 Time       | 这个时刻**允不允许、来不来得及**   | 码头作业时间、仓历、LFD/免费期、提≤送≤卸≤还                      | 移窗或标逾期风险                 |
| 合规 Compliance | **无论有没有空位都必须拒绝或加证** | 危品隔离、保税、超重上路许可、禁运品                             | 硬拒绝或强制复核，不靠改限额绕过 |
| 费用估计 Cost   | 等下去/改场地**大概花什么钱**      | 上表分项预计                                                     | 只影响排序，不能单独否决可行性   |

能力、合规是「接不接得住」；资源是「挤不挤得下」；时间是「卡不卡点」；费用是「值不值得」。四类不要合成一个分数后偷偷自动下单。

### 港口-车队-仓库：能力对应与分配

备选缓冲不配在仓库上，也不维护「仓 A → 堆场 Y」这种一对一场地。只配**车队的堆场能力**（能否场外存放、日限额、危品/超限/承重等）。物理落场由车队作业时报出，那是执行事实，不是计划主数据。

港口、车队、仓库形成一张**能力对应 + 分配**表。一行表示：这个车队被允许、并被分配去服务「某港 → 某仓」这条内陆路。

| 列       | 填什么                                                                                       |
| -------- | -------------------------------------------------------------------------------------------- |
| 港口     | 提柜港/码头（与到港事实对应）                                                                |
| 仓库     | 目的仓                                                                                       |
| 车队     | 拖车服务商                                                                                   |
| 对应能力 | 这条路上车队声明能做什么：提、送、场外缓冲（堆场能力）、还箱协同。未声明的能力不能拿来排路 B |
| 分配     | 主派 / 备派；可选名额或优先级。没分配的车队即使能力够也不自动上场                            |

路 B 不是仓库一满就自动改去堆场。下面是**已登记的内陆顺序策略** `warehouse_unload_first`（可改选或再登记别的策略，不写死为唯一排法）：

```text
1. 仓库卸柜能力 → 当天最多送进仓的柜数 N（先过合规/能力：这柜仓接不接得住）
2. 已分配车队先把运力用在「提柜 → 送仓」上，最多 min(N, 车队当日运力, 待提柜数)
3. 仍在港、当天进不了仓的柜子，且车队提完送仓后还有余力
   → 才评估：继续留码头（Demurrage 等）vs 提到该车队堆场缓冲
4. 车队没有余力 → 剩下的柜只能等仓，不算路 B
5. 人看分项预计后拍板；不自动选更便宜的路
```

数字 N、运力、余力、比价是否必须人确认，全部来自档案和策略配置。

举例（人话，不是公式）：仓明天能卸 10 柜，车队明天能跑 15 趟，港上待提 18 柜。

1. 先排 10 柜提了直送仓（占卸柜名额和 10 趟车）。
2. 还剩 8 柜在港、车队还剩 5 趟 → 最多 5 柜进入「滞港 vs 送堆场」比价；另 3 柜只能等。
3. 比价分项，缺合同就标算不了。进车队缓冲 ≠ 已送到目的仓 ≠ 已卸完。

若仓能卸 10、车队只能跑 6：当天只送 6 柜进仓，仓位空 4 个也不得用堆场去「填满车队」——余下车力没有，路 B 不开。

路 B 怎么找缓冲：查该港+该仓已分配的车队 → 筛「声明了场外缓冲且过得了本柜能力/合规」→ 占的是**车队堆场能力的名额**，不是某个堆场主数据 ID。没有已分配且具备缓冲能力的车队，或车队没有余力，路 B 都不算。

### 可配置对象（主数据，不是代码）

1. **仓库能力档案**：目的仓 / 月台。属性例如：日限额、作业日历、月台高度、最大柜型、最大承重、能否 OOG、危品等级、证照。没有的属性表示「未声明」，规则写明是当允许还是当未知阻断。
2. **车队能力档案**：运力（可服务的港、仓、柜型）+ **堆场能力**（能否缓冲、限额、危品/超限/承重）。不要求在仓库或港口下挂具体堆场。
3. **港口-车队-仓库分配表**：上节。对应是「能不能」，分配是「派谁」。
4. **货柜/货物属性**：柜型、重量、尺寸、危品类别、是否超限、是否保税。来自主数据和单证，不在计划里手填一套平行真相。
5. **规则包**：租户可增删改。每条 = 条件（货+仓/车队+时间）+ 效果（禁止 / 必须复核 / 占用某资源 / 增加预计费项）。版本化，变更留审计。
6. **占用日历**：按占用时机策略扣仓日限额或车队缓冲名额，取消退回。与规则分离：规则说能不能，日历说还剩多少。写死「提交才扣」或「草稿即扣」都禁止。
7. **计划参数与策略**：凡能改的都在这里，不进源码常量。

### 拒绝硬编码

**机制进代码，决定进配置。** 封闭规则：凡能做成参数或策略的，必须做成参数或策略。新算法只登记策略码，不在业务 `if` 里写死一种排法。发现新的可变点，加配置项，不加分支。

自检：「这个数字或这个选择，换一个仓 / 租户 / 季节会不会变？」会变 → 配置。拿不准 → 先当会变。只有已接受目录里的不变量才进代码：节点完成仍靠权威事件、三类费用分项、时间线信封、模块边界、参数/策略查找与注册表。这些不是业务数字。

缺配置、缺策略码、策略未注册：显式失败或进入复核，**禁止**静默套源码默认（含免费天数、缓冲小时、主派优先、未知当允许、同一作业日、永远确认才占）。

| 键                   | 类型      | 问什么                                                                                              | 禁止                                 |
| -------------------- | --------- | --------------------------------------------------------------------------------------------------- | ------------------------------------ |
| 参考日选取           | 策略      | 有实际用实际否则 ETA，或只用指定时刻字段                                                            | 写死永远只用 ETA 或永远只用实际      |
| 清关与排程           | 策略      | 未完成清关时是否仍排内陆草稿、是否倒推必完日                                                        | 写死必须等清关完再排，或永远先排     |
| 清关缓冲             | 参数      | 清关必完日比计划提柜早多少（数值+小时或工作日）                                                     | 写死 24h / 1 个工作日                |
| 港到仓拖车时间       | 参数      | 倒推提柜日用多久                                                                                    | 写死「同一作业日」                   |
| 占用时机             | 策略      | 确认才占、草稿预占待确认、或其它已登记码                                                            | 写死其中一种                         |
| 重排触发             | 策略      | 新 ETA、能力变更、清关延误时是否重排草稿、是否退占用                                                | 写死永远重排或永不重排               |
| 下一可约搜索         | 参数      | 往后搜几天/几个工作日                                                                               | 写死 7 天窗口                        |
| 能力层开关           | 参数      | 日限额 / 工位 / 班次开哪几层                                                                        | 写死三层全开或只开日限额             |
| 未知属性策略         | 策略      | 危品/超限/承重未声明时阻断、复核还是允许                                                            | 写死「未知即允许」或「未知一律阻断」 |
| 争仓决策             | 策略      | 多柜抢卸柜名额；**须能走人工决策**（如 `human_decide`、`rule_rank_then_human`）                     | 规则排完自动占满、人看不见           |
| 多车队缓冲           | 策略      | 多支车队都有堆场能力时怎么给选（如 `primary_first`、`present_all`、`cost_rank_then_human`，可再加） | 写死永远主派或永远并列               |
| 内陆顺序             | 策略      | 当前登记 `warehouse_unload_first`（卸柜能力先、车队先送仓、余力才比堆场）；可再登记                 | 把五步写死成唯一排法                 |
| 争位排序因子         | 规则包    | 免费期、Detention、危品当日卸等权重                                                                 | 在代码里写死优先级名单               |
| 计划确认人           | 参数/权限 | 谁可以提交占用                                                                                      | 写死「只有调度」或「只有领班」       |
| 卸空计划时刻是否展示 | 参数      | 调度屏是否显示卸空计划钟点                                                                          | 写死显示或不显示                     |

策略输出是建议。是否占执行名额，走占用时机策略；需要人拍板的策略，人确认前不得把建议写成执行占用。

### 和工单怎么接

约束失败要变成任务台能看懂的等待/阻塞原因（缺许可、月台高度不够、日限额已满、免费期将尽），不要只返回内部码。能力不足生成的是「改约/改场/补证」类协调工单，不是把节点标完成。

## 模块放哪

按 ADR-010：

| 对象                             | 所有者                                   | 计划引擎禁止做的事                                                      |
| -------------------------------- | ---------------------------------------- | ----------------------------------------------------------------------- |
| 14 节点状态机、实际事件          | `lifecycle-control`                      | 用计划时刻推进节点                                                      |
| 到港/ETA 等外部时刻采集          | `ocean-port-visibility` 经飞驼等 Adapter | 计划引擎直连飞驼；把 ETA 写成 ATA                                       |
| 工序任务、领取/完成工单          | `work-execution`                         | 在引擎里改工单状态                                                      |
| 提送卸还作业事实                 | `inland-fulfillment`                     | 把预约回执当成 `gate_out` / `delivered` / `unloaded` / `returned_empty` |
| 三类超期费预计/应计/账单         | `charges-settlement`                     | 用费用状态推进主流程                                                    |
| 仓/月台/车队能力、港-车队-仓分配 | `master-data`                            | 在仓库上预绑具体堆场；在流程模块再复制一份                              |

计划、占用、规则求值放在 `inland-fulfillment` 的公开计划端口（或该上下文内的计划子域），**不新建微服务**，也不写进 `lifecycle-control` / `work-execution`。费用引擎只被问「如果这天提/这天还，各类型预计多少」，不决定走哪条路。

## 第一刀（建议，尚未开工）

范围小、可验证：

1. 触发：目的仓已知，且参考日策略能选出目的港 ETA 或到港实际。时刻可来自飞驼采集，**未接 API 前允许导入或手工更新**（必须带来源；手工要原因）。清关与排程、是否倒推 `customs_must_complete_by` 读配置，不写死「等清关完再排」或「永远先排」。
2. 资源：从参考日起用目的仓卸柜能力（工作纸层 A 日限额）决定各日进仓柜数；车队运力先服务于这些进仓趟次。
3. 方案：进仓排满或排到车队运力用尽为止。仅当车队仍有余力、且还有柜当天进不了仓时，才对该子集算路 A（继续滞港）和路 B（提到已分配车队的堆场能力）。车队无余力、或车队未声明堆场能力，不算路 B。不配具体堆场名。
4. 产出：四个计划时刻 + 清关最晚完成日 + 分项预计（能算的算，不能算的标复核）。
5. 提交：争仓、占用时机、多车队、清关与排程全部从配置读取；需要人拍板的策略，确认前不占执行名额；取消退回。
6. 不做：硬编码任何可配的数字、开关或唯一排法；用倒推完成清关节点；计划引擎直连飞驼；把导入/手填写成飞驼实际；自动改目的地；把占用写进 lifecycle。

能力、规则包、参数和策略从第一刀就留表。空规则不等于全部允许；未知属性走「未知属性策略」配置，不在代码里写死阻断或放行。配置表里还没有的键，先加键再写行为，禁止先写死再补配置。

## 还没拍板

现场把参数初值和策略码填进配置。不在代码里拍板这些值。第一刀开工前至少要有：参考日、清关与排程、清关缓冲、拖车时间、占用时机、重排触发、争仓、多车队、未知属性、内陆顺序、确认人。表可加键，不可把缺的键写成源码默认。

现场核对三句才能把候选升格：这座仓一天到底限什么、约满了听谁的、这条港-仓路派了哪几支车队以及他们的堆场能力怎么填。



下面是**候选计算口径**，不是已定稿契约。权威边界见 [FEE_DEMURRAGE](../product/domain/FEE_DEMURRAGE.md)（候选）和原则 P8：四种费用分项、缺标准就「算不了、要复核」，**禁止套系统默认免费天数**。具体起算事件、是否含首日、自然日/工作日，一律读该条标准上的字段，不写死。

## 1. 匹配逻辑

一条**滞港费标准**命中一柜，当且仅当下面四者一致（货柜上的属性 vs 标准上的键）：

```text
标准.港口     = 货柜.目的港
标准.船司     = 货柜.船司
标准.货代公司 = 货柜.货代公司
标准.费用类型 ∈ { 滞港, 存储, 滞箱, D&D }
```

同时只取**生效中**的标准（生效日 ≤ 参考日 ≤ 失效日；状态为有效）。箱型、运输方式、码头若标准上有值，也必须一致；标准上该维为空表示「不限」，不是静默忽略。

- 零条命中 → 该柜算不出最晚提柜日/最晚还箱日，标「要配标准」，不准用 7 天或缺省费率。
- 多条命中（四种类型各一条，或同类型多条）→ **每条先算出自己的截止日，再取最小**。

---

## 2. 共用原语（每条标准各算一次）

记标准 \(i\) 的免费天数为 \(F_i\)（来自标准，禁止默认），日历基准为 \(B_i\)（自然日 / 工作日，来自 `free_days_basis`），起算规则为 \(C_i\)（如「按到港」「按卸船」，来自 `calculation_basis`）。

**起算日**（有实际用实际，否则用预计；都没有则整柜算不了）：

```text
S_i = 按 C_i 选出的事件日
      按到港 → arrival_actual ?? arrival_plan
      按卸船 → discharged_actual ?? discharged_plan
      按提柜 → pickup_actual ?? pickup_plan   // 滞箱常用
```

**把免费期加到起算日上**（是否把起算日算作第 1 天，读标准的「含首日」参数 \(I_i\)，不写死）：

```text
若 I_i = 含首日：  LFD_i = S_i ⊕ (F_i − 1)   // ⊕ 按 B_i 加自然日或工作日
若 I_i = 不含首日： LFD_i = S_i ⊕ F_i
```

\(F_i = 0\) 表示起算日当天已无免费，LFD 按含首日规则回退到起算日前一日或当日结束，仍读标准，不在代码里猜。

LFD 是**该条费用自己的最后免费日**（当日仍免费；次日开始计费）。这是预警用的预计截止，不是账单。

---

## 3. 四种费用各贡献哪一个截止日

四种费用**不能共用一条「到港到提柜」公式**。各自的责任段不同：

| 类型 | 代码意向 | 钟走在哪 | 约束最晚提柜日 | 约束最晚还箱日 |
| --- | --- | --- | --- | --- |
| 滞港 | Demurrage | 重箱还在码头/场内 | 是 | 否 |
| 存储 | Storage | 货/场地占用（港内堆存常见） | 是（港内存储时） | 仅当该条标准的截止事件是还箱/离场后堆存 |
| 滞箱 | Detention | 提离场后用箱 | 否 | 是 |
| D&D | 滞港+滞箱组合 | **一条钟**：从场内起算，提到还不停表 | 是（提柜不得晚于组合 LFD） | 是（还箱不得晚于组合 LFD） |

### 3.1 滞港 → 只推最晚提柜日

```text
S_dem  = 该条 calculation_basis 对应的到港或卸船日
LFD_pickup(dem) = apply_free(S_dem, F_dem, B_dem, I_dem)
```

含义：不晚于该日 `gate_out`，否则开始计滞港。

### 3.2 存储 → 默认也推最晚提柜日（港内堆存）

```text
S_sto  = 该条起算事件（种子里常见「按卸船」）
LFD_pickup(sto) = apply_free(S_sto, F_sto, B_sto, I_sto)
```

若某条存储标准的截止事件明确是场外/仓库堆存，则它改计入最晚还箱日（或单独的堆存截止），不要并进提柜日。

### 3.3 滞箱 → 只推最晚还箱日

滞箱从**提柜**起算，所以还箱截止依赖提柜日 \(P\)：

```text
P = pickup_actual ?? pickup_plan
    若都没有：用下面第 4 节算出的「最晚提柜日」作为上限假设
LFD_return(det | P) = apply_free(P, F_det, B_det, I_det)
```

含义：提柜日为 \(P\) 时，不晚于该日 `returned_empty`，否则开始计滞箱。  
提得越早，滞箱钟越早响，还箱截止越提前；不是「提柜越晚还箱可以越晚」这么简单，见第 5 节。

### 3.4 D&D（组合）→ 提柜、还箱共用一个最后免费日

组合钟从场内起算，**提柜不断表**：

```text
S_dd = 该条起算（到港或卸船）
LFD_dd = apply_free(S_dd, F_dd, B_dd, I_dd)

LFD_pickup(dd)  = LFD_dd    // 不能把组合免费期耗在码头上超过这一天再提
LFD_return(dd)  = LFD_dd    // 还箱也必须落在同一免费期末日或之前
```

因此 D&D 命中时：最晚提柜日和最晚还箱日的候选值相同。剩余免费天数 = 组合免费 − 已在场内用掉的天数，不能再给滞箱另加一段免费（那是分设滞港+滞箱时的算法）。

---

## 4. 多条命中：取最小

对命中集合 \(\mathcal{M}\)：

```text
最晚提柜日 T_pickup*
  = min { LFD_pickup(i) | i ∈ M 且该条约束提柜 }

最晚还箱日 T_return*
  = min { LFD_return(i) | i ∈ M 且该条约束还箱 }
```

空集合（没有任何条约束该日）→ 该日「算不了」，不要用另一种费用去顶。

再加两条硬约束（目录不变量，不是费率）：

```text
T_pickup*  ≥ S_参考日     // 不能早于起算事实
T_return*  ≥ T_pickup*    // 不能还在提之前；若 min 之后出现还箱 < 提柜，标冲突并复核
```

冲突典型原因：D&D 的组合 LFD 早于「滞箱按最晚提柜再加免费」得到的还箱日——此时以 **min 之后仍须还箱 ≥ 提柜** 为准，把还箱日钳在 \(\max(T_{return}^*, T_{pickup}^*)\)，并记复核。

---

## 5. 滞箱与「最晚还箱日」要用哪一个提柜日

对外展示一个「最晚还箱日」时，提柜日 \(P\) 必须说清楚，建议两条都算、标签分开：

| 名称 | 所用 \(P\) | 公式 | 用途 |
| --- | --- | --- | --- |
| 还箱截止（按计划提柜） | `pickup_plan` 或实际提柜 | `apply_free(P, F_det, …)` 再与 D&D 取 min | 已有计划/已提，执行预警 |
| 还箱截止上限（用满场内免费） | \(P = T_{pickup}^*\) | `min( apply_free(T_pickup*, F_det, …), LFD_dd )` | 还没排提柜时的最晚可能还箱日 |

不要把「今天立刻提」得到的还箱截止叫做最晚还箱日——那是更紧的执行窗口，不是上限。

---

## 6. 一柜算例（说明 min，不是系统默认）

假设参考日起算日 \(S\) = 到港日，含首日、自然日；命中：

- 滞港 \(F=5\) → \(T_{pickup}(dem)=S⊕4\)
- 存储 \(F=3\) → \(T_{pickup}(sto)=S⊕2\)
- 滞箱 \(F=4\)，尚未提柜，用提柜上限
- D&D \(F=7\) → \(T_{pickup}(dd)=T_{return}(dd)=S⊕6\)

```text
T_pickup* = min(S⊕4, S⊕2, S⊕6) = S⊕2     // 存储更紧
T_return* = min( apply_free(T_pickup*, 4), S⊕6 )
          = min( (S⊕2)⊕3, S⊕6 )          // 含首日时 4 天 → ⊕3
```

金额仍按各类型分项预计，**不要合成一个「滞港费」**；这里只合成两个日期。

---

## 7. 和计费天数的关系（避免和 LFD 混）

LFD 只回答「免费期末日」。超期天数（给费用引擎）是另一件事：

```text
计费日集合 = (起算截止开区间里的日历日) − 免费日 − 合同暂停日
金额 = Σ 各计费日命中的阶梯费率   // 定点小数 + 币种
```

不能写成「(提柜日 − 到港日) × 日费率」。预计 ≠ 应计 ≠ 账单。

---

**必须从标准读、禁止写死的**：\(F_i\)、\(B_i\)、\(C_i\)、是否含首日、生效期、费用类型、匹配键。代码只保留：匹配、按类型选钟、`apply_free`、再 `min`。

本套截止日算法落在 `charges-settlement`（`COMPUTE_OVERDUE_DEADLINES`）；计划引擎只读最晚提柜日 / 最晚还箱日，不算钱。费率公式仍是候选，非正式契约。
