# 任务：出运装船事实与岗位操作闭环

> 承接 [`DOMAIN_VERTICAL_DELIVERY_PLAN`](../DOMAIN_VERTICAL_DELIVERY_PLAN.md) `2.2b`。本刀把订舱、船名航次、提单、VGM 交接、重柜进港和实际装船组合成出运岗位可完成的纵向闭环。

## 目标

让出运岗位在同一工作台识别待办与业务缺口，保存可更正的出运交接快照，录入重柜进港和实际装船日期事实，并看到 `loaded` 是否已被采信、等待什么或为何被拒绝。`loaded actual` 只有在当前装箱版本、出运交接、证据、来源权威和生命周期前序同时合格时才能过站。

## 边界 / 不做

- 遵守 `AGENTS.md` 的四者协同、分层、日期事实和 Git 纪律。
- `ContainerDispatchSnapshot` 由 `shipment-registry` 拥有；跨模块编排由 `shipment-lifecycle-orchestration` 完成；日期事实和过站仍由 `lifecycle-control` 拥有。
- 出运快照只保存订舱、承运、船名航次、提单引用、VGM 交接与当前装箱版本引用，不复制箱封、重量体积或日期事实。
- `gate_in` 是重要子里程碑但不完成出运节点；`loaded actual` 才申请完成 `shipment_dispatch`。
- 工单领取、完成或页面提交成功均不能替代 `loaded actual`。
- 提单号允许装船后补录；本刀不实现完整订舱系统、电子提单签发、船司主数据治理或其他 13 个岗位页面。

## 验收

- [x] 出运岗位能从全局任务池进入本柜，看到装箱/VGM 基线、订舱与运输信息、进港/装船事实、缺口和允许动作。
- [x] 出运交接快照支持首次保存、版本更正、幂等回放、异载荷冲突、租户隔离、并发版本冲突和证据作用域校验。
- [x] `loaded actual` 缺少当前出运快照、引用过期装箱版本或合格证据时进入 `pending_application`；补齐后自动重放。
- [x] `gate_in actual` 可独立保存且不完成出运节点；工单完成不直接产生 `loaded`。
- [x] 前端覆盖加载、空态、阻塞、保存、更正、实际日期提交、失败恢复和窄屏主路径。
- [x] 迁移通过空库与既有库专项验证；`pnpm validate` 全绿。

## 业务与数据协同设计

| 业务岗位要完成什么                      | 操作时需要看到什么                                               | 系统允许做什么                                      | 数据如何可靠保存与反馈                                                                |
| --------------------------------------- | ---------------------------------------------------------------- | --------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 从共享池领取并判断本柜能否交给船司/码头 | 柜号、备货单、任务时限、当前节点、装箱版本、箱封、VGM、出运缺口  | 领取当前工单；无权或条件不符时只读并返回原因        | 任务归属由服务端授权；装箱与出运投影分别读取各自权威模型                              |
| 确认订舱和运输安排                      | 订舱号、船司、船名、航次、主/分提单、VGM 交接状态和证据          | 首次保存或基于当前版本更正出运交接                  | 快照追加版本、旧版失效不覆盖；幂等键、请求哈希、乐观版本和证据作用域共同保护          |
| 登记重柜实际进港                        | 当前进港事实、地点/时区、应用结果                                | 提交 `gate_in actual`；可在统一更正机制下追加新版本 | 写入统一 `LifecycleDateFact`，保留来源、原值、时区、证据、核验和权威裁决；不触发过站  |
| 确认实际装船并完成出运业务结果          | 当前 `loaded` 事实、快照是否当前、VGM 是否已接收、前序与证据缺口 | 提交 `loaded actual`；补齐快照后重放 pending 事实   | 日期事实先保存；专业守卫核验当前装箱/出运快照与证据，合格后由状态机应用并激活下一节点 |
| 处理失败与更正                          | 稳定原因、当前版本、已保存事实、下一步动作                       | 刷新、修正快照、补证据或重新提交新幂等操作          | 业务拒绝、pending、技术失败分开展示；历史版本和审计链保留                             |

## 方案

1. 新增 `ContainerDispatchSnapshot` 版本模型、迁移、领域校验、Prisma 仓储和读写端口。
2. 在编排模块核验证据后保存快照并自动重放本柜 pending 日期事实。
3. 为 `shipment_dispatch + loaded` 增加专业 readiness 守卫，并把新增 pending 原因纳入公共错误契约。
4. 新增 `/workspaces/dispatch`，复用岗位工作台骨架和任务操作能力，组合快照、装箱基线与日期事实。
5. 以领域、仓储、应用、控制器、组件和 Playwright 测试覆盖主路径及失败路径，最后执行高风险门禁。

## Review notes

- 装船前不强制提单号，避免把装船后签发的最终提单误设为前置阻塞。
- `gate_in actual` 保留为重要日期事实，但不替代 `loaded actual` 完成出运节点。
- 出运交接锁定当前装箱版本，仓储再次核验 VGM 值；`loaded` 事实还必须与交接证据相交。
- 人工实际日期沿用统一来源权威裁决，先进入复核，不允许操作员自证后直接过站。
- 快照迁移同时约束状态/失效时间、入口渠道、载荷哈希及核心文本边界，防止绕过应用层写入非法版本。
