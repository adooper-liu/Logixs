# 任务：对象活动流 + Activity 任务投影

> 采纳条目：`0.1 + 0.2`，见
> [`INCREMENTAL_MODULE_PLAYBOOK`](../../architecture/INCREMENTAL_MODULE_PLAYBOOK.md) §3、§5。

## 目标

让用户从货柜或任务看到同一业务对象上的问题通知与任务活动，并能从通知直接回到对应货柜、节点任务或工单。把“到期做什么、谁负责”投影到现有 `NodeTask` / `WorkOrder`，形成可执行的下一动作；活动流只读投影既有业务事实，不成为新的流程状态来源。

## 边界 / 不做

- 挂靠 `notification`、`work-execution` 与 `lifecycle-control`；跨模块引用遵守 `CROSS_MODULE_REFERENCE_CONTRACT_V1`，只经公开 Port、契约或读模型协作。
- 通知显式关联 `containerId` / `taskId`（需要时关联 `workOrderId`）；服务端校验租户和对象可见范围，不信任前端传入的对象关系。
- 下一动作、负责人、到期时间来自现有任务/工单真相；计划、预计和实际时间保持不同语义，活动投影不得推进生命周期或伪造实际事件。
- 兼容已存在的 `entityType` / `entityId` 通知；新增结构采用追加迁移和显式回填，无法可靠识别的旧数据不猜测关联。
- 不做 Discuss 频道/私聊，不做独立通用 TODO 引擎，不复制任务状态机或权限规则。
- 本刀不做条目 `0.3`（助手摘要与允许动作深化），不做条目 `1.1`（可配置事件自动化）；二者后续各建独立 brief，并按 `0.3` → `1.1` 顺序推进。

## 验收

- [ ] 货柜详情可按稳定顺序读取活动时间线，至少包含关联的问题通知和现有任务/工单活动，并支持明确的分页边界。
- [ ] 通知可跳转到其服务端确认过的货柜、节点任务或工单；不存在、跨租户或无权对象明确拒绝，不泄露对象存在性。
- [ ] Activity 展示的下一动作、负责人、到期时间来自 `NodeTask` / `WorkOrder`；领取、提交或通知本身不改变货柜生命周期状态。
- [ ] 同一业务活动重放不产生重复时间线项；并发更新保持稳定排序和可追踪来源。
- [ ] API 输入、分页、认证、能力码和对象级授权有成功、拒绝与边界测试；Web 覆盖从货柜/通知进入任务的关键交互。
- [ ] 数据变更采用 `database/migrations/` 追加迁移，验证空库升级、已有通知兼容与关键索引。
- [ ] 风险对应门禁通过：相关 API/Web lint、typecheck、test、build，迁移与关键流程验证；跨模块/数据库风险面完成 `pnpm validate`，以 PR `quality` 为合并前最终权威。

## 方案

1. **引用模型**：为通知增加类型化的货柜/任务/工单逻辑引用；保留旧字段兼容读取，写入经 Application 层校验引用完整性与租户范围。
2. **活动读模型**：定义稳定活动项契约，从通知、任务/工单状态和既有生命周期事实投影对象时间线；每项保留来源类型、来源 ID、发生时间和跳转目标，不另建可写业务真相。
3. **Activity 投影**：在 `work-execution` 公共读能力中给出可执行动作、分派人和到期时间；若补充持久字段，以 `WorkOrder` 为执行归属并明确 UTC/ISO 8601 规则。
4. **API 与权限**：提供按货柜读取的游标分页 API；Application 层执行租户、能力码和对象范围校验，Transport 只解析与转换。
5. **Web 闭环**：在货柜工作台展示紧凑活动时间线；通知项提供对象/任务跳转，任务项复用现有任务入口，不在前端推导允许动作。
6. **验证**：先覆盖领域投影、引用拒绝、幂等与排序，再做 Repository/API 集成测试和 Web 关键交互；最后运行跨模块与迁移门禁。

## Review notes

- 活动时间必须使用事实自身的 `occurredAt` / 业务发生时间；`createdAt` 只能表达系统收录时间，二者不得混用。
- “下一动作”是现有任务/工单的读投影，不是通知状态，也不是第二套任务状态机。
- 任何跳转目标都必须由服务端返回并授权，前端不得仅凭通知中的裸 ID 拼接越权链接。
