# 任务：端到端工作台串行实施 V1

## 目标

先保持从市场信号到还箱收口的完整工作台网络，再按业务顺序一次实现一个岗位工作台。当前切片把已确认的“市场与经营信号 → 选品立项”岗位流程落成正式公共契约、最小持久化、真实 API 和两端可操作工作台。

## 边界 / 不做

- 负责人确认完整业务链是产品工作台范围；`docs/product/POST_DEPARTURE_WORKBENCH_DELIVERY_BASELINE.md` 的出运后细节继续有效，但不再代表产品全部范围。
- 本切片交付统一目录、工作台框架、实施状态和相邻业务域交接定义，不一次性实现寻源、预测、采购、生产等尚无领域模型的业务闭环。
- 已有七个真实工作台保持原路由和 API；框架页不新增保存、确认、完成等假动作。
- 工作台间通过稳定业务事实和版本化交接传递，不共用宽表、不跨域回写、不复制对方状态机。
- 费用与异常是横向消费者，不强行串成主生命周期的后继节点。
- 当前切片只新增已批准的市场信号、判断、机会交接和选品接收最小结构；不新增市场评分模型、ROI 门槛或自动审批。

## 业务与数据协同设计

| 业务步骤与岗位结果 | 信息产生时机/前置事实                  | 操作时需要看到什么                             | 系统允许做什么                       | 数据如何可靠保存与反馈                                        |
| ------------------ | -------------------------------------- | ---------------------------------------------- | ------------------------------------ | ------------------------------------------------------------- |
| 找到所属工作台     | 人员收到业务信号、任务或上游交接       | 完整链路、当前阶段、责任结果、真实实施状态     | 进入已有工作台或查看框架边界         | 工作台目录是唯一前端权威，不从数据库表生成菜单                |
| 判断上游是否可交接 | 上游形成可识别且版本化的业务事实       | 交接名称、产生时机、最小事实和接收方           | 真实工作台执行已有动作；框架页仅查看 | 交接定义使用稳定代码并由相邻工作台共同引用                    |
| 进入真实工作台     | 该业务域已有 API、权限、事务和审计闭环 | 任务原因、当前事实、缺口、允许动作和结果       | 执行服务端返回的允许动作             | 继续使用各域现有权威事实和接口                                |
| 进入待实施工作台   | 业务边界已知但领域模型或用例未完成     | 岗位要达成的结果、上游输入、所需信息和下游输出 | 返回全链目录或进入相邻已实现工作台   | 不创建空壳业务记录，不用浏览器状态冒充流程事实                |
| 处理横向事项       | 主链产生费用条件或异常事实             | 来源阶段、影响对象和责任边界                   | 当前仅查看框架边界                   | 后续切片由独立领域事实消费主链事件，不写回综合状态            |
| 判断经营信号       | 市场或经营变化被人员或来源发现         | 处理原因、市场渠道、观察事实、来源与经营假设   | 继续观察、交给选品或不采纳           | 判断、完整度、操作者和版本写入服务端；交接原子写快照与 Outbox |
| 领取经营机会       | 经营人员完成版本化机会交接             | 交接事实、来源、假设、机会说明和仍待补内容     | 领取后接受交接                       | 团队队列先不指定个人；领取和接受追加接收版本并保留实际责任人  |

## 方案

1. 校准出运后基线，明确产品范围扩大但实施仍保持串行小切片。
2. 建立一个类型化工作台与交接目录，测试唯一性、既有工作台映射和主链连通性。
3. 建立全链目录，使用连续接力线表达先后顺序；费用和异常单列为横向能力。
4. 为缺失业务域建立共享框架页，只呈现岗位结果、交接事实和后续实施边界。
5. 注册一个侧栏入口和全部框架深链；已有真实工作台不改业务实现。
6. 完成桌面/窄屏视觉检查与 Web 中风险质量门禁。
7. 从市场与经营信号开始，逐个切片把框架页替换为以岗位结果为中心的交互；岗位流程确认后，按公共契约、加法迁移、两域用例和真实 API 的顺序实施。

- 前一阶段用交互样板确认了待判断、继续观察、交给选品和不采纳的岗位流程；本切片已将市场与选品两个阶段升级为 `live`。
- 五条 V1 规则已落入真实用例：仅标题即可登记，来源可预览，被采纳信号固定进入选品团队队列，缺观察日期或不采纳原因时保存但不关闭，完整处理后保留回执并连续进入下一条。
- 实际操作复核后，登记表单改为“标题优先、其他资料按需展开”，删除未接文件存储的附件假动作，并让未闭环按钮准确表达保存结果。
- 移除继续观察的硬编码日期，避免系统替业务人员编造后续安排；缺日期按已确认规则保存为待补。
- 待补提示改为可执行入口：按稳定缺口码打开对应表单，补充结果回到当前事实区，未处理缺口不受影响。
- `market_opportunity` 由人的业务决定触发，普通缺失随交接保留；`market_opportunity_handoff.v1` 与最小持久化已获批准并完成运行时接入。
- 数据库集成验证发现原生 SQL 依赖隐式 `search_path`；已改为持久化当前版本标记与 Prisma 查询，新旧交接版本仍保持不可变。
- 修正“旧样板专用缺口冒充正式规则”：市场信号登记与待补只判断通用事实；竞争供给证据、价格带、售后原声改为选品评估阶段由适用规则生成，逐条说明为什么适用并提供直接“添加证据”，不适用的机会不显示，证据登记复用来源信号的统一证据服务。
- 本切片已完成全部门禁；仅 `format:check` 因容器以 root 创建的 `apps/ai-service/.pytest_cache` 无法被 prettier 遍历而在本机中止，属环境阻塞，已逐路径验证格式干净，评审结束。
- 评审收口时修正一处切片内自相矛盾：选品工作台的「本机会适用的专业要求」面板原先在机会尚未领取（`queued`、无商品范围）时也会渲染，并列出「还有 N 项暂时生成不了」，与面板自带说明「评估阶段才会出现」冲突。按负责人决定改为面板仅在存在适用要求时出现；`withheld` 仍保留，用于在已有可办要求时区分「不适用」与「还判断不了」。
- 下一步：开始「选品立项判断 → 产品开发/NPI」的岗位操作评审；不得提前伪造立项结论。
