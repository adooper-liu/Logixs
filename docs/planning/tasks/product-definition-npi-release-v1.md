# 任务：产品定义与 NPI 发布 V1

> 全链工作台 **3 号节点「产品开发与 NPI 工作台」的第二片**。

>

## 已定的口径（负责人 2026-09-27）

按行业标准做法选型，四条：

| #   | 决定                | 选定                                                                             | 理由                                                                                                                                                   |
| --- | ------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | **阶段模型**        | **EVT → DVT → PVT → MP**                                                         | 代工厂天天在说这四个词，运营与供应商之间不用翻译；Stage-Gate 的前半段（找想法、初筛、商业论证）已由 1–2 号节点覆盖，这里缺的正是"开发→验证→上量"这一段 |
| 2   | **门禁**            | **中**：只有"发布"卡硬（必须有规格版本与合规假设）；阶段推进只要本阶段结论已登记 | 与"普通缺失不阻断"的一贯口径一致；但发布必须卡死，否则下游建不出稳定身份                                                                               |
| 3   | **发布去向**        | **发布 / 暂缓 / 终止**                                                           | "退回选品"是 `product-initiative-return-path-v1` 那条 blocked 片的事，不在这里重开口子                                                                 |
| 4   | **合规假设 / 角色** | 本岗位**人工登记**合规假设；**单角色**（产品负责人）                             | 规则生成属于合规域（4 号之后才有）；单角色与刚做完的 NPI 领取一致                                                                                      |

## 目标（一个业务结果）

**产品负责人把自己负责的立项推进到发布，产出一份可建档的产品定义交给主数据侧。**

推进过程留痕：走到哪个阶段、每个阶段的结论是什么、依据哪些证据、规格是哪一版。

## 业务步骤 → 所需信息 → 允许动作 → 权威事实

| 业务步骤      | 操作时需要看到                                   | 系统允许做什么                 | 数据如何可靠保存                                   |
| ------------- | ------------------------------------------------ | ------------------------------ | -------------------------------------------------- |
| 登记产品规格  | 上一版规格、合规假设、当前阶段                   | 写规格与合规假设（形成新版本） | 版本递增；发布过的版本由交接快照冻结，不被覆盖     |
| 推进 NPI 阶段 | 当前阶段、下一阶段、本阶段要交的结论             | 登记本阶段结论与依据，前进一段 | 阶段只能逐级前进；每次推进留痕（谁、何时、依据）   |
| 看还缺什么    | 当前阶段未登记的结论、未填的规格                 | 就地补                         | 缺口按当前阶段**现算**，不存成库里的人工状态       |
| 发布或暂缓    | 当前规格版本、合规假设、各阶段结论               | 发布 / 暂缓 / 终止             | 发布在同一事务内写不可变交接快照；旧的标记已被替代 |
| 交给主数据侧  | 交接内容：规格版本、NPI 阶段、合规假设、发布决定 | —（交接后只读）                | 快照不可变，追加版本不覆盖旧版                     |

## 阶段与出段判据（这一片实现的部分）

| 阶段           | 本阶段要交的结论            | 出段条件                |
| -------------- | --------------------------- | ----------------------- |
| `evt` 工程验证 | 功能验证结论 + 关键料风险   | 结论已登记              |
| `dvt` 设计验证 | 设计冻结结论 + 合规风险盘清 | 结论已登记              |
| `pvt` 生产验证 | 试产结论（可行性/良率）     | 结论已登记              |
| `mp` 量产      | —（发布即离开本工作台）     | 有规格版本 + 有合规假设 |

## 边界 / 不做

- **不做打样/样品管理、BOM、认证流程本身** —— 那是 4 号之后的事；本片只登记"结论与依据"。
- 不做转交与放手（上一片遗留，仍等真实诉求）。
- 不改 `product_initiative*` 与既有 wire value；只做加法。
- 不改已共享迁移。
- **不投 outbox**：与上一片一致，没有消费方就先不造事件。4 号节点接上时再补。
- **不伪造结论**：阶段结论只能由人登记，系统不替人判断"验证通过"。

## 允许动作（服务端授权）

## 验收

- [ ] 已领的立项能进入产品定义；没领的进不来（那是上一片的门槛）
- [ ] 能登记规格与合规假设，形成新版本；旧版本不被静默覆盖
- [ ] 阶段只能逐级前进（EVT→DVT→PVT→MP），不能跳级、不能倒退
- [ ] 本阶段结论未登记时明确说明还缺什么，而不是让阶段推进按钮点了没用
- [ ] 发布时同一事务写不可变交接快照（规格版本、NPI 阶段、合规假设、发布决定）
- [ ] 暂缓/终止有去向与原因，且不产生交接快照
- [ ] 并发推进用版本乐观锁，冲突拒绝而不是覆盖
- [ ] 跨租户不可见
- [ ] 相关质量门禁全绿

## 方案

1. **契约加法**：`ProductDefinitionV1`、`ProductDefinitionStageOutcomeV1`、
   `ProductDefinitionSpecVersionV1`、`ProductDefinitionCommandV1`、
   `ProductDefinitionReleaseCommandV1`、`ProductDesignReleaseHandoffV1`。
2. **加法迁移**：`product_definition`（一票一行、版本递增的当前态）+
   `product_definition_release`（发布的不可变交接快照）。**与立项同构**，不另造一套形状。
3. **领域规则**：阶段推进、门禁、发布去向（纯函数 + 单测）。
4. **仓储 / 服务 / 控制器**：读写产品定义、发布命令。
5. **前端**：`/workspaces/product-npi` 增加"我负责的"那一票的推进区（规格、阶段、发布）。
