# 任务：出运后 Shipment 模型与四表字段基线评审

> 本文件只承载任务状态、验收和交接。设计正文唯一位于
> [`POST_DEPARTURE_CORE_MODEL_GAP_V1`](../../product/domain/POST_DEPARTURE_CORE_MODEL_GAP_V1.md)，不得在任务 brief 复制第二套字段或结构结论。

## 目标

在任何公共契约或数据库迁移前，批准 Shipment 粒度、柜侧活动基数、事件主体、`post_departure` 可靠提交、统一 Shipment Handoff 接收边界，以及四张维护表的 V1 字段覆盖下限、只读详情投影和扩展治理。

## 边界 / 不做

- 本任务只做领域、数据库和契约方向评审，不修改 Prisma、迁移、Seed、运行时代码或数据库数据。
- 四张维护表定义字段覆盖下限，不定义四张同名物理表，也不令全部字段首日非空。
- 十张详情表只作为 `container_operational_view` 的对拍证据，不成为第五个写模型。
- 原始工作簿保留在外部只读目录；项目证据层保存文件哈希、XML 实际范围、逐列表头及非空统计，不复制原始业务文件。

## 业务与数据协同设计

| 业务岗位要完成什么 | 操作时需要看到什么                                     | 系统允许做什么                             | 数据如何可靠保存与反馈                                                      |
| ------------------ | ------------------------------------------------------ | ------------------------------------------ | --------------------------------------------------------------------------- |
| 导入已实际出运数据 | 票、柜、SKU、提单、航线、必填缺口、重复和冲突          | 预检、修正映射、提交或转人工               | Adapter 生成 Handoff；T1 核心事务、逐对象结果、来源和幂等留痕；下游状态可查 |
| 跟踪在途与到港     | 一个柜的跨域只读详情、各专业状态、时间版本、证据和缺口 | 从详情进入所属域的受权动作，不编辑综合快照 | 各域维护自己的事实；查询投影实时聚合并带版本/asOf                           |
| 扩展来源字段       | 字段规范语义、所有者、类型、适用阶段和兼容版本         | 提交字段注册与映射版本，不直接加自由 JSON  | 强类型列/关系或版本化行保存；契约 parity 和 fixture 验证                    |

## 方案

1. 以核心差异文档作为唯一设计基线，现行数据库契约只记录当前物理事实和目标链接。
2. 负责人批准后把已核验的 146 个原始表头映射到 Handoff 规范字段，再实例化公共字段目录、Handoff、事件 V2 和查询契约。
3. 公共契约通过 parity 后形成加法迁移、回填、验证查询和恢复方案；迁移评审通过后才改代码。

## Review notes

- 当前阻断不是技术模型或来源缺失，而是业务负责人批准，以及 146 个原始表头尚未实例化为公共字段码。
- 旧 P2 brief 的“一备货单一柜”与目标基数冲突，已在核心差异文档登记为废止口径；不修改历史记录本身。
- 当前 `TARGET_FIELD_CATALOG V1.2` 仍服务已实现兼容入口，不得被误读为 Shipment V1 的完整字段集。
- 统一接收不能变成跨模块巨型事务：Handoff/Shipment 核心事实 T1 原子提交，生命周期和专业域通过 Outbox/Inbox 可恢复吸收。
