# 任务：选品立项判断 V1

> 本文件是执行、评审与交接的**唯一载体**。状态只看 frontmatter，改状态就改这里。
> 本片是「选品立项判断 → 产品开发/NPI」的第一半；第二半（NPI 工作台）等本片验收通过后另立 brief。

## 目标

选品负责人在选品立项工作台，把一票**已接受**的经营机会推进到「形成有责任人的立项结论」：补齐评审要点与目标结果后立项，或明确暂缓、不立项、退回经营团队。立项成立时写出不可变的立项交接，进入 NPI 待办队列。

## 边界 / 不做

- 遵循 `docs/product/domain/IMPORT_DOMAIN_MODEL.md`、`AGENTS.md` 的来源保留、幂等、预检、事务与审计边界，以及 `apps/web/src/data/workbenchNetwork.ts` 已声明的 stage 2 / `product_initiative` 交接定义。
- **不做 NPI 工作台**（领取、五阶段推进、发布决定）。本片只保证立项交接正确落库并出现在 NPI 待办。
- **不新增人员目录**。因此立项时只记「立项责任人 = 操作人（服务端从认证身份取）」，**产品负责人要到 NPI 领取时才产生**。
  ⚠️ 这是对 catalog 措辞「机会完成评审并**明确产品负责人**和目标结果时」的**有意偏离**：系统内没有可选人的目录，宁可不对齐措辞，也不伪造一个选人动作。
- **不改 catalog 的 wire value、不改已共享迁移**；只做加法迁移。
- 不新增 ROI 门槛、评分模型或自动审批；不提前写任何立项**结论**内容。
- 不把 NPI 的 stage 状态机复制进本片。

## 验收

- [ ] 已接受机会可在同一工作台补齐评审要点与目标结果，并**成功立项**
- [ ] 评审要点缺项时**不能**立项，主按钮准确说明还差几项，而不是静默失败或冒充成功
- [ ] 暂缓**必须填原因**；队列上「看过但先放着」与「还没看过」可分辨
- [ ] 不立项缺原因时**保存但不关闭**机会（复用上游"不采纳缺原因"同一规则）
- [ ] 退回经营团队追加退回事实与理由，机会回到经营团队队列；旧交接版本保持不可变
- [ ] 立项在同一事务写入立项聚合、不可变交接快照与 Outbox；重复提交幂等，版本冲突拒绝而非覆盖
- [ ] 立项成功后从服务端重读，NPI 待办队列能查到该立项
- [ ] 每个缺口给出当前值、影响动作和一个**直接就地补录**入口；补录后回显并只关闭该缺口
- [ ] 迁移验证空库升级与旧版本升级；真实 PostgreSQL 集成测试覆盖约束、事务与并发
- [ ] 相关质量门禁全绿（`pnpm validate`；本机 `format:check` 受 `apps/ai-service/.pytest_cache` 环境阻塞时逐路径验证并如实说明）

## 工作台避坑检查

- [ ] 首屏按业务原因和紧迫度组织，不按表或接口资源组织
- [ ] 系统产生立项编号、交接快照、幂等键与缺口；人员只写自己掌握的业务事实
- [ ] 已接受机会、证据与专业要求自动带入，不要求重复录入
- [ ] 每个缺口显示当前值、影响动作和直接处理入口
- [ ] 待补与阻断分轨：四项要点缺 = 不能立项但仍可暂缓保存；身份或引用冲突才拒绝
- [ ] 页面只有一个当前机会主选择源，一个随去向变化的主动作
- [ ] 生命周期、资料完整度与冲突不合成大状态
- [ ] 待办、待补与结果均来自服务端事实，刷新不丢
- [ ] 正常项批量/收拢，逐条只服务于例外与冲突
- [ ] 操作后重读服务端结果，区分成功、业务拒绝、并发冲突与技术失败

## 决策与待确认

**已由负责人确认**：四个去向（立项／暂缓／不立项／退回经营团队）；立项门槛＝负责人＋目标结果＋四项要点齐备；NPI 有五个阶段（设计定稿／打样／送测／试产／量产）；不做人员目录。

**以下是实现方（我）提的、负责人选定或按行业做法推定，实施前请确认**：

1. **四项评审要点的具体名称**（目标用户与市场／竞争供给／价格带与利润／合规风险）是我提的选项，非负责人原话。
2. **「事实 + 结论」两份存**是负责人选定。代价如实记账：同一事实在证据区（挂来源信号）与评审要点各存一份，会随时间分叉。缓解：评审要点的事实栏**只读且标注"立项当时"**，补事实只能回证据区。
3. **暂缓必须填原因**由我追加。不这样做暂缓就与「尚未处理」无法区分，会退化成坟场。
4. **严门槛的保险**：四项要点哪些算立项门槛、哪些算待补，实现为**一处配置**。第一半验收时若队列积压，改这一处即可降级某项，不需重写。

## 方案

1. 在 `product-selection` 内新增 `ProductInitiative` 聚合（结论、目标结果、立项责任人、四项要点的事实与结论、暂缓原因），不新开模块 —— 同一岗位、同一工作台、同一队列。
2. 公共契约加法新增 `product_initiative_handoff.v1`（立项编号／目标市场／用户问题／负责人／评审结论），沿用既有 Schema→TS 生成链路。
3. 一条加法迁移建立立项与交接快照的权威对象，复用既有持久待补、幂等与乐观版本机制，不另造一套。
4. 复用既有 intake（领取／接受／旧版本被替代），本片不复制也不重构它。
5. 前端在同一页面新增评审要点与去向两块，缺口就地补录；按去向切换主动作。
6. 覆盖领域规则单测、真实 PostgreSQL 集成、接口契约与授权、组件行为与三视口 E2E。
