# 任务：NPI 待办队列与领取 V1

> 全链工作台网络 **3 号节点「产品开发与 NPI 工作台」**（`/workspaces/product-npi`）的第一片。
> 上游 2 号节点「选品立项」已交付并合入（PR #53），它把立项交接投进 NPI 待办 ——
> 但**没有任何可查的队列**（前一片任务书明写「本片不做 NPI 工作台」）。
> 所以这一片补的是链条上真实存在的断点：**上游已经在往一个没人看得见的队列投东西。**
>
> 路线与节点定义见 `apps/web/src/data/workbenchNetwork.ts`。

## 目标（一个业务结果）

**产品负责人打开产品开发与 NPI 工作台，能看见选品交过来的立项，把其中一件领到自己名下。**

领取后该立项有明确的产品负责人，不再处于"投出去没人接"的状态。这是 2 号节点到 3 号节点
真正接通的那一刻 —— 本片只做到"接住"，不做到"做完"。

## 上游事实（已有，本片不改）

| 事实                       | 位置                                                                   | 状态             |
| -------------------------- | ---------------------------------------------------------------------- | ---------------- |
| 立项及其当前去向           | `product_initiative`（`product_initiative_queue_idx`）                 | 已有             |
| 交给产品侧的**不可变快照** | `product_initiative_handoff`（`product_initiative_handoff_queue_idx`） | 已有，索引已建   |
| 出站事件                   | outbox（前一片集成测试覆盖）                                           | 已有             |
| **领取回执**               | —                                                                      | **缺，本片新建** |

**v1 已知不会出现第二个交接版本**（前一片明写：退回发生在立项之前，NPI 只读该快照）。
因此队列按 `handoffId` 一条待办，不做版本去重；追加版本的处理留到真有该路径时再开。

## 业务步骤 → 所需信息 → 允许动作 → 权威事实

| 业务步骤           | 操作时需要看到什么                                         | 系统允许做什么 | 数据如何可靠保存                                    |
| ------------------ | ---------------------------------------------------------- | -------------- | --------------------------------------------------- |
| 找出哪些立项等我接 | 队列：目标结果、来自哪个信号/市场、交接时间、有没有人接    | 选一条         | 队列来自服务端投影，稳定排序，刷新不丢              |
| 看懂它为什么值得做 | 立项目标、目标用户与市场、四项评审结论及各自证据、机会说明 | 只看，不改     | 快照不可变；证据引用指向已登记证据，不另存一份      |
| 决定要不要接       | 上一段选品谁在负责、交接版本                               | 领取           | 追加领取回执；幂等键 + 期望版本，冲突拒绝而不是覆盖 |
| 确认接住了         | 领取回执：产品负责人、领取时间；队列位置变化               | 刷新再看       | 回执落库；重复提交不产生第二条                      |

## 边界 / 不做

- **不做产品规格、里程碑、发布决定**（那是 3 号节点的第二片）；本片只到"接住"。
- 不做立项退回的回程（`product-initiative-return-path-v1`，blocked，独立片）。
- 不改 `product-initiative-decision.v1` 与 `product_initiative_handoff.v1` 的既有 wire value；只做加法。
- 不改已共享迁移。
- **不投出站事件**：本片没有消费方。选品侧要不要显示"已被产品侧接走"是后续片的事，
  不为未知消费方先造事件（负责人 2026-09-27：技术是让事情更有效，不为了数据链完整而造无用物）。
- **不伪造立项结论**：快照只读，NPI 不得改写立项阶段的事实与结论（前一片明写的红线）。

## 验收

- [ ] 首屏是**待领取的立项队列**，每条写明为什么它在这（交接时间、目标结果、来源市场）以及有没有人接
- [ ] 选中一票能看到**完整立项快照**：立项目标、目标用户与市场、四项评审结论与各自证据、机会说明
- [ ] 领取后该立项有明确的产品负责人，队列里移到"我负责的"，刷新不丢
- [ ] 已被别人领走的不再能被领走（并发拒绝，不覆盖他人领取）
- [ ] 重复提交同一领取请求不产生第二条回执（幂等）
- [ ] 跨租户不可见
- [ ] 界面上不出现立项阶段之外的状态或结论
- [ ] 相关质量门禁全绿

## 待确认（我按推定实现，有异议随时叫停）

1. **队列同时显示"待领取"和"我负责的"两类。** 推定：分两组呈现，一个人能看到自己手上几票。
2. **一个人可以同时持有多个立项。** 推定：可以，不设上限。
3. **领取后不能放手或转给别人。** 推定：本片不做，等出现真实诉求再开。

## 方案

1. **契约加法**（`packages/contracts/schemas/v1/product-initiative.schema.json`）：
   `ProductInitiativeNpiQueueEntryV1`、`ProductInitiativeNpiQueuePageV1`、
   `ProductInitiativeClaimCommandV1`、`ProductInitiativeClaimV1`。
2. **加法迁移**：`product_initiative_claim` 回执表（幂等键、期望版本、产品负责人、领取时间）。
3. **领域**：领取规则（幂等、并发拒绝、只有已交给产品侧的立项可领）。
4. **仓储 / 服务 / 控制器**：`GET /product-initiative-npi/queue`、`POST /product-initiative-npi/:handoffId/claim`。
5. **前端**：`/workspaces/product-npi` 接真实 API，按基线 §5 三区（原因队列 → 立项快照 → 领取动作）。

## 落地记录（2026-09-27）

**服务端**：契约加法 4 个 def；加法迁移 `product_initiative_claim`；领域规则
`prepareProductInitiativeClaim`；`GET /product-initiative-npi/queue` 与
`POST /product-initiative-npi/:handoffId/claim`。**不投 outbox** —— 本片没有消费方。

两处实现取舍：

1. **先判归属再判版本。** 两种情况的现场相同（读到时没人接、点下去时已被接走），
   提示「已被领走」对人才有用；报「版本冲突」会让人以为自己点错了地方。
2. **版本列与 `(handoff_id, claim_version)` 唯一索引保留**，即使 v1 每个快照只会被领一次 ——
   两个人同时点，后到的那笔在数据库层失败，而不是靠应用层先读后写去赌。

**前端**：`/workspaces/product-npi` 接真实 API，三区（待办队列 → 立项快照 → 领取动作）。
队列按「等我接手／我负责的／已在他人手上」分组 —— 这是操作第一眼要分的事。
打开工作台**默认落在最该处理的那一条**，不必先点一下才看得见内容。
岗位作业规格已补进 `workbenchNetwork.ts`，节点状态 `stage` → `liveStage`。

**连带修复**：新迁移的外键依赖让既有的「旧版本升级」验证（DROP 表模拟停在上一版本）
删不掉表 —— 那条测试正是为此存在的。已按「更晚的迁移必须一起回退」修正，否则会留下
「记账说已应用、表却不在」的半状态。
