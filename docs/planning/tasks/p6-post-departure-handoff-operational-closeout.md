# 任务：已出运接管作业闭环

> 路线图：`DOMAIN_VERTICAL_DELIVERY_PLAN.md` 的 `UI-01B`。
> 前置交付：PR #47 已完成任一来源上传、联合预检、受控修正、单票接管和内部事实 Handoff 首片。
> 页面归属：现有“出运工作台”内，不新增顶层入口。
> 工作台纪律：逐项遵守 `ROLE_WORKBENCH_HUMAN_CENTERED_DESIGN.md` 的 `HW-D01`～`HW-D16`。

## 目标

让出运运营人员把一批正常候选一次接管，并让所有“已接管但仍缺资料”的事项进入服务端持久队列。退出、刷新或隔日返回后，人员仍能继续补全；资料未齐不阻止保存，也不阻止不依赖该资料的后续工作。

## 边界 / 不做

- 只收口“候选接管 → 正式 Shipment → 已接管待补”三个阶段，不同时建设 Shipment 在途总览、清关、提柜或智能排程。
- 不把待补退回预检候选，也不把浏览器内存作为任务保存位置。
- 不把全部缺口升级为阻断。只有业务对象无法识别、必需引用不成立或互斥关系冲突才局部拒绝。
- 不要求业务人员逐条打开正常候选；单票接管保留给冲突核对和特殊处理。
- 不用“确认”“处理问题”等空动作。每项待补必须打开当前值、候选值和实际输入/选择控件。
- 不新增第二套备货、装箱或 SKU 导入；系统内事实继续通过统一 Handoff 复用。

## 业务与数据协同设计

| 业务步骤     | 操作时需要看到什么                                          | 系统允许做什么                           | 权威事实与反馈                                         |
| ------------ | ----------------------------------------------------------- | ---------------------------------------- | ------------------------------------------------------ |
| 判断批次     | 可接管、待补、冲突、重复的 Shipment/柜数量及影响范围        | 一次接管全部非阻断候选；也可打开单票核对 | 服务端重新预检并按 Shipment 归组，不能信任前端旧判断   |
| 执行批量接管 | 每票身份、柜数、货物/提单概况和待补数量                     | 提交一个批量命令                         | 每个 Shipment 独立事务；一票失败不回滚已成功的其他票   |
| 确认结果     | 每票成功、重复、冲突或失败；Shipment 链接和 traceId         | 打开 Shipment、重试失败项或返回问题队列  | 回执按对象持久保存；HTTP 成功不冒充整批成功            |
| 继续待补     | 已接管 Shipment、具体缺口、当前值、责任人、截止和受影响动作 | 直接补录、选择、上传证据或保存当前进度   | 待补项来自服务端投影，刷新后仍存在；缺口消失后自动关闭 |
| 部分保存     | 已填内容、仍空内容和本次会影响的动作                        | 全空或部分填写均可保存                   | 已填项按版本/并发校验；空值继续待补，不写默认值        |

## 方案

1. 先核对 PR #47 的候选、接管回执和补全存储，区分可直接复用的事实与仅存在于 composable 的页面状态。
2. 为“已接管待补”定义服务端查询投影。它引用 Shipment 和当前缺口事实，不复制生命周期状态，不创建人工综合状态。
3. 增加批量接管应用用例：服务端重做预检、稳定归组、逐组调用现有 `AcceptShipmentHandoffService`，返回逐组回执。
4. 出运工作台把接管区分为“待接管”和“已接管待补”两个阶段视图，共用同一对象上下文与缺口编辑器。
5. 删除“接管前最后一步”等硬闸文案；主动作按阶段切换为“接管全部可接管项”或“保存待补进度”。
6. 使用真实 fixture 完成 API 集成、Vue 组件和三视口 E2E；再核对任务刷新、重放、并发冲突和部分失败。

- 待补队列已提供逐项入口，并统一展示当前值、来源值、系统候选、责任角色、截止来源、受限动作和正式 Shipment 专用写控件；没有权威期限或限制规则时明确显示“未设定”和“当前不限制流程”。

- 评审确认正式货物行和提单必须保留 `source_handoff_id`；待补写入已通过 operator Handoff、对象回执、租户边界、幂等和版本校验落地，不另建无审计 PATCH。
- Shipment 标量待补通过专用事务写入器追加 operator Handoff 审计；它按租户和 Shipment 串行补值，不重建货柜、关系或流程，也不误增只用于关系图的 `relationship_version`。
- 隔离 PostgreSQL 集成测试已覆盖补值、幂等、并发版本、禁止覆盖、租户隔离，并证明不会新增货柜、关系、流程实例或 Outbox。
- “补充 SKU 装载明细”已成为当前工作台内的直接动作：人员选择可见柜号并逐行填写或批量粘贴 SKU、数量、单位；系统匹配已有 SKU 主数据，自动登记操作证明并追加 operator Handoff 和柜货分配。未匹配 SKU 不阻止保存，自动转为后续待匹配项。
- 首次货物补录不会覆盖任何已有或历史货物版本；发现既有货物/分配事实时明确要求进入版本化更正流程，不以数据库约束 500 代替业务反馈。
- `product_sku_missing` 已成为同屏动作：界面展示货物行 SKU 编号与数量，系统按租户内唯一产品编号精确匹配；不存在时建立 SKU 主数据后绑定。业务人员不输入内部 ID，绑定追加 operator Handoff 和对象回执，原货物来源 Handoff 保持不变。
- `bill_of_lading_missing` 已成为同屏动作：业务人员选择 Booking/MBL/HBL、填写号码与可选 SCAC，并按可见柜号选择关联范围。正式单证和柜关系共同引用本次 operator Handoff；只录 Booking 时缺口继续保留，至少存在 MBL/HBL 后才自动关闭。
- 空白提单表单允许保存并继续待补；同一 Shipment 一类缺口清零后，动作区自动切换到下一类，不要求人员重新选票。
- 待补投影已统一返回当前值、来源系统与可用值、系统候选、责任角色、截止来源、受限动作和直接动作；当前没有权威截止或下游限制规则时明确返回“未设定”和空受限动作，界面显示“当前不限制流程”，不编造期限或硬闸。
- 隔离 PostgreSQL 已验证 SKU 绑定和提单补录的 Handoff 来源、对象回执、柜关系、租户、版本、幂等和冲突；工作台三视口 E2E 已覆盖刷新恢复、直接录入提单及补齐后队列自动关闭。
- 内部履约 Handoff 的真实 PostgreSQL 闭环暴露并修复两处数据库契约漂移：`shipment_handoff_profile_check` 现接受公共契约中的 `internal_fulfillment_v1`；`container_cargo_allocation_line_reference_check` 现允许同一装载事实同时保留备货行和由该备货行派生的 Shipment Cargo Line 引用。两项均使用追加迁移，未修改历史迁移。
