# 任务：工作台共享控制面 V1

> 本 brief 是跨工作台技术控制面的唯一活动设计载体，不是第三套业务规格。
> 岗位结果、流程、允许动作和完成标准仍只认 `doc/`；本任务只把已经定案的业务要求映射为
> 可复用的队列、详情元数据、缺口、动作和回执信封。各领域事实继续由所属模块和领域契约拥有。

## 目标

建立一个跨工作台一致、默认由服务端计算的读写控制面，使队列优先原因、责任和时限、
可执行缺口、允许动作、写入回执及恢复路径不再由各页面临场发明。

控制面采用“小型共享信封 + 领域类型外挂”，不建设包含全部业务字段的巨型通用 DTO，
也不把工作台 UI 壳提升为业务规则所有者。

本任务按“三体一面”交付：共享契约不能脱离业务消费者单独验收，必须与市场与经营信号首台的岗位任务、
权威事实和技术保障共同验证；首台通过后严格按 `doc/08` 的业务顺序逐台接入，以选品立项作为第二台
验证跨领域复用，不要求先迁完 20 台。

统一的是信息职责、交互契约、视觉壳和完成标准，不是把 20 台压成同一张表或同一种领域详情。
所有工作台均按“队列 -> 事实与缺口 -> 动作与结果”的因果顺序组织，并共同满足 `WB-B01`～`WB-B10`、
`HW-D01`～`HW-D23`；领域摘要、输入控件、业务规则和结果载荷仍由所属工作台负责。

## 前置门禁与排期关系

1. **门槛一是业务动作授权闭环**：路由清单、逐路由 capability、数据影响、Guard 默认拒绝、
   稳定错误和 CI 防漏标必须对齐。它关闭默认放行，但不替代对象范围和业务前置校验。
2. **门槛二是工作台任务控制面闭环**：GC 归属、五类信封和 Schema 必须与市场与经营信号首台共同验真；
   只完成 Schema 不算通过，只完成页面也不算通过。
3. 安全和 OIDC 最终门禁完成前，可以继续市场信号业务复审、真实样本、三面映射、Schema fixture 和
   只读 Adapter 对拍；
   不得合入新的生产受保护端点或写动作，也不得返回会被误解为安全许可的 `executable=true`。
4. 门槛二通过后即可恢复其余工作台逐台打磨。共享 UI 组件仍须两个真实消费者证明稳定后再抽取，
   但不作为恢复业务代码的前置条件。
5. 业务主链和 UI 打磨从 `market_signals` 开始；`workbenchOperationalReviewOrder` 继续表达全量操作规格的
   复审优先级，两者用途不同。本 brief 不另立第三份 20 台顺序。

## 边界 / 不做

- 不在 `docs/` 重写任一工作台的岗位流程、审批政策、阶段门槛或行业规则。
- 不把所有领域字段塞进共享 Schema；领域摘要和详情必须引用各自版本化 Schema。
- 不新增通用工作台业务表，不让共享层拥有领域状态机、缺口业务码或动作前置谓词。
- 不让前端从状态文字、颜色、空值或按钮可见性推导权限和允许动作。
- 不把 `allowedActions` 当安全边界；命令到达服务端后仍按 `GC-008` 全量重验。
- 不用自由文本代替稳定 reason code，不用 HTTP 成功代替业务接受或可靠提交。
- 不先抽一套通用 Vue 组件；至少两个真实消费者证明字段稳定后再进入稳定 UI 门面。
- 不越过选品、NPI 和主数据提前恢复寻源切片 2；轮到寻源时按已定信封接入，不再发明台内形状。
- 不在本任务吸收 NPI 退回 WIP 或无关本地迁移。

## 共享控制面组成

### 1. 组合方式

建议登记新的技术契约 `GC-012 Workbench Control Plane V1`，由全局契约负责人评审后分配最终 ID。
它只组合 `GC-005/008/009/010/011`，不复制这些契约的枚举和状态。若负责人决定扩展 `GC-010`，
则以 `GC-010` 的主版本升级承载；评审前不得同时维护两个候选权威。

TypeScript 消费形态使用泛型：

```text
WorkbenchQueuePageV1<TSummary>
WorkbenchDetailV1<TDomainDetail>
WorkbenchFactV1<TValue>
WorkbenchActionReceiptV1<TResult>
```

JSON Schema 不使用无约束 `object` 模拟泛型。每个领域通过 `allOf` / `$ref` 组合已登记的领域
Schema，生成具体消费者类型；共享信封只拥有控制字段。

### 2. 权威字段表

#### 队列页与队列项

| 字段                   | 必填 | 权威来源                | 规则                                                               |
| ---------------------- | ---- | ----------------------- | ------------------------------------------------------------------ |
| `items[]`              | 是   | 领域查询投影            | 每项为 `WorkbenchQueueItemV1<TSummary>`                            |
| `pageInfo`             | 是   | `GC-010`                | 不透明游标、稳定排序、页大小上限；前端不得自行拼游标               |
| `asOf`                 | 是   | `GC-010`                | 响应快照截止时间，不是业务发生时间                                 |
| `projectionVersion`    | 是   | 投影所有者              | 单调版本，用于刷新和并发可见性                                     |
| `sourceVersions[]`     | 是   | 各源模块                | 说明组合快照使用了哪些来源版本                                     |
| `workItemRef`          | 是   | `GC-005` 或领域事项投影 | 稳定工作项引用；不得用数组位置或标题当身份                         |
| `subjectRef`           | 是   | 领域模块                | 当前处理的业务对象引用，与工作项身份分开                           |
| `workbenchCode`        | 是   | 工作台登记表            | 稳定 code，不承载岗位文案                                          |
| `priorityReasons[]`    | 是   | 服务端投影              | 稳定 reason code；排序由服务端完成，前端不得重算优先级             |
| `ownership`            | 是   | `GC-005` / 领域事项     | 当前责任、下一责任、责任队列和分派状态；未知须显式，不造默认人     |
| `dueAt`                | 否   | 领域事项                | UTC ISO 8601；为空表示业务未设定，不等于不紧急                     |

| `version`              | 是   | 工作项所有者            | 后续命令的并发基线                                                 |
| `summary`              | 是   | 领域 Schema             | 只含该岗位判断所需摘要，不进入共享契约字段目录                     |

`ownership` 最少包含 `assignmentState`、`currentOwnerRef?`、`currentQueueRef?`、
`nextOwnerRef?`。若无法确定下一责任人，返回明确的队列或空值，不写“待定负责人”假实体。

## 业务步骤到技术消费者

本任务不交付单一岗位结果，直接消费者和承接方式如下：

| 使用场景     | 消费者需要看到什么                                | 服务端允许做什么                   | 可靠保存与反馈                              |
| ------------ | ------------------------------------------------- | ---------------------------------- | ------------------------------------------- |
| 岗位进入队列 | 为什么现在处理、责任、期限、阻断/待补数、主动作   | 只返回已重验的动作投影             | 队列来自可重建投影，游标和快照稳定          |
| 打开对象详情 | 事实、来源、版本、新鲜度、冲突、缺口和异常分轨    | 缺口指向实际处理动作               | 领域事实不复制，控制面保存引用和版本        |
| 执行动作     | 输入契约、确认等级、不可执行原因、expectedVersion | 按 `GC-008` 命令信封提交           | 幂等、并发、审计和事务由动作所有者负责      |
| 确认结果     | 接收、业务裁决、提交、结果版本、下一动作          | 重试、刷新或按 recovery 动作恢复   | 回执引用 client operation，刷新后与投影对拍 |
| 交班续做     | 当前/下一责任、等待原因、未解决缺口和最后结果     | 领取、转交或恢复仅在领域允许时出现 | 跨会话由服务端事实或可重建投影恢复          |

## 三体一面参考验证

市场与经营信号作为唯一首台 UI 与控制面参考。首台之后按 `doc/08` 的业务顺序推进，以选品立项作为
第二台复用验证。参考切片必须针对同一条负责人确认的真实路径同步完成：

| 面       | 参考台必须证明什么                                                                                                            |
| -------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 岗位任务 | 复审市场信号岗位流程并与 `workbenchOperationalSpecs` 中 code 为 `market_signals` 的条目对齐，责任、时限、缺口、动作和交接可续 |
| 数据事实 | 队列和详情字段均能追溯来源、版本和新鲜度；写回引用真实结果，不复制或虚构领域事实                                              |
| 技术保障 | 五类信封、服务端动作投影、权限、幂等、并发、错误和回执在同一路径中通过验证                                                    |

安全与 OIDC 最终门禁完成前先做业务规格、样本、字段来源矩阵、Schema fixture 和只读 Adapter 对拍，
不合入依赖未完成安全边界的新生产端点。门禁完成后接入该路径的写动作与回执。市场信号达到本 brief
验收线后，门槛二即通过，可以沿业务主链继续逐台打磨；选品立项作为第二个真实消费者，验证共享
队列行、缺口条、动作条和回执条后，才决定哪些组件进入稳定 UI 门面。

### 首批回归样例（已知问题，尚未修复）

- 市场信号进入 `handed_off` 后，服务端动作投影不得再返回“继续观察 / 交给选品 / 不采纳 /
  作废 / 归档”等去向动作；若业务允许交接后补事实，应只保留补事实动作，不把对象误判为完全关闭。
- 选品已立项后，页面不得显示没有服务端动作支持的“撤回”。NPI 的只读提示必须描述真实回程：
  只有产品负责人正式退回后，选品才恢复编辑；未领取撤回、已领取退回和已发布新版本若未定案，
  一律不摆假按钮或错误指引。
- 工作台默认态一个字段最多两行：标签不超过 8 字，状态不超过 15 字；同一状态一屏只表达一次，
  子字段不重复父级前缀，删除“系统自辩”文案。教学、字段解释和只读原因进入可聚焦的
  `InfoTooltip`，但错误、阻断和当前主动作不能藏进 tooltip。
- 上述三项必须先由控制面动作/状态投影提供真实依据，再做页面压缩；当前 brief 记录问题，不声称已修复。

## 兼容与迁移策略

- 采用加法端点或显式契约版本，不原地改变现有页面依赖的响应含义。
- 每台先建立“旧响应 -> 控制面”的服务端 Adapter 和对拍测试；前端不得承担转换业务规则。
- 不新增通用持久化表。队列和详情从领域事实与任务/工单投影组合，必要缓存必须可重建。
- 公共 Schema 进入 `packages/contracts/schemas/v1/` 后由目录登记、生成类型和 fixture 统一派生；
  禁止 API/Web 各手写类型。
- 破坏性变更走新主版本和消费者迁移窗；旧端点的退役条件必须有调用清单和监控证据。
- 每个试点提供字段来源矩阵，证明没有把显示摘要提升为权威事实，也没有改变领域所有权。

## 实施切片

### A. 市场信号三面基线

- 复审市场信号从登记/接收到补事实与证据、判断去向、交接或关闭、退回重判/恢复的岗位路径，
  并与 `workbenchOperationalSpecs` 中 code 为 `market_signals` 的条目对齐。
- 选定覆盖正常、等待、拒绝、冲突、返工和恢复的真实或脱敏样本；现有页面和操作规格只作实现事实，
  不反向充当业务权威。
- 建立“岗位步骤 -> 权威事实/写入 -> capability/守卫/契约/反馈”映射，不补不存在的业务规则。

### B. 契约定案

- 决定采用新 `GC-012` 还是 `GC-010` 主版本升级，只保留一个权威入口。
- 从市场信号参考路径提炼最小 Schema、正负 fixture、TypeScript 生成类型和 GC 登记；不包含领域 payload。
- 对拍 `GC-005/008/009/010/011`，禁止复制枚举。

### C. 安全前置

- `authz-default-deny-v1` 完成：路由、岗位动作和数据影响对齐；无 capability 即拒绝，并有静态枚举门禁。
- Web OIDC/PKCE 属独立任务；未进入生产认证链时，试点只能作为受限开发验证。

### D. 市场信号参考实现

- 市场信号建立队列、详情和缺口 Adapter，保持现有 API 兼容；覆盖责任/时限、稳定分页、分轨、过期投影和跨租户裁剪。
- 参考动作按 `GC-008` 登记并返回输入 Schema、确认政策和拒绝原因；前端不计算资格。
- 命令回执按三阶段返回，提交后重新读取并对拍结果版本和下一动作。

### E. UI 门面

- 市场信号先按“队列 -> 事实与缺口 -> 动作与结果”完成桌面、窄屏和移动端样板；单一选择源、
  单一主动作、可执行缺口、责任/时限、业务回执和失败恢复必须同时成立。
- 统一视觉遵守 `UI_SYSTEM.md` 的 Operations Shell；不新增营销式大卡片、嵌套卡片或第二套主题私有规则。
- 选品立项作为第二个消费者接入；只有两个消费者都证明稳定的展示组件才抽入共用 UI 壳。
- 后续继续按 `doc/08` 业务顺序逐台接入，不因某台材料更完整而跳序。

## 验收

- [ ] 控制面只有一个批准后的权威契约入口，且登记到全局契约表
- [ ] 市场信号同一参考路径具备岗位任务、权威事实、技术保障与界面四面映射，任何一面未完成均不通过门槛二
- [ ] 队列、详情、缺口、动作和回执字段均有明确所有者、来源和版本
- [ ] 领域 payload 通过具体 `$ref` 校验；共享层不存在无约束巨型 DTO
- [ ] `allowedActions` 完全来自服务端，前端未从状态或文案推导动作
- [ ] 默认拒绝授权和路由 capability 枚举门禁先于任何写动作试点合入
- [ ] 回执分开表达接收、业务裁决和提交，不用 HTTP 200 冒充业务完成
- [ ] 市场信号完成旧/新响应对拍和统一 UI 验收后按业务顺序推广；选品立项作为第二个消费者通过前不抽共享 UI 组件
- [ ] 现有消费者保持兼容；弃用有调用证据、迁移窗和恢复方案
- [ ] 契约生成、drift、API、授权、真实 PostgreSQL 集成和关键 E2E 按高风险门禁通过
- [ ] 真实或脱敏样本覆盖正常、等待、拒绝、冲突、返工和恢复；未完成前不称业务闭环

## 验证计划

设计定案前只运行文档和仓库检查。进入公共契约实现后按高风险执行：

1. `pnpm contract:generate`、`pnpm contract:check`、`pnpm contract:drift`。
2. 控制面 Schema 正负 fixture、旧/新 Adapter 对拍和消费者类型检查。
3. API 授权、租户、对象范围、拒绝原因、幂等和并发测试。
4. 启动本地 PostgreSQL 后运行相关 `test:integration` 与迁移验证。
5. 市场信号 Web 组件测试和参考路径关键 E2E；最后运行高风险 `pnpm validate`。
