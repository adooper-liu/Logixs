# 任务：备货工作台以人为中心改造

> 唯一方案依据：[角色工作台以人为中心的设计契约](../../product/ROLE_WORKBENCH_HUMAN_CENTERED_DESIGN.md)。
> 本任务只记录实施范围、验收和进度；通用规则、信息动线和 SKU 显示示例不在此复制。
> 2026-09-23 边界评审：项目核心已改为“实际出运后的在途与到港生命周期”。本任务实现降为上游辅助面并冻结扩展；目标模型和处置门禁见
> [`POST_DEPARTURE_CORE_MODEL_GAP_V1`](../../product/domain/POST_DEPARTURE_CORE_MODEL_GAP_V1.md)。

## 目标

把现有备货工作台从“先选货柜、查看技术任务状态、逐项评审所有 SKU”改为以备货人员真实结果为中心的工作流。人员可从备货单开始，识别今天需要处理的业务原因，只处理新/未知 SKU 和实际适用的资料缺口，并在同一上下文完成服务端允许的动作、等待与结果确认。

本切片同时验证通用契约 `HW-D01`～`HW-D10` 可落地，但不在本任务扩改其他岗位工作台。

## 边界 / 不做

- 复用现有 `ProductSku`、`ProductComplianceProfile`、合规规则/评审、证据、工作项、备货单和装柜分配权威，不新增重复事实表。
- 允许增加面向工作台的 Application 查询编排和加法式 DTO；前端不得自行计算规则适用性、证书要求、放行或允许动作。
- 保持一柜多单、一单多柜；货柜不是开始备货的前置条件。
- 本切片提供备货单导入/新建的清晰入口与承接状态；若现有后端写能力不足，另行收窄为可真实落库的最小入口，不制作假提交或浏览器临时成功。
- 不重写已完成任务 `p6-cargo-ready-operational-workbench.md`，不把历史错误口径继续复制到新文档。
- 不新增通用动态表单引擎，不扩展法规规则表达式，不改生命周期状态机，不把 `ExternalWorkItem` 合并为 `NodeTask`。
- 不为其他七个工作台制作空壳页面；它们在各自切片复用同一通用契约。

- [x] 无货柜时仍可从备货单开始；分配后支持一柜多单和一单多柜，选择上下文保持唯一。
- [x] 队列标题使用业务原因，不以“可执行/阻塞/临期”或内部任务类型作为工作的主含义。

## 业务与数据协同设计

| 业务岗位要完成什么 | 操作时需要看到什么                       | 系统允许做什么                             | 数据如何可靠保存与反馈                                              |
| ------------------ | ---------------------------------------- | ------------------------------------------ | ------------------------------------------------------------------- |
| 接收备货工作       | 导入/新建入口、预检结果、重复和逐行错误  | 导入批量数据或新建单条备货单               | 复用导入 Application 用例、事务、幂等、原始来源与逐行结果           |
| 确认商品身份       | 未匹配行、SKU 候选、关键差异             | 匹配已有 SKU；仅对新 SKU 创建/确认         | `ProductSku` 保存稳定身份；匹配决定和来源可审计                     |
| 补齐必要物料事实   | 仅显示未知/冲突属性、影响和来源          | 确认属性、提交更正或等待主数据责任人       | `ProductComplianceProfile` 追加版本，不覆盖旧事实；并发版本显式校验 |
| 处理适用资料       | 规则为何适用、证据状态、缺口责任和期限   | 补充适用附件或进入合规处理；不允许前端放行 | 规则、证据版本、评审发现与工作项分别由权威模块保存                  |
| 安排装柜           | 未分配数量、候选货柜和分配约束           | 一单分多柜、一柜装多单；仅执行授权分配     | `ContainerCargoAllocation` 记录来源行、数量、单位和版本；总量可对账 |
| 确认本次结果       | 已完成事实、剩余缺口、等待对象和操作回执 | 执行唯一主动作、按原因恢复或等待           | 幂等操作与三段回执可追踪；结果刷新队列与同一业务上下文              |

## 方案

### 1. 先固定读模型，不从现有页面反推

- 为备货工作台定义岗位读模型，至少包含：备货单身份/版本、SKU 与本次数量、当前有效属性摘要及来源、适用要求与原因、证据状态、真实缺口、责任/期限、等待主体、允许动作、结果回执。
- 读模型由 Application 层组合公共 Port；DTO 与前端类型显式映射，公共契约变更按契约一致性门禁执行。
- 缺数据时返回稳定缺口码和解释，不把缺少评审对象转换成固定五项“未评审”。

### 2. 重构单一工作上下文

- `CargoReadyWorkbench.vue` 只编排一个当前工作项/备货单上下文，移除与队列竞争的货柜主选择器。
- 队列按业务原因和紧迫度组织“待我处理/等待他人”，技术状态只作辅助筛选或解释。
- 中区显示方案 §5.3 的 SKU 摘要与真实缺口；右区只显示当前允许动作、完成条件和结果。
- 装柜分配作为后续业务动作出现，分配完成后货柜成为关联对象而非备货入口。

### 3. 测试真实岗位路径

- 领域/应用测试覆盖属性适用性、正常项不产生活、规则命中、证据缺失、版本失效和装载关系变化。
- API 测试覆盖租户/权限、DTO、分页、稳定排序、幂等和冲突。
- 组件测试覆盖三种规范 SKU、单一选择源、等待/错误/空态及动作权限。
- E2E 使用真实样本 `26DSC01811/26DSC01812` 覆盖无货柜开始、一柜多单/一单多柜、缺口处理和结果确认。

## Review notes

- **产品边界变更**：备货、SKU 补齐、装柜安排属于出运前履约准备，不再是当前项目核心流程。现有未提交实现予以保留，但不得继续扩展成上游状态机或作为首页主工作流。
- **处置门禁**：在 Shipment 目标导入和生命周期工作台切片确定前，本任务不标 `done`。评审需选择保留为辅助查询/维护面、收窄路由和文案，或延期；不得无审查删除已实现代码。
- **Shipment 技术评审**：已完成主运输执行粒度、柜次唯一活动归属、V2 事件主体和两阶段可靠初始化评审；结论为建议批准，等待负责人确认四项业务取舍后才进入公共契约与迁移设计。
- 待关闭：服务端备货单投影已提供 SKU 身份、物料档案缺口、装柜分配和基础允许动作，但未把所有未选中订单的合规评审聚合为队列原因；当前仅在选中备货单后经权威合规接口展示适用资料和证据缺口。完成前需决定由跨模块 Application 投影聚合，还是保留分段加载并补充稳定服务端原因。
- 能力边界：当前真实写入口只有导入备货明细以及关联货柜返回的领取/完成工单。SKU 匹配、物料属性维护和装柜分配尚无适合本页直接提交的服务端命令，因此界面只解释缺口和责任，不制作假按钮。
- 门禁状态：本任务触及文件格式检查通过；全仓 `pnpm validate` 在两份既有 `docs/superpowers` 文档的 Prettier 检查处停止。失败点之后已分别确认全仓 typecheck、test、test:e2e 和 build 通过。
