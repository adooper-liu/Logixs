# 任务：供应商准入、报价与定点 V1

> 全链工作台 **5 号节点「寻源与供应商定点工作台」的第一片**。
> 上游 4 号节点已交付（`product-identity-master-data`，已合入）：发布了一份
> `sellable_sku_release` —— **但至今没有消费者**。这一片补的就是这个断点。
>
> 本仓库**此前没有任何供应商实体**，这一片是从零起一个域。

## 已定的两条口径（负责人 2026-09-28，按行业做法选定）

| #     | 事项               | 选定                                                                                                                           | 理由                                                                                                                  |
| ----- | ------------------ | ------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| **A** | **BOM 谁编**       | **不由主数据侧先编**；在 5 号 **由供应商报价时带入**，只收一层「关键物料清单」（物料、规格、用量、损耗、是否客供）             | 你不排产，你比价 —— 多级 BOM 是给工厂排产与库存用的。而且**自己编的是"声称"，供应商报的才是"承诺"**：后者出错有人负责 |
| **B** | **商务条件怎么进** | 报价单**结构化录入十项**（单价阶梯、贸易术语、MOQ、模具费、样品费、交期、包装、付款、质量、有效期），并**回填 4 号**的订货条件 | 这十项里**六项不是"价格"而是"条件"**：只比单价是外行比价 —— 真实差异常在模具费谁承担、MOQ 多高、交期多长              |

**行业依据**：报价单十项与「沉默不等于确认」（供应商必须列排除项与假设）来自
[China Supplier RFQ Template](https://ucsourcing.com/fr/china-supplier-rfq-template/)；
BOM 类型与单级/多级取舍来自 [Greenlight 的 BOM 词条](https://www.greenlight.guru/glossary/bill-of-materials)
（该来源**未覆盖"不自己生产的贸易方"**，所以「贸易方用一层关键物料清单」是我的判断，不是引用）。

## 目标（一个业务结果）

**寻源负责人为一件可售 SKU 收齐候选供应商的报价，选定一家定点，产出一份可交到
需求与补货侧的定点交接。**

交接要带齐网络声明的五项：**供应商身份 · 定点 SKU · 报价条件 · 样品结论 · 产能约束**。

## 上游事实（已有，本片不改）

`sellable_sku_release`（`product_identity_release`）：产品与 SKU 身份、各层关键属性
（含品类、原产国、HS 编码、目标市场、认证、危险品、订货条件）。**不可变，只读**；
BOM 与 Listing 作为**待补**随行 —— 本片正好把 BOM 那一半补上（由报价带入）。

## 业务步骤 → 所需信息 → 允许动作 → 权威事实

| 业务步骤            | 操作时需要看到                                       | 系统允许做什么                     | 数据如何可靠保存                                          |
| ------------------- | ---------------------------------------------------- | ---------------------------------- | --------------------------------------------------------- |
| 找出哪些 SKU 待寻源 | 队列：来自哪一票、品类、目标市场、认证要求、还缺什么 | 选一条                             | 队列取自发布快照，稳定排序，刷新不丢                      |
| 登记候选供应商      | 已有供应商、国别、联系人、准入状态                   | 新建或复用一个供应商               | 供应商是**稳定身份**，一处登记多处引用                    |
| 录入报价            | 该 SKU 的要求、已有几家报价                          | 按十项录入；**关键物料由报价带入** | 报价按供应商追加版本，旧版不覆盖；同商同 SKU 只一条当前版 |
| 定点                | 各家的价格与条件、样品结论、产能约束                 | 选定一家（或都不选）               | 定点写不可变交接快照；旧版标记已被替代                    |
| 交给需求与补货      | 交接内容                                             | —（交接后只读）                    | 快照不可变                                                |

## 边界 / 不做

- **不做多级 BOM**、不做排产、不做库存 —— 那是工厂侧的事（口径 A）。
- **不做打样流程本身**（寄样、改样、确认的往返）—— 本片只登记**样品结论**这个事实。
  完整的打样往返等有真实诉求再开。
- 不做供应商绩效/评级、不做账期与对账。
- 不改 `product_identity` 与既有 wire value；回填 4 号的订货条件走**加法**字段。
- 不改已共享迁移。
- **不投 outbox**：与前几片一致，没有消费方就先不造事件。

## 验收

- [ ] 首屏是**待寻源的可售 SKU 队列**，每条写明来自哪一票、品类、目标市场、认证要求
- [ ] 供应商能登记并复用；同一租户下供应商名称不重复
- [ ] 报价按**十项**录入，且**关键物料清单由报价带入**（不是主数据侧预先编的）
- [ ] 同一供应商对同一 SKU 的报价**追加版本**，旧版不覆盖；重复提交幂等
- [ ] 定点写下不可变交接快照，**带齐五项**（供应商身份、定点 SKU、报价条件、样品结论、产能约束）
- [ ] 定点后该 SKU **不再出现在待寻源队列**，但可回看
- [ ] 并发定点用版本乐观锁，冲突拒绝而不是覆盖
- [ ] 跨租户不可见
- [ ] 相关质量门禁全绿

## 一处已知的变通（不是设计，是门禁逼出来的）

量纲类型（`MeasureV1` / `MeasureUnitV1`）**物理上留在 `product-identity.schema.json` 里**，
本片的契约**跨文件引用**它。这不是理想的归属 —— 量纲是商品属性与供应商报价共用的。

试过把它搬进 `common.schema.json`，**被 `contract:check` 挡住**：它把"定义从 A 文件消失"
判成破坏性变更，而**标量类型（`type: object`）的破坏性变更不能声明豁免**
（`pre-release-breaking-changes.json` 只对枚举成员的移除生效 —— 见
`validate-contract-schemas.mjs` 的两条分支）。

所以要么改门禁，要么接受这个归属。本片选后者：**不为一个归属问题去放宽破坏性变更检查**。
等 `common.schema.json` 的搬家用得上真正的契约版本化时再一起做。

## 方案

1. **契约加法**：`SupplierV1`、`SupplierQuotationV1`、`QuotationKeyMaterialV1`、
   `SupplierNominationV1`、`SupplierNominationHandoffV1` 与三条命令。
2. **加法迁移**：`supplier`（供应商身份）· `supplier_quotation`（报价，含关键物料 JSONB）
   · `supplier_nomination_release`（定点交接快照）。
3. **领域规则**：供应商名称唯一、报价十项校验、定点门槛与幂等（纯函数 + 单测）。
4. **仓储 / 服务 / 控制器**：待寻源队列、供应商登记、报价录入、定点。
5. **前端**：`/workspaces/sourcing` 接真实 API，三区（待寻源队列 → SKU 要求与各家报价 → 登记与定点）。

## 待确认（我按推定实现，有异议随时叫停）

1. **同一 SKU 至少几家报价才能定点？** 推定：**1 家即可**（不设人为门槛；比价是手段不是目的，
   只有一家时硬卡会让人去凑数）。
2. **定点后能不能改？** 推定：**能改**，再定点一次追加新版本（旧快照不覆盖）。
3. **报价的有效期怎么用？** 推定：只**登记与显示**，到期不自动作废 —— 自动作废会让
   定点记录失去依据。过期了由人重新询价。
