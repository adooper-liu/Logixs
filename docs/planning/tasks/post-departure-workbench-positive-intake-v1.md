# 任务：已出运 Shipment 业务建档与接管 V1

## 目标

让出运运营在出运工作台按真实业务顺序完成一票已出运 Shipment 的建档或接管：优先复用系统内备货、SKU、装箱、货柜和离港事实；确无上游事实时按业务对象手工建档；大量数据才使用批量工具。普通资料缺失进入持久待补，不要求人员先理解导入文件、数据库字段或内部 ID。

## 边界 / 不做

- 遵循 `docs/product/POST_DEPARTURE_WORKBENCH_DELIVERY_BASELINE.md` 的 `WB-D01`～`WB-D19` 和 `UI-01`。
- 复用既有 Shipment Handoff 预检、冲突检查、原子接管、生命周期初始化和待补投影，不另写 Shipment 落库事务。
- 标准模板和旧四表保留为次级工具；本任务不删除、不重写其解析器。
- 本任务只完成已出运建档/接管和结果交接，不提前实现清关、提柜、仓库或 Shipment 在途总览。
- 公共契约仅做加法；不修改已有 wire value，不修改已共享迁移。

## 验收

- [ ] 首屏先显示系统内待接管业务，人员不上传文件即可完成正常接管
- [ ] 确无内部事实时，可从同一工作台打开“手工建立 Shipment”，只填写业务可识别内容
- [ ] Shipment 业务号和至少一个货柜身份成立即可建档；其他普通缺失进入持久待补
- [ ] 起运港、目的港和货主使用受控候选选择；销售国家与货主名称分字段显示
- [ ] 系统生成请求身份、幂等键、来源身份和内部 ID，界面不要求人员编造
- [ ] 同柜活动 Shipment 冲突或业务号冲突明确拒绝，并保留输入供修正重试
- [ ] 成功后显示创建/复用的 Shipment、货柜关系、待补数量和下一步入口，并从服务端重读结果
- [ ] 标准模板与旧四表只出现在次级“批量工具”中
- [ ] 桌面与移动端保持“入口/当前事实/动作结果”的清晰顺序
- [ ] Web/API 聚焦测试、类型检查、生产构建和关键 E2E 通过；最终按高风险公共契约要求运行 `pnpm validate`

## 业务与数据协同设计

| 业务步骤与岗位结果 | 信息产生时机/前置事实                  | 操作时需要看到什么                                   | 系统允许做什么                         | 数据如何可靠保存与反馈                             |
| ------------------ | -------------------------------------- | ---------------------------------------------------- | -------------------------------------- | -------------------------------------------------- |
| 找到待接管业务     | 备货、装箱、货柜和离港事实已在系统形成 | 船名航次、路线、柜、备货单、SKU 数量和真实缺口       | 批量接管无冲突候选；异常逐票处理       | 服务端候选投影实时读取同一组上游关系               |
| 选择手工建档       | 确认系统内没有可复用候选               | 建档所需最小身份、哪些可后补、当前已填事实           | 打开单票业务表单；返回内部候选继续复用 | 不为打开表单写库，不生成空壳对象                   |
| 填写业务身份       | 已知 Shipment 业务号和至少一只货柜     | 当前值、港口候选、货主及独立销售国家、可后补提示     | 选择受控值、录入当前事实、提交建档     | 服务端校验身份与引用；技术来源和幂等信息由系统生成 |
| 建档并接管         | 身份成立且不存在互斥活动关系           | 将保存的 Shipment/柜关系、非阻断缺失、真正阻断和影响 | 一次提交；冲突后原地修正重试           | 复用 Shipment Handoff 事务；普通缺失形成持久待补   |
| 继续后续工作       | Shipment 已接管                        | 服务端重读详情、待补数量、下一责任与可进入工作台     | 打开已接管待补或进入 Shipment 后续流程 | 刷新待补队列和详情，不以浏览器成功提示代替结果     |
| 使用批量工具       | 需要一次处理多票或只有来源文件         | 标准模板与旧格式的适用场景、已选文件和预检结果       | 下载/上传/预检/批量接管                | 继续使用既有 ImportBatch 与统一 Handoff            |

## 工作台避坑检查

- [ ] 首屏按“系统内待接管 → 手工建立 → 批量工具”组织，不按文件类型组织
- [ ] 系统产生请求身份、内部 ID、重复判断、缺口和审计；人员只选择、录入或确认业务事实
- [ ] 已有权威事实自动带入；不要求重复录入备货、SKU、装箱或货柜资料
- [ ] 每个缺口在接管后进入直接可处理的持久待补，不显示无法执行的说明文字
- [ ] 资料待补与身份/关系冲突分轨；普通缺失不阻断建档
- [ ] 页面只有一个入口选择和一个随入口变化的主动作
- [ ] 生命周期、资料完整度、冲突和导入解析结果不合成大状态
- [ ] 成功后重读服务端 Shipment 详情与待补队列
- [ ] 内部候选正常项支持批量接管，冲突项保留逐条恢复
- [ ] 错误区分业务冲突、无权、输入不合法和技术失败，并保留可恢复路径

## 方案

1. 校准交付基线和导入领域文档，固定业务建档优先、导入次级的入口顺序。
2. 在公共契约增加手工建档命令、参考数据投影和结果类型；现有 Handoff 契约保持兼容。
3. Application 层把业务命令映射为 `ShipmentHandoffCommandV2`，由服务端生成来源身份并复用现有接管事务。
4. 提供出运运营可读的国家、货主和港口候选查询，服务端验证受控引用。
5. 拆分工作台入口选择、手工建档和批量工具组件，首屏默认内部事实。
6. 成功后重读 Shipment 详情和持久待补；业务冲突原地展示并保留输入。
7. 覆盖服务端映射/授权/冲突、Vue 表单行为、工作台入口顺序和关键 E2E，再做桌面/移动视觉检查。
