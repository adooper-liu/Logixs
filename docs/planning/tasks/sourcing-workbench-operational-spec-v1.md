## 当前技术事实

### 已实现并有仓库证据

- 主数据发布的可售 SKU 按 SKU 展开待寻源队列，稳定键为 `skuReleaseId + skuId`。
- 供应商有稳定身份与 `pending / admitted / suspended` 准入状态；未准入或暂停供应商不能定点。
- 报价契约可表达价格阶梯、Incoterms、MOQ、模具费、样品费、交期、包装、付款、质量、有效期、关键物料和排除项。
- 定点要求样品结论和产能约束，写入不可变 `SupplierNominationRelease`；重复请求有幂等保护，并发使用版本检查。
- 定点快照冻结供应商名称、国别、报价版本、价格阶梯和贸易术语等事实。
- 既有测试覆盖未准入拒绝、并发定点、幂等重放、租户隔离和快照冻结。

### 关键技术差距与错误表述

| 严重度 | 观察到的事实                                                                            | 直接后果                                   | 技术修复方向                                     |
| ------ | --------------------------------------------------------------------------------------- | ------------------------------------------ | ------------------------------------------------ |
| P0     | 旧 brief 声称报价修订不覆盖旧版，但仓储实际对同一 `supplier + skuRelease` 执行 `update` | 未选报价的修订历史无法还原                 | 追加保存报价版本或建立不可变历史表，并修正旧表述 |
| P0     | 页面在登记供应商时用普通复选框直接写 `admitted`                                         | 登记和准入没有独立允许动作、证据和审计边界 | 登记默认待准入；准入作为独立服务端授权动作       |
| P0     | 页面只提供报价契约的一部分输入                                                          | UI 无法完成业务文档要求的结构化报价收集    | 按业务规格提供渐进录入、待补和不适用表达         |
| P0     | 页面直接比较不同数量档、币种和 Incoterms 下的最低单价                                   | 不可比数据被呈现为可排名结果               | 先计算可比性；依据不完整时禁止生成比较结论       |
| P0     | 当前没有责任人、下一责任人、期限、等待原因和接收队列落账状态                            | 工作无法交班，也无法识别超期和下游未接收   | 建立服务端持久的寻源事项和责任/等待投影          |
| P1     | 登记、报价、定点同时平铺为等权动作                                                      | 页面把业务顺序交给用户猜                   | 由服务端允许动作投影唯一当前主动作               |
| P1     | `USD`、MOQ `500`、`FOB Ningbo` 和“已准入”被预填                                         | 默认值可能被保存成虚假业务事实             | 业务事实默认空；模板必须显式选择并保留来源       |
| P1     | 上游接收之外的入口、三层退出、正常批量和异常恢复不完整                                  | 线下业务外循环，误建和停做事项不能收口     | 共用用例与校验补齐适用入口、退出和批量能力       |
| P1     | 定点快照没有接收队列、待补事项和同步/签收状态                                           | 已写快照可能被误认为下游已接收             | 扩展交接与同步投影，业务事实和传输状态分轨       |

## 技术方案取舍

| 方案                      | 范围                                                        | 成本与风险                             | 结论             |
| ------------------------- | ----------------------------------------------------------- | -------------------------------------- | ---------------- |
| A. 只修文案和布局         | 去默认值、弱化最低价、折叠表单                              | 成本低，但责任、历史、交接和退出仍断裂 | 不选             |
| B. 按业务规格补齐事项闭环 | 责任/时限、报价历史、完整比较、入口退出、版本交接、异常恢复 | 跨契约、数据、API、UI 和测试，成本中高 | 推荐，拆成小切片 |
| C. 立即建设完整 SRM       | 门户、合同、绩效、质量、结算全部纳入                        | 成本和跨域风险很高，真实证据不足       | 暂不选           |

在真实样本确定字段、权限和流程前，不给方案 B 伪造精确工期。

| 业务权威要求                       | 当前技术事实                                    | 本任务技术验收                                       |
| ---------------------------------- | ----------------------------------------------- | ---------------------------------------------------- |
| 寻源项目从需求到定点连续推进       | 当前只有可售 SKU 队列、供应商、报价和定点第一片 | 每个切片引用对应业务章节，不在代码中补写隐含规则     |
| 报价、样品、准入、定点与交接可追溯 | 报价修订覆盖当前行；定点快照不可变              | 报价历史、决定与替代关系可审计，旧事实不被覆盖       |
| 工作台共同十项要求                 | 责任、时限、入口退出、状态分轨和批量能力不完整  | 服务端事实、允许动作、读模型和界面逐项建立证据       |
| AI 不代替业务决定                  | 当前第一片没有 AI 决策                          | 后续接入只消费可追溯建议，不开放自动准入、定点或推进 |

## 六类岗位验收的技术矩阵

场景含义以 `doc/` 的岗位工作台验收规则为准；下表只说明技术系统必须提供的可观察证据。

| 路径 | 业务样本要求                                 | 技术可观察结果                                         |
| ---- | -------------------------------------------- | ------------------------------------------------------ |
| 正常 | 已准入供应商、同口径完整报价、样品和产能依据 | 完成比较与定点，下游队列收到版本化交接                 |
| 等待 | 供应商未回复、样品待验或产能待确认           | 持久显示等待对象、期限和影响动作；无关工作可继续       |
| 拒绝 | 未准入/暂停供应商，或关键引用不成立          | 服务端稳定拒绝，保留输入并返回恢复动作                 |
| 冲突 | 两人同时修订报价或定点                       | 后提交者收到版本冲突，刷新后仍在同一事项               |
| 返工 | 定点后条件变化或上游规格更正                 | 追加报价/交接版本，旧快照可追溯，下游看到替代关系      |
| 恢复 | 导入部分行错误、响应丢失或同步失败           | 正常行按既定原子性落账，错误行逐条修复；重试不重复写入 |

样本必须来自真实岗位或脱敏后的真实业务，不能用开发者编造的 happy path 替代。

## 实施计划

1. **事实纠偏**：修正文档中的报价历史错误表述；去除静默默认值和登记即准入；补回归测试。
2. **事项与责任**：建立寻源事项、当前/下一责任、期限、等待原因和五轨读模型；动作由服务端投影。
3. **报价与比较**：报价追加版本、完整报价渐进录入、可比性判定和来源追溯；不先建设自动“最优供应商”。
4. **入口与批量**：上游接收、本岗建项、批量导入共用用例和校验；正常批量、异常逐条恢复。
5. **退出与交接**：按业务规则实现回退/重开、作废/归档、受限删除；交接补齐接收队列、待补和同步/签收状态。
6. **岗位界面**：以寻源事项为单一队列，按事实/缺口/动作动线呈现服务端返回的主动作；覆盖窄屏和无障碍。
7. **真实验收**：六类样本走查并确认剩余风险，再将 `sourcing` 加入 `workbenchOperationalSpecs`。

## 边界 / 不做

- 不在 `docs/` 内重新定义寻源业务规则；业务变化先进入 `doc/` 或业务 ADR。
- 不建设完整供应商门户、合同、对账、付款、绩效或供应商风险平台。
- 不把供应商报价的一层关键物料自动提升为标准物料或多级生产 BOM。
- 不让 AI 猜报价、准入、质量、样品或产能事实。
- 不自行规定最低报价家数、自动过期政策或强制四眼审批。
- 不修改已共享迁移；数据结构变化只追加迁移，并验证旧数据升级与恢复。
- 不触碰当前工作树中的 NPI 退回实现。
