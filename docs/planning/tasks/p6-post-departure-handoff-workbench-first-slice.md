# 任务：已出运数据接管工作台首片

> 唯一产品方案：
> [出运后工作台交付基线](../../product/POST_DEPARTURE_WORKBENCH_DELIVERY_BASELINE.md) `UI-01`。
> 当前实现基础：`POST /api/shipment-handoffs/preflight`、`POST /api/shipment-handoffs/accept`、
> Shipment Handoff 公共契约与真实四表字段注册。
> 页面归属：现有“出运工作台”内的“接管已出运数据”，不新增顶层工作台。

## 目标

让出运运营人员从手头已有的任一来源文件开始，在同一界面完成独立上传、联合预检、逐柜冲突处理、正式接管和待补追踪，并看到每票、每柜和下游初始化的明确结果。

## 边界 / 不做

- 本任务只完成“数据进入系统”的业务结果，不同时改造 Shipment 在途详情、清关、提柜、送仓、卸柜或还箱工作台。
- 四类来源共用一个接管页面，不形成四套导入页面，也不互相写回；不要求四个文件同时上传。
- 首片不实现任意字段映射器；只支持已登记的四表版本，未知列、损坏值和未知字典进入明确问题清单。
- 不用默认国家、港口、时区、SKU 或当前时间伪造来源事实；只有日期的出运事实按正式 `date_only` 补时规则另切片实现。
- 非内部主键、必需外键/租户引用和对象身份冲突的缺失项进入待补，可创建正式 Shipment；`rejected` 只隔离受影响对象。
- 不要求业务人员阅读规范字段码、JSON、数据库 ID 或 146 字段目录。

## 业务与数据协同设计

| 业务步骤 | 操作时需要看到什么                                                      | 系统允许做什么                                    | 权威事实与反馈                                           |
| -------- | ----------------------------------------------------------------------- | ------------------------------------------------- | -------------------------------------------------------- |
| 选择来源 | 已收到哪些文件、来源版本、文件名、实际数据行数和各文件处理结果          | 选择/替换任一文件，开始预检                       | 每个原文件、哈希、工作表与实际 XML 范围独立进入批次证据  |
| 查看归组 | 归成多少票、柜、提单和货物行；跨表未匹配项                              | 展开一票或筛选问题原因                            | 预检不写正式业务表，结果绑定批次与 payload hash          |
| 判断问题 | 人话问题、影响对象及受影响动作                                          | 点击缺口动作，在当前候选内直接打开并聚焦编辑器    | 未知港口、时区、货主、SKU、ATD 分别形成稳定缺口码        |
| 确认接管 | 可接管/待补/逐柜冲突/重复数量，以及本次将建立的对象                     | 单票接管，或一次接管队列内全部非阻断 Shipment     | 服务端按 Shipment 归组并逐组事务接管；冲突对象留在原队列 |
| 确认结果 | 每票是否落账、Shipment 链接、柜/货/单结果、生命周期初始化和下游吸收状态 | 打开已接管 Shipment；重试可恢复下游；返回问题队列 | 三阶段回执与 traceId 可追踪，不以 HTTP 200 冒充整批成功  |

### 已完成子切片：待复核基础缺口处理

| 业务步骤          | 操作时需要看到什么                                                                   | 系统允许做什么                                       | 权威事实与反馈                                                                            |
| ----------------- | ------------------------------------------------------------------------------------ | ---------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| 确认所属 Shipment | 当前柜、备货单、提单、船名航次，以及系统建议和现有 Shipment 的路线、时间、状态与柜数 | 核对系统建议后选择现有 Shipment，或新建独立 Shipment | 保存受控动作与目标关系版本；内部身份由系统生成，业务人员不能填写或编造 Shipment ID/业务号 |
| 确认权威港口      | 来源港口原文、UN/LOCODE、官方名称和国家/地区段                                       | 搜索并选择 active UNECE 发布中的起运港和目的港       | 保存港口稳定 ID 与当时 UN/LOCODE；候选名称或失效发布不得通过                              |
| 确认离港事实      | 来源出运日期、实际离港时间、IANA 来源时区和业务可理解的附件/记录号                   | 登记并核验证据后确认实际离港事实                     | UTC 时间、来源时区、证据 UUID、原因和操作者进入 append-only 修正版本                      |
| 查看剩余缺口      | 已修正项、仍缺的业务资料、下一责任方和受影响的具体动作                               | 保存本次修正；也可先接管并后续补齐                   | 服务端重新计算 issue；缺口进入完整度投影，不把 Shipment 生命周期退回出运前                |

基础缺口修正不得覆盖四表原始快照；同一候选每次修改追加版本并封存上一版，同幂等键异载荷明确冲突。
保存表示保存当前工作进度，不表示资料齐全；所属 Shipment、港口、离港时间、时区或依据仍为空时也必须保存成功，并继续作为待补项显示。

### 当前子切片：宽松建档与来源独立接收

| 业务步骤 | 操作时需要看到什么                                      | 系统允许做什么                       | 权威事实与反馈                                    |
| -------- | ------------------------------------------------------- | ------------------------------------ | ------------------------------------------------- |
| 独立上传 | 四类来源各自是否已收到、成功、失败及真实行数            | 上传任一或多个文件，失败文件单独重试 | 单文件上传/解析同成同败；其他文件结果不回滚       |
| 联合归组 | 当前已到来源能组成哪些 Shipment、柜和提单，仍缺哪些来源 | 用现有资料继续预检，也可后续追加来源 | “未上传其他文件”是来源缺口，不是整包失败          |
| 逐柜处理 | 哪只柜发生身份或活动 Shipment 冲突，其他柜是否可接管    | 隔离冲突柜并继续接管无冲突对象       | 冲突结果绑定柜；Shipment 写入仍保持自身事务完整   |
| 宽松接管 | Shipment 可识别性、待补字段、每项责任人和受限动作       | 建立 Shipment 并进入 `departed`      | 只有内部身份/引用完整性失败；其余缺失生成待补事项 |

### 当前子切片：内部备货/装箱事实 → Shipment Handoff

| 业务步骤 | 操作时需要看到什么                                   | 系统允许做什么               | 权威事实与反馈                                                           |
| -------- | ---------------------------------------------------- | ---------------------------- | ------------------------------------------------------------------------ |
| 发现候选 | 已实际离港、尚未关联活动 Shipment 的内部柜及归组建议 | 刷新候选；不上传已有系统数据 | 由 dispatch、装箱、装载、路线和当前 actual departed 事实实时投影         |
| 确认范围 | 船名航次、路线、柜、来源备货单、SKU 装载行和待补数量 | 单票接管进入统一 Handoff     | 候选指纹只用于幂等和重查，不把 booking/柜号/备货单号升级为 Shipment 身份 |
| 建立关系 | 接管后 Shipment、来源备货单、SKU、柜和仍待补的字段   | 打开 Shipment 继续后段工作   | 原装载分配只绑定 ShipmentCargoLine，不重建或复制；缺字段形成待补投影     |
| 回看去向 | 备货工作台显示每张备货单已交接至哪票 Shipment        | 从备货单直接进入对应出运     | 备货侧通过 ReplenishmentOrderLine → ShipmentCargoLine 读取同一关系       |

内部候选必须满足“当前 dispatch/装箱/装载版本 + 当前有效实际离港事实 + 无活动 Shipment 关系”。装箱或承运交接本身不等于已出运。内部接管和文件接管共用 `AcceptShipmentHandoffService`，不得另建 Shipment 写路径。

## 界面动线

```text
选择当前已有的一个或多个来源文件
  -> 各文件独立完整性与行数确认
  -> 联合预检
  -> 按“可接管 / 待补资料 / 映射问题 / 业务冲突 / 完全重复”分组
  -> 选择一票查看关系和具体原因
  -> 修正可修正项并重新预检
  -> 逐柜隔离冲突并确认接管可识别项
  -> 查看逐票结果并进入 Shipment
```

宽屏使用“问题队列 → 当前 Shipment 候选及缺口 → 当前动作/结果”；窄屏保持相同顺序。只有队列是主选择源，不再增加独立柜选择器。主动作在预检前为“开始预检”，预检后为“接管可接管项”；不会同时出现多个等权提交按钮。

缺口不得展开成“怎么处理 / 在哪里处理 / 谁处理”的说明卡。每项显示缺口、来源当前值、业务影响和一个动词动作；点击后立即在当前候选下方展开并聚焦港口候选、离港、归组或 SKU 输入控件。内部补全记录只在实际保存时自动确保存在，不得成为打开编辑器的前置条件。预检完成后来源上传区收为摘要，需要补充来源时再展开。

## 验收

- [x] 业务人员不接触 JSON 即可上传任一真实来源文件并看到该文件实际读取行数；工作簿错误声明 `A1` 时仍按真实 XML 单元格范围处理或明确拒绝。
- [x] 真实样本按 Shipment 归组，能展开看到柜、提单、货物和来源行；一柜多备货单关系不丢失。
- [x] ready、review_required、rejected、duplicate 和 conflict 使用业务语言区分，并给出责任人、缺口和恢复动作。
- [x] 无时区、未知港口、未知货主或缺 SKU 明细时仍可创建 Shipment，并明确显示待补内容、责任人和真正受限的动作。
- [x] 每个可处理缺口都有直接动作；点击后无需先登记待复核、无需自行寻找页面，即可进入并聚焦正确编辑控件。
- [x] 单文件上传/解析失败不产生该文件的部分结果；多个文件同时上传时各自成功或失败，不互相回滚。
- [x] 柜级身份冲突只隔离受影响柜；无冲突柜可继续，且不会形成半票关系或跨租户引用。
- [x] 接管前明确显示影响范围；接管后显示逐对象结果、traceId、生命周期初始化和下游吸收状态。
- [x] 补全表单允许全空或部分填写保存当前进度；未填写字段保持待补，不伪造默认值，也不阻止其他业务动作。
- [x] 导航继续使用一个“出运工作台”入口；接管页是其内部视图，备货/装箱降为上游历史入口，不新增并列工作台。
- [x] 重放同一来源和载荷不重复写入；同幂等键异载荷明确冲突。
- [x] 业务拒绝、技术失败和并发冲突分别给出可恢复反馈，用户已选文件和当前票上下文不丢失。
- [x] Shipment 归属不提供自由身份输入；系统建议必须落到“选择现有出运”或“新建独立出运”，选择现有对象时显示路线、船名航次、ATD、状态与柜数并校验关系版本。
- [x] 桌面、窄桌面、移动端、键盘与屏幕阅读顺序符合 `HW-D01`～`HW-D10`。
- [x] API 权限、事务、租户隔离、组件测试和真实样本 E2E 通过；风险对应门禁全绿。
- [x] 系统内已有备货、装箱和实际离港事实可直接形成 Handoff 候选，无需再次上传或录入。
- [x] 内部接管复用统一 Handoff 事务和原装载分配；备货工作台可回看 Shipment 去向，Shipment 详情返回来源单、SKU、柜和待补项。
