# 任务：Shipment 风险队列（UI-02A）

> 本文件是执行、评审与交接的**唯一载体**。状态只看 frontmatter。
> 路线图：`DOMAIN_VERTICAL_DELIVERY_PLAN.md` 阶段 B 的 `UI-02A`。
> 阶段 A（`UI-01A`/`UI-01B`）已完成并合入 main。

## 目标

出运运营在出运工作台打开首屏，就能**按业务原因**找到"现在该处理哪一票 Shipment"——因为它临期、有缺口、或在途异常，而不是因为它排在列表第一行。选中一票后能看清它为什么排在前面，并从同一页进入该票对应的专业岗位。

## 边界 / 不做

- 遵循 `POST_DEPARTURE_WORKBENCH_DELIVERY_BASELINE.md` 的 `WB-D02`（Shipment 是运营主轴，不得用单柜列表代替）、`WB-D04`（为何处理 → 已知事实/真实缺口 → 当前允许动作 → 结果/下一责任人）、`WB-D05`（一个页面只有一个主选择源）、`WB-D09`（一次只实施一个工作台切片）、`WB-D16`/`WB-D17`（缺口必须是可执行动作，附来源当前值与候选项）。
- **本片不接外部在途来源。** 路线图 `EN-01`（首个真实在途来源）排在 `UI-02` 之后，且要求 `UI-02` 先能展示来源、新鲜度、版本与冲突。因此本片**只能用系统已有事实**（计划/预计/实际时间事实、缺口投影），**不得**显示或暗示实时船期 ETA。
- 不做 Shipment 详情页（`UI-02B`）；本片只做队列与"为什么排在这"。
- 不做单证、清关、提柜、送仓、卸柜的业务动作；那些是对应工作台的事。
- 不改公共契约已有 wire value；只做加法。不改已共享迁移。

## 验收

- [ ] 首屏是一条 Shipment 队列，每票给出**它为什么现在需要处理**（临期/缺口/异常）与它最近的约束
- [ ] **多条截止共同参与默认排序**（当前为「预计到港 + 任务截止」；**免用箱期是否纳入待确认**，见「三类截止的真实成本」），每票写明命中的是哪一条、还有多久；不是固定按其中某一条
- [ ] **可自由选择排序键与方向、可按条件筛选**，并一键回到默认视图
- [ ] 选定的视图**进 URL**，把链接发给接手的人能看到同一顺序
- [ ] 排序与筛选都在**服务端**完成；**游标绑定排序键与筛选条件**，换排序后翻页不重不漏（不得前端自排）
- [ ] 界面上常驻显示当前排序方式；本地记住的偏好**写明"只保存在本机"**，不暗示跨设备或跨人共享
- [ ] 缺口以可执行动作呈现，点开即就地打开对应编辑器，并给出**来源当前值**与系统候选项（`WB-D16`/`WB-D17`）
- [ ] 只有一票是当前选中项；选中驱动右侧上下文与动作，不再并排一个独立柜选择器（`WB-D05`）
- [ ] 一票没有任何已知风险或缺口时**不谎报风险**（不为了填满首屏而编造紧急度）
- [ ] 缺在途观测时如实说明"无来源"，不用预计时间冒充实际（`WB-D23`：不得把虚构数据标成真实业务完成）
- [ ] 相关质量门禁全绿

## 业务与数据协同设计

| 业务步骤与岗位结果   | 信息产生时机/前置事实 | 操作时需要看到什么                       | 系统允许做什么         | 数据如何可靠保存与反馈                       |
| -------------------- | --------------------- | ---------------------------------------- | ---------------------- | -------------------------------------------- |
| 找出今天该处理哪一票 | Shipment 已接管并启动 | 为什么是它、紧迫度来自哪条事实、截止时间 | 在队列中选择当前票     | 队列来自服务端投影，稳定排序，刷新不丢       |
| 看懂这一票缺什么     | 事实/引用不齐         | 缺口的来源当前值、候选项、影响哪个动作   | 就地补录并回显         | 缺口与其他状态分轨，不合成一个大状态         |
| 判断在途是否异常     | 已有生命周期时间事实  | 已有什么事实、**缺什么来源**、版本       | 查看，不做外部状态改写 | 外部观测只能形成版本化观测，不能遥控生命周期 |
| 交给正确的专业岗位   | 该票进入某专业环节    | 下一步归谁、在哪处理                     | 进入对应工作台         | 交接写明稳定业务身份与版本，不共享宽表       |

## 工作台避坑检查

- [ ] 首屏按业务原因与紧迫度组织，不按表、接口资源或创建时间组织
- [ ] 一个页面只有一个当前 Shipment 主选择源
- [ ] 系统产生紧迫度判断与缺口；人员只写自己掌握的业务事实
- [ ] 已接管事实与缺口自动带入，不要求重复录入
- [ ] 待补与阻断分轨：普通缺失可继续，只有身份/引用/冲突才阻断
- [ ] 生命周期状态、资料完整度与异常不合成一个大状态
- [ ] 队列与缺口均来自服务端事实，刷新不丢
- [ ] 操作后重读服务端结果，区分成功、业务拒绝、并发冲突与技术失败

## 决策与待确认

### 已定：截止是**多条件**，不是单一条

负责人 2026-09-27：**不应固定为单一截止，多条件参与更好。**

三种候选各有真实事实支撑（已核实，不是设想）：

| 截止条件   | 已有事实来源                                                                | 谁在意               |
| ---------- | --------------------------------------------------------------------------- | -------------------- |
| 预计到港   | 生命周期计划/预计时间事实（`Shipment.etaAt`，真实列）                       | 到港准备、清关、提柜 |
| 免费用箱期 | `charges-settlement` 滞期引擎（**算出来的，无直接可查的死线列**，见成本表） | 提柜、还箱、费用     |
| 任务截止   | 节点任务的 `dueAt`（真实，已在容器运营视图映射）                            | 当前承接该环节的岗位 |

**实现口径：**

1. **排序：多条一起参与，默认取"离它最近的约束"。** 每票写明命中的是哪一条、还有多久 —— 无论用户选了哪种排序，"为什么它在这"始终可解释（`WB-D04`）。
2. **可选的是"看什么"，不是"怎么排"：筛选项。** 允许按约束类型、时窗、责任岗位筛选；筛选是**服务端过滤**，不改变顺序。
3. **自由配置排序：负责人 2026-09-27 定为现在就做** —— 见下一节。

### 已定：自由配置排序视图（现在就做）

**可配置什么**：排序键（默认「离最近约束」；可选「预计到港」「免用箱期」「任务截止」「最近更新」）+ 方向；筛选条件；都能随时一键回到默认。

**三条原顾虑怎么解掉（这些是设计要求，不是建议）：**

1. **正确性：排序必须落在服务端。** 队列是游标分页，前端只能排当前页 —— 第 2 页的票可能比第 1 页更急，用户会被骗。因此排序与筛选都进查询参数，**游标必须绑定排序键与筛选条件**（现有 `list-shipments` 的游标已绑定 `status`，照此扩展）。**前端不得自排。**
2. **交接说不清：让"当前是什么视图"和"为什么它在这"始终可见。** ① 排序方式常驻显示在队列头部；② 每条仍写明自己的紧迫依据（与排序方式无关）；③ **视图进 URL**，可把链接直接发给接手的人，对方看到同一顺序；④ 「默认视图」一键可达。
3. **配置存哪：先用浏览器本地，并如实说明它不跨设备。** 依据：schema 与契约里**都没有**用户偏好落库面（已核实），而前端已有 `useAppShell` 的 localStorage 先例。存本地还顺带消掉了"谁能改"的权限问题——每个人改的是自己这台机器。**界面上必须写清"此偏好只保存在本机"**，不得让人以为它在团队间共享或跨设备生效。
   **升级条件**：出现"换台机器就丢了"的真实抱怨时，再补服务端偏好（需要新表 + 契约 + 接口 + 权限），那时才做。

**代价（如实记账）**：这超出路线图给 `UI-02A` 的"只补最小能力（Shipment 级查询投影、稳定排序、责任与允许动作）"，本片因此变大——多出排序参数、游标绑定、视图选择与本地记忆。已在路线图对应行补注。

### 实现前核实结果（四条全查完，2026-09-27）

1. **现有列表能否扩展**——已核实：`list-shipments.service.ts` 按 `updatedAt DESC, id DESC` 分页、只按 `status` 过滤，是"最近更新优先"而非风险队列；游标已绑定过滤条件（有现成模式可扩展排序键）。**结论：扩展它，不另建平行队列。**
2. **截止的事实来源**——**三类成本差别很大**（详见下节）。
3. **异常已到 Shipment 级**——✅ `OperationalExceptionCase.shipmentId` 是可空外键，可汇总到 Shipment。**但两个坑**：① **没有 `(tenantId, shipmentId, …)` 索引**，现只有 `(tenantId, containerRecordId, status, occurredAt, id)`，Shipment 级聚合要加索引（加法迁移）；② `shipmentId` 可空，**部分案件只挂货柜、没有 Shipment**，这些在 Shipment 队列里会看不见 —— 必须如实说明，不能当成"没有异常"。
4. **缺口可按 Shipment 直接聚合**——✅ `listPendingCompletion` 就是一条 `shipment.findMany` + OR 缺口条件，返回 `{ shipment, pendingItems[] }`，**缺口本来就是 Shipment 级、现算的**，不另建聚合。

### ⚠️ 发现：缺口里的 `deadline` / `responsibility` / `candidateValues` 是占位，不是真的

`ShipmentPendingItemV1` 契约预留了 `deadline`、`responsibility`、`candidateValues` —— 正是本片想要的。但实现在 `prisma-shipment-read.repository.ts` 里**硬编码**：

- `deadline` → `{ dueAt: null, source: "not_configured", label: "未设定" }`，每条都是
- `responsibility` → 每条都写死「出运运营」
- `candidateValues` → 恒为 `[]`

**所以"多条件截止"不能建在这上面**，否则队列的紧迫依据是假的（违反 `WB-D23` 与 AGENTS §1.6）。真正可用的是 `code` / `label` / `currentValue` / `directAction`（这些是真的），`WB-D16` 因此已满足大半；`WB-D17` 的"系统候选值"目前**没有**。

### 三类截止的真实成本（决定本片做多少）

| 截止条件 | 真实来源                                        | 成本                                                                                                                              |
| -------- | ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| 预计到港 | `Shipment.etaAt`（真实列）                      | **低**：队列投影直接取                                                                                                            |
| 任务截止 | 工单 `dueAt`（真实，已在容器运营视图里映射）    | **中**：要升到 Shipment 级聚合                                                                                                    |
| 免用箱期 | `charges-settlement` 的滞期引擎（**算出来的**） | **高**：`OverdueChargeStandard` + 事实推导，**没有可直接查的死线列**；且路线图把费用域排在后面，只允许取"影响可提/临期的最小事实" |

**建议（需负责人确认）**：本片先用**前两类**做默认排序（预计到港 + 任务截止，都真实且成本可控），**免用箱期留出接口位置但不接**——等 `FEE-01` 或有人真要按它排时再接。理由：把一个算出来的跨域死线塞进 Shipment 队列，要么每票调引擎（性能与跨域耦合），要么先落一份投影（新的持久化面），两者都远超本片范围；而现在接了它，得到的紧迫度还不如前两类可靠。

### 以下是实现方（我）的推定，实施前请确认

1. **队列默认只显示"在途/未关闭"的 Shipment**，已关闭的不进队列（否则首屏被历史淹没）。关闭的定义需在实现时对齐生命周期状态。
2. **没有风险也不缺口的票默认不进首屏**，通过"查看全部"进入——避免为了填满首屏而制造紧急度。
3. **同紧迫度下的次级排序**取最近更新，保证分页稳定。

## 方案

1. 复用既有 Shipment 列表读取链路（`list-shipments` + `listPendingCompletion`），加法补上风险排序与风险依据字段（契约加法）。**不另建平行队列。**
2. **截止来源只用真实的**：`Shipment.etaAt`（预计到港）与工单 `dueAt`（任务截止）。**不得使用 `pendingItems[].deadline`** —— 那是硬编码占位（见上）。
3. **异常聚合要加索引**：`OperationalExceptionCase` 现无 `(tenantId, shipmentId, …)` 索引，需一条加法迁移；`shipmentId` 为空的案件**如实说明"未归属 Shipment"**，不得当成没有异常。
4. 风险依据面板呈现：缺口的 `code`/`label`/`currentValue`/`directAction`（真实），临期依据（哪条截止、还有多久），异常，以及来源缺失。
5. **`WB-D17` 的"系统候选值"本片不做** —— `candidateValues` 恒为空，填它属于补录编辑器的能力，不在队列范围；界面上不得显示空候选让人以为"系统没意见"。
6. 不接外部来源；在途观测缺失时如实显示缺失。
7. 覆盖服务端投影单测、接口契约与授权、组件行为与三视口 E2E。
