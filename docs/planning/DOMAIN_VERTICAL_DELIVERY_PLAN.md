# 业务纵向交付路线图

> 状态：**负责人确认的实施路线 v2** · 2026-09-23 · 负责人：刘志高。
> 一句话：Shipment 技术基础已经足够，主线切换为出运后岗位界面的串行纵向切片；每刀先交付一个人能完成的业务结果，只补该结果需要的最小后端能力。

## 1. 当前方向

```text
当前核心：可证明的实际出运
  -> Shipment 接管
  -> 在途与到港准备
  -> 清关
  -> 提柜
  -> 送仓
  -> 卸柜与空箱确认
  -> 还箱
  -> Shipment 关闭
```

- 出运前计划、采购、备货和装箱只保留稳定引用、历史追溯与扩展接口。
- Shipment 是运营主轴，Container 是后段执行单元；不再从单柜或数据库表倒推页面。
- 前端交互是当前主交付面。API、表和事件只有被岗位界面用于判断、行动和结果确认时才构成业务价值。
- 通用底座按需补齐，不再连续开发脱离当前岗位结果的后端机制。

完整岗位分工、DCSA 角色映射、信息时机和工作台边界统一引用
[出运后工作台交付基线](../product/POST_DEPARTURE_WORKBENCH_DELIVERY_BASELINE.md)。

## 2. 每刀固定结构

```text
一个岗位结果
  -> 一条真实样本主路径
  -> 为什么要处理
  -> 完成判断所需事实与缺口
  -> 服务端允许的一个主动作
  -> 落账、等待、拒绝和恢复反馈
  -> 相关角色交接
```

每刀必须同时交付最小 UI、必要读模型、必要写用例和风险对应测试。不得把数据库/API 完成当作 UI 切片完成，也不得先创建后续工作台空壳。

## 3. 串行任务线

| 顺序    | 任务线             | 目标岗位能完成的结果                                           | 后端只允许补什么                 | 不做                        |
| ------- | ------------------ | -------------------------------------------------------------- | -------------------------------- | --------------------------- |
| `UI-01` | 已出运数据接管     | 上传四表来源包，预检、处理明确缺口、接管或保存待复核并确认结果 | 来源包适配、候选查询、受控修正   | Shipment 全详情、下游工作台 |
| `UI-02` | Shipment 在途总览  | 按风险找到一票，查看柜/货/单/路线/时间并进入正确专业岗位       | 查询投影缺失字段、允许动作       | 新专业状态机、管理大屏      |
| `UI-03` | 到港准备与清关     | 完成适用资料、申报、查验和货柜级清关交接                       | 清关案件/单证的真实缺口          | 提柜调度、AI 自动决定       |
| `UI-04` | 联合可提与提柜     | 看清全部可提条件，安排并完成 Gate Out，失败可恢复              | Release/Hold/Terminal/计划事实   | 送仓和优化算法              |
| `UI-05` | 送仓交接           | 安排运输并把货柜交到正确仓库，确认 POD                         | 承运任务和到仓证据               | WMS 库存、卸柜完成          |
| `UI-06` | 卸柜、还箱与关闭   | 记录实收差异、空箱、还箱 EIR，并核对整票关闭条件               | 还箱事实和 Shipment 聚合关闭规则 | 通用费用平台                |
| `UI-07` | 外部协作与标准接入 | 合作方通过受限任务提交证据，DCSA/供应商消息进入同一事实链      | 外部身份、工作单和 Adapter       | 外部直接改内部状态          |

同一时刻只允许一行处于 `design | coding | review | fix`。下一行不得因为后端已存在而提前开工。

## 4. 页面层级

| 层级     | 入口                                     | 责任                                           |
| -------- | ---------------------------------------- | ---------------------------------------------- |
| 个人     | 我的任务                                 | 只聚合“为什么现在需要我处理”，跳转专业工作台   |
| 专业     | 出运、清关、提柜、送仓、卸柜、还箱工作台 | 完成本岗位结果，显示唯一主动作和交接反馈       |
| 对象     | Shipment 详情、一柜一档                  | 只读组合权威事实，按权限下钻，不拥有专业规则   |
| 管理     | 风险、计划、KPI、技术支持                | 监督和异常处理，不混入现场人员首屏             |
| 上游参考 | 备货、装箱历史                           | 查看来源、补证据、发起更正，不产生当前核心任务 |

## 6. 文档消费纪律

每次实现只读：

1. [出运后工作台交付基线](../product/POST_DEPARTURE_WORKBENCH_DELIVERY_BASELINE.md)；
2. 当前唯一活动 task brief；
3. brief 直接链接的领域权威和代码入口。

`docs/Logixs 需求迭代/` 的两份长文档和附件只作需求来源与调研记录，不作为实现必读或规则权威。新的业务结论先进入短基线或对应领域契约，禁止继续追加到长篇汇编。

## 7. 每刀完成门槛

- 真实岗位能从进入、判断、执行到结果确认走完约定主路径。
- 等待、业务拒绝、技术失败、并发冲突和恢复路径可辨认。
- 页面只有一个主选择源和一个当前主动作，已有权威事实不重复录入。
- 服务端提供权限、前置条件、幂等、并发和稳定错误反馈；前端不自行推导。
- 桌面、窄桌面和移动端完成组件/视觉检查，关键路径有 E2E。
- 数据库、公共契约或跨模块高风险变更运行完整门禁与专项验证；纯 UI 切片运行受影响模块门禁。
