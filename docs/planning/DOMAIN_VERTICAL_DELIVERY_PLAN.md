# 业务纵向交付路线图

> 状态：**当前实施路线 v3** · 2026-09-24 · 负责人要求按新增业务需求重新校准。
> 一句话：先完成“已出运 Shipment 从接管到关闭”的岗位闭环，再按工作台的真实缺口接入外部数据；智能排程、外部协作、完整费用与 AI 合规不得抢在基础作业流之前。

## 1. 当前产品主线

```text
接管可证明的已出运 Shipment
  -> 在途跟踪与到港准备
  -> 清关资料、传送、申报与放行
  -> 联合可提与提柜
  -> 送仓交接
  -> 卸柜、空箱与还箱
  -> Shipment 关闭
```

- Shipment 是运营主轴，Container 是后段执行单元；页面从岗位结果和任务原因出发，不从数据库表或接口资源出发。
- 出运前采购、备货、装箱和 VGM 保留为上游事实、历史追溯和未来扩展接口，当前不继续扩建成第二条产品主线。
- 数据不齐原则上进入待补；只有对象身份无法建立、引用完整性失败或互斥业务事实冲突才局部阻断。
- 状态、完整度、异常和外部观测保持分轨。外部 API、DCSA 消息和 Arrival Notice 只能形成版本化观测或单证，不能直接遥控内部生命周期。
- 前端交互是当前主交付面。数据库、API、事件或算法只有被岗位用于判断、行动和确认结果时才构成交付。

工作台内容、岗位顺序和信息出现时机以
[出运后工作台交付基线](../product/POST_DEPARTURE_WORKBENCH_DELIVERY_BASELINE.md) 为准。

## 2. 新增需求如何进入路线

`docs/Logixs 需求迭代/` 的两份长文档包含大量业务设想、调研证据和技术候选。它们不是一个可直接执行的大任务，也不因描述详细就自动成为已批准契约。

| 新增要求簇                                             | 对当前主线的判断                            | 进入时机                     | 承接方式                                     |
| ------------------------------------------------------ | ------------------------------------------- | ---------------------------- | -------------------------------------------- |
| 四表导入、内部备货/装箱交接、宽松建档                  | 当前闭环入口，必须先完成                    | `UI-01B`                     | 统一 Handoff，不再新增导入路径               |
| Shipment/Equipment/Vessel 三条旅程、在途 ETA           | 当前工作台必需，但先消费已有事实            | `UI-02`                      | Shipment 总览 + 柜下钻；观测与实际事实分开   |
| 清关资料参数、接收方、传送、申报、查验、放行           | 当前闭环必需                                | `UI-03A`、`UI-03B`           | 适用性配置和单票执行分开，不把附件列继续铺宽 |
| Arrival Notice、Carrier/Terminal release、Hold、免费期 | 联合可提必需                                | `UI-04` 前按缺口补最小能力   | 版本化单证/事实，不等同于已清关或可提        |
| 派车、送仓、卸柜、还箱、差异                           | 当前闭环必需                                | `UI-05`、`UI-06`             | 正常路径先闭环，异常案件正交处理             |
| 船司、港口、飞驼、云当、DCSA Track & Trace             | 输入能力，不是独立产品主线                  | 某工作台缺少可信输入时       | 一次只接一个真实来源，不先造万能平台         |
| 智能排柜、资源日历、三方堆场                           | 依赖稳定事实、资源和人工排程基线            | 基础闭环之后                 | 先可用人工排程，再约束校验，最后优化建议     |
| 清关行门户、车队移动端、仓库协作                       | 依赖内部任务、权限和回执已稳定              | 内部岗位闭环之后             | 受限工作单，不允许外部直接改内部状态         |
| 完整费用、分摊、请款、支付                             | 独立业务域；当前只取影响可提/临期的最小事实 | `UI-04` 后独立规划           | 免费期/放货条件先行，财务闭环后置            |
| 法规摄取、HS 归类、AI 合规生产线                       | 高价值但不应阻断当前主链                    | 有真实样本、负责人和评测集后 | AI 只建议，证据、人工决定和执行结果分开      |
| DCSA Commercial Schedules、OVS、VGM                    | 分属计划、执行观测和出运前合规              | 有对应岗位消费者时           | 独立 Adapter/聚合，不复制外部模型为核心表    |

## 3. 串行实施路线

### 阶段 A：把数据真正接进来

| 顺序     | 任务           | 岗位业务结果                                                     | 状态                        |
| -------- | -------------- | ---------------------------------------------------------------- | --------------------------- |
| `UI-01A` | 已出运接管首片 | 任一来源独立上传、联合预检、受控修正、单票接管；内部事实直接交接 | PR #47 已合入               |
| `UI-01B` | 接管作业闭环   | 一次接管全部非阻断候选；已接管未补全事项跨会话持续处理           | **当前唯一活动任务（fix）** |

完成 A 阶段后，接管候选、正式 Shipment 和已接管待补必须是三个明确阶段，不能继续混在同一临时队列。

### 阶段 B：形成 Shipment 在途运营入口

| 顺序     | 任务                | 岗位业务结果                                     | 只补最小能力                                    |
| -------- | ------------------- | ------------------------------------------------ | ----------------------------------------------- |
| `UI-02A` | Shipment 风险队列   | 按 ETA、缺口、异常和最近截止找到当前应处理的一票 | Shipment 级查询投影、稳定排序、责任与允许动作   |
| `UI-02B` | Shipment 详情与交接 | 看全票/柜/货/单/路线/时间，进入正确专业岗位      | `container_operational_view` 逐值对拍、对象链接 |
| `EN-01`  | 首个真实在途来源    | 一个已批准来源的观测进入同一时间事实链           | Adapter、来源健康、冲突裁决；不建设通用配置平台 |

`EN-01` 只有在 `UI-02` 已能展示来源、新鲜度、版本和冲突时才启动。没有消费者的接口接入不排入当前开发。

### 阶段 C：到港准备、清关与联合可提

| 顺序     | 任务               | 岗位业务结果                                                   | 关键边界                                 |
| -------- | ------------------ | -------------------------------------------------------------- | ---------------------------------------- |
| `UI-03A` | 清关资料准备       | 系统按国家/贸易模式/SKU 属性生成适用资料；人员补件、换版和核验 | 不把所有附件类型无差别列给每票           |
| `UI-03B` | 资料传送与清关案件 | 选择已维护接收方，发送并处理回执、申报、查验、扣留和放行       | “已发送、已收到、已申报、已放行”分开     |
| `UI-04A` | 联合可提           | 同屏解释海关、提单/换单、Carrier、Terminal、Hold、费用条件     | 单一条件不得冒充可提结论                 |
| `UI-04B` | 提柜执行           | 安排提柜、记录 Gate Out、失败原因、重排和临期风险              | 计划、预计、实际分开；失败不靠改计划掩盖 |

Arrival Notice 或外部 Release 接入只在 `UI-03B/UI-04A` 需要真实来源时形成窄 Adapter 任务。完整接口管理平台仍不提前实施。

### 阶段 D：送仓、卸柜、还箱和关闭

| 顺序     | 任务                 | 岗位业务结果                                        | 关键边界                             |
| -------- | -------------------- | --------------------------------------------------- | ------------------------------------ |
| `UI-05`  | 送仓交接             | 锁定仓库和预约，安排承运，确认到仓/POD，异常可恢复  | 到仓不等于卸柜完成                   |
| `UI-06A` | 卸柜与实收差异       | 保存部分进度、实收差异、卸完和独立空箱事实          | 差异进入异常案件，不静默修改预期数量 |
| `UI-06B` | 还箱与 Shipment 关闭 | 安排取空、确认 EIR/场站接收，按所有柜和未结异常关闭 | 单柜还箱不能关闭整票                 |

### 阶段 E：在稳定闭环上扩展

| 顺序           | 能力                     | 启动前置                                         |
| -------------- | ------------------------ | ------------------------------------------------ |
| `EXT-01`       | 外部清关行/车队/仓库协作 | 内部工作单、权限、证据、回执和恢复路径已稳定     |
| `PLAN-01`      | 人工提送卸还排程         | 提柜至还箱的任务、资源、截止和实际结果可用       |
| `PLAN-02`      | 约束校验与方案版本       | 人工排程已有真实使用样本和冲突分类               |
| `PLAN-03`      | OR-Tools 优化建议        | 目标函数、硬约束、成本口径和人工发布机制获批     |
| `FEE-01`       | 费用预测与结算           | 免费期和执行事实稳定，财务责任与审核链获批       |
| `COMP-01`      | 合规知识与 AI 辅助       | 真实法规来源、评测集、采信等级和人工复核责任明确 |
| `INT-PLATFORM` | 通用连接器配置平台       | 至少两个真实 Adapter 证明了共同变化点和隔离边界  |

## 4. 每个工作台的固定设计顺序

```text
岗位本次要得到什么结果
  -> 什么事件触发任务
  -> 首屏凭什么判断优先级
  -> 系统已有事实与来源是什么
  -> 哪些内容必须选择、录入或确认
  -> 服务端此刻允许哪个主动作
  -> 成功、等待、拒绝、失败如何反馈
  -> 完成后交给谁，未完成如何恢复
```

每个 task brief 必须提供“业务步骤 → 所需信息 → 允许动作 → 权威事实/落库”表。以下内容不得作为完成证明：只有表、只有 API、只有字段展示、只有按钮、只有成功提示。

## 5. 页面层级与共同布局

| 层级     | 入口                               | 责任                                           |
| -------- | ---------------------------------- | ---------------------------------------------- |
| 个人     | 我的任务                           | 聚合为什么现在需要我处理，跳转专业工作台       |
| 专业     | 出运、清关、提柜、送仓、卸柜、还箱 | 完成本岗位结果，提供有限动作和交接反馈         |
| 对象     | Shipment 详情、一柜一档            | 只读组合权威事实并按权限下钻，不拥有专业规则   |
| 管理     | 风险、计划、KPI、集成运维          | 监督和异常处理，不混入现场岗位首屏             |
| 上游参考 | 备货、装箱历史                     | 查看来源、补证据、发起更正，不生成当前核心任务 |

专业工作台统一采用三个独立区域：

```text
原因队列 -> 当前对象、事实与缺口 -> 当前动作与结果
```

- 只有队列是当前对象的主选择源。
- 队列显示身份、路线、业务原因、截止、阻断/待补数量，不平铺全部详情。
- 每个缺口提供一个直接动作；当前值、候选值和输入/选择控件同时可见。
- 编辑器在问题附近展开并保持上下文；正常项收拢、异常项展开。
- 主动作随阶段变化，不能同时摆放多个等权提交按钮。
- 页面结果必须来自服务端刷新；刷新后任务和进度不能丢失。

## 6. 任务治理规则

1. 同一时刻只允许一个 task brief 处于 `design | coding | review | fix`。
2. 当前任务是
   [p6-post-departure-handoff-operational-closeout](./tasks/p6-post-departure-handoff-operational-closeout.md)。
3. 后续任务只在前一任务达到岗位结果后创建，不预建空页面、空状态机或假接口。
4. 某工作台因缺少真实数据无法继续时，才创建一个与该消费者绑定的窄数据接入任务。
5. 候选调研先进入需求输入；负责人确认后才进入短基线或领域契约；实现任务只引用短权威文件。
6. 每刀必须用真实样本验证主路径、缺口、拒绝、恢复和跨会话继续处理。

## 7. 当前能力与处置

| 能力                                              | 当前事实                   | 路线处置                                     |
| ------------------------------------------------- | -------------------------- | -------------------------------------------- |
| 生命周期、日期事实、证据、任务和可靠消息          | 已有主干                   | 不重建；按当前工作台缺口复用和修正           |
| SKU、装载、合规档案、备货和装箱页面               | 已实现                     | 当前作为上游事实和历史入口，不继续扩建主流程 |

| 清关、提柜、送仓、卸柜旧页面                      | 有纵向实现                 | 不宣布全链路完成；按新基线逐台复核和收口     |
| 还箱工作台                                        | 缺失                       | `UI-06B` 独立交付，不塞入卸柜页面附带完成    |
| 通用连接器、智能排程、外部门户、完整费用、AI 合规 | 需求输入充分，运行证据不足 | 保留路线位置，不进入当前活动任务             |

## 8. 文档消费纪律

每次实施只读：

1. 本路线图；
2. 对应工作台短基线；
3. 当前唯一活动 task brief；
4. brief 直接链接的领域权威和代码入口。

`docs/Logixs 需求迭代/Logixs 需求迭代.md` 与 `API.md` 是需求来源和调研记录，不是实现必读、数据库契约、状态机或 API 契约。新的已确认结论必须进入对应短权威文件，禁止继续让实现者从长篇汇编中自行猜测规则。

## 9. 每刀完成门槛

- 目标岗位能从进入、判断、执行到结果确认走完真实主路径。
- 用户明确知道为什么需要处理、当前值是什么、缺什么、能做什么、完成后交给谁。
- 非关键缺失可以部分保存并进入持久待补；真正阻断说明对象、原因和恢复动作。
- 等待、业务拒绝、技术失败、并发冲突和恢复路径可区分。
- 已有权威事实不重复录入，内部 ID 和状态码不作为主要操作语言。
- 桌面、窄桌面和移动端完成组件、可访问性和视觉验证，关键路径有真实样本 E2E。
- 数据库、公共契约或跨模块高风险变更运行完整门禁与专项验证；局部 UI 切片运行受影响模块门禁。
