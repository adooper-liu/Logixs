# 角色工作台以人为中心的设计契约

> 状态：**负责人确认原则 + 实施基线 v1.1** · 2026-09-24。
> 消费者：产品、业务负责人、设计、Web、Application/API、领域模块、测试与评审人员。
> 使用时机：新建或改造任何称为“工作台”的页面时，在画信息架构、定义读模型或拆实现任务之前使用。
> 维护者：产品与前端共同维护；业务规则、权限和数据所有权仍由各领域权威文档维护。
> 首个完整样例：备货工作台。实现任务见
> [p6-cargo-ready-human-centered-redesign](../planning/tasks/p6-cargo-ready-human-centered-redesign.md)。
> 出运后各工作台的岗位分工、参与顺序、信息时机和串行切片见
> [POST_DEPARTURE_WORKBENCH_DELIVERY_BASELINE](./POST_DEPARTURE_WORKBENCH_DELIVERY_BASELINE.md)。

本文固定工作台如何帮助具体岗位完成业务结果，不复制状态机、权限、字段或数据库定义。通用 UI 约束以
[UI_SYSTEM](./UI_SYSTEM.md) 为权威；SKU 属性和合规事实分别以
[PRODUCT_ATTRIBUTE_GOVERNANCE](./domain/PRODUCT_ATTRIBUTE_GOVERNANCE.md) 与
[COMPLIANCE_MANAGEMENT](./domain/COMPLIANCE_MANAGEMENT.md) 为权威。

## 1. 证据与状态

| 类型                 | 本文内容                                                                         | 使用边界                                   |
| -------------------- | -------------------------------------------------------------------------------- | ------------------------------------------ |
| 负责人确认目标（O）  | 系统为人服务；工作台从岗位结果和真实操作顺序出发，技术只用于让工作更简单、更高效 | 所有工作台不得偏离                         |
| 当前运行事实（R）    | 备货工作台以货柜选择和技术任务状态组织页面，并对所有 SKU 展开相同评审项          | 用于说明本次改造起点，不提升为目标设计     |
| 实施基线（Decision） | `HW-D01`～`HW-D16`、标准信息动线、避坑对照和 SKU 示例                            | 方案与实现共同引用；变更须回到本文评审     |
| 后续候选（C）        | 具体组件拆分、接口形状和视觉细节                                                 | 可在 task brief 中细化，但不得改变实施基线 |

## 2. 所有工作台的共同规则

| 决策     | 规则                                                                                                         | 可验收结果                                             |
| -------- | ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------ |
| `HW-D01` | **岗位结果优先**：先写清“谁要完成什么业务结果”，再决定页面、对象、接口和表字段                               | 首屏能回答岗位今天要完成什么，而不是先解释系统模块     |
| `HW-D02` | **按真实业务起点进入**：以人员收到工作、识别对象和开始处理的实际顺序组织入口                                 | 业务尚未产生后续技术实体时，人员仍可开始工作           |
| `HW-D03` | **单一选择源**：一个工作上下文只能有一个主选择源；其他列表、摘要和动作随其联动                               | 不出现顶部选择器、左侧队列和卡片各自选中不同对象       |
| `HW-D04` | **因果信息动线**：稳定顺序为“为什么要处理 → 已知事实与真实缺口 → 现在允许做什么 → 结果如何确认”              | 用户不需要在多张无因果关系的卡片间拼答案               |
| `HW-D05` | **例外优先披露**：正常项汇总或折叠，只展开需要判断、补充或恢复的项                                           | 正常数据不制造待办，注意力集中在真实缺口               |
| `HW-D06` | **适用性先于检查项**：先依据权威事实判断要求是否适用，再检查证据；不得把完整规则目录当作人人必审清单         | 不适用项不显示为“未评审”，未知事实形成一项明确确认任务 |
| `HW-D07` | **动作由服务端授权**：前端展示当前上下文唯一主动作，以及必要的次级恢复/异常入口                              | 页面不从状态文字推导权限、放行或状态推进               |
| `HW-D08` | **等待也有负责人**：等待、拒绝、冲突和失败必须显示等待谁、缺什么、期限和恢复路径                             | 用户知道是否需要自己行动，不会反复提交                 |
| `HW-D09` | **权威事实只录一次**：已有可信数据直接复用；仅在缺失、冲突、更正或本次交易特有时采集                         | 不要求业务人员重复填写 SKU、单证或系统已有事实         |
| `HW-D10` | **结果可确认**：操作后显示业务结果及落账状态，必要时保留追踪和幂等恢复入口                                   | “按钮已点击”或“请求成功”不冒充业务完成                 |
| `HW-D11` | **缺失不等于全局阻断**：资料不齐进入待补，只限制真正依赖该资料的动作；对象身份、引用或互斥事实冲突才局部阻断 | 缺附件仍可在途跟踪，发送资料前才要求补齐               |
| `HW-D12` | **明确人工参与类型**：区分系统自动产生、业务选择、业务录入和责任确认，不把内部身份或计算结果交给人员编造     | 每个字段和动作都能说明为何需要人参与                   |
| `HW-D13` | **缺口必须可执行**：显示当前/来源/候选值并提供输入、选择、上传或跳转；说明文字和空确认按钮不算处理入口       | 用户点击缺口即可在当前上下文开始处理                   |
| `HW-D14` | **作业进度跨会话持续**：待办、待补、提交结果和恢复状态来自服务端事实或可重建投影                             | 刷新、退出或隔日返回后仍能继续同一任务                 |
| `HW-D15` | **正常批量、异常逐条**：无冲突对象默认批量处理，逐条操作只用于冲突、例外和高风险确认                         | 正常业务不被机械点击拖慢，异常仍可精确控制             |
| `HW-D16` | **状态分轨**：生命周期、资料完整度、异常/阻断和外部观测分别表达，不合成含义不清的综合状态                    | 用户能理解当前进度、真实缺口和受限动作                 |

这些规则约束备货、出运、船务、单证、清关、内陆运输、入库、还箱及后续新增工作台。岗位不同会改变业务对象、事实和动作，但不会改变上述推导顺序。

## 3. 设计与评审顺序

每个工作台必须依次完成下表，禁止从已有表、接口或状态码倒推页面：

| 顺序        | 必须回答                                             | 产物                        |
| ----------- | ---------------------------------------------------- | --------------------------- |
| 1. 岗位结果 | 哪个岗位在什么场景下，要把什么业务结果做到什么标准   | 一句可验证的岗位目标        |
| 2. 实际流程 | 人员现实中从哪里收到工作，如何判断、处理、等待和确认 | 正常路径与异常/等待路径     |
| 3. 所需信息 | 每一步做判断所需的事实、来源、时效和解释是什么       | 信息清单及权威来源          |
| 4. 允许动作 | 此刻可以做什么、不能做什么、由谁批准或接手           | 服务端允许动作与恢复动作    |
| 5. 可靠结果 | 数据如何校验、落库、审计、去重、处理并发并反馈       | 写入用例、回执和可追踪结果  |
| 6. 界面结构 | 如何用最短视线和最少重复操作完成上述流程             | 队列、事实/缺口、动作的布局 |

评审必须让真实岗位人员用一个具体样本走完流程。只证明 API 可调、数据可展示或页面有按钮，均不算工作台完成。

## 4. 通用信息动线

```text
┌ 角色工作台 ─────────────────────────────────────────────┐
│ [开始主要业务]                 待我处理 N · 等待他人 M   │
├──────────────┬────────────────────────┬──────────────────┤
│ 为什么要处理 │ 已知事实与真实缺口     │ 现在可以做什么   │
│              │                        │                  │
│ 按业务原因   │ 当前业务对象           │ 当前问题原因     │
│ 与紧迫度排序 │ 关键事实与来源         │ 完成所需信息     │
│              │ 只展开异常/缺口        │ [唯一主操作]     │
│ 等待项分区   │ 正常项汇总折叠         │ 结果与恢复反馈   │
└──────────────┴────────────────────────┴──────────────────┘
```

三栏是宽屏的信息责任，不是强制组件数量。窄屏按“待办 → 事实/缺口 → 动作/结果”保持同一因果顺序；允许用路由、抽屉或分步视图，但不能产生第二套选择状态或业务规则。

### 4.1 区域责任与关系

| 区域          | 只回答                                           | 不得承担                                 |
| ------------- | ------------------------------------------------ | ---------------------------------------- |
| 工作入口      | 如何导入、新建或接收本岗位的工作                 | 不直接宣告下游业务完成                   |
| 待办/等待队列 | 为什么现在需要关注，责任和期限是什么             | 不展示内部任务表名、投影状态或全部监控项 |
| 事实与缺口    | 当前对象是什么，哪些事实已确认，真正缺什么       | 不重复提供另一套选择器或自行计算放行     |
| 动作与反馈    | 当前允许做什么，完成标准是什么，操作结果是否落账 | 不把多个等权按钮交给用户猜顺序           |

左侧选择工作原因，驱动中间业务上下文；中间的事实和缺口解释右侧动作为什么出现；右侧结果落账后刷新同一上下文和队列。任何区域都不能成为孤立卡片。

## 5. 备货工作台完整样例

### 5.1 岗位目标与真实操作顺序

备货人员要把一张备货单从收到数据推进到“SKU 身份与必要属性明确、适用资料齐全、可以进入后续装柜安排”。货柜可能尚未创建，也可能随后发生一柜多单或一单多柜，因此不能以货柜作为备货工作的前置入口。

```text
导入备货单 / 新建备货单
  -> 匹配已有 SKU；只创建或确认新 SKU
  -> 只确认该 SKU 缺失或未知的权威属性
  -> 服务端按 SKU 属性、目的地、日期和规则计算适用要求
  -> 只核验适用要求所需的证据或附件
  -> 正常 SKU 自动收拢；真实缺口进入责任队列
  -> 条件满足后进入装柜分配
  -> 可一单分多柜，也可一柜绑定多张备货单
```

批量导入是多行备货单的默认入口，必须预检、去重并逐行报告问题；单条手工新建用于临时或少量业务。导入备货单时优先匹配 SKU 主档，不要求业务人员事先逐个建立全部 SKU；仅对未匹配 SKU 或关键属性未知项发起最小确认。

### 5.2 备货工作台标准信息动线

```text
┌ 备货工作台 ─────────────────────────────────────────────┐
│ [导入备货单] [新建备货单]   待我处理 6 · 等待他人 2      │
├──────────────┬────────────────────────┬──────────────────┤
│ 今天要处理   │ 当前备货单 / 当前问题  │ 现在可以做什么   │
│              │                        │                  │
│ 确认新SKU 2  │ 26DSC01812             │ 问题原因         │
│ 补物料资料 1 │ 15个SKU，2个需要处理   │ 所需资料         │
│ 分配装柜 2   │                        │ [唯一主操作]     │
│ 修正导入 1   │ 只展开有缺口的SKU      │ 操作结果与反馈   │
│ 等待合规 2   │ 已通过13个折叠显示     │                  │
└──────────────┴────────────────────────┴──────────────────┘
```

“确认新 SKU、补物料资料、分配装柜、修正导入、等待合规”是业务原因示例，不是硬编码状态全集。服务端投影必须同时提供稳定原因码和岗位语言；界面不得直接把 `ready/blocked/due` 等技术分类当作工作标题。

### 5.3 SKU 的显示与动作

SKU 行先显示身份、此次数量和已确认的关键属性，再显示由规则推导出的适用资料。属性“否”和“不适用”是正常事实，不是待评审；属性“未知”才形成针对该属性的确认任务。

| 情况                           | 默认显示                         | 用户动作               |
| ------------------------------ | -------------------------------- | ---------------------- |
| 属性已知且无适用要求           | 一行摘要；归入已通过组           | 无动作                 |
| 属性已知且有适用要求，证据齐全 | 属性、要求及已核验状态；默认收拢 | 按需查看证据           |
| 属性已知但适用证据缺失/失效    | 展开缺口、原因、责任和期限       | 补充附件或进入对应处理 |
| 关键属性未知                   | 只显示未知的具体属性及其影响     | 确认物料属性           |
| 属性或证据冲突                 | 显示冲突来源与当前权威状态       | 更正、复核或等待责任方 |

正常 SKU 的规范示例：

```text
SKU 311-013GY
不含电池 · 非危险品 · 不含制冷剂
本次无需补充合规资料
```

存在适用证据要求的规范示例：

```text
SKU 311-023V01CW
含锂电池 · 随设备包装
需要：UN38.3、运输条件鉴定
UN38.3 已核验
运输条件鉴定缺失          [补充附件]
```

属性未知的规范示例：

```text
SKU 311-025
物料档案尚未确认是否含电   [确认物料属性]
```

禁止为每个 SKU 固定显示“电池、危险品、制冷剂、商检、证书”五项并全部标为“未评审”。证书不是与这些属性并列的通用维度，而是 SKU 属性、目的地、规则生效日期和证据有效性共同推导出的要求。

### 5.4 数据权威链

```text
ProductSku（稳定身份）
  -> 当前有效 ProductComplianceProfile（已核验属性版本）
  -> 当前司法辖区/日期/SKU 适用规则
  -> 本次要求的证据/证书及有效性
  -> 评审发现与责任工作项
  -> 当前允许动作与业务结果
```

- `shipment-registry` 拥有备货单、备货明细和装柜分配；`master-data` 拥有 SKU 与结构化属性档案。
- `document-records` 拥有证据文件与核验版本；`compliance-management` 拥有适用性、发现和决定。
- `work-execution` 只投影需要人处理或等待的工作；任务状态不能反向覆盖上述事实。
- API 读模型必须返回属性事实、来源/版本、适用要求、要求原因、缺口、责任、等待主体和允许动作。前端不得重写适用性或用“无评审记录”推断五项全部未知。

## 6. 状态与响应式验收

| 场景       | 必须表现                                                         |
| ---------- | ---------------------------------------------------------------- |
| 加载       | 保留三块稳定尺寸，局部骨架不改变当前选择                         |
| 首次空状态 | 显示岗位可执行的开始入口，如“导入备货单/新建备货单”              |
| 筛选无结果 | 保留筛选上下文并提供清除方式，不伪装系统无业务数据               |
| 等待他人   | 单独分区，显示等待对象、所缺事实或决定、期限和自动刷新/接手条件  |
| 业务拒绝   | 显示可行动原因，不归类为网络错误，不改写原事实                   |
| 技术失败   | 保留原操作标识、追踪 ID 和安全重试入口                           |
| 并发冲突   | 告知数据已变化，刷新后保留用户所在业务对象并重新计算允许动作     |
| 移动/窄屏  | 保持队列 → 事实/缺口 → 动作顺序；44px 触控目标；主动作不遮挡内容 |

键盘焦点必须按同一业务顺序移动；状态不能只靠颜色；完成任务所需信息不得藏在 tooltip；展开/折叠和动作结果应通过可访问状态告知辅助技术。

## 7. 验收场景

1. 普通 SKU：属性明确且无适用要求时自动归入正常摘要，不产生人工评审任务。
2. 属性未知：仅要求确认未知属性，并解释它阻止了哪项适用性判断。
3. 适用证据缺失：显示规则为何适用、缺哪份证据、由谁补充，以及唯一允许动作。
4. 尚无货柜：备货人员仍能导入、匹配 SKU、补属性和处理资料。
5. 一柜多单：装柜分配后可在货柜上下文查看多张备货单，备货事实不被复制。
6. 一单多柜：同一备货明细可按数量分配到多个货柜，并可对账总量。
7. 等待其他岗位：待办从“待我处理”移到“等待他人”，并显示责任方、期限和恢复条件。
8. 档案或分配过期：SKU 档案版本、规则版本或装载集合变化时旧评审失效，页面解释变化并重新给出缺口和动作。
9. 操作拒绝或冲突：原数据不丢失，不提示盲目重复提交，用户可按原因恢复。
10. 其他岗位复用：至少用一个非备货工作台样本验证 `HW-D01`～`HW-D16`，业务对象可变但因果动线不变。

## 8. 禁止模式

- 从数据库表、API 列表、状态枚举或技术模块名直接生成工作台导航和卡片。
- 把“全部任务”“全部评审项”平铺给每个人，让用户自行判断什么适用。
- 用多个对象选择器、重复主按钮或互不联动的卡片制造并行上下文。
- 把等待外部、系统监控或自动完成事项伪装成用户必须点击的步骤。
- 用空值、无评审记录或接口失败推断业务事实为“否”“不适用”或“全部未知”。
- 要求用户重复录入系统已有的权威事实，或用前端临时值覆盖已核验档案。
- 只验收页面能打开、API 成功或数据落库，不验证岗位能否完成真实业务结果。

### 8.1 已发生问题的防复发对照

| 已发生问题                                 | 业务后果                           | 后续评审必须检查                                                               |
| ------------------------------------------ | ---------------------------------- | ------------------------------------------------------------------------------ |
| 从数据库表、接口和技术状态倒推页面         | 岗位看得到数据却无法完成工作       | 先提供岗位目标、真实操作顺序和完成标准，再评审页面与接口（`HW-D01`、`HW-D02`） |
| 把资料未齐当作整个流程不能继续             | 真实业务被不必要地阻塞             | 明确该缺失只限制哪个动作；其余动作继续（`HW-D11`）                             |
| 要求不同时间产生的来源同时提交             | 人员只能等待或制造假数据           | 每个来源按真实产生时机独立接收，联合判断不得改变单来源原子性                   |
| 为同一事实建设多套导入或补录入口           | 重复录入、结果不一致、责任不清     | 已有权威事实自动复用，新增入口必须证明不同业务结果（`HW-D09`）                 |
| 让人员填写内部 ID、归组号或系统计算值      | 内部身份被编造，关系难以审计       | 系统生成身份；人员只在明确候选间选择或确认责任决策（`HW-D12`）                 |
| 只有“确认”按钮或说明文字，没有当前值和控件 | 用户不知道确认什么，也无法完成处理 | 展示当前/来源/候选值并打开实际操作控件（`HW-D13`）                             |
| 所有 SKU 无差别展开完整规则目录            | 大量正常项变成人工待办             | 先计算适用性，只暴露未知属性和适用证据缺口（`HW-D06`）                         |
| 生命周期、完整度、异常和观测混成一个状态   | 无法解释下一动作和真实风险         | 分轨保存、分别展示，再由允许动作投影组合（`HW-D16`）                           |
| 大量卡片平铺待补内容                       | 占据首屏，处理顺序仍不清楚         | 使用单一队列和因果动线；正常项收拢、异常项展开（`HW-D03`～`HW-D05`）           |
| 任务和成功结果只保存在前端内存             | 刷新后任务消失，无法交班和追踪     | 服务端持久或可重建投影，重新进入后恢复上下文（`HW-D14`）                       |
| 正常对象只能逐条点击                       | 批量业务被机械操作拖慢             | 默认批量处理无冲突对象，异常再逐条处理（`HW-D15`）                             |
| 操作后只显示请求成功，不重新读取事实       | 页面结果可能与正式落账不一致       | 重新读取服务端结果并显示业务回执和恢复入口（`HW-D10`、`HW-D14`）               |

## 9. 变更规则

- 新工作台必须在 task brief 中逐项引用适用的 `HW-Dxx`，并给出岗位样本和业务/信息/动作/落库映射。
- 通用规则只在本文和 `UI_SYSTEM` 维护；领域文档只声明该领域的权威事实和约束，不复制界面方案。
- 若实现发现规则与真实岗位操作冲突，先用样本回验并修改本文，禁止在代码中形成未记录的第二套解释。
- 具体状态码、字段、权限和接口变更仍按各自公共契约、ADR、迁移和评审流程执行。
