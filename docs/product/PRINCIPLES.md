## 0. 元治理：确认 ≠ 正确（M0）

负责人确认（sign-off）仅代表**业务意图明确**与**范围/优先级授权**，不自动证明方案在领域一致性、行业规范（S）、数据可靠性与现场可操作性上正确。方案定案必须依次通过 **冲突分析 → 边界验证 → 样本回验**（回验见 [NODE_PDCA_VALIDATION](./domain/NODE_PDCA_VALIDATION.md) F1–F8），评审合格后才升格为 `Decision` 进入正式方案；文档不得仅凭"负责人确认"状态戳标注正确性。
分级：**O**=已确认业务目标/事实；**S/R**=行业规范与现网证据；**C**=待验证设计候选；**Decision**=冲突分析、边界验证、样本回验通过后进入正式方案。

## 1. 核心运行模型：主流程管道 + 工序子管道（负责人 2026-09-08）

### 1.1 四级执行链与五类独立状态

货柜的一次完整流转是一条主流程管道。货柜流转记录是主任务载体，14 个节点是顺序工序；进入节点时激活该节点的工序子任务，工序子任务按责任、事务和证据边界生成一张或多张作业工单。人员、系统或外部参与方在工单内执行动作，动作形成数据记录、证据和同步回执。

| 层级/状态                    | 回答的问题                                     | 推进依据                                        | 不得混同                               |
| ---------------------------- | ---------------------------------------------- | ----------------------------------------------- | -------------------------------------- |
| 流程实例状态 processStatus   | 这次货柜流转当前位于哪道工序                   | 由实际事件经货柜状态机合法转换                  | 不得由按钮、工单状态或同步成功直接改写 |
| 工序任务状态 taskStatus      | 当前节点整道工序做到哪                         | 聚合必要工单结果、前置条件和完成政策            | 工序完成不必然推进主流程               |
| 作业工单状态 workOrderStatus | 某个责任主体的一项具体作业做到哪               | 工单动作、结果、证据及异常恢复规则              | 一张工单完成不代表整道工序完成         |
| 数据同步状态 syncStatus      | 某次动作是否被服务端接收、接受并落账           | clientOperationId、幂等结果、traceId 和三段回执 | 同步成功不代表业务完成                 |
| 数据状态 dataStatus          | 某条数据是否草稿、待核验、有效、被拒绝或被更正 | 来源权威、校验、版本和更正关系                  | 不得由流程状态反推数据有效             |

| 关联层级                             | 基数   | 含义                                                     |
| ------------------------------------ | ------ | -------------------------------------------------------- |
| ContainerRecord -> FlowInstance      | 1:1    | 一条货柜流转记录承载一次主流程实例                       |
| FlowInstance -> NodeTask             | 1:N    | 主流程经过多个节点工序；正常链同一时刻只有一个当前节点   |
| NodeTask -> WorkOrder                | 1:N    | 一道工序按责任、事务等待或独立验收结果拆成多张工单       |
| WorkOrder -> ClientOperation         | 1:N    | 工单可发生领取、执行、采证、提交、重试、异常、取消等动作 |
| ClientOperation -> Data/Result/Event | 1:0..N | 动作可被拒绝，也可更新数据、形成工单结果或合法事件       |

#### 正常执行链

```text
货柜进入管道节点
  -> 激活节点工序任务
  -> 生成/开放一或多张作业工单
  -> 工单动作形成操作记录、数据、证据与同步回执
  -> 服务端校验后推进工单状态
  -> 按工单聚合规则更新工序任务状态
  -> 满足完成政策并形成合法实际业务事件
  -> 状态机推进主流程进入下一节点
```

一张工单不得越级推进主流程。只有结果事件映射有效、来源权威、证据齐全且状态转换合法时，主流程才能推进。工单完成但其他必要工单未完成、任务完成但不产生推进事件、异常返工、以及权威外部事件先到而内部工单后补，均为合法场景。

#### 动作、数据与状态

动作是唯一写入入口。每个改变归属、工单结果、证据或业务数据的动作必须形成 ClientOperation，并绑定 containerRecordId、flowInstanceId、nodeTaskId、workOrderId、actionCode、actor、occurredAt 和幂等键。

```text
动作请求
  -> 请求已接收
  -> 权限/归属/并发/前置/证据/数据规则校验
  -> 业务接受或拒绝
  -> 事务落操作记录 + 数据版本 + 工单结果
  -> 聚合更新工序任务
  -> 如产生合法结果事件，再推进主流程
```

数据记录保留原始值、规范值、来源、发生时间、记录时间、操作者、证据、版本与关联动作。更正追加新版本并引用旧记录；未知值显式失败或进入复核队列。被拒绝、超时或技术失败也保留尝试与回执，但不得生成完成结果。

#### 最小三段提交确认

| 段             | 成立条件                                   | 对业务状态的影响                        |
| -------------- | ------------------------------------------ | --------------------------------------- |
| 请求已接收     | 服务端持久识别幂等键并可查询/重放          | 不推进业务状态                          |
| 业务已接受     | 权限、归属、并发、前置、证据和数据校验通过 | 可进入受控执行，仍不等于完成            |
| 业务事实已落账 | 操作、数据版本和结果事务提交               | 才可更新工单/任务；仅合法事件推进主流程 |

🗣️ 白话：一柜是一条主任务，节点是一道工序子任务，工序里按责任拆工单。员工动作先形成记录和数据，再判断工单、工序是否完成，最后才判断柜子能否进入下一节点。

### 1.2 管理映射：维度 × 节点 × 作业

| 层       | 结构角色                                       | 核心内容                                                                               | 映射与关联                                                                                       |
| -------- | ---------------------------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 管理层   | **维度**：从不同管理视角切分、聚合和比较       | 进度、预警、异常、风险、绩效、改善、资源规划与管理                                     | 维度落到具体节点与动作，可下钻到货柜事实、任务、证据和回执；改善结果受控反馈到计划/规则/资源配置 |
| 主流程层 | **节点**：定义货柜生命周期所处位置与先后       | 从备货单建档到还空箱的节点、计划/预计/实际时间、事件、状态、标记、单证、费用与来源证据 | 节点提供可写窗口、任务条件和业务上下文；接收作业动作经校验产生的合法事件与数据更新               |
| 作业层   | **工序任务 / 工单 / 动作**：节点内由谁完成什么 | 工序上下文、工单、动作、证据、结果和异常恢复                                           | 逐级聚合后以合法事件影响主流程                                                                   |

```text
管理层：维度（进度/预警/异常/风险/绩效/改善/资源）
                         ×
主流程层：节点（备货单 → ... → 还空箱）
                         ×
作业层：工序任务 → 作业工单 → 动作/证据 → 结果确认（异常可从任意阶段进入）
```

三层不是三条互不相干的流程，而是同一货柜上下文的映射：一个管理维度可以观察多个节点与动作；一个节点可以产生多个任务/动作；每个动作必须关联一个业务节点，并把结果反馈给主流程和管理投影。这里的“×”表示关联坐标，不表示为所有维度、节点和动作生成无效的笛卡尔积组合。

### 1.3 数据、信息、状态与时序

| 要素 | 三层中的位置                                                                                                          | 约束                                                                           |
| ---- | --------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 数据 | 节点事实、动作记录、扫描/报工证据、异常、同步回执                                                                     | 保留原始值、来源、操作者、时间与关联 ID；历史不可由管理报表反向改写            |
| 信息 | 面向员工/管理者的任务上下文、进度、预警、风险、绩效与资源投影                                                         | 由数据按管理维度聚合或解释，必须可下钻回原始事实和动作                         |
| 状态 | 主流程消费 processStatus；工序任务消费 taskStatus；工单消费 workOrderStatus；动作消费 syncStatus；数据消费 dataStatus | 各状态独立记录并以稳定 ID 关联                                                 |
| 时序 | 主流程按生命周期节点顺序；作业按任务/动作发生顺序；管理按统计时点/周期观察                                            | 区分计划/预计/实际与发生/提交/确认时间；预计不推进业务状态，未确认提交不计完成 |

### 1.4 闭环硬约束

- UI 必须按场景呈现流程、工序任务、作业工单、数据同步和数据状态，不能只显示一个笼统的“成功”。
- UI 的当前动作必须来自服务端授权任务，不得仅凭货柜状态在前端自行推导；任务完成时保留结果与证据，不能只改一个状态徽章。
- 每次会改变归属、业务结果或证据的作业提交必须幂等、可追踪、可重试；离线/超时时保留“未确认”事实，不伪装完成。领取、物料确认、扫描、报工等仅在任务定义要求时出现。
- 业务动作绑定 clientOperationId + actionCode + containerRecordId + flowInstanceId + nodeTaskId + workOrderId，并保持确认、回执与审计一致。
- 提交反馈至少遵守“请求已接收 → 业务已接受 → 业务事实已落账”的语义边界；业务拒绝不是同步失败，已接收后的处理超时也不得提示员工重新生成操作 ID。
- 作业成功路径、拒绝、重复提交、并发占用、异常阻塞、恢复/返工均须在任务领域模型与契约中定义。
- 任一管理维度、主流程节点和作业动作都必须能沿映射关系相互定位；禁止产生无法关联节点的任务或无法下钻事实的指标。
- 管理指标必须能下钻到货柜事实、任务记录与同步回执；绩效不得使用未被服务器确认或未通过业务校验的提交。

| ⑥ 异常与反馈         | 出问题怎么办、如何持续改善 | 异常上报、分派、处理、跟进、恢复、根因和规则/价格/资源反馈                                                                    | 异常与货柜状态正交；处置结果回流①计划与规则配置                     |
| ⑦ 会议机制           | 如何复盘和作决策           | 报表、绩效、Sub./HQ 物流例会、供应商月度会议及决议跟踪                                                                        | 读取③④⑤及⑥的事实和指标；会议决议形成改善动作并回到①                 |

七组是**领域设计与验收时的完整性检查框架**，不是页面信息架构，也不表示每个节点都复制七张物理表、七个对象或七个固定页签。节点设计要说明各组“适用/不适用/继承”的关系；运行时只实例化真正发生的计划、任务、事件、费用、异常或决议，不能为了填满七格制造空记录。

| 角色/场景 | 默认只呈现                                                                                    | 按需展开                                               |
| --------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| 现场员工  | 当前任务上下文、可执行动作、任务要求的资料/资源与证据、结果或异常入口，以及当前操作的同步反馈 | 与当前动作直接相关的货柜节点、前置条件、证据和处理原因 |
| 计划/调度 | 能力、月/周/日计划、服务商分配、计划与达成差异                                                | 柜级任务、前置条件、异常与资源缺口                     |
| 运营/客服 | 货柜状态、周期、异常、单证和待协调事项                                                        | 任务证据、来源冲突、费用影响                           |
| 财务/管理 | 费用、绩效、风险、趋势与会议决议                                                              | 下钻到货柜、节点、任务、账单和原始证据                 |

同一用户可因角色与当前任务看到不同组合；隐藏不相关信息不等于删除数据关系。员工最小操作闭环优先于展示框架的完整性。

```text
①计划/能力 → ②执行/达成 → ③状态沉淀 → ④周期 + ⑤费用
      ↑                                          ↓
      └──── ⑦会议复盘 ← ⑥异常/反馈/改善 ────────┘
```

- ③是贯穿全部表单的主数据流；柜号是装箱后到卸柜前的共享业务追踪线索，但不是所有表的数据库主键，内部关联仍须使用稳定的货柜流转记录 ID，并保留备货单来源锚。
- ①的年度能力必须逐层分解到月、周、日和具体责任主体；下游计划必须显式引用其前置条件，例如到港计划是拖卡/卸柜计划的输入。
- ②中的“做到”只认服务端确认且通过业务校验的任务结果；客户端待同步记录不能计入达成。
- ④和⑦是管理投影；⑤中的费率、合同与实际账单是独立业务事实，预计费用和聚合结果是派生信息。它们都不得反向覆盖③的货柜事实；人工复核结论、会议决议与 AI 建议必须分开留痕。
- 会议本身不是作业表单流或货柜节点；它消费报表并产生可跟踪的决议动作。

### 1.7 非线性事件与风险触发复核

“计划 → 执行 → 状态 → 分析”是 PDCA 的因果结构，不是系统只能按此顺序收数。实际运行允许以下情况存在，但必须保持可解释和可恢复：

| 情况                             | 系统处理                                                                                             | 禁止做法                                         |
| -------------------------------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| 权威状态事件先到、员工任务后补   | 先按来源权威和状态规则落业务事件，再对未完成/缺失任务生成对账差异或补充动作                          | 为了等任务而压住真实货柜状态，或倒填员工已完成   |
| 事件乱序或迟到                   | 保留业务发生时间与接收时间；去重后按事件序列重算投影，必要时进入冲突复核                             | 用接收顺序冒充发生顺序，直接覆盖历史             |
| 撤船、甩柜、查验、返工或计划变更 | 作为事件/异常分支追加记录，并驱动重新计划、任务取消/替换或恢复动作                                   | 把异常硬折叠成正常主状态，或删除原计划与原事件   |
| 外部更正/撤回                    | 追加引用原事件的更正/撤回事实并重放可重建投影；若会使已密封状态倒退，则生成不一致/补偿任务并进入复核 | 原地篡改已被消费的历史事实，或自动回退已密封状态 |
| 多源事实冲突                     | 按字段/事件类型的权威策略自动采纳、拒绝或进入人工复核，并产出对账结果                                | 使用“最新到达”或全局来源排名静默覆盖             |

人工复核只在风险或冲突改变业务结论时触发，例如未知映射、权威来源冲突、密封历史纠正、关键证据缺失、高风险状态推进、重大费用差异或需独立验证的异常关闭。已知映射、同值重复、幂等重放、低风险且规则可确定的正常动作不得统一加审批。具体风险等级、金额阈值和复核权限保持候选，须用真实样本校准。

### 1.8 证据分级与正式决策门禁

| 标记       | 含义                                                   | 可以证明什么                             | 不能直接证明什么                 |
| ---------- | ------------------------------------------------------ | ---------------------------------------- | -------------------------------- |
| `O`        | 负责人确认的业务目标、约束或事实                       | 目标业务应该如何运行、哪些问题必须解决   | 现网已经如此、候选设计已经可实现 |
| `S`        | 行业规范、法规、标准或权威外部说明                     | 在明确版本、地区和适用范围内的外部约束   | 本项目已采用或现网已满足         |
| `R`        | 现网代码、数据、样本、表单或运行记录                   | 当前或历史上实际出现过什么               | 该做法就是目标方案或普遍规律     |
| `C`        | 尚待验证的设计候选                                     | 可供冲突分析、原型、契约或样本验证的方案 | 已获批准的正式规则               |
| `Decision` | 经过冲突分析、边界验证和代表性样本回验后批准的正式决策 | 在记录的范围、版本和生效时间内约束实现   | 超出适用范围的永久真理           |

`D1...Dn` 只是评审清单里的追踪编号，不自动等于 `Decision`。正式决策至少记录负责人、证据、冲突与替代方案、适用边界、样本结果、影响和生效版本；`O/S/R` 之间没有可脱离语境的固定优先级，发生冲突时必须说明责任主体和适用范围。

原有 Excel/表单属于 `R` 级业务证据与需求素材：用于提取字段、动作、责任、时序和统计口径，不作为新系统的表结构或菜单模板。目标模型以货柜、节点、任务、事件、费用、异常和决议等统一对象为底，再按角色生成任务视图、计划视图和管理投影，禁止把重复填报原样电子化。

## 2. 超期费用管理的纳入口径（负责人确认类型边界）

- **纳入核心范围**：围绕业务俗称“滞港费”的超期费用，分别建立 Demurrage、Detention、Storage 的免费期(Last Free Day)、费率标准、费用预估/预警、对账与一键处置闭环；对接到港/卸船/可提/提柜/还箱等适用事件与异常预警。
- 依据/资产：现网 `ext_demurrage_standards`（目的港+船司+免费期+费率+币种，LAX 免5天 Demurrage 80 USD/天）与 `ext_container_charges`（费用记录）→ 迁移与复用输入；外部规范 `SRSD/SRSE`(运费滞留/结清)、码头超期滞留预警 作对标。
- **计费框架（负责人确认边界，具体规则待样本定稿）**：Demurrage、Detention、Storage 分别选择费用责任段、起算/截止事件、免费期、自然日/工作日、是否含首尾日、阶梯费率、币种、生效区间和账单权威；不能固化为“到港至提柜天数 × 单一日费率”。**预计**由事件/计划与合同标准计算，**账单金额**来自服务商单据，**审核确认金额**由对账结果产生，三者不得互相冒充；清单见 [FEE_DEMURRAGE](./domain/FEE_DEMURRAGE.md)。
- 尚未纳入（保持候选，另审）：其他费用种类（海运费核对除外）、扣货/罚款等——如需纳入另走评审。
- 关联动作：`notify_delay`/`dispatch_exception`/`schedule_empty_return`（ACTION_CATALOG）；K7 免费期剩余预警（NODE_PDCA）。

## 3. 应用规则

- 方案评审以此清单为验收锚（M0 + P1–P10，见 [PROPOSAL_SELF_AUDIT](./domain/PROPOSAL_SELF_AUDIT.md) A 类矛盾回查）。
- 涉及外部事实/来源权威、事件乱序/补录/分支、服务器确认三档、费用类型化与复核触发、表单数字化为投影时，逐条对照 P5–P10 应用约束。
- 涉及货柜、任务、扫描提交或管理指标的设计，必须逐项核对 §1 的流程实例、工序任务、作业工单、同步与数据状态，以及管理维度、节点和作业映射。
- 每个主流程节点必须按 §1.6 七组 SOP 核对其计划、执行、状态、周期、费用、异常改善和会议消费关系；不适用项也须明确说明。
- 七组不得机械生成七张表或七个页签；现场员工默认只见任务上下文、当前可执行动作、必要证据、结果/异常入口和同步反馈。领取、物料、扫描、报工不是所有节点的固定步骤。
- 所有写操作按 §1.1 的最小三段确认检查；是否增加更细状态必须用责任、事务、恢复或用户动作差异证明必要性。
- 外部事实按 §1.7 与 INTEGRATION_BOUNDARIES 的字段级权威规则接入；乱序、异常分支、更正、重放、对账与人工纠偏必须可追踪。
- 所有方案按 §1.8 标记 `O/S/R/C/Decision`；没有通过决策门禁的候选不得进入正式契约或实现。
- 术语/口径漂移即时回正；不因单点便利牺牲原则清单之任一（M0 + P1–P10）。
