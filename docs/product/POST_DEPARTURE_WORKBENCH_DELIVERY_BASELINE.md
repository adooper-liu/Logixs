> 状态：**技术交付映射 v1.4** · 2026-09-29。
> 消费者：前端、Application/API、领域实现、测试与技术评审人员。
> 业务权威：[岗位工作台](../../doc/cross-border-supply-chain/08-role-workbenches.md)与
> [寻源与补货工作台](../../doc/cross-border-supply-chain/03-sourcing-and-replenishment-workbenches.md)。

> 维护边界：本文只记录工作台网络的技术映射、当前实现边界和交付切片，不拥有工作台分工、岗位顺序或业务完成标准；状态机、字段、权限和数据库引用各自运行时技术契约。

## 1. 技术交付约束

以下 `WB-Dxx` 只约束实现和交付，不得作为独立业务规格。业务范围或岗位规则变化时，
必须先修改 `doc/`，再同步本文件。

| 决策     | 规则                                                                                                                                             |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `WB-D01` | 产品工作台覆盖市场信号至还箱收口的完整业务链；出运后 Shipment 生命周期仍是当前最深的已实现纵向能力，但不再是产品范围的唯一入口。                 |
| `WB-D02` | Shipment 是运营主轴，Container 是后段执行单元；不得继续用单柜列表代替 Shipment 工作台。                                                          |
| `WB-D03` | 备货、装箱及更早上游阶段都是端到端工作台网络的正式节点；已有能力继续真实运行，未实现阶段先明确岗位结果和交接接口，不得伪造状态机或业务动作。     |
| `WB-D04` | 每个工作台统一按“为何处理 → 已知事实/真实缺口 → 当前允许动作 → 结果/下一责任人”组织。                                                            |
| `WB-D05` | 一个页面只有一个主选择源；队列选择驱动上下文和动作，不再同时保留独立柜选择器。                                                                   |
| `WB-D06` | DCSA 参与方是外部业务角色，不是 Logix 菜单或内部岗位顺序；项目顺序由事实依赖和门禁决定。                                                         |
| `WB-D07` | 单证在需要判断或执行的时机出现；不得把固定附件格子铺满页面，让用户自行猜哪些适用。                                                               |
| `WB-D08` | 前端与岗位结果优先。每个切片先定义用户能完成的结果，只补支撑该结果所需的最小 API/领域缺口。                                                      |
| `WB-D09` | 一次只实施一个工作台切片；一个 task brief、一个业务结果、一组验收场景，不再使用跨全链路大任务。                                                  |
| `WB-D10` | “我的任务”是跨岗位个人入口，“一柜一档”是只读事实档案；二者都不拥有专业业务规则。                                                                 |
| `WB-D11` | Shipment 是一次具有明确起运地、目的地、运输责任和货物范围的运输组织单元；它串联计划引用、订舱、单证、货柜和到港执行。                            |
| `WB-D12` | 旧系统四表导入兼容链从 `departed` 接管；这只是当前导入切片的技术起点，不是端到端业务起点。普通字段缺失形成待补，身份、引用或互斥冲突才局部拒绝。 |
| `WB-D13` | 四类来源可单独或组合上传；单文件上传/解析原子，多个文件互不回滚；联合业务冲突按柜处理。                                                          |
| `WB-D14` | 无 SKU 明细允许建档并进入已出运流程，显示“货物明细待补”；SKU 完整度不得冒充运输生命周期状态。                                                    |
| `WB-D15` | 只有出运日期时按已解析来源时区的当地 `00:00` 规范化，并保留 `date_only` 精度和补时规则，不展示成精确时刻。                                       |
| `WB-D16` | 缺口必须呈现为可执行动作，点击后在当前工作台打开并聚焦对应编辑器；系统自动完成内部登记，不得用“怎么处理/在哪里处理”的说明文字代替真实入口。      |
| `WB-D17` | 缺口动作必须同时呈现来源当前值、系统可识别的候选值和最终输入/选择控件；不得先要求空确认，也不得把内部复核记录作为打开编辑器的前置条件。          |
| `WB-D18` | 已出运接管默认从工作台业务建档和内部事实交接开始；标准模板是次级批量工具，货柜、清关、物流、仓库四表只作为旧系统兼容入口。                       |
| `WB-D19` | 标准模板只强制 Shipment 业务号和柜号；其余缺失形成待补，已填写但非法的标准码、数量或跨对象引用才阻断受影响候选。                                 |
| `WB-D20` | 完整工作台网络先建立统一入口、真实实施状态和相邻交接边界，再按一个业务结果一个切片逐段接通；“有框架”不得对外宣称“业务已实现”。                   |
| `WB-D21` | 工作台之间传递稳定业务身份、版本化快照和明确交接事实；不得用共享宽表、跨域回写或一个万能状态机代替领域所有权。                                   |
| `WB-D22` | 工作台按“谁在工作 → 为何处理 → 要完成什么 → 判断所需信息 → 可执行动作 → 缺失如何继续 → 交给谁”逐个实施；完成岗位流程后再反推最小数据结构。       |
| `WB-D23` | 前端交互样板与已落库业务能力必须显式区分；样板可用于逐项校准岗位作业，但不得把浏览器状态、演示结果或虚构数据标记成真实业务完成。                 |

## 2. DCSA 角色与项目顺序

DCSA Arrival Notice 1.0.1 官方范围只标准化 Publisher 与 Receiver 的信息交换：Publisher
通常为 Carrier 或 Freight Forwarder；Receiver 可以是 Consignee、Customs Broker、Freight
Forwarder、Collect Invoice Payer、Warehouse Personnel、Trucker 等。其官方 BPMN 也明确说明，
图只包含标准化消息所需交互，并非航运组织的完整作业流程。

因此项目采用三条观察轴，但不把它们拼成一个大状态：

| 观察轴            | 回答的问题                         | 主要外部参与方                                                             | Logix 中的消费位置           |
| ----------------- | ---------------------------------- | -------------------------------------------------------------------------- | ---------------------------- |
| Shipment Journey  | 单证、货权、费用和放货条件是否满足 | Carrier、Forwarder、Consignee、Notify Party、Customs Broker、Invoice Payer | 出运、清关、提柜工作台       |
| Vessel Journey    | 船期、航次和港口作业何时发生       | Carrier、Vessel Operator、Port、Terminal                                   | 出运工作台的在途/到港事实    |
| Equipment Journey | 柜在哪里，下一次移动和还箱是什么   | Terminal、Trucker、Warehouse、Depot                                        | 提柜、送仓、卸柜、还箱工作台 |

项目自己的岗位参与路径是依赖图，不是所有角色严格串行：

```text
来源系统/Carrier/Forwarder 提供已出运交接
  -> 内部出运运营接管 Shipment
  -> 在途跟踪与到港准备
       ├─ 清关人员/Customs Broker 准备并申报
       ├─ Carrier/Forwarder 更新到货通知和放货条件
       ├─ Terminal 提供卸船、可提和 Gate 事实
       └─ Finance/Invoice Payer 处理适用费用条件
  -> 按适用政策的联合可提门禁满足
  -> 内陆调度安排 Trucker 提柜
  -> Trucker 送仓
  -> Warehouse 收柜、卸货并确认空箱
  -> Trucker 将空箱交 Depot/Terminal
  -> 出运运营核对所有柜和未结异常后关闭 Shipment
```

清关准备、到货通知、费用处理和仓库预约可以并行提前发生；实际提柜、送仓、卸柜、还箱必须受前序事实门禁约束。Arrival Notice、HTTP 成功或外部人员点击“完成”都不能单独推进生命周期。

官方核对来源：
[Purpose & Scope](https://reference.dcsa.org/content/standards/releases/arrival-notice/v1/an-v1-purpose-and-scope)、
[User Stories](https://reference.dcsa.org/content/standards/releases/arrival-notice/v1/an-v1-user-stories)、
[Business Process Model](https://reference.dcsa.org/content/standards/releases/arrival-notice/v1/an-v1-business-process-model)。

## 3. 工作台目录

| 工作台/页面       | 目标定位                 | 首屏先回答                               | 主动作与交接                                    | 当前边界                                   |
| ----------------- | ------------------------ | ---------------------------------------- | ----------------------------------------------- | ------------------------------------------ |
| 我的任务          | 个人跨域入口             | 今天为什么需要我处理，最晚何时           | 打开所属专业工作台                              | 不执行专业规则，不展示全部系统任务         |
| 出运工作台        | **核心 Shipment 工作台** | 哪些已出运数据待接管、哪票临期或异常     | 预检/接管；处理在途事实；把专业事项交给对应岗位 | 从 Shipment 进入，不再以单柜装船任务为首页 |
| 进口清关工作台    | 清关案件与货柜放行准备   | 缺哪份适用资料、哪案待申报/回执/查验     | 补件、申报、记录回执、确认货柜级清关完成        | 单案 release 不等于整柜可提                |
| 提柜工作台        | 联合可提与 Gate Out      | 哪柜已可提、为何不可提、免费期何时到     | 安排提柜、记录失败/恢复、确认可信 Gate Out      | 清关、Carrier、Terminal、Hold 条件分轨显示 |
| 送仓工作台        | 内陆运输与到仓交接       | 柜在哪里、送哪个仓、预约窗和延误风险     | 派车/改仓、记录运输、确认到仓/POD               | 到仓不等于卸柜完成                         |
| 卸柜工作台        | 仓库收货与卸空           | 哪柜待卸、实收差异和剩余货物             | 记录部分卸货、差异、卸完、独立空箱确认          | 差异进入异常案件，不靠备注掩盖             |
| 还箱工作台        | 空箱回收与生命周期收口   | 哪柜已空、还箱点、截止时间和场站接收状态 | 安排取空、提交 EIR、确认实际还箱                | 当前缺失的核心工作台，后续独立切片补齐     |
| 备货工作台        | 上游引用/历史追溯        | 已出运记录来源、SKU 和缺失血缘           | 查看来源、补证据、发起更正                      | 当前不产生待备货任务，不继续扩建           |
| 装箱工作台        | 上游引用/历史追溯        | 外部装箱快照是否完整、装载关系是否可解释 | 查看、补证据、受审计更正                        | 已出运后不允许重新完成装箱                 |
| 合规/日期事实复核 | 专业支持队列             | 哪个高风险结论需要独立复核               | 批准、驳回或要求补证                            | 不作为所有岗位的默认主页                   |
| 一柜一档          | 跨岗位只读档案           | 这只柜发生过什么、来源和版本是什么       | 下钻到有权限的专业工作台                        | 不直接写回各域事实                         |

`干活`、`看档`、`看提交`、`看失败` 等现有页面应分别归类为对象浏览、计划/管理或技术支持页，不得与专业工作台并列后让用户自行判断入口。

### 3.1 市场与经营信号工作台

| 项目     | 已确认 V1 定义                                                                                                 |
| -------- | -------------------------------------------------------------------------------------------------------------- |
| 使用者   | 经营与市场负责人                                                                                               |
| 进入时机 | 市场、渠道、客户、竞品或内部经营数据出现值得判断的变化                                                         |
| 工作结果 | 将当前信号处理为继续观察、交给选品评估或不采纳，不要求先形成产品方案                                           |
| 首屏信息 | 为什么现在处理、市场与渠道、观察事实、来源证据、尚待验证的经营假设、当前负责人                                 |
| 主要动作 | 快速登记信号；查看来源；补充判断；选择继续观察、交给选品评估或不采纳；完成相应的下次观察、机会说明或不采纳原因 |
| 系统代劳 | 汇集来源和重复信号、保留原始事实、提示普通缺失、生成处理记录和交接回执                                         |
| 缺失处理 | 除可识别标题外的普通资料缺失不阻止登记或保存；无观察日期或无不采纳原因时保存但不关闭，补齐后才进入已处理分组   |
| 交接结果 | 被采纳信号进入选品团队队列，带上市场与渠道、来源证据、经营假设和未补事项；由选品人员领取后形成实际负责人       |
| 操作纪律 | 不要求人员填写内部编号，不把假设显示成事实，不用统一评分代替负责人判断，不以资料不全阻止先处理                 |

当前页面已接入 `market_signal`、判断历史、证据引用和版本化交接的真实 API；选品工作台已接入团队队列领取与接受动作。页面不得回退到浏览器内存样板，测试演示数据只允许存在于测试边界，不写入生产 Seed。

V1 连续作业规则：来源证据必须能打开内容或原始链接；处理完成后保留可核对回执并自动进入下一条待判断信号。市场人员不预先指定具体选品个人，也不因普通缺失反复停留在登记环节。

#### 3.1.1 实际操作体验评审

| 环节     | 评审结论 | V1 操作规则                                                                                  |
| -------- | -------- | -------------------------------------------------------------------------------------------- |
| 进入任务 | 保留     | 队列先说明“为什么现在处理”，选择一条后再联动事实和动作，不增加第二选择器。                   |
| 快速登记 | 已修正   | 首屏只要求可识别标题；市场、渠道、事实、假设和来源按需展开，不铺满登记面板。                 |
| 来源证据 | 保留     | 先看来源摘要和内容预览；存在有效链接时再打开原始来源。                                       |
| 附件     | 已修正   | 未接入文件存储前不显示“上传附件”假动作；正式实现后复用证据服务。                             |
| 待补处理 | 已修正   | 每个待补项提供就地补录按钮和对应表单；保存后立即显示当前值，其他缺口继续保留。               |
| 继续观察 | 已修正   | 查看日期默认留空，由人员选择；无日期时按钮明确为“保存，日期稍后补”，保存后仍留在待判断队列。 |
| 交给选品 | 保留     | 接收方固定为选品团队队列，普通缺失随交接继续保留，不要求市场人员指定个人。                   |
| 不采纳   | 已修正   | 无原因时按钮明确为“保存，原因稍后补”，只有补齐原因后才关闭。                                 |
| 连续处理 | 保留     | 完整处理后保留上一条回执，并自动选中下一条待判断信号。                                       |

三种业务去向必须保持独立语义：

| 去向     | 立即保存什么                             | 何时算本次处理完整       | 下一责任                     |
| -------- | ---------------------------------------- | ------------------------ | ---------------------------- |
| 继续观察 | 判断依据、查看重点、已有或空的查看日期   | 已有下次查看日期         | 原经营团队                   |
| 交给选品 | 机会说明、已有事实/证据/假设及全部待补项 | 交接快照进入选品团队队列 | 选品团队，领取后才落实到个人 |
| 不采纳   | 判断依据、已有或空的不采纳原因           | 已有不采纳原因           | 原经营团队归档               |

#### 3.1.2 最小持久化与交接契约 V1

> 状态：**负责人于 2026-09-25 批准，作为公共契约、加法迁移和 API 实现基线。**

V1 不建立一张“市场与选品宽表”，也不复用只适用于货柜生命周期的 `NodeTask`。最小权威事实如下：

| 权威对象                     | 所有者              | 最小职责                                                                                   |
| ---------------------------- | ------------------- | ------------------------------------------------------------------------------------------ |
| `market_signal`              | market-intelligence | 稳定信号身份、标题、可空业务范围、事实摘要、假设、当前去向投影、负责人团队和并发版本。     |
| `market_signal_decision`     | market-intelligence | 追加保存每次继续观察、交接或不采纳判断，以及输入、完整度、操作者和时间；不得覆盖旧决定。   |
| `evidence_record`（现有）    | document-records    | 通过 `subject_type=market_signal` 关联链接或文件证据；保留来源、内容引用、哈希和核验状态。 |
| `market_opportunity_handoff` | market-intelligence | 交给选品时生成不可变版本快照、幂等键、发送方和选品团队队列；更正只能追加新版本。           |
| `product_opportunity_intake` | product-selection   | 选品人员领取与接受交接的回执、实际负责人和时间；不回写市场判断，也不复制市场域状态机。     |

`market_signal` 只有 `title` 是登记必填。`market_code`、`channel_code`、`category_ref`、`observed_fact_summary` 和 `hypothesis` 都允许为空；已填写但格式非法或引用不存在时明确报错，不得静默改成空值。

稳定状态码：

| 轨道         | 稳定码                                               | 规则                                                                  |
| ------------ | ---------------------------------------------------- | --------------------------------------------------------------------- |
| 当前去向     | `needs_decision / watching / handed_off / dismissed` | 只由最新一条完整判断投影；不完整判断仍是 `needs_decision`。           |
| 判断类型     | `watch / handoff / dismiss`                          | 表达人作出的业务选择。                                                |
| 判断完整度   | `pending_completion / completed`                     | 与当前去向分轨；用于“已保存但尚未关闭”。                              |
| 选品接收状态 | `queued / claimed / accepted / superseded`           | `claimed` 才产生个人负责人；更正版本到达后旧开放版本变 `superseded`。 |

`market_opportunity_handoff.v1` 的正式交换内容下限：

| 字段                                 | 必填 | 含义                                               |
| ------------------------------------ | ---- | -------------------------------------------------- |
| `handoffId/version`                  | 是   | 稳定交接身份与追加版本。                           |
| `signalId/signalVersion`             | 是   | 来源信号及交接时锁定的版本。                       |
| `title`                              | 是   | 选品队列可直接识别的机会标题。                     |
| `recipientQueueCode`                 | 是   | 固定为 `product_selection`，不得预填个人。         |
| `marketCode/channelCode/categoryRef` | 否   | 交接时已有的业务范围。                             |
| `observedFactSummary`                | 否   | 已观察事实，不得混入假设。                         |
| `evidenceRefs`                       | 否   | 已有证据稳定引用。                                 |
| `hypothesis`                         | 否   | 尚待选品验证的经营假设。                           |
| `opportunityStatement`               | 否   | 市场人员希望选品进一步验证的内容。                 |
| `judgmentNote`                       | 否   | 本次交接判断依据。                                 |
| `pendingFieldCodes`                  | 是   | 受控字段码数组；可为空数组，普通缺失不得阻断交接。 |
| `createdBy/createdAt`                | 是   | 发送责任与审计时间，时间使用 UTC/ISO 8601。        |
| `idempotencyKey`                     | 是   | 防止重复点击生成两条相同版本交接。                 |

原子性要求：一笔“交给选品评估”必须在同一事务中追加完整判断、创建交接版本并写出站事件；任何一步失败则三者都不成立。选品领取通过独立幂等命令写 `product_opportunity_intake`，并返回领取回执。并发编辑使用 `signalVersion` 乐观锁；过期页面提交返回冲突和最新事实，不覆盖他人判断。

本切片已按以下顺序实施：公共 schema 与状态码 → 加法迁移 → market-intelligence 写用例与查询 → product-selection 领取用例 → 两端工作台接真实 API。公共 JSON Schema 是跨端 DTO 的权威来源；前端展示类型只负责界面投影，不能反向充当数据库实体。

运行时实现补充：`market_opportunity_handoff.is_current` 只用于可靠读取每条信号的当前交接版本；创建新版时在同一事务内取消旧版当前标记。旧版本保持不可变并在按 ID 查询时投影为 `superseded`，不得删除或覆盖。

### 3.2 已出运接管的真实操作顺序与责任边界

```text
出运运营查看系统内已形成的备货、装箱、货柜和离港事实
  -> 直接接管可识别的内部 Shipment 候选
  -> 确无上游事实时，按业务对象手工建立已出运 Shipment
  -> 数据量较大时，才使用标准模板或旧系统兼容文件
  -> 系统复用同一 Handoff 规则识别 Shipment / 货柜 / 提单 / 货物
  -> 出运运营只处理身份冲突和错误引用
  -> 系统为缺失业务字段生成待补事项
  -> 出运运营接管可识别的 Shipment，生命周期从 departed 开始
  -> 各资料责任人持续补港口、时区、单证、SKU 和后段计划
  -> 只有依赖某项资料的具体动作受限，其他工作继续
```

| 责任方         | 负责                                                       | 不负责                                         |
| -------------- | ---------------------------------------------------------- | ---------------------------------------------- |
| 来源负责人     | 提供当前已产生的业务事实；批量场景下上传已有来源文件       | 为使用系统而另造文件；等齐四个文件后才开始     |
| 出运运营       | 确认 Shipment 归组，处理逐柜冲突，接管并追踪待补事项       | 输入数据库 ID；为缺失事实编造默认值            |
| SKU/资料负责人 | 后补 SKU 装载明细、附件和业务属性                          | 阻止 Shipment 建档或整票在途跟踪               |
| 系统           | 保证单文件原子、跨文件独立、逐柜判定、幂等、审计和缺口投影 | 以“字段不全”笼统拒绝；把缺口混入生命周期主状态 |

“允许继续”不等于所有动作无条件开放。例如缺清关必需附件时，Shipment 仍可在途跟踪，但“发送清关资料”只对已具备本次发送所需内容的案卷开放；不可执行原因必须指出缺什么、由谁补、在哪里补。

### 3.3 已出运接管入口顺序

新数据入口按业务自然程度固定为：

```text
系统内事实交接（默认）
  -> 手工建立单票已出运 Shipment（确无上游事实时）
  -> 标准模板批量接管（数据量较大时）
  -> 旧系统四表兼容接管（历史来源无法替换时）
```

四条入口最终都进入同一个 Shipment Handoff、冲突检查和持久待补链路，不形成不同的业务落库规则。工作台先让人员看到已有业务对象、当前事实和可执行动作；不得先要求下载或整理文件。

标准模板仍不出现数据库 UUID、人工归组键或技术状态。固定字段、工作表、必填层级和受控值只由
[`post-departure-standard-import.json`](../../packages/contracts/catalogs/v1/post-departure-standard-import.json)
定义，工作簿生成器和解析器共同读取该契约。模板上传按单文件原子处理，不调用 AI 猜测列名，也不要求业务人员再做字段映射。

标准模板不能与四表兼容来源组成同一次预检。批量工具中二选一：规范批量数据使用标准模板；确实只能取得历史四表时展开“兼容旧系统四表”，仍允许四份文件分别到达和逐柜合并。

## 4. 信息在正确时机出现

| 时机           | 必须突出                                                                                | 此时允许                                             | 不应提前出现                                |
| -------------- | --------------------------------------------------------------------------------------- | ---------------------------------------------------- | ------------------------------------------- |
| 建档或接管前   | 内部已有事实、票/柜/货/单关系、离港依据、缺失项、重复与逐柜冲突                         | 复用内部事实、手工建档、打开批量工具、处理冲突、接管 | 清关、提柜或关闭动作                        |
| 已接管、在途中 | Shipment、船名航次、起讫港、ATD、最新版 ETA、来源/新鲜度、柜数和异常                    | 核验时间、查看到货通知、分派到港准备事项             | 把 ETA 当实际到港；要求逐柜重复录入票级事实 |
| 到港前准备     | 适用单证、申报截止、Arrival Notice 版本、放货/费用/预约缺口                             | 补件、发送、申报、预约和分派                         | 将固定附件目录全部标成未完成                |
| 到港与可提判断 | ATA/卸船/可提事实、海关放行及适用的 Carrier release、Terminal release、Hold、最后免费日 | 处理缺口；门禁满足后安排提柜                         | 仅凭“已清关”开放提柜                        |
| 提柜执行       | 码头、预约、车队、车辆、目的仓、计划时间                                                | 记录失败原因或可信 Gate Out                          | 用计划时间冒充实际提柜                      |
| 运输与到仓     | 当前承运任务、仓库地址/联系人/预约窗、POD、延误/改仓                                    | 发运、改仓、到仓交接                                 | 到仓自动等于卸完                            |
| 卸柜与差异     | 预期与实收、部分进度、破损/短少/多货、空箱状态                                          | 保存进度、建异常、确认卸完和空箱                     | 有差异就静默改数量或阻断所有后续            |
| 还箱与关闭     | 还箱点/截止、EIR、场站接收、未结异常和费用                                              | 确认还箱；所有柜满足规则后关闭 Shipment              | 单柜还箱即关闭整票                          |

单证区统一显示“为什么需要、覆盖对象、当前版本、核验状态、责任人和截止时间”。用户提供的附件网格截图只作为现状证据；目标界面不再固定铺设所有附件类型。

### 4.1 清关资料与传送的真实操作顺序

```text
按销售国家/目的国 + 贸易模式 + SKU 属性匹配适用规则
  -> 生成本案卷应有资料清单
  -> 资料负责人补附件并核验版本、有效期和覆盖对象
  -> 清关运营选择已维护的接收方与传送路径
  -> 系统创建并执行传送任务
  -> 记录 To / CC / Contact、方式、时间、结果和证据
  -> 失败可重试；接收方确认后进入申报
  -> 申报 / 查验 / 扣留 / 放行分别记录事实
  -> 全部必需案卷有效放行后形成货柜级清关完成
```

| 责任方              | 权威内容                                                    | 主要动作                                       |
| ------------------- | ----------------------------------------------------------- | ---------------------------------------------- |
| 合规/清关规则管理员 | 各国、贸易模式和 SKU 属性对应的资料要求、适用期和规则版本   | 在前端维护参数；不逐票上传附件或点击发送       |
| 接收方管理员        | 国别、清关公司、传送方式、To、CC、Contact、有效期和启停状态 | 维护接收方主数据；不确认单票放行               |
| 资料负责人          | 单票附件、版本、有效期和覆盖对象                            | 补件、换版、提交核验                           |
| 清关运营            | 单票接收方选择、发送确认、失败处理、申报/查验/放行跟进      | 发起传送、处理回执、登记业务结果               |
| 系统                | 适用规则计算、缺口、传送执行、回执、重试、审计和状态投影    | 不以“点击发送”推导送达，不以“附件齐全”推导放行 |
| 清关行/相关方       | 接收确认、申报和外部结果                                    | 返回受理、查验、扣留或放行事实                 |

参数表与接收方信息是 `UI-03` 的正式输入，但不成为 Shipment 表字段，也不在 `UI-01` 提前实施。海关案卷、证据和放行语义继续引用既有海关业务契约；本节只补齐此前缺失的“资料要求如何产生、发给谁、如何证明送达”的操作边界。

## 5. 标准界面动线

```text
┌ 出运/专业工作台 ─────────────────────────────────────────────┐
│ 当前责任：谁在处理 · 最近截止 · 下一责任人 · 数据更新时间      │
├──────────────┬──────────────────────────┬───────────────────┤
│ 原因队列     │ 当前对象与事实/缺口      │ 当前动作与结果    │
│ 临期/冲突/   │ Shipment 为主上下文；    │ 一个主动作；      │
│ 待我/等待他人│ 柜仅在本票内下钻         │ 拒绝原因和恢复路径│
└──────────────┴──────────────────────────┴───────────────────┘
```

“当前责任 → 下一责任”的交接带是所有工作台的共同识别元素。它表达真实业务接力，不新增领域状态。宽屏可三栏，窄屏保持“队列 → 事实/缺口 → 动作/结果”顺序；视觉令牌、字体和色彩继续使用现有 UI 体系，不另建主题。
