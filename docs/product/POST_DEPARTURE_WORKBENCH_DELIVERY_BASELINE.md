# 出运后工作台交付基线

> 状态：**负责人确认的交付方向 v1.2** · 2026-09-24。
> 消费者：产品、业务负责人、前端、Application/API、测试与评审人员。
> 使用方式：实现者只需先读本文，再读当前唯一活动 task brief；无需通读
> `docs/Logixs 需求迭代/` 下的长篇需求汇编。
> 维护边界：本文拥有工作台分工、岗位顺序、信息出现时机和交付切片；状态机、字段、权限和数据库仍引用各自权威契约。

## 1. 结论

| 决策     | 规则                                                                                                                                        |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `WB-D01` | 当前产品从**可证明的实际出运事实**接管，出运后 Shipment 生命周期是开发主线。                                                                |
| `WB-D02` | Shipment 是运营主轴，Container 是后段执行单元；不得继续用单柜列表代替 Shipment 工作台。                                                     |
| `WB-D03` | 备货、装箱属于上游引用和历史追溯，当前不继续扩建其状态机或默认导航入口。                                                                    |
| `WB-D04` | 每个工作台统一按“为何处理 → 已知事实/真实缺口 → 当前允许动作 → 结果/下一责任人”组织。                                                       |
| `WB-D05` | 一个页面只有一个主选择源；队列选择驱动上下文和动作，不再同时保留独立柜选择器。                                                              |
| `WB-D06` | DCSA 参与方是外部业务角色，不是 Logix 菜单或内部岗位顺序；项目顺序由事实依赖和门禁决定。                                                    |
| `WB-D07` | 单证在需要判断或执行的时机出现；不得把固定附件格子铺满页面，让用户自行猜哪些适用。                                                          |
| `WB-D08` | 前端与岗位结果优先。每个切片先定义用户能完成的结果，只补支撑该结果所需的最小 API/领域缺口。                                                 |
| `WB-D09` | 一次只实施一个工作台切片；一个 task brief、一个业务结果、一组验收场景，不再使用跨全链路大任务。                                             |
| `WB-D10` | “我的任务”是跨岗位个人入口，“一柜一档”是只读事实档案；二者都不拥有专业业务规则。                                                            |
| `WB-D11` | Shipment 是一次具有明确起运地、目的地、运输责任和货物范围的运输组织单元；它串联计划引用、订舱、单证、货柜和到港执行。                       |
| `WB-D12` | 当前流程从 `departed` 开始。业务字段缺失默认形成待补事项并允许继续；只有内部身份、引用完整性或对象冲突失败才局部拒绝。                      |
| `WB-D13` | 四类来源可单独或组合上传；单文件上传/解析原子，多个文件互不回滚；联合业务冲突按柜处理。                                                     |
| `WB-D14` | 无 SKU 明细允许建档并进入已出运流程，显示“货物明细待补”；SKU 完整度不得冒充运输生命周期状态。                                               |
| `WB-D15` | 只有出运日期时按已解析来源时区的当地 `00:00` 规范化，并保留 `date_only` 精度和补时规则，不展示成精确时刻。                                  |
| `WB-D16` | 缺口必须呈现为可执行动作，点击后在当前工作台打开并聚焦对应编辑器；系统自动完成内部登记，不得用“怎么处理/在哪里处理”的说明文字代替真实入口。 |
| `WB-D17` | 缺口动作必须同时呈现来源当前值、系统可识别的候选值和最终输入/选择控件；不得先要求空确认，也不得把内部复核记录作为打开编辑器的前置条件。     |

## 2. DCSA 角色与项目顺序

DCSA Arrival Notice 1.0.1 官方范围只标准化 Publisher 与 Receiver 的信息交换：Publisher
通常为 Carrier 或 Freight Forwarder；Receiver 可以是 Consignee、Customs Broker、Freight
Forwarder、Collect Invoice Payer、Warehouse Personnel、Trucker 等。其官方 BPMN 也明确说明，
图只包含标准化消息所需交互，并非航运组织的完整作业流程。

因此项目采用三条观察轴，但不把它们拼成一个大状态：

| 观察轴            | 回答的问题                         | 主要外部参与方                                                             | Logix 中的消费位置           |
| ----------------- | ---------------------------------- | -------------------------------------------------------------------------- | ---------------------------- |
| Shipment Journey  | 单证、货权、费用和放货条件是否满足 | Carrier、Forwarder、Consignee、Notify Party、Customs Broker、Invoice Payer | 出运、清关、提柜工作台       |
| Vessel Journey    | 船期、航次和港口作业何时发生       | Carrier、Vessel Operator、Port、Terminal                                   | 出运工作台的在途/到港事实    |
| Equipment Journey | 柜在哪里，下一次移动和还箱是什么   | Terminal、Trucker、Warehouse、Depot                                        | 提柜、送仓、卸柜、还箱工作台 |

项目自己的岗位参与路径是依赖图，不是所有角色严格串行：

```text
来源系统/Carrier/Forwarder 提供已出运交接
  -> 内部出运运营接管 Shipment
  -> 在途跟踪与到港准备
       ├─ 清关人员/Customs Broker 准备并申报
       ├─ Carrier/Forwarder 更新到货通知和放货条件
       ├─ Terminal 提供卸船、可提和 Gate 事实
       └─ Finance/Invoice Payer 处理适用费用条件
  -> 按适用政策的联合可提门禁满足
  -> 内陆调度安排 Trucker 提柜
  -> Trucker 送仓
  -> Warehouse 收柜、卸货并确认空箱
  -> Trucker 将空箱交 Depot/Terminal
  -> 出运运营核对所有柜和未结异常后关闭 Shipment
```

清关准备、到货通知、费用处理和仓库预约可以并行提前发生；实际提柜、送仓、卸柜、还箱必须受前序事实门禁约束。Arrival Notice、HTTP 成功或外部人员点击“完成”都不能单独推进生命周期。

官方核对来源：
[Purpose & Scope](https://reference.dcsa.org/content/standards/releases/arrival-notice/v1/an-v1-purpose-and-scope)、
[User Stories](https://reference.dcsa.org/content/standards/releases/arrival-notice/v1/an-v1-user-stories)、
[Business Process Model](https://reference.dcsa.org/content/standards/releases/arrival-notice/v1/an-v1-business-process-model)。

## 3. 工作台目录

| 工作台/页面       | 目标定位                 | 首屏先回答                               | 主动作与交接                                    | 当前边界                                   |
| ----------------- | ------------------------ | ---------------------------------------- | ----------------------------------------------- | ------------------------------------------ |
| 我的任务          | 个人跨域入口             | 今天为什么需要我处理，最晚何时           | 打开所属专业工作台                              | 不执行专业规则，不展示全部系统任务         |
| 出运工作台        | **核心 Shipment 工作台** | 哪些已出运数据待接管、哪票临期或异常     | 预检/接管；处理在途事实；把专业事项交给对应岗位 | 从 Shipment 进入，不再以单柜装船任务为首页 |
| 清关工作台        | 清关案件与货柜放行准备   | 缺哪份适用资料、哪案待申报/回执/查验     | 补件、申报、记录回执、确认货柜级清关完成        | 单案 release 不等于整柜可提                |
| 提柜工作台        | 联合可提与 Gate Out      | 哪柜已可提、为何不可提、免费期何时到     | 安排提柜、记录失败/恢复、确认可信 Gate Out      | 清关、Carrier、Terminal、Hold 条件分轨显示 |
| 送仓工作台        | 内陆运输与到仓交接       | 柜在哪里、送哪个仓、预约窗和延误风险     | 派车/改仓、记录运输、确认到仓/POD               | 到仓不等于卸柜完成                         |
| 卸柜工作台        | 仓库收货与卸空           | 哪柜待卸、实收差异和剩余货物             | 记录部分卸货、差异、卸完、独立空箱确认          | 差异进入异常案件，不靠备注掩盖             |
| 还箱工作台        | 空箱回收与生命周期收口   | 哪柜已空、还箱点、截止时间和场站接收状态 | 安排取空、提交 EIR、确认实际还箱                | 当前缺失的核心工作台，后续独立切片补齐     |
| 备货工作台        | 上游引用/历史追溯        | 已出运记录来源、SKU 和缺失血缘           | 查看来源、补证据、发起更正                      | 当前不产生待备货任务，不继续扩建           |
| 装箱工作台        | 上游引用/历史追溯        | 外部装箱快照是否完整、装载关系是否可解释 | 查看、补证据、受审计更正                        | 已出运后不允许重新完成装箱                 |
| 合规/日期事实复核 | 专业支持队列             | 哪个高风险结论需要独立复核               | 批准、驳回或要求补证                            | 不作为所有岗位的默认主页                   |
| 一柜一档          | 跨岗位只读档案           | 这只柜发生过什么、来源和版本是什么       | 下钻到有权限的专业工作台                        | 不直接写回各域事实                         |

`干活`、`看档`、`看提交`、`看失败` 等现有页面应分别归类为对象浏览、计划/管理或技术支持页，不得与专业工作台并列后让用户自行判断入口。

### 3.1 已出运接管的真实操作顺序与责任边界

```text
来源负责人分别上传手头已有的文件
  -> 系统逐文件完整接收、解析并保存原始证据
  -> 系统跨已到达来源归组 Shipment / 货柜 / 提单 / 货物
  -> 出运运营逐柜处理身份冲突和错误引用
  -> 系统为缺失业务字段生成待补事项
  -> 出运运营接管可识别的 Shipment，生命周期从 departed 开始
  -> 各资料责任人持续补港口、时区、单证、SKU 和后段计划
  -> 只有依赖某项资料的具体动作受限，其他工作继续
```

| 责任方         | 负责                                                       | 不负责                                         |
| -------------- | ---------------------------------------------------------- | ---------------------------------------------- |
| 来源负责人     | 上传当前可取得的任一来源文件，确认来源和文件版本           | 等齐四个文件后才开始；手工拼接跨表结果         |
| 出运运营       | 确认 Shipment 归组，处理逐柜冲突，接管并追踪待补事项       | 输入数据库 ID；为缺失事实编造默认值            |
| SKU/资料负责人 | 后补 SKU 装载明细、附件和业务属性                          | 阻止 Shipment 建档或整票在途跟踪               |
| 系统           | 保证单文件原子、跨文件独立、逐柜判定、幂等、审计和缺口投影 | 以“字段不全”笼统拒绝；把缺口混入生命周期主状态 |

“允许继续”不等于所有动作无条件开放。例如缺清关必需附件时，Shipment 仍可在途跟踪，但“发送清关资料”只对已具备本次发送所需内容的案卷开放；不可执行原因必须指出缺什么、由谁补、在哪里补。

## 4. 信息在正确时机出现

| 时机           | 必须突出                                                                                | 此时允许                                              | 不应提前出现                                |
| -------------- | --------------------------------------------------------------------------------------- | ----------------------------------------------------- | ------------------------------------------- |
| 上传后、接管前 | 已收到哪些来源、逐票归组、票/柜/货/单关系、离港依据、缺失项、重复与逐柜冲突             | 补充任一来源、重新预检、处理冲突、接管可识别 Shipment | 清关、提柜或关闭动作                        |
| 已接管、在途中 | Shipment、船名航次、起讫港、ATD、最新版 ETA、来源/新鲜度、柜数和异常                    | 核验时间、查看到货通知、分派到港准备事项              | 把 ETA 当实际到港；要求逐柜重复录入票级事实 |
| 到港前准备     | 适用单证、申报截止、Arrival Notice 版本、放货/费用/预约缺口                             | 补件、发送、申报、预约和分派                          | 将固定附件目录全部标成未完成                |
| 到港与可提判断 | ATA/卸船/可提事实、海关放行及适用的 Carrier release、Terminal release、Hold、最后免费日 | 处理缺口；门禁满足后安排提柜                          | 仅凭“已清关”开放提柜                        |
| 提柜执行       | 码头、预约、车队、车辆、目的仓、计划时间                                                | 记录失败原因或可信 Gate Out                           | 用计划时间冒充实际提柜                      |
| 运输与到仓     | 当前承运任务、仓库地址/联系人/预约窗、POD、延误/改仓                                    | 发运、改仓、到仓交接                                  | 到仓自动等于卸完                            |
| 卸柜与差异     | 预期与实收、部分进度、破损/短少/多货、空箱状态                                          | 保存进度、建异常、确认卸完和空箱                      | 有差异就静默改数量或阻断所有后续            |
| 还箱与关闭     | 还箱点/截止、EIR、场站接收、未结异常和费用                                              | 确认还箱；所有柜满足规则后关闭 Shipment               | 单柜还箱即关闭整票                          |

单证区统一显示“为什么需要、覆盖对象、当前版本、核验状态、责任人和截止时间”。用户提供的附件网格截图只作为现状证据；目标界面不再固定铺设所有附件类型。

### 4.1 清关资料与传送的真实操作顺序

```text
按销售国家/目的国 + 贸易模式 + SKU 属性匹配适用规则
  -> 生成本案卷应有资料清单
  -> 资料负责人补附件并核验版本、有效期和覆盖对象
  -> 清关运营选择已维护的接收方与传送路径
  -> 系统创建并执行传送任务
  -> 记录 To / CC / Contact、方式、时间、结果和证据
  -> 失败可重试；接收方确认后进入申报
  -> 申报 / 查验 / 扣留 / 放行分别记录事实
  -> 全部必需案卷有效放行后形成货柜级清关完成
```

| 责任方              | 权威内容                                                    | 主要动作                                       |
| ------------------- | ----------------------------------------------------------- | ---------------------------------------------- |
| 合规/清关规则管理员 | 各国、贸易模式和 SKU 属性对应的资料要求、适用期和规则版本   | 在前端维护参数；不逐票上传附件或点击发送       |
| 接收方管理员        | 国别、清关公司、传送方式、To、CC、Contact、有效期和启停状态 | 维护接收方主数据；不确认单票放行               |
| 资料负责人          | 单票附件、版本、有效期和覆盖对象                            | 补件、换版、提交核验                           |
| 清关运营            | 单票接收方选择、发送确认、失败处理、申报/查验/放行跟进      | 发起传送、处理回执、登记业务结果               |
| 系统                | 适用规则计算、缺口、传送执行、回执、重试、审计和状态投影    | 不以“点击发送”推导送达，不以“附件齐全”推导放行 |
| 清关行/相关方       | 接收确认、申报和外部结果                                    | 返回受理、查验、扣留或放行事实                 |

参数表与接收方信息是 `UI-03` 的正式输入，但不成为 Shipment 表字段，也不在 `UI-01` 提前实施。海关案卷、证据和放行语义继续引用既有海关业务契约；本节只补齐此前缺失的“资料要求如何产生、发给谁、如何证明送达”的操作边界。

## 5. 标准界面动线

```text
┌ 出运/专业工作台 ─────────────────────────────────────────────┐
│ 当前责任：谁在处理 · 最近截止 · 下一责任人 · 数据更新时间      │
├──────────────┬──────────────────────────┬───────────────────┤
│ 原因队列     │ 当前对象与事实/缺口      │ 当前动作与结果    │
│ 临期/冲突/   │ Shipment 为主上下文；    │ 一个主动作；      │
│ 待我/等待他人│ 柜仅在本票内下钻         │ 拒绝原因和恢复路径│
└──────────────┴──────────────────────────┴───────────────────┘
```

“当前责任 → 下一责任”的交接带是所有工作台的共同识别元素。它表达真实业务接力，不新增领域状态。宽屏可三栏，窄屏保持“队列 → 事实/缺口 → 动作/结果”顺序；视觉令牌、字体和色彩继续使用现有 UI 体系，不另建主题。

## 7. 串行交付切片

| 顺序    | 切片                 | 唯一业务结果                                                       | 明确不做                            |
