## ② 定义与澄清

- 别混：采购订单号(采购阶段) ≠ 备货单号(备货阶段建档身份)。
- 备货单号先于箱号存在 → 记录可"先建档、后补箱号"。
- 一票(B/L)多柜 = 各柜各有其备货单；**不是**一柜多单/一单多柜。

## ③ 规则与约束/边界

- 每个备货单 ≤ 一个货柜记录（一单一柜，库级约束）。
- 主备货单号不做任何业务判定（导入/迁移禁止用它判断箱-单）。
- ShipmentPlan / Booking / B/L 归组作为候选对象，模块落点随 P2-06/后续切片；首期导入对象=已出运货柜。
- 迟绑定字段允许空，进入时机见 D；不得把"预计"当"实际"。
- 已出运货柜列表是当前系统内部的下游数据起点，不等于允许导入绕过状态机、来源、审核或审计规则。

## ④ 流程（怎么走）

未来业务全景：计划 → 采购(PO) → 备货(备货单号) → 订舱 → 装箱/配箱 → **出运〔当前系统接入边界：形成已出运货柜列表〕** → 一票多柜 → 出运后生命周期（见 CONTAINER_LIFECYCLE）。

当前上线链路：文件导入已出运货柜 → 预检/审核/对账 → 已出运货柜列表 → 后续节点作业与管理 → 还空箱。后续仅把文件入口替换为上游直连；未来再逐步把前端节点向左延伸。

## ⑤ 注意事项（坑）

- 别把 main_order_number 当父子/归属关系。
- 别假定备货单号出现就有箱号（迟绑定）。
- 别在未定 ShipmentPlan 前把计划层写死。
- 别把未来上游流程当作当前已上线能力，也别另建一套出运后货柜链。
- 别把"任取一柜的票级代表"当业务口径去对账。

## ⑥ 白话注解（🗣️）

🗣️ 现在系统先从“已经出运的柜子清单”接手，再一路管到还空箱。上游仍然有计划、采购、备货、订舱和装箱，只是目前由文件把结果交进来；以后先把文件换成系统直连，再把前端逐段向上游延伸。无论入口怎么变，出运后的柜子只走同一条链。
