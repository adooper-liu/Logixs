## ② 定义与澄清

- 别混：采购订单号(采购阶段) ≠ 备货单号(备货阶段建档身份)。
- 备货单号先于箱号存在 → 记录可"先建档、后补箱号"。
- 产品明细先归备货单；实际装入哪个柜、装入多少由装载分配记录，不从表头箱号猜测。
- `ContainerRecord.orderNumber/replenishmentOrderId` 是旧导入兼容锚，不是柜内全部备货单或 Shipment 的权威关系。
- 出运后货物必须由 ShipmentCargoLine 表达；备货单行只是可选上游血缘，不能成为正式出运存在的前提。

## ③ 规则与约束/边界

- 必须支持一个货柜装载多个备货单，以及同一产品明细按数量拆入多个货柜。
- 跨柜当前有效分配数量合计不得超过产品行出运数量，数量单位必须一致。
- 同一备货单可有多条产品明细；`shippedQuantity` 与整单 `packageCount` 是独立事实，不因样本数值相等而合并口径。
- 主备货单号不做任何业务判定（导入/迁移禁止用它判断箱-单）。
- Shipment 是当前核心目标聚合；ShipmentPlan、备货、装箱和采购只作上游引用。Booking/MBL/HBL 是 Shipment 的多值运输单证关系。
- 迟绑定字段允许空，进入时机见 D；不得把"预计"当"实际"。
- 已出运货柜列表是当前系统内部的下游数据起点，不等于允许导入绕过状态机、来源、审核或审计规则。

## ④ 流程（怎么走）

业务全景：计划 → 采购(PO) → 分仓/装柜规划 → 备货 → 订舱 → 装箱/配箱 → **实际出运〔当前系统接入边界：形成 Shipment、货物和货柜关系〕** → 在途 → 到港后生命周期（见 CONTAINER_LIFECYCLE）。

目标上线链路：文件或未来装箱平台 → `ShipmentHandoffCommandV1` 统一预检/接收 → 提交 Shipment/货物/货柜/单证 → 在途与到港工作台 → 柜级后段作业 → Shipment 关闭。当前代码仍按备货单建 `not_shipped` 柜，属于已登记差异。

## ⑤ 注意事项（坑）

- 别把 main_order_number 当父子/归属关系。
- 别假定备货单号出现就有箱号（迟绑定）。
- 别把上游计划、备货或装箱状态机提前搬进当前核心。
- 别把现有按备货单导入的偶然实现当作目标入口。
- 别把"任取一柜的票级代表"当业务口径去对账。

## ⑥ 白话注解（🗣️）

🗣️ 这个系统从“货已经实际出发”开始接手。它先确认这一票是什么、有哪些柜和货，再跟到港、清关、提柜、送仓和还箱；之前怎么买、怎么分仓、怎么催供应商，只保留单号引用，不在这里再做一套。
