## ② 定义与澄清

- Shipment 是一次具有明确起运地、目的地、运输责任和货物范围的运输组织单元，是 Logix 串联计划引用、订舱、单证、货柜和到港执行的核心业务对象。数据库内部 ID 保证对象可建立；业务维度未齐时显示身份/资料待补，不以拼接字段伪造来源身份。
- 别混：采购订单号(采购阶段) ≠ 备货单号(备货阶段建档身份)。
- 备货单号先于箱号存在 → 记录可"先建档、后补箱号"。
- 产品明细先归备货单；实际装入哪个柜、装入多少由装载分配记录，不从表头箱号猜测。
- `ContainerRecord.orderNumber/replenishmentOrderId` 是旧导入兼容锚，不是柜内全部备货单或 Shipment 的权威关系。
- 出运后货物必须由 ShipmentCargoLine 表达；备货单行只是可选上游血缘，不能成为正式出运存在的前提。
- 无 SKU 明细允许建立 Shipment 并进入 `departed` 流程；它形成独立的货物完整度缺口，后补后更新完整度投影，不倒推或改写运输生命周期。
- 已存在于本系统的备货行、装载分配、装箱快照、dispatch 快照和实际离港事实不得要求业务人员重新导入。系统将其投影为内部 Handoff 候选，经同一 Shipment Handoff 事务接管；备货和出运工作台随后读取同一组正式关系。

## ③ 规则与约束/边界

- 必须支持一个货柜装载多个备货单，以及同一产品明细按数量拆入多个货柜。
- 跨柜当前有效分配数量合计不得超过产品行出运数量，数量单位必须一致。
- 同一备货单可有多条产品明细；`shippedQuantity` 与整单 `packageCount` 是独立事实，不因样本数值相等而合并口径。
- 主备货单号不做任何业务判定（导入/迁移禁止用它判断箱-单）。
- Shipment 是当前核心目标聚合；ShipmentPlan、备货、装箱和采购只作上游引用。Booking/MBL/HBL 是 Shipment 的多值运输单证关系。
- 迟绑定字段允许空，进入时机见 D；不得把"预计"当"实际"。
- 已出运货柜列表是当前系统内部的下游数据起点，不等于允许导入绕过状态机、来源、审核或审计规则。
- 数据准入采用“先建档、缺口可见、局部限制”：除无法建立内部主键、无法满足必需外键/租户引用或存在对象身份冲突外，字段缺失与未知映射进入待补，不阻断整票流程；真正依赖该字段的动作可由服务端单独限制。
- 四类来源不要求同时到达。每个文件完整上传和解析同成同败；多个文件独立保存、独立反馈，再由系统联合归组。跨来源冲突按柜隔离处理，不回滚无冲突柜。
- 来源只有出运日期时，以已解析来源时区的当地 `00:00` 规范化，保存 `date_only` 精度、原始日期和补时规则。来源时区仍缺时保留日期事实和时区缺口，不伪造 UTC 偏移，也不因此停止其他已出运工作。

## ④ 流程（怎么走）

业务全景：计划 → 采购(PO) → 分仓/装柜规划 → 备货 → 订舱 → 装箱/配箱 → **实际出运〔当前系统接入边界：形成 Shipment、货物和货柜关系〕** → 在途 → 到港后生命周期（见 CONTAINER_LIFECYCLE）。

上线链路：内部备货/装箱事实或外部来源文件 → `ShipmentHandoffCommandV2` 统一预检/接收 → 提交 Shipment/货物/货柜/单证 → 在途与到港工作台 → 柜级后段作业 → Shipment 关闭。内部来源复用既有 `ContainerCargoAllocation` 与 `ContainerStuffingSnapshot`，不复制装载事实；文件导入是外部事实进入系统的兜底入口，不是内部数据的重复录入步骤。

## ⑤ 注意事项（坑）

- 别把 main_order_number 当父子/归属关系。
- 别假定备货单号出现就有箱号（迟绑定）。
- 别把上游计划、备货或装箱状态机提前搬进当前核心。
- 别把现有按备货单导入的偶然实现当作目标入口。
- 别把"任取一柜的票级代表"当业务口径去对账。

## ⑥ 白话注解（🗣️）

🗣️ 这个系统从“货已经实际出发”开始接手。它先确认这一票是什么、有哪些柜和货，再跟到港、清关、提柜、送仓和还箱；之前怎么买、怎么分仓、怎么催供应商，只保留单号引用，不在这里再做一套。
