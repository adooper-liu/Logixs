# 参考字典与业务伙伴主数据（MASTER_DATA_DICTIONARY）

> 状态：**负责人方向已确认 + 领域设计候选 v0.1** · 2026-09-20 · 负责人：刘志高。
> 已确认方向：建立国家、地点/港口、码头/场站、船司、清关行、拖车公司等统一目录；飞驼、云当等外部来源可补充候选、别名和覆盖能力，但不能直接发布为 Logix 权威主数据。
> 消费者：Master Data、Shipment Registry、Compliance Management、Booking Origin、Ocean Port Visibility、Customs Compliance、Inland Fulfillment、Integration Import、Web。

## 1. 结论

这些数据需要统一治理，但不能全部塞进一张通用“字典表”。Logix 采用四类模型：

| 类型           | 典型对象                                                           | 治理方式                           |
| -------------- | ------------------------------------------------------------------ | ---------------------------------- |
| 参考数据       | 国家/地区、币种、单位、运输方式                                    | 稳定标准码 + 数据集版本            |
| 地点与设施     | UN/LOCODE 地点、港口、码头、堆场、仓库、口岸                       | 层级关系 + 地理身份 + 有效期       |
| 组织与业务伙伴 | 船司、货代、清关行、拖车公司、码头运营方、仓库运营方、集团内部公司 | 法律实体 + 多角色 + 资质/服务范围  |
| 外部映射与能力 | 飞驼/云当代码、别名、接口覆盖港口和船司                            | 供应商独立映射 + 生效期 + 审核状态 |

“国家”是一个参考实体；“出口国、产地国、销售国、进口国、公司所在国”是国家在不同业务对象上的**关系角色**，不能复制成五套国家字典。港口和码头也不是同一对象：港口是运输地点，码头/堆场是港口或内陆地点内的具体作业设施。

## 2. 权威边界

- `master-data` 拥有规范身份、标准标识、别名映射、伙伴角色、数据集版本和候选审核状态。
- `integration-import` 和供应商 Adapter 只提交原始值、外部标识和候选，不直接写主数据表。
- 业务模块只通过公开 Port 解析或引用主数据 ID；不得各自维护港口、船司或国家副本。
- 业务事实保存主数据 ID，并按审计需要保存当时的代码/名称快照；名称后来更正不能改写历史单据含义。
- 主数据只回答“这个对象是谁/在哪里/具有什么角色”；日期事实、放行、合规决定、费用和生命周期状态仍归各专业模块。
- 外部供应商是信息传输方或候选来源。供应商代码命中不等于来源权威，也不自动授予过站资格。

跨模块引用遵守 [GC-007](./CROSS_MODULE_REFERENCE_CONTRACT_V1.md)：公共实体使用稳定 UUID，业务代码和供应商 ID 只是有版本的业务键。

## 3. 国家及其业务角色

### 3.1 国家主数据

`Country` 候选字段：

```text
countryId
isoAlpha2
isoAlpha3
isoNumeric
officialName
displayNames
status
datasetVersion
effectiveFrom / effectiveTo
```

国家/地区采用有版本的 ISO 3166 基线；历史代码不得被新代码静默覆盖。关税区、海关辖区、经济区和制裁区域不是普通国家别名，需要独立的 `Jurisdiction`/区域关系表达。

### 3.2 国家角色不是国家字段别名

| 角色码（候选）               | 绑定对象          | 人话含义                 | 关键约束                               |
| ---------------------------- | ----------------- | ------------------------ | -------------------------------------- |
| `export_country`             | Shipment/报关案卷 | 从哪个国家办理出口       | 取申报司法辖区，不能只由起运港推断     |
| `import_country`             | Shipment/报关案卷 | 在哪个国家办理进口       | 取目的进口申报辖区                     |
| `country_of_origin`          | SKU/备货单行/批次 | 商品原产资格属于哪里     | 可一票多原产国；不等于供应商或装货地址 |
| `sales_market_country`       | 销售/合规评审对象 | 商品销售或投放哪个市场   | 驱动市场准入；不等于收货仓地址         |
| `company_registered_country` | LegalEntity       | 公司依法注册在哪里       | 来自企业登记资料，不从联系人地址猜测   |
| `manufacturing_country`      | SKU/批次/工厂关系 | 实际制造发生在哪里       | 不自动等同法定原产国                   |
| `departure_country`          | 路线航段          | 实际运输从哪个国家出发   | 由权威地点关系得到，只作物流语义       |
| `destination_country`        | 路线航段          | 运输目的地点属于哪个国家 | 不自动等同进口国或销售国               |

业务记录应保存 `subjectType + subjectId + countryRole + countryId + effective period + source/evidence`。需要多值的角色使用关系表，禁止在一列用逗号拼接。

## 4. 地点、港口与设施目录

```text
Country
└── Location（UN/LOCODE 地点/城市/口岸）
    ├── Port
    │   ├── Terminal
    │   └── Yard/Depot
    ├── RailRamp
    ├── Airport
    └── Warehouse/Factory/CustomsOffice
```

### 4.1 建议对象

| 对象                 | 关键字段                                                            | 说明                                                         |
| -------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------ |
| `Location`           | `locationId`、国家、UN/LOCODE、行政区、经纬度、时区、功能码、有效期 | UN/LOCODE 是地点码，不应直接冒充所有具体设施                 |
| `Port`               | `portId`、`locationId`、正式名称、港口类型、状态                    | 起运港/目的港引用此对象或明确的 Location                     |
| `Facility`           | `facilityId`、类型、所属地点/港口、运营方、地址、坐标、时区         | 统一承载码头、堆场、铁路场站、仓库、工厂和海关办公点         |
| `FacilityIdentifier` | 标识类型、代码、签发方、有效期                                      | 可保存 SMDG/运营方/海关/供应商设施码，不假设存在全球唯一代码 |
| `LocationAlias`      | 语言、别名、来源、原始码、有效期、映射状态                          | `盐田`、`Yantian`、供应商代码都映射到规范对象                |

地点时间必须使用 IANA 时区；UTC 偏移只属于某次事实的原始证据，不能作为地点永久时区。港口合并、码头更名或停用采用版本/替代关系，不删除历史 ID。

## 5. 组织、船司与服务商目录

同一家公司可能同时是货代、清关行、拖车公司或仓库运营方，因此采用“法律实体 + 角色档案”，不为每种角色复制一张互不关联的公司表。

```text
LegalEntity
├── OrganizationIdentifier[]
├── PartnerRoleAssignment[]
├── OrganizationAlias[]
└── Relationship[]（集团、代理、分公司、委托关系）
```

### 5.1 通用对象

| 对象                     | 关键字段                                         | 规则                                   |
| ------------------------ | ------------------------------------------------ | -------------------------------------- |
| `LegalEntity`            | 法定名称、注册国家、登记号、税号、状态、注册地址 | 法律身份；简称/品牌不作唯一键          |
| `BusinessPartner`        | 租户、法律实体、伙伴状态、风险/准入状态          | 表达本租户是否与其合作                 |
| `PartnerRoleAssignment`  | 角色、国家/地点/航线/运输方式范围、生效期        | 一家公司可多角色，角色可有不同服务范围 |
| `OrganizationIdentifier` | `identifierType`、值、签发机构、国家、有效期     | 标识类型化；原值不塞进通用备注         |
| `OrganizationAlias`      | 品牌、简称、外文名、供应商名、来源与有效期       | 用于解析，不覆盖法定名称               |

### 5.2 专业角色档案

| 角色                                          | 额外内容                                                        |
| --------------------------------------------- | --------------------------------------------------------------- |
| 船司 `ocean_carrier`                          | SCAC/SMDG/供应商船司码等标识、承运方式、航线/港口范围、订阅覆盖 |
| 无船承运人/货代 `nvocc` / `freight_forwarder` | 许可证/登记号、代理范围、可服务国家和港口                       |
| 清关行 `customs_broker`                       | 许可司法辖区、许可证号、申报主体能力、有效期、海关/口岸范围     |
| 拖车公司 `trucking_provider`                  | 道路运输资质、车队能力、危险品/冷链能力、服务港口/仓库/半径     |
| 码头运营方 `terminal_operator`                | 运营设施关系、预约/EIR/放行接口能力                             |
| 仓库运营方 `warehouse_operator`               | 运营仓库关系、DG/保税/温控/卸柜能力                             |
| 公司主体 `internal_company`                   | 公司注册国、经营国、进出口主体资格及关联租户                    |

许可证、税号和资质有国家差异，不应强行寻找一个全球统一公司代码。清关行、拖车公司和公司主体优先以合同、准入、政府登记或企业提供资料建档；飞驼/云当事件中出现的名称只能补候选别名。

## 6. 外部来源如何补充目录

### 6.1 可采集范围

| 来源            | 可形成的候选                                                                | 不能直接认定                                             |
| --------------- | --------------------------------------------------------------------------- | -------------------------------------------------------- |
| 飞驼            | 船司识别结果、港口/港区代码、码头名称/代码、船舶档案、接口覆盖范围          | 法律实体、清关行/拖车公司资质、供应商推断港口的权威性    |
| 云当            | `carrierCd`、港口/码头/场站原始值、国家码、船东与码头来源信号、接口覆盖范围 | 具体权威主体身份、公司登记身份、供应商中文名称的正式语义 |
| 导入文件        | 业务正在使用的港口、船司、清关行、拖车公司和公司名称                        | 未经核验的拼写、简称或一列多义值                         |
| 人工维护        | 合同伙伴、证照、服务范围、确认别名                                          | 绕过审核直接改变已被业务事实引用的身份                   |
| 标准/官方数据集 | ISO 国家码、UN/LOCODE、适用的设施或企业登记标识                             | 超出数据集范围的业务角色和合作关系                       |

飞驼资料已说明港区/EIR 覆盖按港口和生效期变化；云当也要求按港口、码头、船东和接口能力区分。因此这些内容进入独立 `ProviderCapability`，不能把“供应商支持某港”写成港口自身属性。

### 6.2 供应商映射复合键

```text
provider
+ objectType
+ rawCode（可空）
+ normalizedRawName
+ country/context（必要时）
+ providerDatasetVersion
= canonicalEntityId / review_required / rejected
```

同一个代码在不同供应商处必须保留独立映射。名称相似只能产生建议；只有标准标识精确命中且上下文唯一时才允许自动匹配，不能仅凭字符串相似自动合并公司、港口或码头。

## 7. 候选、审核与更正流程

```text
原始载荷/文件
-> ExternalReferenceObservation（原值留存）
-> MasterDataCandidate（归一候选）
-> 标准码/已有别名匹配
-> 自动唯一命中 或 人工复核
-> 发布规范对象/别名/角色/能力版本
-> 下游通过稳定 ID 引用
```

- 未识别值进入 `review_required`，导入按字段要求决定阻断整行还是允许待补；不得静默创建 active 主数据。
- 同一外部键同载荷幂等，异载荷冲突；保存来源批次、原始值、规范化算法版本和审核记录。
- 已发布对象更正采用新版本或追加别名；实体合并保存 `replacedById` 和迁移审计，不物理删除历史引用。
- 拆分误合并对象时必须能回放原始观察并重新绑定；合规决定和历史业务事实仍锁定当时快照。
- 高风险对象（清关行、承运人、危险品运输商、公司主体）的创建/启用需要能力码和复核；普通别名审核不得顺带授予资质。

## 8. 最小公共能力候选

运行时实现前应冻结公共 DTO/Schema；候选 Port 如下：

```text
ResolveReferenceValue       原始码/名称 -> 唯一规范对象或待复核
GetMasterDataEntity         按稳定 ID 读取当前有效版本
ListMasterDataEntities      分页、稳定排序、按类型/状态/国家筛选
SubmitMasterDataCandidate   供应商/导入提交候选，不直接发布
ReviewMasterDataCandidate   批准、拒绝、映射或请求补证
ReplaceMasterDataEntity     受控合并/替代，保留历史
GetProviderCapability       查询供应商在对象和时段上的接口覆盖
```

所有写接口要求租户/系统身份、能力码、幂等键、预期版本、原因和审计。返回给 Web 的是受控投影，不是数据库表结构。

## 9. 与当前项目的衔接

- `shipment-registry`：保存起运/目的地点、承运人、货代及货柜装载关系的主数据引用和必要快照。
- `compliance-management`：明确读取出口国、进口国、原产国、销售市场国、主体注册国和适用伙伴资质；不得使用一个含糊 `country` 字段。
- `ocean-port-visibility`：路线航段引用港口/码头 ID 和 UN/LOCODE；飞驼/云当 Adapter 提交别名与能力候选。
- `customs-compliance`：引用海关辖区、口岸、申报主体和清关行资质；海关放行仍是独立事实。
- `inland-fulfillment`：引用拖车公司、场站、仓库及能力档案；排程结果不修改伙伴主数据。
- `integration-import`：通过解析 Port 归一值，逐行返回未知、歧义、停用和上下文不符错误。
- `lifecycle-control`：只消费已经解析的地点/主体引用及事实快照，不拥有主数据，也不因主数据更名重放历史状态。

当前 `master-data` 只有模块骨架，数据库尚无上述正式模型；本文不宣称这些对象已经实现。

## 10. 实施顺序

1. 冻结对象类型、国家角色、伙伴角色、标识类型、状态和跨模块实体引用。
2. 引入有版本的国家与 UN/LOCODE 基线，建立 Location/Port/Facility、别名和候选审核最小模型。
3. 建立 LegalEntity/BusinessPartner、多角色和标识模型，先覆盖船司、清关行、拖车公司、码头与仓库运营方。
4. 让 API、导入、人工维护共用解析、候选提交和审核用例；先完成港口与船司纵向切片。
5. 飞驼、云当 Adapter 从原始载荷提交候选别名和 `ProviderCapability`，以已签约版本联调样本对拍。
6. 合规、路线、清关和内陆模块改为引用稳定 ID；旧文本保留为快照并进入可审计映射，禁止猜测回填。
7. 上线主数据审核台、合并/替代和冲突队列；再按真实查询需求增加搜索索引和批量维护。

第一刀不做全球港口/企业全量抓取，不做模糊匹配自动发布，不把供应商覆盖范围当主数据事实，也不建设通用低代码字典平台。
