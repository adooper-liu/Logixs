# 全链路样本应用结论

## 结论

**这套“全链路样本”目前只被用作设计盘点和证据边界参考，没有被运行时代码、自动化测试、生产 Seed、CI 或当前工作台开发直接消费。**

**有必要应用，但不能整包直接导入。**它最适合成为独立的“真实证据验证通道”，用于工作台真实路径验收、WB-B10 和上线业务验收；不应成为当前编码的普遍前置，也不能用来反向定义业务方向。

仓库曾以脱敏别名记录：

- “受控仓外全链路样本包 v0.3”
- “外部 v0.5 全链路样本”

- GC-012 工作台目录和交接设计的结构对拍；
- 识别工作台覆盖缺口；
- 约束 `R / D / S / P` 证据等级；
- 明确不能把推导、构造和待确认数据冒充真实事实；
- 规定原始工作簿不能未经审批进入仓库。

主要记录在：

- [GC-012 设计](../../../superpowers/specs/2026-10-03-gc12.md)
- [GC-012 rollout 计划](../../../superpowers/plans/2026-10-03-gc012-rollout.md)
- [GC-012 G0 brief](../../../planning/tasks/gc012-g0-catalog-v1.md)

因此，**它已经影响过设计判断和证据纪律，但没有成为应用的数据依赖。**

### 2. 没有应用：代码、测试和生产数据

对当前仓库、Git 历史、worktree 和可见 Git 对象的广泛检索均未发现：

- 运行时读取脚本；
- 生产 Seed；
- CI 输入；
- 当前活动 task brief 的直接依赖。

所以，**当前开发没有真正消费这套数据。**

### 3. 仓库里确实在使用的其他真实样本，不是这套数据

目前活跃使用的是另外两组来源：

1. `D:\Filez\刘志高\已出运货柜`

```text

```

## 二、这套数据实际包含什么

目录中共有：

- 5 个 XLSX：v0.1～v0.5；
- 6 个 Python 构建、推导和检查脚本；
- 1 个 JSON profile；
- 1 个逻辑校验报告；
- 共约 1.06 MiB。

最新 `v0.5`：

- 33 个工作表；
- 约 1,716 条逻辑记录；
- 覆盖 22 个直接业务阶段；
- 合规运营以跨工作台事实存在，没有独立主表。

直接覆盖：

```text
市场信号 → 选品 → NPI → 主数据 → 寻源
→ 需求补货 → 采购 → 可出运供给
→ 出运计划 → 订舱 → 备货 → 装箱 → 出口报关
→ 出运 → 海运 → 进口清关 → 提柜 → 送仓
→ 卸柜 → 还箱 → 费用 → 异常
```

另有：

- 交接链；
- 对账；
- 费率和滞港费计算；
- 历史实绩；
- 推导依据；
- 884 条样本构建记录；
- 待确认事项。

## 三、为什么不能把它整体当成“真实数据”

这套包混合了至少四类信息：

```text
R：来源事实
D：推导结果
S：构造或演练数据
P：待确认/缺失
```

其中 `complete_v04.py` 会采用：

- 插值；
- 比例分配；
- 历史中位数；
- 规则推导；
- 业务假设；

来补足工作簿。

最终 v0.5 将这些内容物化为普通单元格，如果脱离“推导依据”和“样本构建清单”，它们外观上与来源事实非常接近。

因此：

- 有值不等于真实发生；
- 日期不等于实际时间；
- 工作表存在不等于工作台已验收；
- 交接行存在不等于下游真实接收；
- 费用计算正确不等于费率有生产权威；
- 76 项检查通过不等于独立验证完成。

逻辑报告中的“76 项通过、0 问题”由与生成器同源的代码产生，证明内部一致性，但不能独立证明来源真实性、完整性或业务闭环。

## 四、是否有必要应用

### 1. 对编码和产品机制开发：不是普遍前置

当前仓库权威已经明确：

- 缺少真实样本，不阻止边界清楚、可回滚的产品机制开发；
- 可以使用永久标记为 `synthetic_rehearsal` 的正反例；
- 真实样本不门禁技术设计、编码和达到 `operational`。

依据见 [08-role-workbenches.md](../../../../doc/cross-border-supply-chain/08-role-workbenches.md)。

所以当前选品立项 S3a 不应因为这套样本而暂停。它真正依赖的是：

- 已批准的单位经济政策；
- 正式 ISO 4217 币种参考数据；
- 契约、迁移、计算和业务路径验证。

全链路样本不能代替官方币种数据，也不能为选品自动产生利润阈值。

### 2. 对自动化测试：仅在能提供特殊价值时使用最小派生物

普通领域、API、PostgreSQL 和 E2E 测试不需要复制真实工作簿。

只有当真实来源能够提供合成数据难以覆盖的内容时，才值得从中派生最小 fixture，例如：

- 真实表头差异；
- 混合日期格式；
- 业务主键粒度；
- 一对多或多对多关系；
- 来源冲突；
- 特定平台导出格式；
- 异常占位文本；
- 费率版本和日期边界。

派生 fixture 必须：

- 最小化；
- 脱敏；
- 有批准；
- 有来源别名和转换记录；
- 永久标记 `deidentified_real_derived`；
- 不进入生产 Seed；
- 不冒充原始事实。

### 3. 对 WB-B10 和真实岗位验收：有必要

`WB-B10` 要求真实岗位用真实或脱敏真实样本覆盖：

- 正常；
- 等待；
- 拒绝；
- 冲突；
- 返工；
- 恢复。

这套数据可以提供候选业务对象和链路事实，但工作簿本身仍不足够。还需要：

- 真实岗位身份与权限；
- 服务端允许或拒绝；
- 真实操作回执；
- 操作前后责任主体；
- 不可变交接；
- 下游接收和使用；
- 冲突与恢复记录；
- 岗位人员反馈。

所以它是 **WB-B10 的输入之一，不是 WB-B10 本身。**

### 4. 对生产启用：需要真实证据，但不能直接导入

可以在没有这套数据的情况下：

- 开发；
- 合并代码；
- 生成不可变制品；
- 部署关闭状态或非用户可见机制。

但受影响工作台正式业务启用前，需要：

- 真实或脱敏样本验收；
- 权限和真实身份验证；
- 外部参考数据；
- 环境迁移证据；
- 业务负责人验收。

这套工作簿不是生产授权，也不应直接成为生产数据导入源。

### 5. 对“业务损失已经下降”的声明：必要但远远不够

少量样本可以证明页面和流程能工作，不能证明经营损失下降。

损失改善声明至少需要：

- 明确指标口径；
- 分子与分母；
- 基线期和观察期；
- 完整样本总体；
- 失败项和排除项；
- 独立结果来源；
- 时间暂停和异常口径；
- 对季节、品类和政策变化的解释。

不能用挑选出的成功样本证明整体改善。

## 五、推荐应用顺序

### 当前主线：不要打断选品工作台

当前继续：

```text
选品立项 S3a 核心
→ S3b UI
→ 任务级门禁与 PR
```

全链路样本不应改变当前业务优先级，也不应反向成为选品需求来源。

虽然工作簿有：

- `01_市场信号`
- `02_选品立项`
- `03_NPI`

但这些上游内容中有不少推导或构造数据。它可以帮助检查结构，却不适合直接证明：

- 真实市场机会；
- 真实投资决定；
- 真实资源承诺；
- 真实选品→NPI 责任接受；
- 单位经济阈值。

### 第一批建议应用：出运计划到出运

优先用于直接来源和链路相对强的区段：

```text
出运计划
→ 订舱
→ 备货
→ 装箱
→ 出口报关
→ 出运
```

适合验证：

- 字段和对象关系；
- 计划、截止和实际时序；
- 文档交接；
- 数量连续性；
- 交接对象；
- 异常和恢复；
- 来源版本冲突。

### 第二批建议应用

在确认对应行确属来源事实后，可用于：

```text
海运运营
→ 进口清关
→ 提柜
→ 送仓
→ 卸柜
→ 还箱
→ 费用
→ 异常中心
```

尤其适合：

- 时间线；
- LFD/LRD；
- Gate Out；
- 收货差异；
- 费率版本；
- 滞港/堆存计算；
- 异常路由。

但不能把单一样本中的费率、期限或异常处置上升为全项目统一规则。

## 六、正确的应用方式

最佳做法是建立独立的“证据通道”，而不是把整个目录导入项目。

### 阶段 1：确认身份与版本

当前仓库里记录的 v0.3 与磁盘当前 v0.3 无法精确绑定：

- 仓库没保存 hash；
- 文档记载 31 个工作表；
- 当前 v0.3 实测 32 个；
- 当前 v0.3 修改时间晚于相关文档提交约 6 分钟。

因此应明确选定：

```text
候选版本：全链路工作台样本_v0.5.xlsx
```

旧版本仅用于 lineage/diff，不能把 v0.1～v0.5 合并成一套数据。

### 阶段 2：仓外受控 manifest

记录但不提交 Git：

- 数据拥有者；
- 版本；
- 文件 hash；
- 文件大小；
- 来源和保管位置；
- 敏感等级；
- 允许用途；
- 禁止用途；
- 保存期限；
- 审批人；
- 销毁规则。

### 阶段 3：安全检查

虽然五个 XLSX 当前检查到：

- ZIP 结构正常；
- 无 VBA；
- 无外部链接；
- 无 workbook connection；
- 无 pivot cache；
- v0.5 无公式和超链接；

仍应做：

- MIME/magic 校验；
- 恶意文件扫描；
- 隐藏 sheet、注释、嵌入对象检查；
- 文件大小、行列数和解压限制；
- 只读隔离处理。

`_profile.json` 含样本行，应当作原始敏感材料，而不是普通说明文档。

### 阶段 4：建立逐 sheet 映射契约

每个 sheet 明确定义：

- 业务粒度；
- 复合主键；
- 外键；
- 字段类型；
- null/占位文本语义；
- 时间精度与时区；
- 币种和金额精度；
- 枚举；
- 来源等级；
- 数据责任方；
- 允许证明什么；
- 不能证明什么。

### 阶段 5：只产生最小脱敏派生物

不要提交整个工作簿。

每个需要验证的工作台只产生：

```text
1 个正常样本
1 个等待样本
1 个拒绝或冲突样本
1 个返工/恢复样本
```

缺少哪种真实路径就保持缺失，不允许 AI 补造后算成真实验收。

## 最终判断

| 问题 | 答案 |
|---|---|
| 当前开发是否直接使用它 | **没有** |
| 是否曾参考它 | **有，作为 GC-012 设计和证据边界输入** |
| 是否有必要应用 | **有，但应用于真实验证通道，不是普遍编码前置** |
| 是否应整包导入仓库 | **不应** |
| 是否应进入生产 Seed | **不应** |
| 是否能直接证明 WB-B10 | **不能** |
| 是否能证明业务损失下降 | **不能** |
| 最优先应用在哪里 | **出运计划→订舱→备货→装箱→出口报关→出运链路** |
| 当前选品 S3 是否等它 | **不等，继续当前主线** |

**推荐采用“双轨”：**

```text
交付轨：
继续选品和业务工作台开发，不因样本包停工

证据轨：
仓外治理 v0.5
→ 安全与脱敏
→ 逐 sheet 映射
→ 最小派生 fixture
→ 真实岗位 WB-B10
→ 单独的经营结果评估
```

这样既能真正利用这套数据，也不会让样本反向制造第二套需求、把构造值冒充事实，或把数据治理变成工作台开发的新阻塞。
