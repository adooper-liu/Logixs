七组用于**节点设计评审**，不是要求每个货柜实例填写七份记录。节点定义要标清“适用/不适用/由上级节点继承”；运行时只创建真实发生的任务、事件、费用、异常或决议。UI 按角色和场景裁剪，现场员工只消费当前任务上下文、可执行动作、必要证据、结果/异常入口及同步反馈。

### 作业动作如何与主流程节点闭环

```text
主流程节点/计划/事件/风险 → 生成或开放任务 → 校验前置条件
→ 按任务定义呈现可执行动作 → 采集该任务要求的证据 → 提交结果
→ 服务器可靠接收 → 校验任务/证据/并发/权限并接受或拒绝
→ 已接受操作完成事务落账 → 任务结果 → 合法业务事件 → 主流程数据与货柜状态更新
                         ↘ 任意阶段可进入异常/等待/恢复/返工
```

“领取、工作物料、扫描、报工/异常”是负责人对低认知现场操作的样例描述，不是所有任务必须依次经过的四个固定步骤。是否出现由任务定义决定：自动派单无需领取，信息任务通常无需扫描，监控任务可由外部事件自动完成，派拖任务可能需要服务商接受回执而不是员工报工；异常是贯穿全程的正交分支，不是最后一步。

- 任务状态回答“员工做到哪”，同步状态回答“服务器是否确认”，两者都不得冒充货柜状态。
- “已接收”“业务已接受”“事实已落账”必须可区分；只有落账结果进入达成、周期、费用和绩效。同步事务可一次完成后两段，不要求制造等待步骤。
- 正常报工、拒绝、重复提交、并发领取、异常阻塞、恢复/返工都必须留任务历史和同步回执。
- 管理维度只从货柜事实、任务结果和确认回执计算进度/预警/绩效；未确认提交不得计入完成量，并必须能下钻到对应节点与动作。
- 权威外部事件可以先于任务结果到达并推进货柜事实；系统随后对任务缺口做对账或生成补充动作，不倒填员工完成。乱序、撤船/甩柜/查验、返工和外部更正按 PRINCIPLES §1.7 追加事件、重放投影和人工纠偏。
- 任务状态码、任务定义结构、证据结构和异常恢复转换尚未定稿，保持候选并进入本文件 §⑦ 待办。

### 任务定义骨架（C，待样本回验）

| 字段                        | 回答的问题                 | 约束                                                                                                     |
| --------------------------- | -------------------------- | -------------------------------------------------------------------------------------------------------- |
| `taskDefinitionKey/version` | 这是什么任务、按哪版执行   | 候选稳定键；任务实例保留版本，不随模板修改漂移                                                           |
| `nodeRef/workCategory`      | 属于哪个节点、解决哪类工作 | 计划、信息、协调、合规、实物、核验、对账、异常等业务性质可以组合；一个任务只承担一个可验收结果           |
| `executionMode/ownerRole`   | 由谁、以什么方式完成       | 区分人工、系统、外部主体或混合执行，并明确责任角色；系统监控不进入员工待办，外部等待仍须有内部跟进责任人 |
| `trigger`                   | 为什么创建                 | 可来自计划、缺失前置、外部事件、SLA/风险或人工发起                                                       |
| `assignmentMode`            | 谁负责、是否需要领取       | `auto/assigned/pool/team` 候选；只有共享任务池或排他作业才显示领取                                       |
| `preconditions[]`           | 何时可执行                 | 未满足时显示等待原因或生成补充任务，不让员工盲试                                                         |
| `actions[]`                 | 当前允许做什么             | 引用 `ACTION_CATALOG`；未入目录的动作只作业务名称候选，不提前造正式 `actionCode`                         |
| `requiredInputs[]`          | 需要哪些资料、资源或能力   | 文档、车辆、月台、设备、权限等；“物料领取”只是其中一种交接方式                                           |
| `evidenceRequirements[]`    | 用什么证明做过             | 外部事件、扫描、照片、附件、签收/EIR、清单或人工说明；只采必要证据                                       |
| `completionPolicy`          | 什么结果才完成             | 可为事实落账、对方接受、指定证据齐全或无需推进货柜状态；支持部分完成/等待外部                            |
| `resultEventCode`           | 是否产生主流程事实         | 仅引用 `EVENT_CODES`；任务完成不必然推进货柜状态，外部权威事件也可先于任务到达                           |
| `exceptionPolicy`           | 失败后怎么恢复             | 定义阻塞、转交、重试、取消、返工和人工复核条件，不删除原任务历史                                         |
| `slaPolicy/riskLevel`       | 何时预警、是否二次确认     | 风险、权限、费用或密封历史改变时才升级复核                                                               |

任务台的稳定信息架构是“任务上下文 → 前置条件 → 当前动作 → 证据 → 结果与恢复”，不是稳定步骤条。某项能力不适用时不生成空步骤；适用但已由系统完成时显示事实和来源，不要求员工重复确认。

### 任务语言系统（C，待服务端契约化）

任务语言不是根据任务实例临时拼接的自由文本，也不由 AI 在运行时决定。当前 Web 演示采用“版本化任务定义 + 实例触发事实 + 状态/回执投影”；正式实现应由服务端返回版本化定义和结构化结果，P3 再进入共享契约。

| 语言字段                  | 来源                    | 写法与边界                                                                               |
| ------------------------- | ----------------------- | ---------------------------------------------------------------------------------------- |
| `title`                   | 任务定义版本            | 使用“动词 + 业务对象 + 必要结果”，例如“确认实际离港时间”；不把故障描述当任务名           |
| `triggerReason`           | 任务实例                | 只陈述触发事实、差异或期限，不夹带操作指令；例如“两方离港记录相差 45 分钟”               |
| `activeGuidance`          | 任务定义版本            | 用主动语态说明当前一步；一个句子只保留必要动作链，不重复按钮、资料清单和页面教学         |
| `blocked/waitingGuidance` | 任务定义版本 + 当前状态 | 明确在等什么、解除条件是什么；不得用“处理中”“请稍候”等无对象文案                         |
| `completionCriteria`      | 任务定义版本            | 描述可独立核验的结果与最低证据，不以“点击提交”或“流程结束”冒充业务完成                   |
| `guardrail`               | 任务定义版本            | 直说不可做事项和“不等于”边界；涉及密封历史、错柜、短少、权限或状态推进时必须直接展示     |
| `resultSummary`           | 已落账任务结果          | 使用过去时说明实际形成的结果；未落账不得生成，完成后替换“下一步”，不能继续显示待办语气   |
| `statusLabel/tone`        | 任务状态语言目录        | 状态码到短标签和语义色单一映射；任务定义与实例不得各自保存一份，避免状态、文字和颜色漂移 |

`taskDefinitionKey/version` 未命中语言目录时必须明确失败或进入配置复核，禁止退回任务键、空标题或通用默认文案。动作按钮继续引用稳定动作目录；语言投影只能解释任务，不能决定权限、动作合法性、完成政策、业务事件或货柜状态。AI 可辅助起草候选文案，但必须经业务样本回验和版本发布后才能进入目录。

🗣️ 白话：标题先说“要得到什么结果”，原因再说“为什么现在要做”，下一步只说“眼下怎么做”。办完以后不再重复命令，而是显示系统实际记下了什么。

### 作业流程分析结论（C，供任务台与任务引擎评审）

节点是货柜生命周期位置，任务是为了得到一个可独立验证结果而创建的工作单元，两者不是一一对应。一个节点可以同时存在多个任务、系统监控和外部等待；同一任务也可能因异常生成返工或复核任务，但不得复制货柜状态。

| 工作单元      | 何时实例化                                                   | 主要责任                              | 员工任务台呈现                                                      |
| ------------- | ------------------------------------------------------------ | ------------------------------------- | ------------------------------------------------------------------- |
| 人工任务      | 必须由人员判断、操作或交接才能得到结果                       | 明确岗位/团队；按排他性决定分配或领取 | 进入队列，展示上下文、前置、动作、必要证据和结果/恢复               |
| 系统监控      | 可由订阅、定时查询或规则持续获取权威事实                     | 系统；业务角色只负责缺口处置          | 正常时不生成员工待办；超时、断流或冲突时生成调查/对账任务           |
| 外部承诺      | 已向清关行、承运商、仓库等发出请求，结果取决于对方接受或履约 | 内部跟进人 + 外部责任方               | 展示已发送/已送达/已接受/已拒绝等真实回执；仅在需要员工动作时进队列 |
| 异常/复核任务 | 风险、冲突、拒绝、证据缺失或恢复条件触发                     | 具备权限的处置人/复核人               | 定向进入队列；关联原任务、事实与证据，关闭前按风险验证影响是否消除  |

拆分以责任边界、事务边界和验收证据为准：跨责任主体、跨事务等待或能独立失败/重试的工作应拆开；同一人同一事务里的点击、扫描、拍照和提交只是任务能力，不因 UI 步骤而拆成多个任务。`monitor_*` 默认表示系统监控定义，不创建常驻人工待办；只有缺口、超时或冲突才派生人工任务。任务完成只记录该任务结果，是否产生业务事件、是否推进货柜状态仍由 `completionPolicy + resultEventCode` 和服务端规则决定。

### 行业模式对齐（用于评审，不替代本地样本）

| 依据                                                               | 可采纳原则                                                                       | 本项目落点                                                                                            | 证实            |
| ------------------------------------------------------------------ | -------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | --------------- |
| OMG BPMN 2.0.2 的 User/Manual/Service/Send/Receive Task 与事件等待 | 人工、系统、外发和等待不是同一种任务，不应强塞进统一人工步骤条                   | `taskType` 区分信息、协调、实物、核验、监控；外部事件可自动完成监控任务                               | S               |
| GS1 EPCIS 2.0 事件可追溯语义                                       | 业务事实需回答对象、发生时间、地点、业务步骤/状态和来源；扫描只是采集手段之一    | `evidenceRequirements` 可引用外部事件、扫描、照片、附件、签收/EIR；统一关联货柜、节点、来源和发生时间 | S·C             |
| ISO 9001:2015 §10.2 不符合与纠正措施                               | 已处理问题不等于风险已消除；必要时需验证措施有效性                               | 异常上报、受理/分派、解决、验证关闭按责任和风险适度拆分                                               | S·C             |
| WMS/TMS 移动作业常见风险控制                                       | 在身份确认、数量/箱封核验和保管责任交接点使用扫码/照片/EIR，而不是每个屏幕都扫描 | #2、#10–#14 实物节点按风险要求证据；信息/监控任务默认不要求扫描                                       | C（待现场回验） |

一手来源：[OMG BPMN 2.0.2 正式规范](https://www.omg.org/spec/BPMN/2.0.2/PDF)、[GS1 EPCIS 2.0](https://ref.gs1.org/standards/epcis/2.0.0/)、[ISO 9001:2015 官方目录](https://www.iso.org/standard/62085.html)。其中 ISO 正文受版权与访问条件限制，本文件只引用 §10.2 的原则，不复制条文；WMS/TMS 风险控制仍为本项目候选，不能标作普适规范。

外部规范只能证明任务/事件应分型和留证，不能替代本地责任、SLA、设备条件和完成政策。§④ 的每条任务仍须经 P2-12 真实样本与现场走查后才能从 `C` 升级。

## ③ 清关当日执行检查（②组的动态任务触发）

| 问                         | 判断    | 动作                      | 产出     |
| -------------------------- | ------- | ------------------------- | -------- |
| 1 计划清关日期今天或已过？ | 是=红灯 | 优先处理                  | 红灯清单 |
| 2 清关状态未完成/异常？    | 是      | 联系清关/补资料           | 跟进     |
| 3 单据传递未全/失败/重传？ | 是      | 重新/手动传递；查附件齐否 | 断点修复 |
| 4 需换单/待确认？          | 是      | 联系货代/船司             | 换单进度 |
| 5 ISF 未申报/失败？        | 是      | 补充重申报                | 申报确认 |
| 6 有异常原因？             | 是(⚠)   | 评估影响/升级             | 处置     |

- 六问是任务触发/优先级检查，不是要求一个员工按 1→6 顺序完成。系统分别生成资料、申报、查验协调或放行核验任务；已由权威外部事件满足的检查只显示事实，不重复派单。
- 独立事件：清关出现查验/开箱 → 生成查验协调任务并记录 `inspection` → 解除扣留 `hold_released`（如适用）→ 核验 `release`；异常处理不占用货柜主状态。
- 闭环：确认"已清关"+实际清关日期（EVENT_CODES release / NODE_TIME #7 actual）。
- 自动规则：附件(出运+14天,提单zip≤10MB)、定时发送、货柜同步、最晚清关日期（D2/D6 待入规则清单）。

## ⑤ 规则/约束（引用，不复制）

- 转换/密封/单调：LIFECYCLE R1–R4；预检：PRECHECK；来源：D7；五主体放行前提见 FIVE_PARTY。
- 每个"今日红灯问题"应可编码为 **TriggerRules 行**（问题→判断→动作→闭环），逐步覆盖 ③，减少纯人肉判断。
- 七组之间只传引用和结果，不复制货柜状态、节点时间或费用底数；周期、费用和会议报表必须能下钻到一柜一档。
- “查验”和“入库”可以作为运营表单链位置展示，但权威领域语义不变：查验是清关事件/异常，入库是 WMS 交接，不新增货柜主状态码。
- 人工复核是风险/冲突触发的跨组控制点，不是每节点固定审批，也不是第四种状态；复核结果关联原计划/动作/证据/费用或决议，并记录人员、时间、理由和前后值。
