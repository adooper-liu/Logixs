# 产品属性与元数据治理（PRODUCT_ATTRIBUTE_GOVERNANCE）

> 状态：**负责人方向已确认 + 数据设计候选 v0.1** · 2026-09-19 · 负责人：刘志高。
> 已确认方向：借鉴元数据驱动以减少低频字段 DDL；不得把核心事实、状态机或合规决定做成无约束 EAV/JSON。
> 消费者：产品主数据、Shipment Registry、Compliance Management、Integration Import、Web、数据分析。

Product/SKU 稳定身份由 `master-data` 拥有；`shipment-registry` 只保存备货单行的逻辑引用和本次交易快照。国家、地点、设施、业务伙伴及外部别名统一引用[参考字典与业务伙伴主数据](./MASTER_DATA_DICTIONARY.md)。

## 1. 结论

采用混合模型：

```text
强类型核心字段
+ 结构化合规子模型
+ 版本化 JSONB 扩展属性
+ 元数据驱动表单
+ 可重建搜索投影
```

纯宽表会造成大量空列和频繁迁移；全 EAV 会削弱类型、约束、查询、证据和审计。JSONB 只承载可选、半结构化、低风险扩展属性，不能成为逃避领域建模的容器。

## 2. 字段分层目录

| `attributeClass`      | 权威存储          | 例子                                            | 规则                             |
| --------------------- | ----------------- | ----------------------------------------------- | -------------------------------- |
| `core_fact`           | 强类型列/关系表   | SKU、数量+单位、金额+币种、箱号、封号、日期事实 | 修改必须走契约和迁移             |
| `regulated_profile`   | 专业结构化表      | 电池、危险品、制冷剂、化学/材质组成、证书       | 可查询、可约束、可被合规规则引用 |
| `extension_attribute` | 版本化 JSONB 快照 | 颜色、表面处理、安装方式等品类差异              | 必须由已发布元数据定义和校验     |
| `search_projection`   | 派生 EAV/索引     | 任意属性筛选、统计                              | 可重建，不作合规或业务事实权威   |

以下内容禁止只保存在动态属性中：生命周期状态/事件/过站条件，计划/预计/实际日期，来源权威，证据核验，数量单位，金额币种，合规决定，危险品运输参数和证书有效性。

## 3. 元数据对象候选

| 对象                               | 关键字段                                                                              | 说明                       |
| ---------------------------------- | ------------------------------------------------------------------------------------- | -------------------------- |
| `AttributeDefinition`              | `attributeCode`、语义所有者、当前状态                                                 | 稳定身份，不随显示名称变化 |
| `AttributeDefinitionVersion`       | 类型、单位维度、精度、基数、校验、敏感级别、可搜索/导入/导出、生效/停用时间、审批状态 | 已发布版本不可原地改义     |
| `AttributeValueSet`                | 值码、标签、本地化、有效期、版本                                                      | 枚举值不直接塞进前端代码   |
| `AttributeTemplate`                | 模板码、模板类型、适用范围                                                            | 组合一组属性定义           |
| `AttributeTemplateVersion`         | 版本、发布状态、生效期、批准人                                                        | 表单和导入锁定版本         |
| `TemplateAttribute`                | 属性版本、必填、顺序、分组、可见条件、证据要求                                        | 模板与属性的关联           |
| `ProductAttributeSnapshot`         | SKU、模板版本、`values`、来源、证据、核验、更正关系                                   | 追加式权威快照             |
| `ProductAttributeSearchProjection` | SKU、属性码、单一类型值                                                               | 可重建的查询加速层         |

属性定义还需声明 `display_only | operational | compliance_input`。`compliance_input` 只有经过领域评审、稳定码发布、证据要求和测试样本后才能被合规规则引用；后台临时新增的显示属性不得立即成为阻断规则。

## 4. 模板组合与适用性

仅按品类配置字段不足以处理跨境业务。运行时表单由服务端按确定规则组合：

```text
基础品类模板
+ 目标国家/地区模板
+ 进口/出口方向模板
+ 运输方式模板
+ 客户模板
+ 承运人/设施模板
= 已解析表单版本
```

服务端返回最终 `resolvedTemplateVersion` 和冲突结果；前端不得自行合并必填性、单位或合规条件。覆盖只能收紧要求，客户/承运人模板不得放宽法律法规或公司硬政策。

## 5. 存储规则

`ProductAttributeSnapshot.values` 使用 PostgreSQL `JSONB`，但必须：

- 数据库约束其为 object，并保存 `templateVersionId`、`schemaVersion`。
- Application 在写入边界按对应 JSON Schema 校验类型、枚举、范围、单位和未知键。
- 保存来源系统、接入渠道、证据引用、核验/置信/有效状态、操作者、记录时间和幂等键。
- 更正追加新快照并通过 `supersedesSnapshotId` 关联旧值；已经参与评审的版本不可覆盖。
- 空值、未知、明确为否分开表达；非法值不得用默认值替代。
- 高频等值/范围查询先测量，再为批准字段添加表达式/生成列索引；不要无条件给大 JSONB 建多个索引。

若跨 SKU 任意属性筛选成为高频需求，可生成类型化搜索投影：

```text
productId + attributeCode + definitionVersion
+ valueText | valueNumber | valueBoolean | valueDate
```

一行只能命中一种值类型；投影有来源快照版本和重建游标。合规判定必须读取核验后的权威快照，不能依赖可能延迟的搜索投影。

## 6. SKU 与合规专业档案

### 6.1 SKU 基础与包装候选目录

| 分组 | 候选字段                                                                    |
| ---- | --------------------------------------------------------------------------- |
| 身份 | SKU/产品号、名称、型号、品牌、品类、用途、目标年龄、生产商、供应商、原产国  |
| 贸易 | HS 候选/确认值、合同、贸易条款、申报要素、单价+币种                         |
| 数量 | 数量+单位、销售/包装单位、箱数、托盘数；包装数不得从产品数量猜测            |
| 量尺 | 单件/整箱净重毛重、尺寸、体积，全部显式单位                                 |
| 包装 | 单品/内盒/外箱/托盘层级、GTIN/条码、批次/序列、箱唛、堆码、防潮、防震、温控 |
| 组成 | 材质、成分、木材种类、纺织成分、食品接触、动植物来源等                      |

本目录是候选输入；正式 V1.1 运行时字段仍以 [TARGET_FIELD_CATALOG](./TARGET_FIELD_CATALOG.md) §E 为权威。

### 6.2 必须结构化的合规档案

| 档案                    | 至少保存                                                                           |
| ----------------------- | ---------------------------------------------------------------------------------- |
| `BatteryProfile`        | 是否含电、电池化学体系、型号、电芯/电池数量、Wh、锂含量、可拆卸性、安装/同包装方式 |
| `RefrigerantProfile`    | 是否含制冷剂、类型、充注量、单位、GWP、密封方式                                    |
| `DangerousGoodsProfile` | DG 判定、UN 编号、类别/项别、包装等级、海洋污染物、运输名称、闪点等适用参数        |
| `ProductComposition`    | 受监管材质/化学物质及含量、计量基础、阈值判定所需字段                              |
| `ProductCertificate`    | 类型、编号、签发方、SKU/型号/国家覆盖、生效/到期、文件和核验状态                   |
| `InspectionRequirement` | 商检、植检、熏蒸、卫生、兽医、食品等要求及适用范围                                 |

“含电”“含制冷剂”“危险品”布尔值仅作列表提醒；专业判断必须读取对应档案。UN38.3、SDS/MSDS、运输条件鉴定、CE/UKCA/FCC/CPSC、RoHS/REACH/WEEE/EPR、电池法规、原产地/木材来源等证据按适用国家和产品类型管理，不把全部证书设为所有 SKU 必填。

## 7. 备货单、SKU 与货柜关系

`ReplenishmentOrderLine` 是一次备货/出运明细，不是产品主档。目标关系：

```text
Product/SKU -> ProductAttributeSnapshot / regulated profiles
      |
      -> ReplenishmentOrderLine（锁定产品/属性版本和本次交易快照）
             |
             -> ContainerCargoAllocation（数量、箱/托盘、货柜分配）
```

必须支持一备货单多 SKU、同 SKU 因合同/批次/价格出现多行、一条明细拆入多个货柜、一个货柜装载多个备货单。装载分配记录数量和单位、包装层级、来源行及实际装箱证据，禁止只在备货单表头保存一个箱号。

## 8. 动态表单契约

服务端受控返回：

```text
formSchema, resolvedTemplateVersion, currentSnapshotVersion,
fieldPermissions, validationRules, evidenceRequirements,
allowedActions, etag
```

对外契约若采用通用名称，`templateVersion` 对应服务端解析并锁定的 `resolvedTemplateVersion`，`currentValues` 来自 `currentSnapshotVersion` 指向的当前快照；不得把浏览器临时合并出的模板或未保存值冒充服务端版本。

客户端提交：

```text
resolvedTemplateVersion, values, evidenceRefs,
expectedSnapshotVersion/etag, idempotencyKey, reasonCode
```

前端只支持白名单控件，如文本、数值、布尔、枚举、多选、日期、单位值、金额和证书引用。服务端不得下发 HTML、JavaScript、任意表达式、任意组件名或数据库字段；后端必须再次执行 Schema、权限、证据、并发和业务校验。

[ADR-011](../../architecture/decisions/ADR-011-controlled-ui-projection.md) 当前仍为 `proposed`；受控动态编辑表单进入运行时实现前，必须先由指定决定人批准该 ADR。本文不把候选架构状态提升为已接受决策。

“新增字段无需改代码”只在以下条件同时成立时成立：已有数据类型和控件可表达、只属扩展属性、不改变写权限/业务规则/统计口径、不参与合规或过站。新增语义类型、专业规则、公共查询、导出或合规影响时仍须发布契约和代码。

例如“是否含稀土元素”只有在现有类型/控件足以表达，且仅作低风险采集或展示时，才能通过已批准元数据配置增加；一旦影响目标国准入、申报、运输限制或证据要求，就必须发布对应规则版本、证据要求和审批记录，并按本节门禁升格，不能由后台随手配置后直接生效。

## 9. 属性升格规则

动态属性满足任一条件时应评审升格为结构化模型或正式列：

- 参与合规门禁、状态推进、费用或权限；
- 需要数据库唯一、外键、跨字段或精确数值约束；
- 被大量列表、范围查询、排序、聚合或对账使用；
- 需要独立来源、证据、有效期、更正、撤销或多值关系；
- 错误会产生报关、危险品运输、财务或安全后果。

升格采用 expand -> migrate -> contract；旧快照保留，迁移脚本可审计、可验证、可恢复。

## 10. 实施顺序

1. 冻结属性分类、稳定码、元数据版本和快照契约。
2. 建立 SKU 主档归属、模板/定义和 JSONB 快照，不改动生命周期契约。
3. 同批建立电池、危险品、制冷剂、证书等结构化档案。
4. API、导入、人工入口复用同一 Application 写用例和逐字段错误结果。
5. 上线受控动态编辑表单与只读投影。
6. 以真实查询计划决定搜索投影和索引；禁止为假想查询提前全量 EAV 化。
7. 定期评审高频参与规则、查询、报表或对账的动态属性，将满足升格条件者迁移为结构化模型或正式契约字段。
