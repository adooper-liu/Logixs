# 导入领域模型（IMPORT_DOMAIN_MODEL · v1.3）

> 状态：**导入是工作台的次级数据接入能力；旧格式仅兼容** · 2026-09-25 · 负责人：刘志高。
> 一句话：业务工作台、标准模板和来源 Adapter 都生成统一 Shipment Handoff；Shipment 接收边界负责提交可证明的已出运事实，导入域不拥有工作台流程，也不另写业务表。
> 标准模板字段权威见 [`post-departure-standard-import.json`](../../../packages/contracts/catalogs/v1/post-departure-standard-import.json)；旧格式差异和迁移门禁见 [`POST_DEPARTURE_CORE_MODEL_GAP_V1`](./POST_DEPARTURE_CORE_MODEL_GAP_V1.md)。
> 证实度 S·R·O·C。流程状态(批次)正文在 LIFECYCLE/契约，不复制。

## ⓪ 边界修正

| 项             | 当前实现                               | 目标                                                                    |
| -------------- | -------------------------------------- | ----------------------------------------------------------------------- |
| 正式分组锚     | `tenantId + orderNumber`               | 稳定外部交接/Shipment 身份；无 Shipment ID 时进入人工匹配，不自动拼键   |
| 正式写入对象   | 备货单、产品行、兼容货柜、柜级时间事实 | Shipment、出运货物、货柜关系、运输单证、上游引用和事件事实              |
| 准入           | 可创建 `not_shipped` 柜记录            | 必须有 ATD、权威 `DEPARTED` 或带依据的授权人工确认                      |
| 生命周期初始化 | 每个导入柜立即初始化 Flow              | Shipment 正式落账后，按关联柜初始化/复用柜级 Flow，并建立 Shipment 投影 |
| 上游对象       | 备货单是导入主对象                     | 备货单仅是可选上游引用/血缘                                             |

### 当前入口优先级

| 入口               | 定位             | 解析与确认                                                | 原子边界                            | 正式写入                |
| ------------------ | ---------------- | --------------------------------------------------------- | ----------------------------------- | ----------------------- |
| 内部备货/装箱交接  | 默认业务事实路径 | 读取已有备货、SKU、装箱、货柜和离港事实                   | 一个交接快照                        | 统一 Shipment Handoff   |
| 工作台手工业务建档 | 单票补充路径     | 人员选择业务对象并录入当前掌握的事实；技术身份由系统生成  | 一次建档/接管命令                   | 同一个 Shipment Handoff |
| 已出运标准模板 V1  | 次级规范批量路径 | 固定表名、固定表头、固定字段码；不调用 AI，不做人工列映射 | 一个 `.xlsx` 文件整体成功或整体失败 | 同一个 Shipment Handoff |
| 旧系统四表         | 兼容路径         | 每份文件可独立到达，按历史别名和适配规则解析              | 单文件原子；四份文件互不回滚        | 同一个 Shipment Handoff |

标准模板中的 `已出运接管` 一行代表一票 Shipment 与一只柜的关系；`SKU装载明细` 一行代表柜、备货单和 SKU 的实际装载分配。只有 Shipment 业务号和柜号是文件身份必填。SKU 页可为空，港口、船期、提单、货主等普通事实缺失时产生待补；已经填写却不符合权威目录、受控值、数量规则或对象引用时，才拒绝受影响候选。

模板下载时从数据库 active ISO 3166-1 与 UN/LOCODE 发布生成“代码字典”，并为销往国家、起运港和目的港提供“标准代码｜中文显示名｜官方英文名”下拉。国家中文显示名来自运行环境 ICU/CLDR 的 `zh-CN` 区域名称；港口中文名只使用数据库中的 `zh-Hans` 已确认或候选别名，候选和缺失必须显式标注，不得把机器翻译冒充权威港名。标准模板解析器只提取并保存下拉值前缀中的 ISO/UNLOCODE 代码。模板下拉不是完整性边界；上传预检仍须按同一 active 权威目录校验，代码未知时允许留空并进入待补，已填写非法代码才阻断受影响候选。

## ② 定义与澄清

- 导入只“把数据可靠放进来”，**不拥有业务事实**。当前兼容端口是 `applyReplenishmentOrderImport`；目标只允许调用 `PreflightShipmentHandoffPort` / `AcceptShipmentHandoffPort`，契约及原子边界见 [`POST_DEPARTURE_CORE_MODEL_GAP_V1` §5.10](./POST_DEPARTURE_CORE_MODEL_GAP_V1.md)。
- 批次=一批文件；来源行不等于货柜。产品明细文件按 `tenantId + orderNumber` 聚合成一个备货单和兼容货柜表头，行级字段逐条落产品明细；后续 SKU 绑定和装载分配走独立公开 Port。
- 旧 `tabular-v2` 兼容解析中的 AI 只产“建议”，全部人工确认后才预检/写入；标准模板按固定契约解析，不调用 AI。
- 文件「物流状态」列：表达来源方声明的实际状态而非计划/预计；归一后作为状态证据，必须经 D7 字段/事件权威、证据一致性和状态机合法转换校验。通过后由业务事件推进 `currentStatus`，冲突进入对账/复核。
- 当前用例会建立 `not_shipped` 柜记录，这是已登记的目标差异。新核心入口不得先建出运前记录再等待推进；只有合格的实际出运证据通过后才能创建正式 Shipment。
- 目标入口允许四类来源任意子集到达。文件上传/解析按单文件原子，多文件结果互不回滚；联合归组后的业务冲突按柜隔离，不能用“来源包不完整”阻断所有已到数据。
- 除内部主键、必需外键/租户引用和对象身份冲突外，缺失字段进入待补事项并允许 Shipment 从 `departed` 开始。无 SKU 明细是货物完整度缺口，不是导入失败或全流程阻断。

## ③ 规则与约束/边界

- 批次幂等：同 idempotencyKey 再次上传 → 返回原批次不重写。
- 新批次原文件先进入 MinIO/S3，再创建批次与解析行；PostgreSQL 只保存对象键、SHA-256、MIME、字节数和留存时间，不保存文件体。
- 对象键由服务端批次 UUID 生成，不包含原文件名或租户名称；幂等命中不重复上传，建批失败只删除本批独占对象。
- 历史批次没有原文件证据时必须标记 `not_retained`，不得根据解析行反向拼装或伪造原文件。
- 重新解析/修正采用替代批次：操作人重新提供文件，新批次记录 `parserVersion + replacesBatchId`，重新走映射、审核、预检和执行；旧批次及其行、建议、审核、结果保持不可变。
- 有效幂等范围包含解析器版本和被替代批次；同版本同文件同替代目标的重试返回同一新批次，解析器升级后允许同一文件形成新快照。
- 任何改变表头识别、来源行快照或版式判定的发布必须提升 `parserVersion`；仅重构且输出语义不变时保持版本。
- 单个表格区域只承载一种行粒度；横向产品明细与纵向货柜字段值块混排时，解析阶段以 `LAYOUT_MIXED` 阻断，不把详情字段伪装成产品行。不同实体/粒度应拆分 Sheet 或使用显式命名区域。
- 预检 blocker → 禁止写业务表（硬约束）。
- `ContainerRecord.orderNumber/replenishmentOrderId` 仅保留当前导入兼容语义；不得据此拒绝一柜多单或一条明细拆入多柜。
- 同一备货单可有 N 条产品明细；`productNumber` 不能单独作为明细唯一键。
- 已提供装载分配时必须先核验并绑定 Product/SKU；未提供时建立 `cargo_detail_incomplete` 待补事项。导入不得在事务外静默创建 SKU、从整柜汇总反推 SKU 或猜测历史行绑定。
- `shippedQuantity + quantityUnit` 与整单 `packageCount` 独立保存；缺单位不得因当前样本与箱数相等而默认成“箱”。
- 同一备货单聚合必须事务落账：表头与全部有效产品明细同成同败；不同备货单可分别记录结果并继续执行。
- 实际时间遵守 LIFECYCLE_CONSISTENCY R10–R12；来源状态缺实际时间、来源 UTC 偏移不明、来源系统/证据缺失或推导值冒充 actual 时预检阻断；推导值使用 `estimated + system_derived` 并带规则版本。
- V1.2 时间事实保留原值、来源 UTC 偏移、UTC 标准值、来源系统、来源状态、证据/推导规则和来源批次/行；只落领域事实，不自动生成规范事件或推进状态。
- 状态列归一须过字典；未知字典值进待处理（不静默）。
- 标准入口只用于业务岗位已经确认“已出运”的数据。缺离港时间或附件时建立待补事项，不阻断 Shipment 接管；来源明确表明仍在出运前、否认已出运或与既有实际事实冲突时，才拒绝受影响候选并转人工处理。
- 标准模板以单文件为事务边界，同一文件中任一结构、身份或非法值错误都会阻止该文件进入正式接管；预检仍逐行返回错误，联合预检中的业务冲突按柜隔离。旧四表之间互不回滚，但每个文件内部同样不得部分接收。
- 写前过 来源权威(D7)/可写窗口/密封(LIFECYCLE)。

## ④ 流程（怎么走）

当前兼容链路：上传 → 解析 → 映射/审核 → 按备货单预检 → 逐备货单事务写入兼容记录 → 柜级 Flow 初始化 → 行结果。

业务主链路：工作台读取内部业务事实 → 直接接管内部候选；确无上游事实时按单票手工建立 Shipment → 生成统一 Shipment Handoff → preflight 权威码、引用和活动关系 → 处理冲突/生成待补项 → 初始化 `departed` 生命周期并由专业域吸收后续事实。

规范批量链路：下载标准模板 → 上传一个标准 `.xlsx` → 固定契约解析并原子保存原始证据和来源行 → 按 Shipment 业务号归组柜、单证和可选 SKU → 生成同一个 Shipment Handoff → 后续步骤与业务主链路一致。标准模板是提高批量效率的工具，不决定工作台布局和默认操作顺序。

兼容链路：任一旧四表上传 → 单文件原子保存 → 跨已到来源归组 → 生成同一 Shipment Handoff → 后续步骤与主链路一致。兼容 Adapter 不得反向决定标准模板字段，也不得建立独立落库规则。

## ⑤ 注意事项（坑）

- 别把 AI 建议当事实直接落业务表。
- 别跳过人工审核/预检硬闸当快捷方式。
- 别用主备货单号或箱号做唯一键（迟绑定/票级代表）。
- 别让 Excel Adapter、未来 packing Adapter 或人工入口各写一套 Shipment 落库逻辑。
- 状态文本列别静默吞成 not_shipped（老反例 A1）。
- 别把出运前或无法确认是否已出运的行混入当前列表。
- 同一记录多次导入=更新，别误建多行。
- 别在旧批次上原地重跑新解析器或覆盖旧建议；重新提供文件并创建带血缘的新批次。
- 别把对象键、bucket、endpoint 或存储凭据暴露给浏览器；下载/重解析必须由服务端鉴权后读取。
- 别把同备货单多产品行当重复，也别在尚未支持产品明细时放行并静默丢弃第二行以后数据。
- 别把同一 Sheet 里的纵向货柜详情当成横向产品明细；先拆分数据区域，再分别按明确粒度导入。
- 别用状态、导入时刻或规则计算结果补造实际清关/卸柜/卸空时间。

## ⑥ 白话注解（🗣️）

🗣️ 业务人员首先处理的是已经出发的一票货，不是一个导入文件。系统内已有事实就直接接管，单票缺资料就先建档后补；只有批量数据确实来自文件时才打开导入工具。
