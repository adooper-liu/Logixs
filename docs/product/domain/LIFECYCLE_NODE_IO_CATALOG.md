### 1.1 过站（释义备注）

本表「过站」= 状态机里的**完成当前节点**，不是口头上的「走进下一站」。权威仍是 [GC-002](./CONTAINER_LIFECYCLE_STATE_MACHINE_CONTRACT_V1.md)：当前流程在不在跑、现在停在哪一站、这条事实能不能完成本站、完成本站后能不能打开下一站。术语表见 [GLOSSARY](../GLOSSARY.md)「过站」。

日常可以这么记：

1. **过站 = 本站从「进行中」变成「已完成」。** 要有核验过的实际发生记录。计划、ETA、最晚提柜日、点按钮、同步成功、工单做完，都不能单独过站。
2. **过站成功后，下一站会被打开。** 同一笔事务里：完成本站 → 跳过不适用的可选站（中转港、海铁）→ 激活下一站。货柜同一时刻只有一个当前站。
3. **过站不等于货柜大状态翻页。** 14 站和 8 个粗状态不是一对一。例如送仓过了，货柜仍可能是「已提柜」；卸柜过了才变成「已卸柜」。
4. **还箱过站后没有下一站。** 主管道走完，整条流程结束。
5. **「有资格过站」还不是已经过站。** 填空表里的出站事件只是候选；地点不对、放行不齐、被阻断，本站就还停着。

口语上「过了这一站」≈「可以进下一站」；精确说法是 **先完成本站，再打开下一站**。

## 2. 所有实际过站共用的信封（正式 V1）

实际（`timeKind = actual`）且要申请过站时，至少带：

| 栏 | 必填 | 口径 |
| -- | ---- | ---- |
| 发生时间 `occurredAt` | 是 | 业务真正发生的时刻；UTC / ISO 8601。不是点按钮的时间 |
| 记下时间 `recordedAt` | 是 | 系统第一次记下 |
| 时间种类 `timeKind` | 是 | 计划 / 预计 / 实际分槽，不能拿 ETA 冒充实际 |
| 来源 `source` | 是 | 传输方 ≠ 权威方（港区、船司、海关、WMS…） |
| 合格证据 `evidenceRefs` | 实际至少 1 条 | 同租户、同货柜、已核验、仍有效 |
| 专业事实 `domainFactId` + 类型 | 是 | 由该站所有者模块形成，工单完成不等于专业事实 |
| 地点 `location` | 否，行业规划要逐步补 | 起始地 / 起运港 / 中转港 / 目的港 / 目的地 |

计划、预计可以没有证据；**不能过站**。预约成功、同步成功、司机点一下，都不是过站。

现网缺口：装箱/出运/离港完成工单时，发生时间用服务器当前时刻；证据不区分种类；专业事实载荷（重量、封号、ATA…）未按站采集。作业台尚未按站采集下方锁定的计划/实际/ETA/最晚日。

## 2.1 到港与内陆五站必须具备的时间（本批锁定）

负责人要求：到港、提柜、送仓、卸柜、还箱要有计划时间和实际时间；同时要有最晚提柜日、最晚还箱日；ETA 也要有。  
这些是填空表**必有槽**，不是过站事件本身。作业台现在多数还没采，标「缺口」；**不得**拿按钮时间、ETA 或最晚日去冒充实际，也不得没有数据时在界面编造截止。

| 槽 | 屏幕名 | 种类 | 挂哪站 | 过站？ | 权威 |
| -- | ------ | ---- | ------ | ------ | ---- |
| 计划到港 | 计划到港 | `planned`（STA） | 到港 | 否 | [GC-004](./CONTAINER_LIFECYCLE_TIMELINE_CONTRACT_V1.md) §5 |
| 预计到港 | ETA | `estimated` | 海运滚动 + 到港当前预计 | 否 | 同上；新 ETA 用 `supersedes_estimate` |
| 实际到港 | 实际到港 | `actual`（ATA） | 到港 | 核验后是 | 同上；AIS/ETA 不能替代 |
| 计划提柜 | 计划提柜 | `planned` | 提柜 | 否 | 时间种类正式；字段名见 [NODE_TIME_FIELDS](./NODE_TIME_FIELDS.md) 候选 |
| 实际提柜 | 实际提柜 | `actual` | 提柜 | 核验后是 | 完成资格 `gate_out` |
| 最晚提柜日 | 最晚提柜日 | 计算截止日，不是发生记录 | 提柜对照 | 否 | [FEE_DEMURRAGE](./FEE_DEMURRAGE.md)；`charges-settlement` 算、`inland-fulfillment` 只读 |
| 计划送仓 | 计划送仓 | `planned` | 送仓 | 否 | 候选字段 `delivery_plan` |
| 实际送仓 | 实际送仓 | `actual` | 送仓 | 核验后是 | `delivered` / 权威 `warehouse_arrival` |
| 计划卸柜 | 计划卸柜 | `planned` | 卸柜 | 否 | 候选字段 `unload_plan` |
| 实际卸柜 | 实际卸柜 | `actual` | 卸柜 | 核验后是 | `unloaded` |
| 计划还箱 | 计划还箱 | `planned` | 还箱 | 否 | 候选字段 `return_plan` |
| 实际还箱 | 实际还箱 | `actual` | 还箱 | 核验后是 | `returned_empty` |
| 最晚还箱日 | 最晚还箱日 | 计算截止日，不是发生记录 | 还箱对照 | 否 | 同最晚提柜日 |

四条不得混：

1. **计划**是排期/预约（STA、约提、约仓、约卸、约还）。
2. **ETA** 只表示**预计抵达目的港**（海运在途滚动；到港站展示当前版本）。送仓的预计到仓可以另有预计槽，**不叫 ETA**。
3. **实际**才可能过站。
4. **最晚提柜日 / 最晚还箱日**来自超期费用标准算出的 Last Free Day，不是计划提柜/还箱。缺标准必须显式失败，禁止套默认 7 天。D&D 同时约束提柜与还箱；多条命中取各类型 LFD 的最小值。

## 7. 升格门禁（避免把规划写成法律）

一行要从 `C` 变成正式，必须同时：

1. 能指到 GC-001/003/004/005/006 的修改或已有条款；
2. 有可追踪样本（真实任务/回执/EIR/舱单，见 NODE_PDCA §⑦）；
3. 不增加第 15 个流程节点；
4. 字段进契约后再进 Seed/API，禁止作业壳先造第二套表。

下一步实现顺序建议：装箱定稿字段（重量/件数/封号/箱号）→ **§2.1 五站计划/实际 + ETA + 最晚提柜日/还箱日上表（发生时间可填，无数据不编造）** → 证据种类 → 其余站专业事实端口。仍须单独开任务，不在本目录直接改运行时。最晚日计算落 `charges-settlement`，内陆计划只读，禁止作业壳自算免费期。
