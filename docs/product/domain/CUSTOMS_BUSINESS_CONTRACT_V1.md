# 海关业务契约定稿包 V1

> 状态：业务契约 V1（实现前基线）  
> 定稿日期：2026-09-09  
> 适用范围：14 节点主链中的海关工序，以及相关任务、工单、证据和外部同步  
> 不包含：未经官网核验的供应商裸码、数据库/API 实例化、其余运营环节设计

## 1. 目标与事实链

本文把 12 份真实脱敏样本中可重复验证的事实升格为海关工序 V1 契约。实现必须保持两条链路独立且可关联：

```text
外部/人工证据 -> 规范化观察 -> 海关案卷裁决
  |                    |
  +-> 工单事实回填 -----+-> 内部规范事件 -> 主流程转移守卫

进入海关节点 -> 海关工序子任务 -> 一至多个作业工单
-> 工单聚合作业状态
```

两条链路可以按真实发生顺序交错。工单是作业执行记录，证据是工单推进及业务裁决的事实依据。经验证且与工单要求匹配的外部权威证据，可以自动回填工单状态、业务日期和结果，并触发工单及子任务聚合；人工后补录表达同一业务事实，具有相同的推进语义，只是采集来源不同。权威放行先到时，主流程和匹配工单可以分别依据同一事实推进；无法自动关联时才创建或重开补录/对账工单。

本文使用“必须”“不得”表示 V1 强制规则；“候选”不得进入开发契约。

## 2. 权威边界

发生冲突时依次采用：

1. 海关或监管机构签发且可验证的正式证据。
2. 飞驼等供应商官网当前版本 API 契约及对应原始响应。
3. 企业保存的原始业务单据、回执和人工核验记录。
4. 本系统生成的规范事件与状态投影。
5. 文件名、界面文案、备注和人工口述。

现有权威关系：

- 事件语义码以 [EVENT_CODES](./EVENT_CODES.md) 为唯一权威，本文不复制另一套枚举。
- 主流程节点、状态与转换守卫以[货柜生命周期状态机契约 V1](./CONTAINER_LIFECYCLE_STATE_MACHINE_CONTRACT_V1.md)为唯一权威；海关只形成清关专业事实。
- 模块边界及“外部事实先到”规则以 [CUSTOMS_RELEASE_VERTICAL_SLICE](./CUSTOMS_RELEASE_VERTICAL_SLICE.md) 为实现基线。
- [FIVE_PARTY_CODES](./FIVE_PARTY_CODES.md) 仍为候选；裸码未经官网按接口、版本和上下文核验不得升格。
- 本文定稿业务前置条件、证据、聚合和异常顺序；正式 DTO、OpenAPI 和 Schema 后续从公共契约派生。

## 3. 模块所有权

采用模块化单体和限界上下文，不新增微服务。

| 模块 | 拥有 | 不得负责 |
| --- | --- | --- |
| `shipment-registry` | 货柜身份与业务关联 | 海关裁决、流程转移 |
| `lifecycle-control` | 流程实例、节点位置、守卫和历史 | 工单执行、解释供应商码 |
| `work-execution` | 子任务、工单、分派和作业聚合 | 海关裁决、直接修改主流程 |
| `customs-compliance` | 海关案卷、操作、回执、证据和裁决 | 直接修改主流程 |
| Integration Adapter | 原始请求/响应、供应商映射、同步结果 | 绕过领域规则推进节点 |

依赖方向固定为：

```text
UI / Transport -> Application -> Domain <- Infrastructure
```

跨模块只通过正式公共命令、查询和事件交互。

## 4. 核心对象与基数

| 对象 | 定义 | 标识 |
| --- | --- | --- |
| 货柜主任务 | 一只货柜在主链上的业务执行实例 | `containerTaskId` |
| 流程节点实例 | 货柜进入海关节点的一次停留 | `nodeInstanceId` |
| 海关子任务 | 节点触发的海关工序执行实例 | `nodeTaskId` |
| 报关案卷 | 按管辖区、方向和申报引用区分的裁决单元 | `customsCaseId` |
| 作业工单 | 可分派、可重开、可审计的操作单元 | `workOrderId` |
| 客户操作 | 一次申报、查询或补料请求 | `operationId` |
| 外部回执 | 客户操作的阶段性或终态响应 | `receiptId` |
| 证据 | 支持业务事实的不可变记录 | `evidenceId` |
| 规范事件 | 经规则验真的内部事实 | `eventId` |

一个海关子任务包含一个或多个案卷和零至多个工单；一个案卷可以包含多次操作、多个阶段回执和多条证据。货柜、提单和案卷不是同一聚合层级，单票结果不得覆盖整柜。

## 5. 四类状态必须分离

### 5.1 主流程

主流程状态沿用生命周期权威状态机。进入海关节点时触发子任务；只有有效规范事件通过转移守卫才可推进主链。`WorkOrder`、`NodeTask`、Adapter 和 UI 均不得直接修改流程实例。

### 5.2 海关子任务

```text
pending -> in_progress -> completed
               |          -> reopened
               -> blocked
               -> cancelled
```

- `pending`：已创建，尚无作业开始。
- `in_progress`：存在执行中或待补录/对账作业。
- `blocked`：作业被退单、资料缺失或外部异常阻断。
- `completed`：本次内部作业已闭环。
- `reopened`：完成后因新事实产生补录、复核或纠错。
- `cancelled`：经授权取消，不表示海关放行。

子任务完成描述内部作业，不是主流程推进的硬前提。

### 5.3 作业工单

具体枚举由 `work-execution` 单一权威状态机定义。V1 锁定：

- 工单可创建、分派、开始、完成、失败、取消和重开。
- 工单状态既可以由授权人员操作推进，也可以由已验真并与该工单规则匹配的外部权威证据推进。
- 外部证据可以回填工单的实际业务日期、外部引用、结果和证据关联；回填必须经过 Application 用例和工单状态机，不得由 Adapter 直接写工单终态。
- 人工后补录与外部证据自动回填具有相同业务语义，必须使用同一命令/规则完成校验与聚合；两者只在 `captureSource`、操作者和审计轨迹上不同。
- 同一外部事实随后被人工补录时必须幂等合并，不得重复完成工单、重复聚合子任务或重复发布事件。
- 业务日期取证据的实际发生时间；补录时间仅记为系统记录时间，不得覆盖实际发生时间。
- 工单完成表示其定义的作业完成条件已经由事实满足；是否同时代表海关受理或放行，取决于该工单类型明确绑定的证据规则，不得从通用“完成”状态反向推导。
- 多工单聚合只改变子任务，不直接修改流程实例。

### 5.4 数据同步

同步状态独立描述待处理、处理中、成功、重试、失败、死信和已补偿。发送成功不等于海关受理；同步成功不等于海关放行；超时、失败或 `NODATA` 不等于海关扣留；同步失败不得清空最后一次有效业务事实。

## 6. 海关案卷裁决

| 语义 | 定义 | 构成案卷放行 |
| --- | --- | --- |
| 未申报 | 尚无有效申报事实 | 否 |
| 已申报 | 已提交舱单或申报 | 否 |
| 处理中 | 海关处理中，尚无终态 | 否 |
| 查验 | 进入查验流程 | 否 |
| 扣留 | 存在有效海关扣留事实 | 否 |
| 退单 | 被退回、拒绝或需要重报 | 否 |
| 放行 | 取得适用于本案卷的有效放行事实 | 是 |
| 取消/作废 | 案卷依法取消或作废 | 仅在不再属于必需案卷时 |

`hold_released` 是扣留解除事件，不是放行同义词。解除后必须依据后续证据重新裁决。

## 7. 内部事件契约

海关范围复用 `EVENT_CODES` 的唯一语义：`customs_filed`、`inspection`、`hold`、`hold_released`、`release`、`container_customs_completed`。前五类表达案卷/主体事实；`container_customs_completed` 是全部必需案卷聚合后的货柜级清关完成事实。不得按国家、方向或供应商另建平行事件码；差异进入上下文。

每个规范事件必须包含：

```text
eventId, eventType, eventVersion, aggregateType, aggregateId,
occurredAt, recordedAt, correlationId, causationId, idempotencyKey,
source, evidenceRefs[],
context.jurisdiction, context.direction, context.subject,
context.customsCaseId（案卷事件）, context.containerId；货柜级聚合事件改携带 data.requiredCaseIds
```

`direction` 为 `import | export`；`subject` 至少区分 `customs | carrier | terminal | maritime | freight`。

## 8. 证据等级

| 等级 | 定义 | 示例 | 单独支持海关放行 |
| --- | --- | --- | --- |
| A | 监管机构签发且可验证的正式结果 | Levante、海关审核放行通知、适用的 CDS 结果 | 可以，须校验适用性 |
| B | 授权供应商返回的权威主体状态 | 经官网契约核验的海关主体放行响应 | 可以，须保留原文和映射版本 |
| C | 支撑性业务单据 | 7501、ISF、H1、发票、装箱单、HTS、商检资料 | 不可以 |
| D | 内部操作记录 | 议付审核、附件齐全、EBS 同步、人工备注 | 不可以 |

证据适用性必须同时验证：

```text
案卷身份 + 管辖区 + 进出口方向 + 监管主体
+ 业务引用 + 时间有效性 + 完整性 + 未撤销/未被更强证据更正
```

文件名和 UI 标签不能覆盖正文类型。Commercial Invoice、费用支付、附件齐全、内部审核或同步成功均不得推导为海关放行。

## 9. 飞驼及第三方映射

供应商状态必须在 Adapter 中按以下复合键转换：

```text
provider + apiVersion + interfaceCode + jurisdiction
+ direction + subject + rawStatusCode
```

原始观察至少保留：

```text
provider, apiVersion, interfaceCode, jurisdiction, direction,
subject, rawStatusCode, rawStatusText, sourceEventId,
businessReference, occurredAt, providerUpdatedAt, receivedAt,
payloadHash, rawPayloadReference, mappingVersion
```

未知组合必须明确失败或进入人工映射队列。已核验组合及适用条件以 [飞驼官网海关接口证据索引与复合映射表 V1](../../integrations/freightower/CUSTOMS_EVIDENCE_MAPPING_V1.md) 为供应商映射基线；未列入批准表的 `RELS`、`CES`、`NODATA` 等裸码及缺少限定字段的组合仍为候选，不得自动推进工单、案卷或主流程。

## 10. 一柜多票聚合

单案卷放行条件：

```text
存在适用于该 customsCaseId 的有效 A/B 级放行证据
AND 不存在时间上更新且仍有效的海关 hold / inspection / reject
AND 证据未撤销、未过期且映射版本已批准
```

货柜级海关完成事实：

```text
requiredCases 非空
AND requiredCases 中每个案卷均已形成有效 release
AND 不存在案卷集合冲突或有效海关阻断
```

单票放行只更新对应案卷。一柜多票必须逐票关联、逐票验真；附件数量、金额或 SKU 聚合不得替代案卷集合。必需案卷集合变更必须授权、审计并进行乐观并发校验。

## 11. 主流程与提柜守卫

主流程从海关节点转移，必须由货柜级有效海关完成事实触发：

| 场景 | 行为 |
| --- | --- |
| 工单先完成、无权威放行 | 子任务可完成，主流程停留海关节点 |
| 权威放行先到、工单未完成 | 验真后主流程推进；同一事实自动回填并推进匹配工单，无法关联或字段不足时才创建/重开对账工单 |
| 重复放行 | 幂等命中，只转移一次 |
| 旧的非放行回执迟到 | 保存观察，不回退有效放行 |
| 更新扣留或撤销证据到达 | 进入异常复核并告警，不改写历史 |

“海关放行”和“可提柜”必须分离：

```text
pickupEntryEligible = customsReleaseSatisfied
  AND carrierReleaseSatisfied
  AND terminalReleaseSatisfied
  AND freightOrCreditConditionSatisfied
  AND noActiveOperationalBlock
```

船司、码头和费用条件由各自上下文拥有。海关模块只消费公开判定结果。

## 12. 幂等、乱序与更正

幂等键优先级：

1. `provider + apiVersion + sourceEventId`。
2. 无事件 ID 时使用复合业务引用、原始状态、发生时间和载荷哈希。
3. 用户写操作使用租户、动作和 `Idempotency-Key`，同时保存请求哈希。

同一键同一内容返回原结果；同一键不同内容明确冲突。所有合法观察先去重再不可变保存，投影按发生时间、证据等级、适用性和更正关系重算，不按接收顺序覆盖。

必须分别保存 `occurredAt`、`providerUpdatedAt`、`receivedAt`、`recordedAt`。时间以 UTC 存储、ISO 8601 交换；不得用接收时间覆盖实际放行时间。

## 13. 同步失败与补偿

- 外部调用必须有超时、有限重试、指数退避和抖动。
- 只对明确可重试错误自动重试；认证、参数和业务拒绝不得无限重试。
- 重试耗尽进入死信，并创建告警或补偿工单。
- 重放沿用原幂等语义，不得产生重复规范事件。
- 人工补偿记录原因、操作者、原请求、结果和追踪 ID。
- 界面同时展示最近有效事实、数据新鲜度和同步异常。

这些是本项目可靠性规则，不由飞驼业务码定义。

## 14. 公共字段与错误语义基线

本文不手工建立第二套 DTO 权威，只规定正式契约必须承载：

- 外部观察：供应商、版本、接口、管辖区、方向、主体、原始码、业务引用、三类外部时间、载荷哈希、原文引用和映射版本。
- 证据登记：案卷、证据类型/等级、来源、范围、签发时间、内容哈希、受控存储引用和幂等键。
- 任务投影：货柜/节点/任务标识、作业状态、案卷统计、阻断、海关放行结果、提柜准入、操作状态、同步状态、版本和更新时间。

稳定错误语义至少覆盖：案卷不存在、非法转移、必需案卷缺失、放行证据缺失、证据范围不匹配、有效阻断、幂等冲突、版本冲突、未知外部映射、无效外部载荷和需要人工复核。

具体枚举、字段可空性和错误码字符串必须在正式公共包一次定义并通过 parity 检查。数据库实体、领域对象和 DTO 必须显式映射。

## 15. 前端操作台契约

操作台必须显示：

- 当前节点、海关事实状态、内部作业状态和提柜准入结果。
- 必需案卷总数、逐票状态、证据和阻断原因。
- 工单负责人、截止时间、失败、重开和补录状态，以及状态/日期来自外部证据还是人工录入。
- 海关、船司、码头、海事、运费主体分栏。
- 请求、服务器接收、业务受理、终态回执和落账时间线。
- 事实发生时间、接收时间、来源、新鲜度和同步异常。
- 受权的证据原件、重试/补偿入口和审计轨迹。

前端不得根据按钮点击、附件上传或同步成功推导领域状态。外部权威证据驱动的工单推进由后端统一用例完成，并在工单上显示来源证据、实际发生时间和系统记录时间。允许动作、权限和阻断原因由后端返回。

## 16. 12 份样本验收矩阵

| 样本 | 必须保持的结论 |
| --- | --- |
| 001 | ISF、海运单、发票和装箱单不能单独证明放行 |
| 002 | HTS、估价和最终用途证明只是支撑证据 |
| 003 | CBP Form 7501 不得映射为放行 |
| 004 | 意大利 H1 与关税借记是不同业务事实 |
| 005 | DUA/Levante 必须按案卷和适用性验证 |
| 006 | CDS 清关结果保留管辖区、方向和原始证据 |
| 007 | 中国出口分票和 SKU 聚合不得丢失逐票边界 |
| 008 | `SRM/TML Hold` 按主体隔离，不统一解释为海关扣留 |
| 009 | 船司部分结果和 `NODATA` 不得推导放行 |
| 010 | 商检、工厂装箱和箱况资料不得完成海关放行 |
| 011 | 八国单据需求矩阵是规则输入，不是运行时事实 |
| 012 | 双案卷逐票放行；全部必需案卷放行后才形成货柜级完成事实 |

实施还必须覆盖正常、多票、外部放行先到、重复、乱序、撤销/新扣留、同步超时、重试耗尽、死信重放、人工补偿、幂等冲突、并发冲突和联合守卫不通过。必须增加“外部证据自动完成工单”与“人工后补录同一事实”对拍：两条路径得到相同业务状态、业务日期和聚合结果，但保留不同采集来源，且组合执行只产生一次有效状态推进。

## 17. 排除项与实施准入

V1 不定稿：

- 未列入飞驼官网证据映射 V1 批准表的裸状态码和版本漂移结论。
- 船司、码头、海事、费用上下文内部状态机。
- 全部 22 个运营环节的工单模板和异常分支。
- 各国全部监管例外。
- 数据库、OpenAPI、JSON Schema 和跨语言类型实例。

后续顺序固定为：

```text
正式公共契约与 schema -> 数据库迁移 -> Domain
-> Application -> API 与 Port/Adapter -> 操作台 -> 样本回放与 E2E
```

进入编码前必须：

1. 负责人确认本文相对候选文档的升格范围。
2. 从飞驼官网建立接口证据索引和批准后的复合映射表。
3. 在正式公共包中一次定义 DTO、事件信封、状态及错误码。
4. 完成 schema、约束、迁移、权限、人工复核和敏感证据访问设计。
5. 释放当前唯一活动任务槽位后，派生唯一海关纵向切片任务 brief。

本文不修改当前活动任务状态，不授权代码、数据库或外部系统变更。

公共契约的枚举、字段、事件版本、错误码和 JSON Schema 对照已在 [海关公共契约实例化设计 V1](./CUSTOMS_PUBLIC_CONTRACT_DESIGN_V1.md) 定稿；实现仍须遵守唯一活动任务门禁。
