> 状态：**设计决策 v1.1** · 2026-09-22
>
> 消费者：产品设计、Web 开发、测试与代码评审。
>
> 边界：本文是视觉壳、设计令牌、组件和交互标准；业务信息架构以
> [PRINCIPLES](./PRINCIPLES.md) 与
> [角色工作台以人为中心的设计契约](./ROLE_WORKBENCH_HUMAN_CENTERED_DESIGN.md)、

## 1. 结论

Logix 采用一套面向物流运营的 **Operations Shell**：

- 结构借鉴 Tabler：稳定侧栏、紧凑顶栏、页头、工具栏和高密度内容区。
- 交互采用折叠导航、移动抽屉、命令面板、主题令牌和明确焦点反馈。
- 管理视图选择性借鉴 Notika：指标带、趋势与异常摘要的扫描节奏。
- 视觉语言保持 Logix 自有：冷灰作业底、港口青绿色品牌、克制边框、低阴影，以货柜时序、
  三状态和异常行动作为第一视觉信号。

模板只作为 R 级参考。工作区内的 `adminator/` 是可随时删除的一次性调研材料，不属于项目源码、
依赖、主题实现或交付物；删除它不得影响安装、开发、构建、测试和运行。禁止复制其 CSS、
JavaScript、HTML、字体或图像资产；实现继续使用 Vue 3、Element Plus 和项目自有领域组件，
避免许可证、供应链和样式耦合风险。

## 3. 设计原则

| 编号   | 决策         | 约束                                                                                                      |
| ------ | ------------ | --------------------------------------------------------------------------------------------------------- |
| UI-D01 | 作业优先     | 现场员工默认进入任务台；管理 KPI 不进入员工首屏。                                                         |
| UI-D02 | 对象不断线   | 页面始终保留货柜、任务、节点上下文，跨页不让用户重新识别对象。                                            |
| UI-D03 | 状态可解释   | 颜色只增强语义；状态必须同时有文字、图标或形态，且可查看时间和证据。                                      |
| UI-D04 | 密度分角色   | 作业与计划视图高密度，管理视图中密度；不使用营销式 hero 和装饰性大卡。                                    |
| UI-D05 | 单事实多投影 | 七组 SOP 不生成七套 UI；任务、计划、管理视图复用同一事实和领域组件。                                      |
| UI-D06 | 逐层披露     | 首屏回答“在哪、做什么、是否落账、哪里异常”，明细通过抽屉、展开或下钻呈现。                                |
| UI-D07 | 壳层稳定     | 导航、页头和内容布局只由壳层组件控制，业务页面不得复制侧栏或顶栏。                                        |
| UI-D08 | 可验证       | 新页面至少覆盖桌面、窄桌面和移动端结构断言；关键路径增加视觉回归。                                        |
| UI-D09 | 表面用人话   | 页面、表格、按钮用现场能说出口的词；格式为「动作」或「动作+对象」或「对象」。契约、模块、投影名不准上屏。 |
| UI-D10 | 人的结果优先 | 工作台先按岗位结果和真实操作顺序组织“原因→事实/缺口→动作→结果”；不得从表、接口、状态或技术实体倒推页面。  |

### 3.1 表面命名

屏幕上的名字只服务操作者。API、表名、契约 ID、状态机码留在接口和文档里。

| 形式      | 何时用                           | 例                       |
| --------- | -------------------------------- | ------------------------ |
| 动作      | 同一对象因下一步不同而拆成两张表 | 干活、看档               |
| 动作+对象 | 动作或对象单独会混               | 看提交、看失败、导入货柜 |
| 对象      | 这一页没有第二种动作             | 我的任务、货柜、一柜一档 |

约束：

1. 侧栏、页题、表格名称必须是同一个词，禁止「侧栏叫流转、表头叫状态链」。
2. 列表因动作不同而分开时，用动作当表名，不用业务阶段名（已出运、First Mile）或方法名（PDCA、投影）。
3. 按钮与页名动词一致：进干活表是去任务，进看档表是开档案。
4. 空态也用人话（还没有货柜 / 这一范围还没有待办），不写无投影、规范事件、死信。
5. 领域口径「已出运货柜列表」仍可出现在 PRINCIPLES / 导入文档，不作为屏幕表名。

当前作业壳用名：

| 路径               | 表面用名 | 形式      | 不做的叫法                |
| ------------------ | -------- | --------- | ------------------------- |
| `/tasks`           | 我的任务 | 对象      | 现场作业、任务工作台      |
| `/containers`      | 干活     | 动作      | 已出运货柜、货柜名单      |
| `/meso`            | 看档     | 动作      | 货柜流转、PDCA、中观      |
| `/container/:id`   | 一柜一档 | 对象      | 货柜全生命周期            |
| `/dashboard`       | 货柜     | 对象      | 运营态势、管理驾驶舱      |
| `/real-operations` | 看提交   | 动作+对象 | 同步操作、ClientOperation |
| `/dead-letters`    | 看失败   | 动作+对象 | 死信队列                  |
| `/import`          | 导入货柜 | 动作+对象 | P6 智能导入               |

    │              ├────────────────────────────────────────────────────────────┤
    │ 角色主导航   │ 页名 + 当前上下文 + 主动作                                │
    │              ├────────────────────────────────────────────────────────────┤

    │              ├────────────────────────────────────────────────────────────┤
    │              │ 页面内容：列表、主从工作台、对象档案或管理投影            │
    │ 用户 / 环境  │                                                            │

### 4.2 壳层区域

| 区域             | 必须内容                                                       | 禁止                                         |
| ---------------- | -------------------------------------------------------------- | -------------------------------------------- |
| AppSidebar       | 品牌、按权限生成的主导航、当前工作区、用户入口                 | 在前端用角色数组充当服务端授权；超过两层菜单 |
| AppTopbar        | 面包屑/对象身份、命令入口、异常/通知、连接或队列健康、用户菜单 | 重复页面标题；放业务表单                     |
| PageHeader       | 页名、当前范围、更新时间、一个主动作和少量次动作               | 营销文案、大面积空白、四个以上同级按钮       |
| ObjectContextBar | 货柜、任务、节点与三状态摘要；仅对象页出现                     | 把计划值伪装成实际状态                       |
| AppContent       | 页面模板插槽和统一滚动容器                                     | 页面自行创建第二套全屏滚动                   |
| MobileActionDock | 当前任务的主动作、异常入口；仅移动作业场景                     | 管理筛选器和低频动作                         |

生产环境的角色和权限来自认证会话与服务端授权；当前“角色切换”仅是演示工具，必须有明确的
demo 标识，不能演进成权限机制。

### 4.3 尺寸与响应式

| 视口       | 侧栏                 | 顶栏 | 内容边距 | 页面策略                              |
| ---------- | -------------------- | ---- | -------- | ------------------------------------- |
| >=1280px   | 232px 展开           | 56px | 24px     | 高密度双栏/三栏；运营表格占满可用宽度 |
| 960-1279px | 64px folded          | 56px | 20px     | 图标导航配 tooltip；次要侧区转抽屉    |
| 768-959px  | 280px overlay drawer | 52px | 16px     | 主从视图保留一列，详情进抽屉或路由    |
| <768px     | overlay drawer       | 48px | 12px     | 单列；44px 触控目标；主动作固定底部   |

- 壳层使用 100dvh，主体只有一个受控滚动容器。
- 表格、轨道、工具栏和按钮必须有稳定尺寸，加载、hover 和状态变化不得推动布局。
- 运营页不套固定 container-xl；只对设置页、空状态等低密度内容设置最大宽度。
- 移动端不能简单把桌面侧栏堆到内容上方，也不能依赖横向滚动完成主要作业。

## 5. 页面模板

| 模板                       | 适用                         | 默认结构                                                    | 第一问题               |
| -------------------------- | ---------------------------- | ----------------------------------------------------------- | ---------------------- |
| TaskWorkspaceLayout        | 现场任务、人工复核           | 待办队列 320-336px + 当前任务弹性区；移动端队列与详情分路由 | 我现在要做什么？       |
| ObjectRecordLayout         | 一柜一档、节点档案           | 对象头 + 三状态 + 生命周期 rail + 当前节点事实/证据         | 柜子实际走到哪？       |
| PlanBoardLayout            | 月/周/日计划、资源分配       | sticky toolbar + 表格/时间板 + 偏差侧栏                     | 计划是什么，哪里偏差？ |
| ManagementProjectionLayout | 进度、风险、费用、绩效、会议 | 信号带 + 生命周期扫描 + 决策队列 + 计划/资源/闭环分析       | 堵在哪里，决定什么？   |

TaskWorkspaceLayout 的待办队列是独立工作区：使用单一外框明确队列边界，标题固定在框内顶部，任务与自动监控位于同一个纵向滚动区。桌面双栏下队列高度不得随任务数无限增长；大量任务由服务端分页或窗口化投影提供，滚动只解决当前批次浏览。移动端队列与详情分屏，继续使用应用主体滚动，禁止再嵌套一个争抢触控手势的滚动区。

### 5.1 角色工作台的因果结构

所有角色工作台统一遵守[角色工作台以人为中心的设计契约](./ROLE_WORKBENCH_HUMAN_CENTERED_DESIGN.md)
`HW-D01`～`HW-D10`。设计顺序固定为“岗位结果 → 实际流程 → 所需信息 → 允许动作 → 可靠结果 → 界面结构”，禁止从数据库表、接口返回或状态枚举直接生成卡片。

| 宽屏信息责任 | 回答的问题                                   | 约束                                                             |
| ------------ | -------------------------------------------- | ---------------------------------------------------------------- |
| 待办/等待    | 为什么现在需要关注，谁负责，期限是什么       | 用业务原因和岗位语言组织；系统监控与等待他人不冒充待我点击的步骤 |
| 事实/缺口    | 当前业务对象是什么，已知什么，真正缺什么     | 单一选择源；正常项汇总；只展开未知、冲突、失效或缺失             |
| 动作/结果    | 现在允许做什么，完成标准是什么，是否可靠落账 | 只消费服务端允许动作；一个主动作；拒绝、冲突和失败有恢复路径     |

三项是因果关系，不要求实现成三张卡片或固定三列。两栏、抽屉和移动分屏都必须保持“为什么处理 → 事实与缺口 → 当前动作 → 结果反馈”的顺序，不得各自保存选择状态。业务对象可以早于后续技术实体存在；例如备货工作可以在货柜创建前开始，因此后续对象不得成为无业务依据的入口前置。

页面区块是全宽 band、表格或主从 pane。卡片仅用于独立、可重复对象或真正需要边界的工具；
禁止页面 section 全部浮成卡片，也禁止卡片嵌卡片。

管理驾驶舱只消费“节点聚合 + 有界重点对象”投影；节点数量用于全局态势，货柜明细按风险优先且限制
首屏数量。禁止为每条数据库记录生成一条常驻轨道，也禁止用前端接收全量记录后冒充分页或聚合。

生命周期扫描必须让时序关系先于表格边界被看见：稳定编号节点用连续主线串联，每个重点货柜用独立
进度段连接起点与当前事实节点。编号和节点名在桌面端必须直接可读；颜色只表达当前货柜的业务语义，
进度段不得暗示尚未发生的计划节点已经完成。移动端隐藏密集总轴时，仍须保留当前节点事实文字。

一柜一档使用“货柜身份 → 货柜事实/任务状态/相关同步 → 生命周期定位 → 当前节点事实 → 下一步动作
→ 事件时间证据”的物流事实主轴。当前节点必须显示稳定序号和节点总数，计划、预计、实际、来源、
接入渠道和业务证据保持可区分；普通节点字段可使用 schema 驱动的 `signal` 投影增强扫描，但不得在
页面模板硬编码数据库字段。事件历史使用有顺序的事实时间轴，已发生与待发生同时用文字和形态区分，
窄屏不得因单行布局截断证据。同步为空闲态时不占醒目空间，存在待确认、失败或最近落账操作时才恢复。

驾驶舱顶部只保留少量、可直接驱动判断的关键运营信号。允许用语义色实底形成醒目分块，但
`brand / ok / warn / risk / info` 必须继续表达既有业务含义。指标卡默认只显示标签、数值、业务解释
和下钻入口；没有明确比较维度、刻度或直接决策价值时，不得附加迷你图、趋势线或装饰图形。七组 SOP
由流程、决策、费用、资源和改善区共同覆盖，不机械映射成七张指标卡；轻微阴影只用于这类可重复
顶部信号，普通工作区仍以边框和分区头建立层级。

同一分析组中的计划与达成、资源负荷、闭环控制等并列工具必须使用独立边界，块间保留 12px 页面底色
作为结构留白；组标题不使用横跨三块的有底色外框。禁止用共享外边框和内部竖线把独立工具重新拼成
一张大表，也不额外添加阴影弥补层级。

计划与达成使用右上角“月 / 周 / 日”分段控件切换真实日历窗口，每格直接显示“完成 / 计划”。月视图
按 `Wxx` 周次展开，周视图按周一至周日展开，日视图按业务时段展开；列定义和分桶结果由服务端投影
提供，组件不得从总数自行拆分或臆造月份、周次、日期。各时间桶必须能与对应月、周、日汇总对账，
缺失桶显式报错而非静默留白。周期格只有在阈值和口径确认后才使用风险色，不能把节点整体风险色
机械复制到每个周期；当前周、当天或当前时段可使用品牌浅色辅助定位。

## 6. 分层执行状态与七组 SOP

### 6.1 分层执行状态的场景化投影

流程实例、工序任务、作业工单、数据同步和数据状态的**语义与关联键固定，视觉形态不固定**；权威关系引用 PRINCIPLES §1.1。当前 StatusTriplet 仅是 V1 的流程/任务/同步摘要，工单和数据状态必须在对应工作区呈现。

1. **货柜状态**：实际物流事实走到哪。
2. **任务状态**：责任人工作做到哪。
3. **同步状态**：本次操作是否完成请求接收、业务接受和事实落账。

| 场景          | 主状态                       | 辅助状态                       | 同步状态                                                     |
| ------------- | ---------------------------- | ------------------------------ | ------------------------------------------------------------ |
| 员工任务台    | 任务状态紧邻任务标题         | 货柜状态作为对象上下文紧凑显示 | 无操作时不占位；操作发生后在动作附近显示三段回执             |
| 一柜一档      | 货柜状态与生命周期事实       | 关联任务只显示当前待办或风险   | 只显示仍待确认、失败或最近一次已落账操作                     |
| 列表/管理投影 | 按用户问题决定列序和视觉主次 | 可将三状态作为独立列或筛选条件 | 必须指明最新操作范围，不能用“同步成功”代表任务完成或货柜推进 |

状态必须提供足以判断业务结论的文字；发生时间、来源、责任和结果引用按场景渐进披露。同步顺利且同事务完成时可直接显示“已落账”，详情仍保留三段回执，不播放无价值的中间动画。

执行方式是任务限定信息，不是第四种状态。默认人工任务不常驻显示“现场人工执行”；只有执行方式会改变权限、等待主体或员工操作时，才显示“需授权复核”“外部办理”“系统监控”或“人机协同”等限定。

货柜状态只提供作业上下文和合法性约束，员工实际执行的指令必须来自服务端授权任务/动作；任务状态表达进度，具体达成由结果与证据呈现。“操作记录”必须复述本次动作名称和最终结论，使“点了什么”与“系统记录了什么”可以直接核对；稳定动作码、操作编号和追踪引用按需查看，失败时保留追踪信息。

### 6.2 七组呈现

七组 SOP 只作完整性检查，具体呈现沿用
[UX_CONTAINER_WORKBENCH §1.6](./UX_CONTAINER_WORKBENCH.md)：

- 员工：任务上下文、前置、适用动作、必要资料/资源、证据、结果/异常、同步反馈。
- 计划员：能力与计划、执行偏差、当前事实、周期风险。
- 管理者：进度、预警、异常、风险、费用、绩效、改善与会议决议。

领取、物料、扫描、报工是可组合能力，不是固定步骤条。页面不得让员工理解七组分类后才能工作。

## 8. 组件体系

### 8.1 分层

    页面模板与业务视图
      -> 领域组件（业务语义）
        -> 稳定 UI 门面（公开契约）
          -> UI Theme Adapter
            -> LogixTheme / 后续主题实现
              -> Design tokens + Element Plus / Lucide 基础能力

- Element Plus 继续提供表单、弹窗、表格、分页等基础行为，并保持按需引入。
- 应用图标统一使用 Lucide Vue；禁止页面内手写 SVG。Element Plus 内部图标不作为业务图标源。
- 不为每个 Element 组件建立空壳包装；只有加入 Logix 语义、默认行为或可访问性约束时才封装。
- 高可视化图表统一预留 Apache ECharts 适配层，按页面懒加载；图表不得自行解释业务状态或
  复制 KPI 口径。

### 8.2 主题契约

主题采用显式、类型化的 `UiThemeAdapter`，并通过 `defineUiTheme` 固化组件定义，避免 Vue 将组件
深层代理；它不是加载任意 HTML/CSS/JavaScript 的插件系统。V1 只纳入已经证明需要替换的
`AppShell` 与 `PageHeader`，不预先包装全部基础组件：

```ts
interface UiThemeAdapter {
  readonly id: string;
  readonly components: {
    readonly appShell: Component;
    readonly pageHeader: Component;
  };
}
```

| 层                 | 可以负责                                                    | 不得负责                               |
| ------------------ | ----------------------------------------------------------- | -------------------------------------- |
| Theme tokens       | 色彩、排版、间距、圆角、阴影、层级、动效                    | 业务状态码、费用口径、时间计算         |
| AppShell           | 导航容器、顶栏、响应式布局、焦点与抽屉交互                  | 服务端权限、路由可达性判定、任务流转   |
| 展示模式组件       | 页头、工具栏、徽标等无业务判断的呈现                        | 从文案反推状态、合并货柜/任务/同步状态 |
| 领域组件与业务视图 | 三状态、生命周期、证据、异常、动作能力及七组 SOP 的角色投影 | 依赖主题私有 class、DOM 结构或模板资产 |

- `components/AppShell.vue` 与 `components/ui/PageHeader.vue` 是稳定门面；业务代码只能导入这些
  公开入口，不得直接导入 `themes/*`。
- `ui-theme/activeTheme.ts` 是唯一主题选择入口；`UiThemeProvider` 负责注入适配器和设置
  `data-ui-theme`，不保存业务状态。
- 每个主题拥有独立目录与作用域化 token；亮暗色是主题内配色模式，不与主题身份混为一谈。
- 新组件只有同时满足“无业务判断、存在真实替换需求、至少两个实现可用同一契约”时才进入
  `UiThemeAdapter`；否则留在通用模式层或领域层。
- 替换主题不得改变路由、权限投影、任务动作、三状态含义和数据字段。需要改变这些内容时，
  必须按产品/领域/契约变更评审，不得伪装成换肤。

### 8.3 主题接入门禁

1. 核验模板或依赖的许可证、来源、维护状态与供应链风险；未核验只能作为 R 级视觉参考。
2. 在独立主题目录用 Vue 3 重新实现已批准的视觉模式；禁止执行模板全局脚本或导入整包 CSS。
3. 通过稳定门面接入，并用第二个最小实现验证 props、slots 和主题标识的可替换性。
4. 对 1440x900、1024x768、390x844 执行布局与视觉回归，验证键盘、焦点、对比度和
   `prefers-reduced-motion`。
5. 只有契约测试、E2E、构建体积与完整 `validate` 通过后，才可成为可选或默认主题。

### 8.4 组件目录

| 层       | 组件                                                                                                                             |
| -------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 壳层     | AppShell、AppSidebar、AppTopbar、PageHeader、ObjectContextBar、MobileActionDock                                                  |
| 通用模式 | DataToolbar、FilterBar、MetricStrip、StateBadge、DynamicFieldPanel、DynamicDataTable、EmptyState、ErrorState                     |
| 领域     | StatusTriplet、LifecycleRail、NodeFactPanel、EventEvidenceTimeline、TaskQueue、SubmissionProgress、EvidencePanel、ExceptionPanel |
| 视图     | ContainerFlowTable、PlanVsActualTable、CycleTrend、CostBreakdown、ImprovementRegister                                            |

StateBadge 只负责视觉语义；业务状态到语义的映射必须来自一个适配器或公共契约，禁止各页面
复制 switch。StatusTriplet、生命周期和任务动作不得从显示文案反推状态。

### 8.5 动态字段纪律

`DynamicFieldPanel` 只消费本节定义的受控展示投影；业务事实、字段授权和裁剪遵守[查询投影契约 V1](./domain/QUERY_PROJECTION_CONTRACT_V1.md)，
用于货柜节点详情等普通只读标量区域。页面传入 `DisplayFieldSet` 和列数，不逐字段写模板；字段新增、
排序、分组和主次层级由展示 schema 决定。

`table` 投影适合逐项核对，`signal` 投影适合当前节点的少量关键事实。两者只改变视觉呈现，不改变
字段授权、来源权威、空值或格式错误语义；当主字段数量增长到无法快速扫描时，必须由展示 schema
重新划分主次字段，禁止靠继续缩小字号或无限增加列数容纳。

- 主字段直接显示，次字段进入“更多字段”，防止数据库字段增长重新造成信息过载。
- 组件负责受控类型格式化、空值、格式错误、响应式跨度和无障碍语义，不负责字段授权或业务推导。
- 未在 schema 中声明的值不渲染；schema 错误可见失败，不使用 `v-html`，不执行服务端下发的代码。
- 页面需要编辑、筛选、排序、聚合或动作时，使用对应表单/表格/领域组件，不能把
  `DynamicFieldPanel` 扩成低代码页面引擎。
- 三状态、生命周期、提交回执、动作、异常、证据和费用规则禁止动态字段化；这些元素的差异会改变
  业务结论，必须保留明确契约和专用交互。
- 产品扩展属性的编辑可以采用元数据驱动表单，但只消费服务端解析后的受控模板版本；强类型核心字段、
  合规专业档案、属性升格和提交契约统一引用[产品属性治理](./domain/PRODUCT_ATTRIBUTE_GOVERNANCE.md)。
- 合规中心和八个组织工作台的候选页面、14 节点映射及合规状态边界统一引用
  [跨境合规管理](./domain/COMPLIANCE_MANAGEMENT.md)；前端不得解释法规、发布规则或自行决定节点放行。

### 8.6 动态表格纪律

架构边界（接受控件化与注册数据集、拒绝 Studio 式选表/任意 JOIN）见
[ADR-011](../architecture/decisions/ADR-011-controlled-ui-projection.md)。

`DynamicDataTable` 消费服务端受控的 `schema + rows + pageInfo` 展示投影。业务页面只装配投影、
路由筛选和行级命令，不逐字段编写表头或单元格模板；列名、顺序、宽度、渲染类型、搜索、排序、
显隐、固定位置和快速筛选均由展示 schema 决定。

- 展示 schema 是 API 契约，不是数据库元数据；禁止浏览器直连数据库、直接返回数据库实体或把任意列
  自动暴露到页面。服务端必须先完成字段级授权、字段白名单和业务展示投影。
- 前端只实现有限、可审计的渲染器集合；服务端不能下发 HTML、脚本、表达式、组件名或任意样式。
- 未在 schema 中声明的行值不渲染；重复列、未知渲染器、非法分页等配置错误必须可见失败。
- 货柜、任务、同步三状态可由动态列决定位置和显隐策略，但值必须使用专用结构化状态类型，禁止从
  显示文字反推状态码、时间或语义色。
- 正式大数据列表采用服务端筛选、最大页大小、稳定排序和游标/窗口分页；前端 `client` 模式只用于
  小型演示或已明确有界的数据集，不得拉取百万级记录后本地过滤。
- 桌面使用语义化表格、吸顶表头和固定对象/操作列；窄屏允许表格容器内部横向滚动，但禁止造成
  页面级横向溢出。风险只用文字、语义色和窄标记增强，不整行染色。
- 高密度对象列表可使用受控 `entity` 渲染器，把一个主标识、最多三个关联标识和一个当前上下文组合为
  单一对象列；组合内容仍由展示 schema 与行投影提供，通用组件不得识别柜号、备货单或提单等业务字段名。
- 宽屏列序优先形成“对象 → 三状态 → 关键时间 → 风险 → 动作”的扫描路径，并通过 schema 声明分组边界；
  标准表头、排序和字段显隐不得为模仿卡片式列表而删除。移动端取消横向固定列，避免首尾固定列覆盖中间操作。

## 9. 交互标准

- 主动作使用明确动词，如“确认已领取”“提交卸柜结果”，不使用含糊的“确定”“提交”。
- 危险、不可逆或产生业务事实的动作必须显示对象、影响与幂等结果；是否二次确认由动作风险决定。
- 请求已接收不等于任务完成；成功消息必须与最终阶段一致。
- 异常入口与主动作同屏可达，但在视觉层级上次于正常主路径。
- 命令面板用于导航、查找货柜/任务和低风险动作；不得绕过权限、校验或二次确认。
- 加载使用骨架或局部 pending，不遮蔽整页；空状态说明下一步；错误状态提供恢复动作和追踪 ID。
- toast 只反馈短暂结果；需要追踪的同步、异常和任务状态必须留在页面稳定区域。
- 所有交互支持键盘、可见焦点、Escape 关闭浮层和合理焦点回归；tooltip 不能承载完成任务所必需的信息。

### 9.1 文字密度与 Tooltip

界面文字按用途分层，不能为了减少字数隐藏业务事实：

| 信息类型   | 默认呈现    | 例子                                              |
| ---------- | ----------- | ------------------------------------------------- |
| 任务必需   | 直接显示    | 指令、前置条件、资料、证据、动作、异常影响        |
| 业务事实   | 直接显示    | 三状态及时间、完成/计划、费用、风险、下一步       |
| 安全与恢复 | 直接显示    | 尚未落账、拒绝原因、追踪 ID、重试动作、空状态指引 |
| 辅助解释   | InfoTooltip | 口径、来源说明、排序规则、模块用途、角色裁剪说明  |

- 辅助解释使用统一 `InfoTooltip`，标题旁只保留帮助图标，不重复常驻副标题。
- Tooltip 必须支持鼠标悬停、键盘焦点、点击/触摸和 `Escape`，并提供明确 `aria-label`；不得只实现 hover。
- Tooltip 文字只能帮助理解，移除后仍必须可以判断状态并完成任务。移动端点击外部可关闭，浮层不得造成横向溢出。
- 页面标题、字段标签和按钮使用员工能识别的业务语言；不在主界面常驻系统实现、页面功能或操作教学文案。

### 9.2 任务注意力与动态导引

任务台的视线顺序固定为“为何需要处理 → 当前业务对象与已知事实 → 真实缺口 → 当前允许动作 → 结果与恢复”。货柜、节点和技术任务状态只在其确实影响判断时作为上下文出现；空闲时不为同步状态预留版面。
导引是根据任务定义与实时状态生成的 UI 准备度投影，不是新的领域状态机，也不能反向更新业务状态。

- 队列主标题使用“确认新 SKU、补资料、安排装柜”等业务原因；`ready/blocked/due` 等技术状态只能辅助筛选、排序或解释。
- 步骤只按适用性出现：任务池才显示领取，有前置/资料/证据要求才显示对应步骤；提交与落账始终保留。
- 完整字段、规则或评审目录只用于覆盖检查，不得无差别铺给每个对象；正常项汇总，未知项形成具体确认任务，缺失证据仅在要求适用时出现。
- 同一时刻只突出一个注意力目标；已完成使用成功语义，等待、阻塞和未开始必须结构与文字可辨，不能只靠颜色。
- 作业路径负责全局进度，当前工作区负责执行；动作带应指向具体未完成项，不重复当前工作区的分组标题。
- 主动作按钮、二次确认与操作记录使用同一业务动词；默认只常驻动作名称、三段业务确认和结果，动作码、操作编号及成功追踪引用放入按需详情，失败追踪信息直显。重试不得换操作编号，失败或拒绝不得改写成完成结果。
- 三段确认的连接线只表达阶段先后，只能连接状态标记，不得穿过阶段文字、时间或图标；阶段文字必须独立占行并在移动端保持可读。
- 主区只常驻当前未完成环节；已完成和尚未轮到的环节统一收进一个“全部要求”入口，不得以多个等权标题重复常驻。
- 当前工作区默认展开；“全部要求”展开后，各辅助环节仍按分组折叠，避免一次重新铺开全部文字。
- 当前动作紧邻导引并早于长表单出现；正常主动作只有在真正可执行时显示，异常入口保持同屏可达且视觉次级。
- 宽屏将作业路径与当前动作置于同一视觉带；1024px 和移动端纵向堆叠，不压缩步骤、动作或业务文字。
- 导引只负责定位，不做成可点击步骤器，不允许跳过前置校验；状态事件乱序到达时可显示后续事实已完成。
- 移动端复用同一任务投影与动作组件，导引在单屏内换行，不新增页面级横向滚动或第二套业务逻辑。

### 9.3 任务语言呈现

任务界面只消费版本化语言投影，不从任意 `title/statusLabel/instruction/tone` 自由字段直接渲染。语言投影必须沿 `taskDefinitionKey/version → 任务定义 → 实例触发原因 → 当前状态/操作结果` 追溯；未知定义或版本明确失败，不静默显示通用占位文案。

- 标题回答“要得到什么结果”，使用员工熟悉的主动业务动词；异常事实放在“原因”，不堆进标题。
- 未完成任务依次显示原因、下一步或当前等待、完成标准和必要安全边界；内容必须各司其职，不得互相复述。
- 完成后隐藏触发原因、下一步和完成标准，用已落账 `resultSummary` 或定义中的完成结果替换；不得让完成任务继续发出命令。
- 任务状态短标签和语义色来自单一状态语言目录；文案不能反推状态，任务实例不能重复保存展示标签或色调。
- 影响历史、身份、数量、权限、费用或状态推进的边界直接显示，不收进 Tooltip；一般来源、口径和扩展说明才按需披露。
- 动作按钮、确认框、操作记录使用同一动作名称；语言目录不得改写动作码、权限、合法转换、完成政策或货柜事实。

## 10. 工程与治理

### 10.1 文件责任

后续实现按下列边界演进，禁止重新形成单体样式文件：

    apps/web/src/
      styles/
        base.css         # reset、排版、focus、滚动
        element.css      # Element Plus token 对齐
        utilities.css    # 少量经批准的布局工具
      ui-theme/
        contracts.ts     # 稳定、类型化的主题契约
        activeTheme.ts   # 唯一主题选择入口
        UiThemeProvider  # 注入主题，不承载业务状态
      themes/
        logix/
          tokens.css     # 仅在 data-ui-theme="logix" 下生效
          LogixAppShell  # 当前基准壳实现
          LogixPageHeader
      components/
        shell/           # 壳层内部交互部件
        ui/              # 稳定门面与 Logix 通用模式
        container/       # 货柜领域
        task/            # 任务领域
        management/      # 管理投影

- 组件样式默认 scoped；跨组件值只能来自 token，不通过全局选择器碰撞修补。
- 禁止新增长度超过 400 行且职责混合的 Vue 组件；超限时按 shell、模式或领域责任拆分。
- 禁止裸十六进制颜色、随意 z-index、!important 和无 token 的间距；第三方兼容覆盖集中在
  element.css 并注明原因。
- 导航配置来自路由元数据和权限投影；服务端仍是授权边界。
- 列表必须分页、稳定排序；大数据表使用虚拟化或服务端窗口，不能把全量货柜渲染到 DOM。
- 主题实现只能由 `ui-theme/` 注册入口和自身测试导入；该边界由仓库检查执行。

### 10.2 质量门禁

| 门禁           | 最低要求                                                                      |
| -------------- | ----------------------------------------------------------------------------- |
| lint/typecheck | Vue、样式与路由配置无错误；禁止未使用组件和裸调试输出                         |
| component test | 状态映射、权限隐藏、键盘交互、空/错/加载状态                                  |
| E2E            | 员工主路径、异常上报、货柜下钻、三段确认                                      |

| performance    | 路由懒加载；图表按需加载；首屏主 JS 保持低于 250KB（gzip 前）并在 CI 观察趋势 |

## 11. 禁止模式

- 不把七组 SOP 变成七个固定页签。
- 不把每个 section、每行数据或每个状态都做成卡片。
- 不以 hero、大插画、渐变球或装饰图占用作业首屏。
- 不把流程实例、工序任务、作业工单、数据同步和数据状态合成一个“综合状态”。
- 不用颜色代替状态文字，不用绿色表示请求已接收。
- 不复制模板导航、假消息、社交组件或无业务价值的 dashboard widget。
- 不直接引入任何第三方后台模板的完整 CSS、JavaScript 或静态页面。
- 不把 Theme Adapter 做成业务插件系统，不允许主题读取领域 Store 后自行决定业务行为。
- 不让页面自己维护权限、状态机、费用公式或指标口径。
- 不以货柜或其他后续技术实体作为上游岗位开始工作的强制前提。
- 不同时设置多个对象选择源，不让队列、顶部选择器和内容卡片形成不同当前上下文。
- 不把全部规则维度或评审项平铺给每个对象并统一标成“未评审”。
- **不把岗位作业台做成驾驶舱**：不以 KPI 仪表板、环形健康度、进度分布图作为作业首屏入口。作业台先回答“岗位要完成什么”（HW-D01）；驾驶舱形态与 §5 的限制只适用于管理投影页。
- **不发明复合指标**：健康度、风险指数、完成百分比等派生口径必须由服务端给出，前端不得自行计算或命名。没有明确比较维度与刻度的迷你图、趋势线、环形图、仪表盘一律不加（§5）。
- **不重定义色彩令牌**：不得为“紧急度”“优先级”“可接管”等新语义另造色板。颜色只表达 §7.1 已定义的业务语义，且**一个语义只有一种颜色**——例如“可接管”是可执行状态，属 `--info`，不得用 `--ok` 绿。
- **不用相近色区分同级语义**：如“待补-紧急”与“待补-常规”不得用两种相近的黄或橙。同级差异靠排序与文字标签，颜色永远不是唯一状态编码。
- **不用 `var(不存在的令牌, 色值)` 伪装在用令牌**：回退值会永久生效，组件看似在用令牌、实则脱离色板且无从发现。颜色属性不得出现任何色值字面量——**含 `var()` 的回退值**。
- **不为追求视觉张力突破字号／字重／行高档位**：焦点靠**档位内的对比**建立（如 20px 对象名 + 14px 正文 + 12px 元数据），不靠超规格字号（如“柜号超大字”）。档位由样式比例门禁强制，见 §7.2。
- **不用卡片阴影制造层级**：卡片默认无阴影（§7.3）；层级由边框、分区头与留白建立。仅可重复的顶部信号允许轻微阴影。
- **不为每条记录生成可视化进度条并按“健康度”渐变着色**：进度段不得暗示尚未发生的节点已完成；状态色不得一色多义。
- **不把“缺什么”逐项平铺并逐条标红黄绿**：按 HW-D05 汇总正常项、只展开需要判断或恢复的项；“优先级”必须由服务端给出，前端不得自评。

## 12. 实施顺序

1. **Shell v1**：拆分 AppShell，实现展开/折叠/抽屉、顶栏、页头和对象上下文插槽。
2. **Token v1**：把现有 style.css 拆为四层样式，修正文档与代码 token 漂移。
3. **模板 v1**：先迁移任务台与一柜一档，再迁移计划与管理投影。
4. **组件治理**：收敛图标、状态映射、工具栏、空/错/加载和审计信息。
5. **可视化适配**：真实指标口径确认后再接 ECharts，不用假图表决定页面结构。
6. **验收**：桌面、窄桌面、移动截图，键盘与 reduced-motion 检查，E2E、构建体积和角色样本回验。

上述顺序只改变展示与交互骨架，不改变业务状态、权限或 API 契约。任何需要新业务字段或状态码
的 UI 需求必须回到领域/契约评审，不能在组件内临时发明。
