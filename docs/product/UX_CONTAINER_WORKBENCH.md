# 货柜工作台 · 全生命周期可视化与一键动作拆解（UX）

> 状态：**候选（待 P2 评审）** · v0.8 · 2026-09-06 · 负责人：刘志高。
> 需求来源（负责人 2026-09-04）：**可视化是明确需求**——货柜抽象为可视化实体，一个界面一眼看尽全生命周期状态/动态/异常，
> 并提示是否需触发下一动作；低风险、默认载荷明确的动作可一键确认，外发、费用、终态或越权等高风险动作按规则复核，不让员工重复录入已有数据。
> 本文把整个流程做**可视化实现拆解**。它是 UX/实现规格，业务语义与状态/标记以领域文档为准（UI 不发明业务）。
> 关联：[CONTAINER_LIFECYCLE](./domain/CONTAINER_LIFECYCLE.md)、[CONTAINER_STATUS_MODEL](./domain/CONTAINER_STATUS_MODEL.md)、
> [CONTAINER_MARKERS](./domain/CONTAINER_MARKERS.md)、[LIFECYCLE_CONSISTENCY](./domain/LIFECYCLE_CONSISTENCY.md)、
> [INTEGRATION_BOUNDARIES](./domain/INTEGRATION_BOUNDARIES.md)、架构 §11（前端特征目录 `features/`）。

## 1. 设计目标

1. **单屏全景**：把一个货柜（ContainerRecord，一单一柜）抽象成一个可视化实体，单屏呈现 全生命周期状态、动态、异常、当前所处节点，以及"是否/该做哪一步下一步动作"。
2. **动作即点即成**：下一步动作以"待办/建议"形式呈现，动作默认载荷已由系统推导，用户只需**确认 → 点击**；需要录入的降到最少（默认值可改可不改）。
3. **可视化不改业务**：所有状态变化、下一动作推导均由服务端规则/状态机给出；前端只消费只读投影 + 执行已授权动作，不绕过状态机（AGENTS §5/§6）。
4. **分层状态不混同**：流程实例、工序任务、作业工单、数据同步和数据状态在操作上下文中分别展示；权威定义与三层映射关系只引用 [PRINCIPLES §1](./PRINCIPLES.md)，UI 不另造口径。

### 1.1 顶层原则（负责人 2026-09-05）

- **聚焦对象·全览无余**：可视化聚焦在"货柜"这个业务对象，全生命周期在一个界面里看全；**不要碎片式**到多处找线索拼。
- **按 时间链 + 状态机 构建视觉路径，所见即所得**：一眼看到的是"货柜走到哪、接下来会怎样、该不该动手"。
- **每节点带三态与行动**：正常 / 预警 / 风险提示，并给出**下一步行动建议 + 闭环操作路径**（点一下就能把事情办完）。
- **三层可视化层级：全局 → 中观 → 微观**，让信息分层呈现、由粗到细，**不淹没**。

### 1.2 三种可视范围（全局 → 中观 → 微观）

> 此处是页面下钻范围，不是 PRINCIPLES §1.2 的业务三层。业务三层固定为“管理维度 × 主流程节点 × 作业动作”。

| 层   | 对象/范围                                           | 呈现                                                                       | 用途/交互                                           |
| ---- | --------------------------------------------------- | -------------------------------------------------------------------------- | --------------------------------------------------- |
| 全局 | 全车队/状态分布/风险                                | 状态分布图·桑基·KPI·逾期风险分桶（见附录 A.1）                             | 总览口径；点扇区/风险桶 → 下钻中观                  |
| 中观 | 一票(提单)多柜 / 一批(计划·ShipmentPlan) / 风险集合 | 组内多柜横向对比：每柜一行"迷你 rail + 状态 + 风险 + 待办数"；可选泳道甘特 | 在"一票/一批"里定位最卡/最险的柜；点某柜 → 下钻微观 |
| 微观 | 单货柜全生命周期                                    | 本工作台：单屏 rail(时间链+状态机视觉路径)+节点详情+标记+动作中心          | 一眼看全、点即执行（本文件主体）                    |

- **下钻不丢上下文**：全局→中观→微观一路带着同一筛选/上下文，避免回到顶部重找（防"碎片式拼线索"）。
- **不淹没**：渐进披露——默认只亮 该层最有信息量的图与"需关注"标记；明细靠 hover/展开/下钻，不一次铺满。

### 1.3 节点视觉三态与闭环路径

- 每个 rail 节点承载：`正常`（绿）· `预警`（橙，如时间偏差/临近）· `风险`（红，如滞留/扣货/缺证据）三态；密封节点灰锁；当前待办节点呼吸灯。
- 节点展开给：**下一步行动建议**（动作中心）→ **一键确认** → 执行后状态推进/事件落账 → 回到 rail（闭环操作路径），无需离开主界面去别处补办。
- 视觉路径 = 时间链(L) + 状态机(currentStatus)；所见即"现在到哪、差什么、怎么走到下一步"（白话：像导航，告诉你已到哪站、下一站和怎么去）。

### 1.4 分层状态与管理映射的 UI 落点

| 核心要素   | UI 主落点                         | 必须让用户看见                                                                                       |
| ---------- | --------------------------------- | ---------------------------------------------------------------------------------------------------- |
| 货柜状态   | 货柜头部 + 生命周期 rail          | 当前节点、实际证据、最近推进时间；只约束可做范围，当前指令来自服务端任务，不由前端看状态猜动作       |
| 任务状态   | 我的任务/节点作业区 + 当前任务条  | 是否待领取/执行/报工/阻塞及责任人；具体做到什么由任务结果与证据回答，状态码待任务模型定稿            |
| 同步状态   | 扫描/提交控件旁 + 待同步队列/回执 | 动作名、动作码和操作编号一致；区分请求接收、业务接受、事实落账，业务拒绝与技术失败不能笼统提示“成功” |
| 管理维度   | 全局/中观筛选、指标和对比视图     | 按进度、预警、异常、风险、绩效、改善与资源观察，并下钻到节点/动作/事实                               |
| 主流程节点 | 生命周期 rail、节点详情、时间线   | 从备货单到还空箱的信息、数据、状态、证据与先后关系                                                   |
| 作业动作   | 我的任务/任务执行台/动作中心      | 当前任务上下文、前置条件、动态动作、必要证据、结果与异常恢复；领取、物料、扫描、报工按任务适用性出现 |

现场员工默认进入任务执行台，而不是管理看板；管理者按维度从全局/中观下钻到节点、货柜与动作。页面必须同时保留“维度 → 节点 → 动作”的定位上下文，但导航与信息密度按角色分开。

#### 提交反馈：内部三段，界面按需展开

| 实际进度                 | 员工主提示    | 详细信息/系统动作                                        |
| ------------------------ | ------------- | -------------------------------------------------------- |
| 尚未获得可靠接收回执     | 待发送/提交中 | 保留本地操作，用同一 `clientOperationId` 重试            |
| 请求已接收、尚无业务决定 | 已接收·校验中 | 可查看接收时间和追踪 ID；客户端查询原操作                |
| 业务已接受、尚未落账     | 已接受·处理中 | 仅异步/跨事务时显示；服务端负责重试、补偿或转人工        |
| 业务事实已落账           | 已完成        | 显示任务/事件/货柜事实结果引用；此时才刷新达成与业务状态 |
| 业务拒绝或需要用户处理   | 需处理        | 直接展示可行动原因；不得伪装成“同步失败”让员工盲目重扫   |

- 同步事务如果一次完成校验和落账，界面直接显示“已完成”，详情中保留三段证据，不播放无意义的中间动画。
- 内部队列、工作线程、重试次数等只有在影响用户动作或排障时才放入详情，不增加顶层状态徽章。
- “已接受但未落账”的技术失败默认由系统恢复；只有需要补资料、解除冲突或人工决策时才转成用户任务/异常。

#### 其它容易误导员工的状态文案

| 后台事实                                 | UI 可以写     | UI 不得提前写               |
| ---------------------------------------- | ------------- | --------------------------- |
| 员工已提交报工，业务尚未落账             | 已报工·待确认 | 任务已完成                  |
| 邮件/单证仅完成发送                      | 已发送        | 对方已收到/已受理           |
| 外部源返回里程碑，尚未完成内部校验和落账 | 已获取·待确认 | 货柜已到港/已放行等权威状态 |
| 异常已有处理结果，仍需复核影响是否消除   | 已处理·待验证 | 异常已关闭                  |
| 费用由时间和费率推算，尚无账单或审核     | 预计费用      | 实际费用/已结算             |
| 改善动作已经执行，尚无效果复核           | 已执行        | 改善已达成                  |

这些差异不全部占用顶层徽章：默认只展示会改变员工下一步动作的一层，其余事实、时间、来源和证据在详情中按需展开。用词和是否拆分以 [PRINCIPLES §1.1](./PRINCIPLES.md) 的适度拆分判据为准。

### 1.6 节点工作区：七组检查、按角色组装

每个 rail 节点可以进入同一个 `NodeSopWorkspace`，但不固定生成七个页签。七组由 [PRINCIPLES §1.6](./PRINCIPLES.md) 用于检查信息是否遗漏；界面根据角色、当前任务、风险和设备尺寸组装少量相关区块，允许从计划、费用或管理入口进入同一节点上下文。

| 七组视角   | 主要用户                   | 默认呈现方式                                                                       | 出现条件/下钻                                                  |
| ---------- | -------------------------- | ---------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 计划与能力 | 计划/调度                  | 计划视图或节点侧栏                                                                 | 有计划编制、资源分配或能力缺口时出现                           |
| 执行与达成 | 现场员工/运营              | **员工默认主界面**：任务上下文、当前动作、必要资料/资源与证据、结果/异常、同步反馈 | 始终围绕当前可执行任务；领取、扫描等控件仅在任务定义要求时出现 |
| 货柜状态   | 全角色                     | 头部状态 + 生命周期 rail                                                           | 查看一柜一档和事件证据；不要求员工进入独立页签                 |
| 周期时效   | 运营/管理                  | 指标详情或预警下钻                                                                 | 存在 SLA、延误或复盘需求时出现                                 |
| 费用结算   | 财务/运营/管理             | 独立费用视图或风险摘要                                                             | 有费用责任或预计风险时出现；员工默认隐藏金额                   |
| 异常与改善 | 运营/管理；员工仅上报/补证 | 当前任务内异常入口 + 统一异常视图                                                  | 员工一键上报；复杂处置、根因和关闭按权限展开                   |
| 会议与绩效 | 管理者                     | 管理投影和决议跟踪                                                                 | 仅管理场景展示，不嵌入现场作业流                               |

- 员工首屏只保留当前任务上下文、可执行动作、必要证据、结果/异常入口和同步反馈，不要求其理解七组分类或浏览计划、费用、绩效和会议内容。“领取、物料、扫描、报工”是能力组件，不是固定步骤。
- 按需呈现的区块共享 `containerRecordId + nodeRef`，再引用计划、任务、事件、费用、异常、复核和会议决议；柜号用于业务查找，不作为各视图的独立主键。
- 人工复核仅由风险/冲突规则触发，以统一待审队列或当前动作提示出现；正常低风险动作不得增加统一审批步骤，也不另造一种货柜状态。
- 周期、费用和绩效指标都必须可点击下钻到原始节点时间、任务结果、费用标准或异常记录。

### 1.7 任务台：稳定区域、动态作业配方

任务台不把某个节点样例写成通用步骤条。服务端根据 `taskDefinitionKey/version + taskId + containerRecordId + nodeRef` 返回当前任务配方，前端只组合适用区域：

| 稳定区域   | 显示内容                                                   | 交互规则                                                               |
| ---------- | ---------------------------------------------------------- | ---------------------------------------------------------------------- |
| 任务队列   | 优先级、SLA、风险、责任人、可执行/等待原因                 | 支持自动派单、指定分配、共享池领取和团队任务；不统一要求领取           |
| 任务上下文 | 货柜、节点、工序任务、工单、同步/数据状态、计划窗口、标记与前置条件             | 前置未满足时显示原因和下一责任方，不让员工反复提交                     |
| 当前动作   | 服务端推导的有限 `actionCode` 与默认载荷                   | 同时只突出当前可执行动作；外部等待显示等待对象和期限，不伪装成人工步骤 |
| 证据区     | 任务要求的外部事件、扫描、照片、附件、签收/EIR、清单或说明 | 只采完成政策需要的证据；已从权威源获得的事实不重复录入                 |
| 结果与恢复 | 完成、部分完成、等待外部、无法完成、取消/返工和异常入口    | 结果提交消费三段确认；异常可从任意阶段进入并保留原任务历史             |

典型裁剪：信息任务可以只有“上下文 + 发送/等待回执”；监控任务可以由权威事件自动完成；派拖任务需要资源选择和承运接受；提柜/卸柜等实物任务才通常需要身份扫描、照片或交接凭证。完整节点任务候选见 [NODE_PDCA §④](./domain/NODE_PDCA.md)。

│ ⑤ 动作中心(下一步)                                                          │

- 主视区 = ① 生命周期轨道（默认可一眼判断"进行到哪、下一个该做什么、有没有异常"）。
- ②③④ 为当前节点/标记/单证动态；⑤ 动作中心是"是否需要触发下一动作"的答案。

## 3. 可视化实体 = 生命周期投影（数据来源）

- 单屏视图是 **只读投影（read model）**，由服务端按 [LIFECYCLE_CONSISTENCY](./domain/LIFECYCLE_CONSISTENCY.md) 的 L 与密封线组装：
  每节点给 状态(planned/actual) + 时间(预计/实际) + 事件动态 + 异常 + 是否已密封；当前节点高亮；
  可选节点（中转/海铁）未发生时显示为可跳过虚线位。
- 标记 chips 来自 [CONTAINER_MARKERS](./domain/CONTAINER_MARKERS.md)（含聚合来源 SKU 提示、撤标入口、各标记动作绑定）。
- 异常来自 exception 相关数据（甩柜/滞留/扣货等），挂在对应节点；异常=红点 + 影响说明 + 处置动作。

## 4. 下一步动作（动作推导引擎 + 一键执行）

### 4.1 推导原则（服务端，UI 不发明）

- 每条「下一步动作」由服务端动作推导引擎生成，输入 = 当前状态/节点 + 一致性 R3/R4（可写窗口）+ 标记→动作绑定 +
  缺失必填/证据 + 异常 + SLA/优先级；输出 = 有限 actionCode 列表（含默认载荷与权限要求）。
- 同一时刻只给「确实可执行且属当前可写窗口」的动作；动作不可违反密封/单调/来源权威（否则不出现或需审批）。

### 4.2 动作模型

- `action = { actionCode, 说明, 触发条件, 默认载荷(收件人/内容/目标节点/指令), 权限, 渠道 }`，actionCode 有限稳定集合（字典机制见 §4.3）。
- 执行 = 一键确认：系统填好默认值 → 用户核对（可微调但默认即可用）→ 确认即调服务端动作接口；服务端校验后执行并审计。
- 动作落地可以是一条指令（下达给供应商/承运/拖车/仓库）、一封邮件/通知（[通知模块]）、一次确认/审核、一次状态推进（经合法转换）、或创建一个异常/任务。

### 4.3 与字典/映射机制一致（D12/D13）

- 动作码、标记码、状态码都走"内部固定 + 外部映射字典"；新业务动作=加 actionCode + 绑定触发 + 可配置默认载荷，**不散落硬编码**。
- 动作默认载荷可配置（如转发邮件模板/收件人映射按 客户/船司/航线），一次配置、一键复用。

### 4.4 生命周期示例动作（首期）

| 当前       | 示例动作（一键）                                            | 载荷/渠道              |
| ---------- | ----------------------------------------------------------- | ---------------------- |
| 装箱       | 确认装箱定稿（真实重量/封号/箱号）；若含致冷剂→温控要求确认 | 确认 + 状态推进        |
| 装箱后     | 一键转发"装箱单/到货通知"邮件                               | 邮件（船司/货代/客户） |
| 待清关     | 一键转发清关文件 / 创建清关待办                             | 邮件 + 指令            |
| 危险品标记 | 一键生成并发送 DG 声明                                      | 邮件/EDI               |
| 到港待提   | 一键下达派拖指令（按默认拖车商）                            | 指令（运输公司/内部）  |
| 甩柜/滞留  | 一键创建异常并升级、转发延误通知                            | 指令 + 邮件            |
| 卸柜后     | 一键确认卸空→可还箱；一键安排还箱/通知承运                  | 确认 + 指令            |

## 5. 实现拆解（组件/数据/接口/阶段）

### 5.1 前端组件（apps/web features，Element Plus + 业务组件层）

- `ContainerWorkbench`（整屏容器）
- `LifecycleRail`（轨道：节点/状态/时间/密封线/可选节点/异常点/待办呼吸）
- `NodeDetailCard`（当前节点动态、预计/实际、证据、事件列表）
- `NodeSopWorkspace`（按角色/任务/风险动态组装区块，共享货柜/节点上下文；七组只作覆盖检查）
- `TaskWorkbench`（路由级编排：任务队列 + 当前任务执行面；不固定四步）
- `TaskQueue`（员工待办与系统监控分区；正常监控不占员工队列）
- `TaskContextHeader`、`TaskPreconditionPanel`、`TaskInputPanel`、`TaskEvidencePanel`、`TaskResultPanel`（消费任务定义投影，按适用性装配）
- `SubmissionProgress`（请求已接收 → 业务已接受 → 事实已落账的三段回执）
- `PlanCapacityView`、`ExecutionAchievementView`、`CycleView`、`CostView`、`ImprovementView`、`MeetingPerformanceView`（七组投影，货柜状态复用 rail/timeline）
- `HumanReviewQueue`（跨组人工复核；显示原对象、证据、理由、责任人与时限）
- `MarkerChips`（标记 chips → 动作抽屉）
- `ExceptionBadge` + `ExceptionPanel`
- `ActionCenter`（下一步动作列表 + `OneClickConfirmDialog`：默认载荷预览 → 确认执行）
- `TimelineDrawer`（该箱历史事件时间线，可下钻）

### 5.2 数据/接口（服务端）

- 只读投影接口：`GET /containers/:id/workbench`（返回 rail/节点/标记/异常/动作中心所需数据，带 Trace ID）。
- 动作接口：`POST /actions/:code/confirm`（携带客户端操作 ID；服务端校验 状态机/密封/来源权威/权限 → 执行 → 返回同步回执 → 审计；动作日志供 P8）。
- 扫描/报工交互：提交后先呈现同步状态；只有服务端回执明确业务结果时才更新任务状态，只有产生合法业务事件时才更新货柜状态。
- 提交结果消费遵守 [PRINCIPLES §1.1](./PRINCIPLES.md) 的最小三段确认；列表/任务上的“已完成”只对应事实已落账。
- 渠道适配：指令/邮件等经 integration 模块（[INTEGRATION_BOUNDARIES](./domain/INTEGRATION_BOUNDARIES.md)）出站，可配置、可降级。
- 投影与动作推导在服务端组装，避免把规则堆在前端（AGENTS §5）。

### 5.3 阶段拆解

- **V1（首期，随 P6）**：已出运货柜列表 + 生命周期轨道只读展示 + 当前节点详情 + 动作中心（导入/确认/状态推进类 + 邮件转发桩）；覆盖“已出运货柜列表→还空箱”的已导入数据。
- **V2**：标记 chips + 异常面板 + 甩柜/滞留/危险品等动作一键化；SLA/优先级排序。
- **V3**：指令/通知渠道打通（拖车派单、海关文件、邮件模板配置）、批量动作、全车队总览。
- **未来上游扩展**：按计划→采购→备货→订舱→出运补充对应角色工作台，并接回同一已出运货柜列表；ShipmentPlan/Booking 等对象仍待领域切片定稿。

### 5.4 当前 Web 演示验证边界（2026-09-06）

- 任务投影已经按任务定义动态装配动作、输入、证据和完成政策；动作携带 `actionCode`、确认等级和默认载荷，不再把领取、物料、扫描、报工固化为统一步骤。
- 演示状态仓库按任务保存独立 `clientOperationId`、三段回执、Trace 与结果引用；切换路由时保持当前页面会话一致，并验证错柜业务拒绝和原操作编号重试。
- 任务完成后上报异常会创建独立异常记录并引用来源任务，不覆盖已落账任务结果；货柜状态只由映射到合法结果事件的动作推进。
- 以上实现仍是浏览器内的 demo adapter：刷新即重置，不证明服务端事务、幂等、并发冲突、认证授权、持久化、事件重放或字段级来源权威已经实现。正式接入时 UI 只消费服务端投影和回执，不迁移前端演示规则为业务权威。

## 6. 待评审决策
