# 货柜工作台 · 全生命周期可视化与一键动作拆解（UX）

> 状态：**候选（初稿，待 P2 评审）** · v0.1 · 2026-09-04 · 负责人：刘志高。
> 需求来源（负责人 2026-09-04）：**可视化是明确需求**——货柜抽象为可视化实体，一个界面一眼看尽全生命周期状态/动态/异常，
> 并提示是否需触发下一动作；**每个动作一键完成**（一键下达指令、一键转发邮件等），只需确认点击，不做过多录入。
> 本文把整个流程做**可视化实现拆解**。它是 UX/实现规格，业务语义与状态/标记以领域文档为准（UI 不发明业务）。
> 关联：[CONTAINER_LIFECYCLE](./domain/CONTAINER_LIFECYCLE.md)、[CONTAINER_STATUS_MODEL](./domain/CONTAINER_STATUS_MODEL.md)、
> [CONTAINER_MARKERS](./domain/CONTAINER_MARKERS.md)、[LIFECYCLE_CONSISTENCY](./domain/LIFECYCLE_CONSISTENCY.md)、

## 1. 设计目标

1. **单屏全景**：把一个货柜（ContainerRecord，一单一柜）抽象成一个可视化实体，单屏呈现 全生命周期状态、动态、异常、当前所处节点，以及"是否/该做哪一步下一步动作"。
2. **动作即点即成**：下一步动作以"待办/建议"形式呈现，动作默认载荷已由系统推导，用户只需**确认 → 点击**；需要录入的降到最少（默认值可改可不改）。
3. **可视化不改业务**：所有状态变化、下一动作推导均由服务端规则/状态机给出；前端只消费只读投影 + 执行已授权动作，不绕过状态机（AGENTS §5/§6）。

### 1.1 顶层原则（负责人 2026-09-05）

- **聚焦对象·全览无余**：可视化聚焦在"货柜"这个业务对象，全生命周期在一个界面里看全；**不要碎片式**到多处找线索拼。
- **按 时间链 + 状态机 构建视觉路径，所见即所得**：一眼看到的是"货柜走到哪、接下来会怎样、该不该动手"。
- **每节点带三态与行动**：正常 / 预警 / 风险提示，并给出**下一步行动建议 + 闭环操作路径**（点一下就能把事情办完）。
- **三层可视化层级：全局 → 中观 → 微观**，让信息分层呈现、由粗到细，**不淹没**。

### 1.2 三层可视化层级（全局 → 中观 → 微观）

| 层 | 对象/范围 | 呈现 | 用途/交互 |
| --- | --- | --- | --- |
| 全局 | 全车队/状态分布/风险 | 状态分布图·桑基·KPI·逾期风险分桶（见附录 A.1） | 总览口径；点扇区/风险桶 → 下钻中观 |
| 中观 | 一票(提单)多柜 / 一批(计划·ShipmentPlan) / 风险集合 | 组内多柜横向对比：每柜一行"迷你 rail + 状态 + 风险 + 待办数"；可选泳道甘特 | 在"一票/一批"里定位最卡/最险的柜；点某柜 → 下钻微观 |
| 微观 | 单货柜全生命周期 | 本工作台：单屏 rail(时间链+状态机视觉路径)+节点详情+标记+动作中心 | 一眼看全、点即执行（本文件主体） |

- **下钻不丢上下文**：全局→中观→微观一路带着同一筛选/上下文，避免回到顶部重找（防"碎片式拼线索"）。
- **不淹没**：渐进披露——默认只亮 该层最有信息量的图与"需关注"标记；明细靠 hover/展开/下钻，不一次铺满。

### 1.3 节点视觉三态与闭环路径

- 每个 rail 节点承载：`正常`（绿）· `预警`（橙，如时间偏差/临近）· `风险`（红，如滞留/扣货/缺证据）三态；密封节点灰锁；当前待办节点呼吸灯。
- 节点展开给：**下一步行动建议**（动作中心）→ **一键确认** → 执行后状态推进/事件落账 → 回到 rail（闭环操作路径），无需离开主界面去别处补办。
- 视觉路径 = 时间链(L) + 状态机(currentStatus)；所见即"现在到哪、差什么、怎么走到下一步"（白话：像导航，告诉你已到哪站、下一站和怎么去）。

## 2. 单屏信息分层（一眼看尽）

```text
┌────────────────────────────────────────────────────────────────────────────┐
│ 货柜工作台  ·  箱号 XXX  ·  备货单 YYY  ·  当前位置 [节点/港口]             │
│ 状态徽章(currentStatus)   标记Chips: 危险品/需植检/致冷剂/超限  (可点看动作) │
├────────────────────────────────────────────────────────────────────────────┤
│ ① 生命周期轨道 (rail)  ←—— 默认核心                                       │
│   ●已完 ●已完 ●已完 ◐当前●(待办高亮) ○待触  ◌未发生  各节点:状态/预计/实际/异常│
│  备货→装箱→出运→离港→海运→(中转)→清关→目的港→(海铁)→拖卡→送仓→卸柜→卸空→还箱 │
│   可选节点灰色虚线; 异常节点红色↑; 当前待办节点呼吸灯; 密封线(不可回改区域)    │
├────────────────────────────────────────────────────────────────────────────┤
│ ② 当前节点详情卡片（动态 + 异常 + 时间 + 证据）  ③ ④ 左右辅助列(可折叠)     │
│   当前: 到港[目的港] 预计 ETA 09-10 实际 ATA 09-09  → (下一个: 清关放行)     │
│   异常: 甩柜/滞留/清关扣货...            |  标记与动作 / SKU特征聚合         │
├────────────────────────────────────────────────────────────────────────────┤
│ ⑤ 动作中心(下一步)                                                          │
│   [一键下达指令: 派拖提柜]  [一键转发邮件: 到港通知/装箱单]  [确认到港] ...   │
│   每项: 动作说明 + 默认接收人/内容 + [确认并执行]                            │
└────────────────────────────────────────────────────────────────────────────┘
```

- 主视区 = ① 生命周期轨道（默认可一眼判断"进行到哪、下一个该做什么、有没有异常"）。
- ②③④ 为当前节点/标记/单证动态；⑤ 动作中心是"是否需要触发下一动作"的答案。

## 3. 可视化实体 = 生命周期投影（数据来源）

- 单屏视图是 **只读投影（read model）**，由服务端按 [LIFECYCLE_CONSISTENCY](./domain/LIFECYCLE_CONSISTENCY.md) 的 L 与密封线组装：
  每节点给 状态(planned/actual) + 时间(预计/实际) + 事件动态 + 异常 + 是否已密封；当前节点高亮；
  可选节点（中转/海铁）未发生时显示为可跳过虚线位。
- 标记 chips 来自 [CONTAINER_MARKERS](./domain/CONTAINER_MARKERS.md)（含聚合来源 SKU 提示、撤标入口、各标记动作绑定）。
- 异常来自 exception 相关数据（甩柜/滞留/扣货等），挂在对应节点；异常=红点 + 影响说明 + 处置动作。

## 4. 下一步动作（动作推导引擎 + 一键执行）

### 4.1 推导原则（服务端，UI 不发明）

- 每条「下一步动作」由服务端动作推导引擎生成，输入 = 当前状态/节点 + 一致性 R3/R4（可写窗口）+ 标记→动作绑定 +
  缺失必填/证据 + 异常 + SLA/优先级；输出 = 有限 actionCode 列表（含默认载荷与权限要求）。
- 同一时刻只给「确实可执行且属当前可写窗口」的动作；动作不可违反密封/单调/来源权威（否则不出现或需审批）。

### 4.2 动作模型

- `action = { actionCode, 说明, 触发条件, 默认载荷(收件人/内容/目标节点/指令), 权限, 渠道 }`，actionCode 有限稳定集合（字典机制见 §4.3）。
- 执行 = 一键确认：系统填好默认值 → 用户核对（可微调但默认即可用）→ 确认即调服务端动作接口；服务端校验后执行并审计。
- 动作落地可以是一条指令（下达给供应商/承运/拖车/仓库）、一封邮件/通知（[通知模块]）、一次确认/审核、一次状态推进（经合法转换）、或创建一个异常/任务。

### 4.3 与字典/映射机制一致（D12/D13）

- 动作码、标记码、状态码都走"内部固定 + 外部映射字典"；新业务动作=加 actionCode + 绑定触发 + 可配置默认载荷，**不散落硬编码**。
- 动作默认载荷可配置（如转发邮件模板/收件人映射按 客户/船司/航线），一次配置、一键复用。

### 4.4 生命周期示例动作（首期）

| 当前 | 示例动作（一键） | 载荷/渠道 |
| --- | --- | --- |
| 装箱 | 确认装箱定稿（真实重量/封号/箱号）；若含致冷剂→温控要求确认 | 确认 + 状态推进 |
| 装箱后 | 一键转发"装箱单/到货通知"邮件 | 邮件（船司/货代/客户） |
| 待清关 | 一键转发清关文件 / 创建清关待办 | 邮件 + 指令 |
| 危险品标记 | 一键生成并发送 DG 声明 | 邮件/EDI |
| 到港待提 | 一键下达派拖指令（按默认拖车商） | 指令（运输公司/内部） |
| 甩柜/滞留 | 一键创建异常并升级、转发延误通知 | 指令 + 邮件 |
| 卸柜后 | 一键确认卸空→可还箱；一键安排还箱/通知承运 | 确认 + 指令 |

## 5. 实现拆解（组件/数据/接口/阶段）

### 5.1 前端组件（apps/web features，Element Plus + 业务组件层）

- `ContainerWorkbench`（整屏容器）
- `LifecycleRail`（轨道：节点/状态/时间/密封线/可选节点/异常点/待办呼吸）
- `NodeDetailCard`（当前节点动态、预计/实际、证据、事件列表）
- `MarkerChips`（标记 chips → 动作抽屉）
- `ExceptionBadge` + `ExceptionPanel`
- `ActionCenter`（下一步动作列表 + `OneClickConfirmDialog`：默认载荷预览 → 确认执行）
- `TimelineDrawer`（该箱历史事件时间线，可下钻）

### 5.2 数据/接口（服务端）

- 只读投影接口：`GET /containers/:id/workbench`（返回 rail/节点/标记/异常/动作中心所需数据，带 Trace ID）。
- 动作接口：`POST /actions/:code/confirm`（服务端校验 状态机/密封/来源权威/权限 → 执行 → 审计；动作日志供 P8）。
- 渠道适配：指令/邮件等经 integration 模块（[INTEGRATION_BOUNDARIES](./domain/INTEGRATION_BOUNDARIES.md)）出站，可配置、可降级。
- 投影与动作推导在服务端组装，避免把规则堆在前端（AGENTS §5）。

### 5.3 阶段拆解

- **V1（首期，随 P6）**：生命周期轨道只读展示 + 当前节点详情 + 动作中心（导入/确认/状态推进类 + 邮件转发桩）；覆盖"装箱后→还箱"已导入数据。
- **V2**：标记 chips + 异常面板 + 甩柜/滞留/危险品等动作一键化；SLA/优先级排序。
- **V3**：指令/通知渠道打通（拖车派单、海关文件、邮件模板配置）、批量动作、全车队总览。
- 计划层（ShipmentPlan/备货单）的可视化（多箱一票）另行拆解。

## 6. 待评审决策

- 单屏默认布局与"一眼"的信息优先级（轨道 vs 详情比重）——需原型验证。
- 动作推导引擎的规则归属（应用层 vs 配置）与首批 actionCode 目录。
- 一键动作的确认粒度（默认执行 vs 高风险二次确认；危险品/付款/越权类仍禁一键）。
- 邮件/通知模板与收件人映射的配置来源（字典/业务管理员）。

### A.3 现网缺、我们要补的（差距）

| 差距 | 我们的补法 |
| --- | --- |
| 无"标记 chips→动作中心→一键执行" | 工作台 MarkerChips + ActionCenter（UX §4/§5） |
| 预警靠手写逾期分桶、非规则化 | 预警规则化（NODE_PDCA/PRECHECK + P8） |
| 状态时间线靠字段现场合成 | 统一事件流水账（TIMELINE_MAPPING/EVENT_CODES） |
| 预计/实际仅"事件成对" | rail 上显式 预计/实际双轨（R0 E/A） |

> 白话注解：老系统像"把每件事按时间摆一排、给关键日子标红黄绿"，好懂但都是代码现场算；我们要把它变成"库里早就记好的流水账 + 固定清单驱动 + 点一下就能办事"的工作台。

### A.4 复用要点（评审后采纳）

- 桑基"每柜只计一次"口径沿用，防重复统计。
- KeyDates 红/橙/绿 阈值(≤0/≤3) 作免费期/到期预警的初始配色口径（待本地样本校准）。
- 分段详情 Tab 结构可作节点详情抽屉蓝本；泳道甘特作可选"时间条视图"。
