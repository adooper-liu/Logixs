# 数据库结构契约 V1

> 状态：现行数据库治理与评审入口，不手工复制全库物理目录，也不创造业务语义。
> 消费者：数据库评审人、模块负责人、迁移作者、Repository 实现者和 CI 维护者。
> 当前表、字段、关系、约束、索引与原生对象请读取生成字典；Schema 与迁移仍是可执行权威。

## 1. 权威顺序

| 层级 | 权威入口                                                                                | 负责回答                                                    | 冲突处理                                     |
| ---- | --------------------------------------------------------------------------------------- | ----------------------------------------------------------- | -------------------------------------------- |
| P1   | [`database/migrations/`](../../database/migrations/)                                    | 已部署结构如何演进；原生 CHECK、FK、索引、函数和触发器      | 已进入共享环境的迁移只能追加纠偏，不能改写   |
| P1   | [`database/schema.prisma`](../../database/schema.prisma)                                | 当前 Prisma model、代码属性、映射、relation 与 ORM 可见类型 | 与迁移最终态不一致时登记缺陷，不静默任选一边 |
| P2   | [`doc/`](../../doc/README.md)                                                           | 业务对象、岗位、流程和业务规则                              | 只有负责人确认内容可成为业务语义             |
| P3   | [`packages/contracts/schemas/v1/`](../../packages/contracts/schemas/v1/) 与正式字段目录 | 公共 DTO、枚举、事件、稳定技术语义、单位与代码映射          | 候选、样本和过时契约不得升格                 |
| P4   | Schema、迁移和精确实现消费者                                                            | 实现意图与当前技术用途                                      | 只能证明实施语义，不能冒充业务定义           |
| P5   | 无可靠来源                                                                              | 未知项                                                      | 标记 `needs_business_confirmation`，禁止猜测 |

物理结构与语义投影：

- [数据库中文数据字典](../../database/dictionary/DATA_DICTIONARY.generated.md)：表、物理字段、三轨关系和证据状态；
- [数据库原生对象清单](../../database/dictionary/NATIVE_OBJECTS.generated.md)：Prisma 未完整表达的对象、函数和触发器；
- [业务评审 Excel](../../database/dictionary/database-data-dictionary.xlsx)：筛选、批注和确认用导出物，不是反向输入；

生成与校验：

```text

```

## 2. 全库通用规则

| 主题      | 固定规则                                                                                        |
| --------- | ----------------------------------------------------------------------------------------------- |
| 命名      | 表、列、约束和索引使用 `snake_case`；Prisma/代码属性使用 `camelCase`；类型使用 `PascalCase`。   |
| 标识      | 公共实体使用不可解释、不可复用的稳定 ID；业务编号、箱号和提单号只能是业务键。                   |
| 租户      | 业务表的 `tenant_id` 是引用范围的一部分；跨模块逻辑引用由所有者 Port 校验同租户。               |
| 时间      | UTC 存储、ISO 8601 交换、用户时区展示；历史默认 `DateTime` 不得在无迁移时宣称为 `TIMESTAMPTZ`。 |
| 金额/数量 | 金额使用定点数并携带币种；数量携带单位；不得用浮点或静默默认业务值。                            |
| 状态      | 公共状态来自正式契约；模块私有状态由 `TEXT + CHECK` 或等价状态机保护；未知外部值不得静默映射。  |
| JSONB     | 只承载来源快照、证据引用、规则快照或低频扩展；稳定关系和查询字段应升格。                        |
| 版本      | 可审计事实采用追加版本、前版本引用和幂等键；不得原地覆盖已消费事实。                            |
| 外键      | PostgreSQL 不自动为 FK 建索引；新增 FK 时必须同时评审查询和删除路径。                           |
| 删除      | 业务事实默认 `RESTRICT`；只有纯从属记录可使用 `CASCADE`，并须有明确依据。                       |
| RLS/分区  | 当前不启用 RLS，也没有分区表；引入任一能力必须新增 ADR、迁移和运行验证。                        |

## 3. 所有权与关系边界

- 每张表只有一个写所有者；其他模块只能通过公开 Application Port、公共契约或事件协作。
- 物理 FK、Prisma relation 和逻辑引用是三种不同事实，生成字典分别标记，不因列名以 `_id` 结尾而猜关系。
- 逻辑引用不是无约束：所有者 Port 必须执行租户、存在性、状态和审计校验。
- 共享可靠性表仍按 `owner_module`、`consumer_name` 或 `target_owner_module` 分区负责，Repository 所在模块不自动取得全部业务所有权。
- 工作台只引用完成当前岗位结果所需的数据事实子集；全库 Excel 不是任何工作台、API 或业务切片的前置门禁。

## 4. 关键不变量

1. 稳定内部身份与可变业务编号分开；业务编号变更不得替换内部身份。
2. 货柜号、订单号、提单号等业务键不得被误当成全局永久身份。
3. 主对象、明细、交接、事实、事件、任务、工单、决定和投影保持各自粒度；不得用一个大状态覆盖。
4. planned、estimated、actual 时间保持不同语义；来源原值、UTC、偏移、权威和证据可追溯。
5. Evidence、AI 建议、人类决定、业务事实、事件应用和执行结果分别保存。
6. active/superseded 版本链保留历史；同幂等键异载荷明确冲突。
7. 外部原始值与内部规范码分层；未知值进入待处理，不生成静默默认。
8. Schema、迁移、Repository 映射和公共契约之间使用显式转换，不依赖偶然同名。

## 5. 索引评审规则

- PK 和 UNIQUE 已形成 B-tree，不为完全相同左前缀重复建索引。
- 每个物理 FK 应有独立索引、可用复合索引或唯一键左前缀。
- 稳定分页使用 `(tenant_id, stable_sort_column, id)` 或等价稳定顺序。
- 状态轮询使用状态与下一次尝试/租约时间；当前版本查询使用所有者身份与 current/active 状态。
- JSONB 只有在存在稳定查询和执行计划证据时才增加 GIN。
- 不为低选择性布尔列单独建索引；必要时使用有业务谓词依据的复合或 partial index。
- 大表优化先用真实数据执行 `EXPLAIN (ANALYZE, BUFFERS)`，无测量不做分区或反规范化。

## 6. 迁移与演进契约

1. 唯一迁移入口是 `database/migrations/<timestamp>_<name>/migration.sql`。
2. 已进入共享环境的迁移不可修改、重命名或删除；纠错追加新迁移。
3. `database/schema.prisma` 与迁移最终态在同一变更中保持一致；生产禁止 `db push` 和自动同步。
4. 不兼容变化使用 expand → migrate/backfill → contract。
5. 新增 `NOT NULL`、默认值、类型转换、唯一约束或大表索引前分析锁、重写、历史脏数据和恢复。
6. 数据修复必须版本化、受审计并包含影响分析、验证查询和恢复方案。
7. Seed 幂等，并区分基础数据、demo/test 数据和生产数据。
8. 数据库高风险变更验证空库升级、旧版本升级、关键拒绝约束和应用回退影响。
9. 新表先确定所有者、租户边界、身份、幂等、版本、删除策略、访问路径和审计。
10. 删除、改名或重释属于破坏性变化，必须提供兼容期和消费者清单。

## 7. 评审清单

- [ ] 表有唯一写所有者，Repository 位于该模块基础设施层。
- [ ] 字段语义可追溯；候选、样本、英文列名和 UI 文案没有被冒充为业务规则。
- [ ] PK、tenant、内部 ID/业务键、时间、金额/币种、数量/单位符合通用规则。
- [ ] NOT NULL、DEFAULT、CHECK、UNIQUE、FK 和引用动作的失败语义明确。
- [ ] 每个 FK 与主要列表、轮询、当前版本查询都有合理索引。
- [ ] 写路径定义事务、幂等、并发冲突、重放和审计。
- [ ] 迁移追加式，并包含历史数据预检和恢复说明。
- [ ] `pnpm data-dictionary:check` 与风险对应专项门禁实际通过。
- [ ] 生成字典中的 reconciliation findings 已处置或明确保留为待修缺陷。

## 8. 维护规则

- 表、字段、关系、约束和索引不再手工复制到本文；生成物是当前评审投影。
- 人工只维护结构无法推导的中文语义、来源、所有者、工作台关联和敏感等级。
- 无可靠来源的语义保持待确认，不阻塞无关工作台或业务切片。
- 生成器只服务数据字典消费者；不得扩成数据库治理平台或两周一次的全库评审循环。
- 若生成链长期没有消费者，可停止 Excel 投影；Schema/迁移对账和已确认语义仍须保留或迁移。
