# 数据库结构契约 V1

> 状态：现行实施契约 V1。本文是数据库评审的单一阅读入口，不创造新的业务语义。
> 消费者：数据库评审人、模块负责人、迁移作者、Repository 实现者和 CI 维护者。
> 使用时机：设计或评审表、字段、约束、索引、跨模块引用、迁移、Seed 和数据修复时先读本文。

## 1. 契约结论

Logix 当前使用 PostgreSQL + Prisma。已发布基线为 73 张业务表、1 个 PostgreSQL 枚举和 71 个追加迁移；当前目标 schema 为 96 张业务表，另含 7 条尚未发布的加法迁移：Shipment 核心 `20260923120000_add_post_departure_shipment_core`、独立异常案件 `20260923160000_add_operational_exception_case`、权威国家/港口主数据 `20260923170000_add_authoritative_location_reference_data`、货主/销售国家映射 `20260923180000_add_cargo_owner_sales_country_mapping`、已出运来源包待复核记录 `20260923190000_add_post_departure_source_package_review`、候选修正版本 `20260924090000_add_post_departure_source_candidate_correction` 与候选 SKU 装载明细 `20260924150000_add_post_departure_candidate_cargo_lines`。数据库按限界上下文共享一个实例，但每张表只有一个写所有者；其他模块只能经公开 Application Port、共享契约或事件协作。

本文提供当前全库的：

- 表与模块所有权；
- 字段、类型和可空性；
- 主键、唯一约束、外键和查询索引；
- 数据库 CHECK 约束族及其保护目标；
- schema、迁移、公共契约和领域文档的权威顺序；
- 新增、兼容和破坏性变更的演进规则。

物理定义仍保持单一可执行来源：当前目标结构是 [`database/schema.prisma`](../../database/schema.prisma)，实际升级历史是 [`database/migrations/`](../../database/migrations/)。本文是二者的评审投影；不得绕过可执行来源只改本文。

## 3. 全库通用规则

| 主题      | 固定规则                                                                                                                                                                         |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 命名      | 表、列、约束和索引使用 `snake_case`；Prisma/代码属性使用 `camelCase`；类型使用 `PascalCase`。                                                                                    |
| 标识      | 公共实体使用不可解释、不可复用 UUID；业务编号、箱号、提单号只能是业务键。历史早期表中 Prisma `String @default(uuid())` 的物理列仍为 `TEXT`，不得无迁移宣称为 PostgreSQL `UUID`。 |
| 租户      | 业务表的 `tenant_id` 是引用范围的一部分；能建立复合 FK 时使用 `(id, tenant_id)`，跨模块逻辑引用由服务端 Port 校验同租户。                                                        |
| 时间      | 新时间事实使用 `TIMESTAMPTZ` 并保存来源偏移；历史 `DateTime` 未标 `@db.Timestamptz` 的列按现有迁移保留，类型修正必须单独迁移和验证历史值。                                       |
| 金额/数量 | 金额使用 `NUMERIC/DECIMAL` 并携带币种；数量携带单位；不得用浮点数或静默默认币种。                                                                                                |
| 状态      | 公共状态来自 JSON Schema/正式状态机；模块私有可演进状态使用 `TEXT + CHECK`，未知外部值不得静默映射。                                                                             |
| JSONB     | 只承载来源快照、证据引用、规则快照或低频结构化扩展；核心关系和稳定查询字段必须升格为列/关系。                                                                                    |
| 版本      | 可审计事实采用追加版本、`supersedes_*`、`version`、`state` 和幂等键；不得原地覆盖已消费事实。                                                                                    |
| 外键      | PostgreSQL 不自动为 FK 建索引；本契约目录中的 FK 查询路径应有显式索引、唯一键左前缀或专项验证依据。                                                                              |
| 删除      | 业务事实默认 `RESTRICT`；只对纯从属记录使用 `CASCADE`，当前明确例外是费用阶梯和助手消息。                                                                                        |
| RLS       | 当前 schema 未启用 PostgreSQL Row Level Security；租户隔离由服务端授权、租户条件和复合约束共同实施。启用 RLS 必须新增 ADR 和迁移。                                               |
| 分区      | 当前没有分区表。只有数据规模与查询/维护证据达到阈值时才引入，并补升级、回退和运行验证。                                                                                          |

## 4. 类型与目录记号

- `?`：数据库允许 `NULL`；没有 `?` 即要求 `NOT NULL`。
- `PK`：主键；`UQ`：字段级唯一；`UNIQUE:name`：命名唯一约束/唯一索引；`INDEX:name`：普通索引；`FK`：物理外键。
- `String`：Prisma 默认 PostgreSQL `TEXT`；`DateTime`：历史默认时间列；`Timestamptz`：`TIMESTAMPTZ`；`Json`：`JSONB`。
- `Uuid`、`Char(n)`、`Decimal(p,s)` 和 `Date` 分别对应显式 PostgreSQL UUID、定长字符、定点数和日期。
- 字段级默认值以 schema 为准；常见默认包括 `uuid()`、`now()`、版本/重试次数 `0/1`、布尔值和空 JSON 数组。默认值不得替代未知业务输入。

## 8. 关键关系和不变量

1. `container_record.id` 是稳定货柜身份；`container_number` 可迟绑定和跨运输实例复用，永远不是全局主键或唯一键。
2. `container_import_binding` 只在 `(tenant_id, source_batch_id, container_number)` 内解析稳定货柜；跨批次只凭箱号不得复用。
3. `replenishment_order -> replenishment_order_line` 是 1:N；备货单与货柜的 N:M 只由版本化 `container_cargo_allocation_set/allocation` 表达。
4. 一柜可装多个备货单，一条产品明细可拆入多个货柜；跨柜合计不得超过出运数量，该跨行聚合规则由事务写端口和真实 PostgreSQL 集成测试执行。
5. `order_number/replenishment_order_id` 在 `container_record` 上只是旧导入兼容锚，不得用于推导一柜一单。
6. 生命周期、任务工单、专业事实分别归 `lifecycle-control`、`work-execution` 和专业模块；任一模块不得直接写另一模块表。
7. planned、estimated、actual 时间保持不同语义；来源原值、UTC 时刻、来源偏移、权威系统和证据必须可追溯。
8. Evidence、AI 建议、人类决定、业务事实、事件应用和执行结果必须保持不同记录，不得合并为一个可覆盖字段。
9. 所有版本化 active/superseded 事实必须保留历史，幂等重放返回原结果；同键异载荷明确冲突。
10. 逻辑引用不是“无约束”：它表示所有权边界要求通过公开 Port、tenant 校验、契约和审计维持一致性。
11. ISO 国家与 UNECE area 是不同身份层；`XZ` 等 UNECE 专用范围不得伪装成 ISO 国家。航线目的国家不得从公司名推测；销售国家只能由已确认货主版本映射，内部简称 `UK` 必须与 ISO `GB` 分离。
12. UN/LOCODE 是地点身份，不保证一码只有一条官方名称；`port_code_entry` 必须保留源行，中文/外部别名只有 `confirmed` 后才能自动规范化。
13. `post_departure_source_package_review` 是不完整来源进入正式 Shipment 前的审计暂存：服务端必须按四个批次重新预检；同租户同包同快照幂等返回原记录，同包异快照冲突；保存该记录不得创建 Shipment 或启动生命周期。
14. `post_departure_source_candidate_correction` 只追加人工确认版本，不覆盖四表原始快照；当前版本取同 review+candidate 的最高 `version`，写入使用 advisory lock、`expectedVersion` 和唯一约束防止并发覆盖。同键同载荷返回原版本，同键异载荷或旧期望版本明确冲突。港口与 Evidence 是跨模块逻辑引用，写入前分别经 `master-data` active UN/LOCODE Port 与 `document-records` 租户/复核记录/有效核验资格校验；保存修正仍不得创建 Shipment。
15. `post_departure_source_candidate_cargo_line` 只属于一个候选修正版本；新版本保存完整 SKU 明细集并整体替代上一版。备货单号必须属于候选，SKU 必须经 `master-data` 公共 Port 命中当前租户，数量必须为正且单位明确；不得由柜级件数、重量或体积反推。保存子记录与父版本同事务，且仍不得提前创建 Shipment。

## 9. 索引评审规则

- PK 和 UNIQUE 自动形成 B-tree；不要为完全相同左前缀重复建索引。
- 每个物理 FK 必须有可用的独立索引、复合索引或唯一键左前缀；新增 FK 的迁移评审必须展示查询/删除路径。
- 租户列表使用 `(tenant_id, stable_sort_column, id)`，避免不稳定分页。
- 状态轮询使用 state + next/lease time；当前/active 版本查询使用 owner identity + state/is_current。
- JSONB 只有出现稳定的 containment/existence 查询并有执行计划证据时才增加 GIN；当前 schema 未声明 GIN。
- 不为低选择性布尔列单独建索引；需要时使用带业务谓词的复合或 partial index，并在迁移中说明访问路径。
- 大表上线前用真实数据量验证 `EXPLAIN (ANALYZE, BUFFERS)`；未测量不做分区或反规范化。

## 10. 迁移与演进契约

1. 唯一入口是 `database/migrations/<timestamp>_<name>/migration.sql`；不得在应用、文档或运维目录散落 DDL。
2. 已进入共享环境的迁移不可修改、重命名或删除；纠错必须追加迁移。
3. `database/schema.prisma` 与迁移最终态必须在同一变更中更新；生产禁止 `db push` 或 ORM 自动同步。
4. 兼容新增优先：先 expand（可空列/新表/双读写准备），再 migrate/backfill，最后 contract（收紧/删除旧结构）。
5. 新增 `NOT NULL`、默认值、类型转换、唯一约束或大表索引前必须分析锁表、表重写、历史脏数据和回滚路径。
6. 数据修复必须有影响分析、版本化脚本、审计、验证查询和恢复方案；不得用未提交临时 SQL 修改生产数据。
7. Seed 必须幂等，并隔离基础数据、demo/test 数据和生产数据；真实证据引用使用稳定 UUID，路径只保存在证据记录中。
8. 迁移至少验证空库升级、旧版本升级、关键拒绝约束和 rollback/应用回退影响；数据库高风险变更运行根级 `pnpm validate`。
9. 新表必须先确定模块所有者、租户边界、主键、幂等键、版本策略、FK 删除策略、访问路径和审计证据；任何一项未知不得进入迁移。
10. 删除/改名/改语义属于破坏性变更，必须提供兼容期和消费者清单；替换 PostgreSQL、Prisma 或启用 RLS/分区须新增 ADR。
