# ADR-008：OIDC / OAuth 2.1 身份与授权模型

> 状态：`accepted` · 日期：2026-09-04 · 决定人：刘志高（2026-09-04 接受）

## 背景

系统面向内部用户并预留多租户 SaaS 化；需要企业身份源接入能力（SSO）、明确的服务身份与最小权限，且写接口须默认认证授权。

## 决策

- 认证协议采用 **OIDC / OAuth 2.1**；授权采用 **RBAC/ABAC**，在服务端执行对象级与操作级权限，前端路由守卫不是安全边界（AGENTS §5）。
- **身份提供方（IdP）采用 Keycloak（或等价自部署 IdP）**，支持企业身份源（OIDC 联合）；部署方式在 P1-08 内定为首期自托管 Compose，云托管作备选。
- 服务与 Worker 使用**服务身份 + 最小数据库权限**（架构 P5-03）；令牌仅经运行环境/密钥系统读取。
- 预留多租户：数据与 AI 能力均带租户边界，但首期内部单租户运行，授权模型一上来即含租户维度。

## 后果

- 正面：支持 SSO/企业源；授权集中、可扩展 ABAC；符合架构 §12 边界。
- 代价：IdP 成为关键依赖；RBAC/ABAC 治理需持续维护。
- 连锁：影响 P5-02（接入）、P5-03（服务身份）、P2-05（租户/角色/权限模型）。

## 备选方案

| 方案 | 取舍 | 为何未选 |
| --- | --- | --- |
| 自研用户名/密码认证 | 简单 | 无 SSO、安全自担成本高 |
| 纯 OAuth 2.0（无 OIDC） | 略简单 | 企业 SSO 普遍需 OIDC；OAuth 2.1 收紧最佳实践 |
| 全托管 IdP（Auth0/Okta） | 免运维 | 数据驻留/预算与内部自用约束不符；自托管 Keycloak 更可控 |

## 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| IdP 高可用/泄露 | 密钥系统 + 监控 + 备用 IdP 预案（P8） |
| ABAC 复杂致授权错漏 | 以 RBAC 起步 + 对象级授权测试（P5-10 跨租户/越权用例） |

## 迁移与撤销条件

切换 IdP、改变授权模型（如引入策略引擎）均须新增 ADR；撤销后须保持服务端授权与最小权限不变。
