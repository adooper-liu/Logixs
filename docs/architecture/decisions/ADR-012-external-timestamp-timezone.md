# ADR-012：外部来源时间的事实化与确定时刻判定

> 状态：`accepted` · 日期：2026-09-18 · 决定人：刘志高（2026-09-18 接受）
> 评审：2026-09-18 负责人就两项开放问题作出决定（见 §2.3 时区来源分档、§1.3 覆盖范围）后接受本 ADR。
> 每份 ADR 独立成文，替换/撤销旧决策用新 ADR，并在旧 ADR 头部标注 `superseded by ADR-NNN`。

## 背景

### 1.1 外部来源的时间普遍没有时区

第三方证据供应商（飞驼、云当网等）返回的时间字段是**无时区的本地时间字符串**。云当网在几乎每一个数据域的接口上明示：

> 所有的时间字段都是字符串类型，格式为 `"yyyy-MM-dd HH:mm:ss"`，如果时间没有值则为空字符串 `""`。

同一供应商内部还自相矛盾：`/api/shipAIS/*` 老接口「返回的时间都是北京时间」，`/api/shipAIS/v2/*` 传 `timeZone` 时返回当地时间、不传时语义未说明，全球码头推送另有 `timeZone` 字段但**只给时区名不给偏移量**（见 [云当网字段与时间语义](../../integrations/trackingeyes/FIELD_AND_TIME_SEMANTICS.md)）。依赖供应商字段自证时区不可行。

### 1.2 契约层其实已经要求了，缺的是实现

这一点是本 ADR 的关键前提——**不需要发明新模型**：

- [canonical-event-envelope.schema.json](../../../packages/contracts/schemas/v1/canonical-event-envelope.schema.json) 的 `occurredAt` / `recordedAt` 引用 `common.schema.json#/$defs/DateTime`，其定义为 `{"type":"string","format":"date-time"}`——**RFC 3339，偏移必填**。
- 同一信封的 `location` 块**必填** `locationType` 与 `timezone`。
- 外部证据的 `source` 块在 `captureSource=external_evidence` 时**必填** `provider` / `interfaceCode` / `mappingVersion`。
- [证据来源权威契约 §5](../../product/domain/EVIDENCE_SOURCE_AUTHORITY_CONTRACT_V1.md) 写明「无法确认原始时区时保存原文并进入复核，不得假定 UTC」。

而实现层有两处没跟上：

| 缺口                     | 现状                                                                                                                                  |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| **规范事件表存不了偏移** | `canonical_event.occurred_at` 是 `TIMESTAMP(3)`（**无时区**），且表只有 6 个字段，是信封的最小切片——没有偏移、没有来源、没有 location |
| **解析规则没有定义**     | 从「供应商原文 + 地点/时区线索」到最终 `occurredAt` 的规则无归属：谁负责、依据什么、配置在哪、按什么版本，都没有规定                  |

`canonical_event` 恰恰是驱动生命周期、R1 时间单调性与节点完成的那个流——**契约要求带偏移，库里存的没有偏移**，这是首要缺口。

### 1.3 导入链路已经解过，但它的解法对供应商不成立

导入切片的 [`ShipmentTimeFact`](../../../database/schema.prisma) 已经落地了一套严格形态，并在迁移里有数据库级约束：

```sql
"raw_value"         TEXT        NOT NULL,
"occurred_at_utc"   TIMESTAMPTZ NOT NULL,
"source_utc_offset" TEXT        NOT NULL,
-- 另有 CHECK：raw_value 非空白；source_utc_offset 必须形如 ±HH:MM（时 00–14、分 00–59）
```

原始值、明确偏移、UTC 时刻三者并存，偏移格式由数据库强制。配套行为是**失败关闭**：[run-precheck.service.ts](../../../apps/api/src/modules/integration-import/application/run-precheck.service.ts) 在缺 `timeSourceUtcOffset` 时直接产出 `TIME_PROVENANCE` blocker 拒绝该行。

**Excel 导入可以失败关闭**——有人可以回去补一列。**供应商推送不可以**：飞驼与云当网在载荷里根本不提供偏移，失败关闭等于永不集成。这是本 ADR 真正要解的问题。

### 1.4 为什么现在决策

导入闭环的 `ShipmentTimeFact` 已把清关/卸柜/卸空时间分槽入库（见 [导入时间事实与来源追溯](../../planning/tasks/p6-import-time-provenance.md)），供应商适配正在推进。此后修改的迁移成本随数据量上升。

## 决策

### 2.1 不重复发明：对齐既有 `ShipmentTimeFact` 形态

外部来源时间一律采用已经存在的三件套形态，**不新建并行模型**：

```text
rawValue          供应商/来源原文（逐字保留）
sourceUtcOffset   明确 UTC 偏移（如 "+08:00"）
occurredAtUtc     可比较、可计费的 UTC 时刻
timeZoneSource    新增：偏移是怎么定下来的（§2.3）
```

### 2.2 不放松既有约束，未解析的时间不进事实表

`shipment_time_fact` 现有的 `NOT NULL` 与偏移格式 `CHECK` **保持不变**。无法解析出偏移的时间**不写入事实表**，而是：

- 原始载荷进 `ProviderRawPayload`（不可变留存）；
- 时间值进**复核队列**，带来源、缺失原因与建议依据。

事实表的语义因此保持为「**已确定的时间事实**」——一条不放松约束的边界。已确定的时刻可以放心用于计费与过站。

### 2.3 时区来源分档（评审已定）

| `timeZoneSource`      | 含义                                                           | 可否驱动不可逆动作 |
| --------------------- | -------------------------------------------------------------- | ------------------ |
| `supplier_declared`   | 供应商显式声明（载荷字段或该接口文档明确声明，须绑定接口版本） | ✅                 |
| `location_configured` | **由「地点 + 接口」经版本化配置解析出的确定偏移**              | ✅                 |
| `manual_confirmed`    | 人工确认                                                       | ✅                 |

**`location_configured` 是本次评审的关键决定**：中国大陆港口、场站、EIR 属**单一法定时区且无夏令时**，按地点解析出的偏移不是猜测而是确定；美国码头与清关按 IANA 规则**按事发当日**换算（§2.6），同样确定。只有「地点未知」或「无可用配置」才落入复核，而不是把一切按地点解析的结果统统降级。

配置必须：

1. **版本化**，并随事实行记录所用配置版本（沿用映射表版本化的做法）；
2. 可审计——能从事实行回溯到「依据哪条配置、哪份资料」；
3. 缺失即**不解析**（进复核），**不得回退到部署时区或 UTC**。

### 2.4 授权规则

- **生命周期过站**（推进节点、推进 8 态）、**超期费用**（LFD、免箱期、阶梯计费）、**R1 时间单调性比较**，只接受上表三种来源产生的时刻。
- 复核队列中的时刻**不参与**上述任何判定。
- **R1 的失败语义要区分**：时刻未解析（在复核队列）**不得**抛 `TIME_ORDER_CONFLICT`——它不是乱序，是未解析。当前 [`ApplyLifecycleEventService`](../../../apps/api/src/modules/lifecycle-control/application/apply-lifecycle-event.service.ts) 只有"拒绝"一种失败，需要区分出"转复核"。

### 2.5 禁止隐式本地时区

适配器与领域层**不得**使用会产生本地时区语义的解析（如 `new Date("YYYY-MM-DD HH:mm:ss")`）——它在 Node.js 中按**运行环境本地时区**解释，同一份载荷在 UTC 容器与 UTC+8 开发机上会得到相差 8 小时的两个时刻，且不报错。必须走显式解析器并显式传入时区来源。**以 lint 规则或 `repo:check` 拦截裸解析。**

### 2.6 夏令时

按地点解析必须使用 **IANA 时区数据**，按**事发当日**的偏移换算，不得使用当前偏移或固定偏移表。美国、欧洲、澳大利亚等辖区在切换日前后会相差一小时。

### 2.7 展示层

按用户时区展示，不改变存储语义；界面必须能区分「已确认时刻」与「复核中」，不得把复核中的值渲染成确定时间。

## 后果

- **正面**：解析结果与部署环境无关；不可逆动作只吃确定时刻；事实表的「已确定」语义由数据库约束背书；复核率可作为**供应商数据质量指标**，支撑准入与谈判。
- **代价**：需要维护「地点 + 接口 → 偏移」的版本化配置（这是一份新的主数据，与尚未开工的 `master-data` 模块相关）；需要 IANA 时区数据依赖；每个适配器必须逐字段声明时区来源；R1 需要区分"拒绝"与"转复核"。
- **对现有文档/模块的连锁影响**：
  1. **`canonical_event` 列类型与字段**（首要）——`occurred_at` 需改为 `TIMESTAMPTZ`，并补齐 `source_utc_offset` / `time_zone_source`。注意该表是契约信封的最小切片，其余信封字段（`source` 块、`location`、`traceId`、`recordedAt`）的补齐属 P2-06 / 契约实例化范围，**不在本 ADR**。
  2. [证据来源权威契约 §5](../../product/domain/EVIDENCE_SOURCE_AUTHORITY_CONTRACT_V1.md)（时间规范）——按其 §15，**收紧来源资格属行为变更**，需版本升并评审。本文只提出，不代改。
  3. [生命周期时间线契约 V1](../../product/domain/CONTAINER_LIFECYCLE_TIMELINE_CONTRACT_V1.md)（时间语义）——需补充"确定时刻"这一前置条件。
  4. P2-06 数据库逻辑模型——需要为时间事实登记 `timeZoneSource` 与地点/接口配置表。
  5. `lifecycle-control` 的 R1 判定——区分"拒绝"与"转复核"。
  6. `charges-settlement` 超期引擎——拒绝复核中的计费输入。
  7. 所有 provider adapter（飞驼、云当网及后续）——统一走本策略。

## 备选方案

| 方案                         | 取舍     | 为何未选                                                                                |
| ---------------------------- | -------- | --------------------------------------------------------------------------------------- |
| 一律按 UTC 解析              | 零成本   | 违反契约；东亚与美洲港口静默错 8~16 小时，直接污染计费与过站                            |
| 按部署时区（Node 默认行为）  | 零成本   | 结果与环境相关，CI 与生产不一致，不可复现；错误静默                                     |
| 一律按供应商主时区（北京时） | 实现简单 | 云当网覆盖美国码头与美国清关，欧美时间全部错位                                          |
| 对供应商也沿用导入的失败关闭 | 复用现有 | 供应商载荷不含偏移，失败关闭＝永不集成                                                  |
| 一切按地点解析的结果都进复核 | 最保守   | 中国港区/EIR/场站全部无时区，等于集成只读；把确定的事标成不确定，是把工程问题伪装成风险 |
| 放松事实表约束以容纳未解析值 | 改动最小 | 会毁掉「事实表＝已确定事实」这条边界，计费与过站失去兜底                                |
| 仅靠供应商 `timeZone` 字段   | 看似直接 | 该字段只给时区名不给偏移量，且多数接口根本没有                                          |

## 风险与缓解

| 风险                           | 缓解                                                                           |
| ------------------------------ | ------------------------------------------------------------------------------ |
| 「地点 + 接口」配置本身配错    | 配置版本化 + 可审计回溯；对拍测试覆盖高频港口；复核率异常时告警                |
| 时区数据过期导致夏令时换算错误 | 使用 IANA tzdata 并随依赖更新；时刻可按配置版本批量重算                        |
| 供应商悄悄改变时间语义         | 对拍测试固化已验证语义；每 provider 记录接口版本与采集日期（见知识库来源索引） |
| 复核队列积压                   | 监控复核率并设为供应商准入指标；优先补齐高频港口与接口的配置                   |
| 迁移期间新旧数据混存           | 迁移显式回填（见下）；无法证明的历史行不伪造偏移                               |
| 开发者绕过策略使用裸解析       | lint / `repo:check` 规则拦截（待实现，列为落地项）                             |

## 迁移与撤销条件

**迁移**（三件事，均走 `database/migrations/`）：

1. `canonical_event.occurred_at` 改为 `TIMESTAMPTZ`。既有值是 Prisma 以 JS `Date`（瞬时）写入的，落在无时区列里成为墙钟值——**须先抽样验证既有值确为 UTC 墙钟，再按 `AT TIME ZONE 'UTC'` 转换**，不得直接假定。
2. `canonical_event` 补齐 `source_utc_offset` / `time_zone_source`。历史行**无法证明偏移**：能从关联证据回填则回填，否则留 NULL 并注明「偏移未记录」。**NULL 只允许存在于迁移前的历史行**，新写入由领域不变量禁止 NULL。
3. `shipment_time_fact` 增加 `time_zone_source`，历史行按既有 `mapping`/来源回填；其 `NOT NULL` 与偏移 `CHECK` **不动**。

迁移需附验证与恢复说明（沿用 [空库迁移恢复](../../planning/tasks/p6-empty-database-migration-recovery.md) 的做法）。

**撤销条件**：

- 若某供应商改为提供带偏移的 ISO 8601 时间，**该供应商路径**退化为"直接采纳"，本决策其余部分不变。
- 若未来引入能保证时刻语义的权威时间源（如海关或码头直接给出 UTC 时间戳），可放宽 §2.3 的白名单——**须新增 ADR**，不在本决策内静默升级。
- 本决策不改变「不能确认时区时不得假定 UTC」这一契约原则；撤销本决策不等于允许猜测。
