# ADR-001：业务后端采用模块化单体

> 状态：`accepted` · 日期：2026-09-04 · 决定人：刘志高（2026-09-04 接受）

## 背景

Logix 首次有清晰业务闭环（智能导入），架构必须支持强模块边界、可演进到服务拆分，但尚无团队规模/部署/故障隔离的客观证据支持一上来就微服务。需要为业务 API 选一个「边界清晰、可演进」的形态。

## 决策

`apps/api` 以**模块化单体**实现，内部按业务能力划分为强边界模块（identity / shipment / logistics-status / import / dictionary / integration / exception-management / notification / reporting / workflow / ai-governance / audit）。依赖方向固定为 `Controller → Application Use Case → Domain ← Infrastructure`，跨模块只经各自公开入口与公共契约包，禁止跨包引用对方内部路径。仅当出现独立部署/扩缩容/故障隔离证据时才拆分为服务（见 ADR-001 撤销条件与架构 §16）。

## 后果

- 正面：共享进程内事务与依赖注入，开发/运维成本低；模块边界仍可支撑未来拆分；契约先行利于测试。
- 代价：进程内故障会互相影响；需纪律约束避免模块间直接耦合（依赖 lint + CODEOWNERS）。
- 连锁：模块清单即 [架构 §6.1](../AI_WORKFLOW_TECHNICAL_ARCHITECTURE.md) 的模块划分；Domain/契约包归属 `packages/`。

## 备选方案

| 方案 | 取舍 | 为何未选 |
| --- | --- | --- |
| 微服务 | 独立扩缩容/故障隔离清晰 | 无团队、部署或故障隔离证据；分布式事务与运维成本过高（过早） |
| 传统分层单体（单模块） | 简单 | 无法控制 import/dictionary 等边界扩散；不可演进 |
| 插件式单体 | 高内聚扩展 | 实现成本高，当前模块数量不需要 |

## 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 模块边界被绕过、退化成大泥球 | 依赖方向用 lint/CI 强制；公共入口收敛于各模块 index；跨模块走 `packages/contracts` 与领域事件 |
| 拆分时重构成本 | 保持模块无隐式耦合、事件契约化；拆分可逐模块进行 |

## 迁移与撤销条件

满足下列之一即触发拆分评估并新增 ADR：需要独立部署/扩缩容；单模块崩溃影响他模块的隔离要求；团队超过单仓库协作瓶颈。撤销后按模块逐个迁出为服务，公共契约与事件保持版本兼容。
